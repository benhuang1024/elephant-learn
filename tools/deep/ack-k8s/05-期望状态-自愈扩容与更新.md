# 精讲：reconcile 循环、滚动更新的数学、与 HPA 的冷却

第 05 章用港口故事讲了自愈。这一节把故事换成**机制与数字**：控制器到底在循环什么、滚动更新为什么是那两个参数、HPA 为什么不会每秒抖一次。

## 1. reconcile 不是定时扫全港，是「watch + 差值」

```text
loop:
  desired ← etcd（Deployment.spec.replicas / image / strategy）
  actual  ← informer 缓存（Pod 列表，watch 推送维护）
  diff    ← desired - actual
  if diff > 0: 创建 Pod（交给 scheduler 选节点）
  if diff < 0: 按策略删除 Pod（受 PDB / grace period 约束）
  if image 变了: 进入 rollout 状态机（见下）
  重新入队（带退避），等下一次 watch 事件或 resync
```

三个容易误解的点：

1. **控制器不「执行步骤」，它「消除差值」**。所以你 kill 一个 Pod，它不需要知道「你 kill 了」——它只看到 actual 少 1。这就是为什么暂停控制器后杀 Pod 不会自愈（实验台可验证）。
2. **watch 是推送，不是轮询**。定时 resync 只是兜底（默认分钟级），正常路径是 etcd 事件驱动。故事里「巡查员走路」是为了让孩子懂，机制上是订阅。
3. **差值收敛是最终一致**。某一瞬间 actual ≠ desired 是正常态；你要监控的是「差值持续 > 0 的时长」，而不是「差值是否曾 > 0」。

## 2. 滚动更新的数学：两个参数决定「发布期间容量曲线」

设期望 R，maxSurge = S，maxUnavailable = U：

```text
任意时刻：
  总 Pod 数 ≤ R + S
  可用 Pod 数 ≥ R - U
新版本就绪数从 0 单调涨到 R；旧版本从 R 单调降到 0
```

| 配置 | 发布期间容量 | 代价 | 适用 |
|---|---|---|---|
| S=1, U=0 | 先加 1 新，就绪后删 1 旧 → 容量 ≥ R | 发布慢（串行替换） | 容量敏感、核心服务（仓库默认） |
| S=0, U=1 | 先删 1 旧，再起 1 新 → 容量 ≥ R-1 | 发布期间少一份容量 | 资源紧张、可容忍短暂降容 |
| S=25%, U=25% | 批量替换 | 快，但容量波动大 | 无状态、副本多 |
| S=0, U=0 | **死锁**：加不了也删不了 | 永远发不完 | 非法配置，API 会拒绝 |

评审时问一句「发布期间最少几个副本在服务？」——答案就是 `R - U`。再问「PDB 的 minAvailable 和它谁大？」——**自愿驱逐（含滚动更新删旧）同时受两者约束，取更严的那个**。实验台打开 PDB(minAvailable=2) 再缩容，能看到控制器拒绝驱逐。

## 3. 探针：自愈的「眼睛」，配错等于把自愈关掉

| 探针 | 回答的问题 | 配错的后果 |
|---|---|---|
| liveness | 「进程还活着吗？」失败 → **重启容器** | 把慢启动当死 → 重启循环（CrashLoop 假象） |
| readiness | 「能接流量吗？」失败 → **摘出 Service endpoints** | 启动期接流量 → 发布瞬间 502 |
| startup | 「启动完成了吗？」成功前屏蔽 liveness/readiness | 不配 → 慢应用被 liveness 杀 |

PHP 对照：php-fpm 的「活着」由 master 管，「能接流量」由 nginx upstream 被动健康检查管。K8s 把这两件事变成**你必须显式声明**的探针。Magento 这种启动要跑 setup / 预热的服务，startup 探针不是可选项。

## 4. HPA：公式、冷却与「为什么不是每秒扩」

```text
desired = ceil( currentReplicas × currentMetric / targetMetric )
例：4 副本 × 80% CPU / 目标 60% = ceil(5.33) = 6
```

四个防抖机制：

1. **容忍带**（默认 10%）：比值在 0.9～1.1 之间不动作。
2. **缩容稳定窗**（默认 300s）：扩容立即考虑，缩容要等窗口内最大值回落——防止流量锯齿导致来回缩扩。
3. **指标延迟**：metrics-server 约 15～60s 粒度，HPA 周期默认 15s → 天然滞后。
4. **上下限**：min/max  replicas 是硬边界，压测再猛也不越界。

所以实验台里「负载拉满 → 副本涨」是简化模型（无冷却）；真实集群会慢半拍且缩容更慢。评审时问「缩容稳定窗设了多少？冷启动多久？」——冷启动 60s 的服务配 30s 缩容窗 = 自激振荡。

## 5. 评审清单

```text
[ ] requests/limits 都写了；HPA 用 requests 算利用率
[ ] readiness 与 liveness 语义分开；慢启动有 startup
[ ] rollout 策略给出 R-U 的容量承诺；PDB 与之一致
[ ] terminationGracePeriod ≥ 摘流 sleep + 在途请求上限
[ ] preStop 有 sleep（等 endpoints 摘除传播）
[ ] HPA 有 min/max、缩容稳定窗与冷启动匹配
[ ] 监控「差值持续时长」「重启次数」「OOMKilled(137)」而非仅 CPU
```
