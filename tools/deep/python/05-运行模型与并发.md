# 精讲：GIL 的真相、asyncio 的边界、与 uvicorn 的容量数学

第 05 章讲了 GIL 与 asyncio。这一节纠正三个流传最广的误解，并给出和 PHP-FPM 对齐的容量算法。

## 1. GIL 到底锁了什么（以及没锁什么）

| 说法 | 真相 |
|---|---|
| 「GIL 让 Python 多线程完全没用」 | 错。**IO 等待时 GIL 会释放**：多线程做 IO 并发仍然有效 |
| 「GIL 让 CPU 密集多线程变慢」 | 对：同一时刻只有一个线程执行字节码，CPU 密集多线程 ≈ 单核 + 切换开销 |
| 「asyncio 绕过了 GIL」 | 错：asyncio 是**单线程**协作调度，根本不需要多核；它解决的是 IO 并发，不是 CPU 并行 |
| 「3.13+ 没有 GIL 了」 | 半对：free-threaded 构建（`python3.13t`）可选去掉 GIL，但生态 C 扩展兼容性仍是代价；默认构建仍有 |

CPU 密集的正解和 Node 一样：**换进程**（`multiprocessing` / `ProcessPoolExecutor` / 独立 worker 服务），或换实现（C 扩展 / numpy 向量化 / Rust 扩展）。

PHP 对照：PHP-FPM 天然多进程，所以你从来没遇到过 GIL 问题——**你的「绕过方案」就是平台默认**。Python 需要显式选择。

## 2. asyncio 的三个「PHP 直觉失效点」

```python
# ① 同步阻塞调用会卡死整个事件循环（= Node 的同步 CPU 段）
async def bad():
    time.sleep(3)          # ✗ 整个 loop 停 3 秒，所有请求一起等
    requests.get(url)      # ✗ 同上
# ✔ await asyncio.sleep(3) / httpx.AsyncClient

# ② 创建任务 ≠ 等待任务
async def fire_and_forget():
    asyncio.create_task(send_metric())   # 不 await → 异常变成 "Task exception was never retrieved"
# ✔ 持有引用 + add_done_callback 记日志，或 await / gather

# ③ 并发扇出要限流（= Node 的 mapWithLimit）
sem = asyncio.Semaphore(8)
async def bounded(x):
    async with sem:
        return await fetch(x)
await asyncio.gather(*(bounded(x) for x in items))
```

| 需求 | PHP 近似 | asyncio |
|---|---|---|
| 并发 IO | `curl_multi` / Guzzle Pool | `gather` + Semaphore |
| 每个的成功/失败 | Pool + settle | `gather(return_exceptions=True)` |
| 超时 | Guzzle timeout | `asyncio.wait_for` / `asyncio.timeout` |
| 取消 | 无语言级 | `task.cancel()` + `CancelledError` |
| 请求态 | 请求生命周期 | `contextvars.ContextVar`（≈ Node ALS） |

`contextvars` 是 FastAPI 依赖注入之外存「本次请求」的正确地方；模块全局变量在常驻进程里跨请求共享——和 Node 同款坑。

## 3. 容量数学：uvicorn worker × 并发，与 fpm 对齐

```text
同步视图（WSGI / Django）：
  吞吐 ≈ workers × threads ÷ 平均请求耗时
  内存 ≈ workers × 单 worker 峰值（Django 常驻后不再每请求释放！）

异步视图（ASGI / FastAPI）：
  单 worker 并发 ≈ 事件循环时间片 ÷ 每请求同步 CPU 段
  吃满 N 核 → uvicorn --workers N（或 gunicorn -k uvicorn.workers.UvicornWorker）
  DB 连接池总量 = workers × pool_size ≤ DB 上限 80%
```

两个 PHP 老手最容易错的点：

1. **Django/FastAPI 常驻后内存不释放**：OPcache 式的「请求结束全释放」没有了。模块级缓存、ORM identity map、未关闭的 client 都会累积。防线同 Node：上限 + TTL + 显式 close。
2. **同步 ORM 混进 async 视图**：SQLAlchemy 同步 Session 在 async 路由里调用 = 阻塞 loop。要么全 async（`async_sessionmaker` + `await session.execute`），要么把同步段扔进 `run_in_executor` / 独立线程池并限流。仓库 shop-api 走全 async 路线，评审时 grep 路由里的同步 `Session()` 是高效 finding。

## 4. 评审清单

```text
[ ] async 路由内无 time.sleep / requests / 同步 Session
[ ] create_task 有引用与异常回收；gather 有 return_exceptions 策略
[ ] 扇出有 Semaphore；外部调用有 timeout
[ ] workers 数 = 核数（CPU 型）或按 IO 等待比放大；池总量对齐 DB 上限
[ ] 请求态用 contextvars / 依赖注入，不用模块全局
[ ] CPU 密集走进程池或独立服务，不在 loop 里算
```
