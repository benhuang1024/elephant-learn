# 精讲：把「常驻进程」当成一种新的部署单元来设计

教材第 03 章给了你六个后果。这一节把它们推进到**设计决策**层面：当你评审一个 Node 服务时，应该追问什么、容量怎么算、请求态放哪里、进程怎么死得干净。

## 1. 容量模型：从 `pm.max_children` 到「一个线程的时间片」

PHP-FPM 的吞吐公式你闭着眼都能写：

```
吞吐 ≈ pm.max_children ÷ 平均请求耗时(秒)
内存 ≈ pm.max_children × 单 worker 峰值内存
```

Node 单进程把这个公式拆成了两半，而且两半的旋钮不在同一个地方：

| 维度 | PHP-FPM 的旋钮 | Node 的旋钮 | 评审时追问 |
|---|---|---|---|
| 并发容量 | `pm.max_children` | 事件循环可用时间片 + `await` 让出点密度 | 「请求路径里有没有同步 CPU 段？超过 1ms 就要解释」 |
| CPU 吃满 | worker 进程数 | 进程数：cluster / PM2 `instances` / K8s replicas | 「8 核机器只跑 1 个 Node 进程 = 浪费 7 核」 |
| 内存上限 | 每 worker 独立，请求结束释放 | 单堆默认上限（64 位约 1.5～4GB，视版本与 flags） | 「堆里常驻了什么？缓存有没有上限和过期？」 |
| 故障半径 | 一个 worker 崩 = 一个请求失败 | 一个未捕获异常 = **整个进程所有请求**失败 | 「`unhandledRejection` / `uncaughtException` 策略是什么？」 |

一个具体的算例：平均请求 20ms，其中 18ms 是 `await` 数据库、2ms 是同步序列化。

- PHP-FPM：`max_children=50` → 理论 2500 req/s（实际受 DB 连接数限制）。
- Node 单进程：同步段 2ms → 单线程上限约 **500 req/s**，与 `await` 多快无关。想吃满 8 核 → 8 个进程 → 约 4000 req/s 的同步段容量，再被 DB 连接池上限截断。

**结论**：Node 的瓶颈通常不是「并发数」，而是「每请求同步 CPU 毫秒数 × 进程数」。评审时让对方给出这两个数字，比问「能扛多少 QPS」有用十倍。

## 2. 请求态放哪里：AsyncLocalStorage 才是 PHP 请求_scope 的等价物

PHP 里「本次请求的用户 / 语言 / traceId」天然挂在请求生命周期上。Node 里模块顶层变量是进程级，于是有人把它挂单例属性上——那就是教材里 `withdraw` 扣成负数的同款错误。

正确等价物是 `AsyncLocalStorage`（ALS）：

```ts
import { AsyncLocalStorage } from "node:async_hooks";

export interface RequestContext { requestId: string; userId?: string; lang: string }
export const requestStore = new AsyncLocalStorage<RequestContext>();

// 中间件里：每个请求一个独立存储，跨 await 自动跟随
app.use((req, res, next) => {
  requestStore.run({ requestId: req.headers["x-request-id"] ?? crypto.randomUUID(), lang: "zh" }, next);
});

// 任何深度的函数里：不用传参也能拿到「本次请求」
export function currentRequestId(): string {
  return requestStore.getStore()?.requestId ?? "no-context";
}
```

三条纪律：

1. **ALS 存请求态，模块顶层只存「进程级共享且只读或带淘汰策略」的东西**（配置、连接池、带 LRU 上限的缓存）。
2. ALS 不是免费的：它给每个异步资源挂上下文，高频小对象场景有可观开销；只存小对象，别把整个 request/response 塞进去。
3. 日志库要接 ALS 才能自动带 requestId。仓库目前 `X-Request-Id` 只进响应头、没进日志行——第 15 章列为生产前必补，评审时这就是一个现成的 finding。

对照表：

| 需求 | PHP | Node 正确做法 | Node 错误做法 |
|---|---|---|---|
| 本次请求用户 | 请求参数 / Session | ALS / 显式传参 | 单例属性、模块顶层 `let` |
| 进程级缓存 | APCu / OPcache | 带上限 + TTL 的 Map / lru-cache | 无界 Map |
| 跨请求计数器 | 外部存储 | 外部存储（Redis / DB） | 模块变量（多进程后各自一份） |
| 定时任务 | cron / queue worker | `setInterval` + 优雅停机清理 / 独立 worker | 请求路径里起定时器 |

## 3. 连接池：从「每请求建连」到「池是进程资产」

PHP-FPM 每请求建连（或 `pconnect` 每 worker 一条）。Node 的池是**进程级资产**，于是出现两个 PHP 里没有的故障模式：

- **池耗尽排队**：`Promise.all(1000 个查询)` 瞬间占满池，其余请求在池队列里等 → 表现为 P99 暴涨而不是报错。教材的 `mapWithLimit` 就是为此存在。
- **池泄漏**：事务里 `await` 了一个永不 settle 的 Promise（比如忘了 reject 的手写 Promise），连接永不归还 → 池慢慢干涸，进程不崩但全服务超时。

评审清单：

```text
[ ] 池大小有明确数字，且 = 进程数 × 池大小 ≤ DB max_connections 的 80%
[ ] 所有取连接的路径都有 finally / using 归还（或驱动自动管理）
[ ] 事务有超时（statement_timeout / 手动 AbortSignal）
[ ] 并发扇出有上限（mapWithLimit / p-limit），不是裸 Promise.all
[ ] 健康检查真的查池（SELECT 1），而不是只返回 {status:"UP"}
```

## 4. 进程怎么死得干净：优雅停机是一段必须写的代码

PHP-FPM 的「停机」是 master 的事，worker 请求跑完就退。Node 里 SIGTERM 到来时，进程里还有：在途请求、池里的连接、定时器、ALS 上下文。不写停机逻辑 = 发布瞬间一批 502。

最小可用版本（仓库 `main.ts` 的 `enableShutdownHooks()` 是 Nest 侧的一半，另一半要自己补）：

```ts
let shuttingDown = false;
process.on("SIGTERM", async () => {
  if (shuttingDown) return;
  shuttingDown = true;
  health.markDraining();            // 1. 健康检查转 fail，让 LB / K8s 摘流量
  await sleep(5_000);               // 2. 等摘流生效（K8s terminationGracePeriod 内）
  await server.close();             // 3. 停止接新请求，等在途请求完成
  await pool.end();                 // 4. 关池
  clearInterval(metricsTimer);      // 5. 清定时器
  process.exit(0);
});
```

顺序不能乱：**先摘流，再拒新，再等在途，再关资源**。K8s 侧对应 `preStop` sleep + `terminationGracePeriodSeconds`，见 ack-k8s 第 05/09 章。

## 5. 内存：把「请求结束全释放」这条拐杖拿走之后

PHP 替你兜住了三类低级泄漏。Node 里它们都会累积到 OOM，而且 OOM 是**整个进程**死：

| 泄漏源 | 为什么 PHP 没事 | Node 的防线 | 检测手段 |
|---|---|---|---|
| 无界缓存 Map | 请求级 | LRU 上限 + TTL；或外部缓存 | `process.memoryUsage().heapUsed` 趋势 |
| 监听器不注销 | 随请求销毁 | 成对 off / `{once:true}` | `MaxListenersExceededWarning` |
| 闭包捕获大对象 | 随请求销毁 | 缩小闭包捕获面；WeakRef/WeakMap | heap snapshot 对比 |
| 全局定时器 | 不存在 | clearInterval；停机清理 | `process.getActiveResourcesInfo()` |

一个实用的生产动作：给进程加**堆水位告警**（heapUsed / heapTotal > 0.85 持续 5 分钟），而不是等 OOMKilled。K8s 里 OOMKilled 的 exit code 是 137，看到它先查堆，别先查流量。

## 6. 评审时的一句话总结

> 「PHP-FPM 把隔离和回收做成了平台默认；Node 把这两件事变成了**你的代码责任**。评审 Node 服务，就是评审它在哪里重新实现了隔离（ALS / 传参）和回收（上限 / 注销 / 停机）。」

把这句话带去评审会，比背事件循环顺序有用。
