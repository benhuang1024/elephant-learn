# 精讲：事务、乐观锁与「同步驱动」的真实代价

第 08 章对照了 Drizzle / Prisma / Eloquent。这一节把三件事讲透：**事务边界画在哪、乐观锁什么时候会骗你、以及 better-sqlite3 的同步 API 为什么既是优点又是陷阱**。

## 1. 事务边界：画在 Service，不是 Controller，也不是 Repository 单条语句

```ts
// ✔ 边界 = 一个业务用例
async place(dto: PlaceOrderInput): Promise<Order> {
  return db.transaction(async (tx) => {
    const lines = await reserveStock(tx, dto.items);   // 读 + 校验 + 扣减
    const order = await insertOrder(tx, dto, lines);   // 写订单 + 订单行
    return order;                                      // commit 由 transaction 负责
  });
}
```

| 画错的位置 | 症状 | PHP 同款错误 |
|---|---|---|
| Controller 里开事务 | 事务跨了序列化 / 日志 / 外部 HTTP，锁持有时间暴涨 | 在控制器里 `DB::beginTransaction()` 然后调第三方 API |
| 每条语句各自事务 | 「扣了库存但订单没写」的部分成功 | 循环里逐条 `save()` 不包事务 |
| 事务里 `await` 外部 HTTP | 对方慢 = 你的锁慢 = 全库排队 | 事务里发 Guzzle 请求 |
| 事务里起定时器 / 发队列 | commit 前消息已发出 → 消费方读不到数据 | 事务里 `dispatch()` 同步队列 |

最后一条的正确姿势：**事务内只写「outbox 行」，commit 后再投递**（或直接用支持事务性 outbox 的队列）。这是 PHP 老手也常踩的坑，只是 PHP 里通常靠「请求结束才发」侥幸躲过。

## 2. 乐观锁：`WHERE version=?` 影响 0 行 ≠ 并发，先排除这三种假阳性

```ts
const r = tx.update(products)
  .set({ stock: newStock, version: old.version + 1 })
  .where(and(eq(products.id, id), eq(products.version, old.version)));
if (r.changes === 0) throw new OptimisticLockException();
```

影响 0 行的可能原因，按概率排：

1. **真并发**：另一个事务先 commit（教材与实验台演示的分支）。
2. **读得太早**：你在事务外读了 version，进事务时别人已改 → 不是「同时写」，是「 stale read」。修法：读也放进事务，或用 `SELECT … FOR UPDATE`（悲观）。
3. **WHERE 写错 / 行已删**：id 不存在也返回 0 行。修法：先区分「行不存在」（404）与「版本不符」（409）。

| 策略 | 适用 | 代价 | 仓库位置 |
|---|---|---|---|
| 乐观锁 version | 冲突率低、读多写少 | 冲突时重试或 409 | shop-api repository 手写 WHERE |
| 悲观锁 FOR UPDATE | 冲突率高、热点行 | 锁等待、死锁风险 | 未用；Postgres 路线可选 |
| 原子扣减 `stock = stock - n WHERE stock >= n` | 单字段扣减 | 无法携带复杂校验 | 未用；最简方案 |
| 串行化隔离级别 | 强一致金融 | 吞吐下降、序列化失败重试 | 未用 |

**诚实提醒**（README 差异表也写了）：better-sqlite3 的同步事务被事件循环串行化，HTTP 层几乎复现不出真并发；冲突分支靠 repository 单测覆盖。换 Postgres + 异步驱动后，实验台的「并发两单」才会在真实 HTTP 层出现。评审时别把「测不出冲突」当成「没有冲突」。

## 3. 同步驱动：better-sqlite3 为什么「快得危险」

better-sqlite3 的 API 是**同步**的：`db.prepare(...).run()` 直接阻塞线程直到 SQLite 返回。

- 优点：没有 Promise 开销、事务天然原子（同步段不被打断）、代码像 PHP 一样直白。
- 代价：**每一次 DB 调用都在占用事件循环**。SQLite 本地文件通常 <1ms，所以演示没问题；但一旦换成网络数据库的同步驱动（或 SQLite 遇到锁等待 / 大事务），阻塞会直接卡死**所有**请求——教材第 03 章「CPU 阻塞卡死全进程」的 DB 版本。

判断准则：

```text
同步驱动可接受 ⇔ 单次调用 P99 < 1ms 且无网络往返且无锁等待
否则 → 异步驱动（node-postgres / mysql2）+ 池 + 超时
```

这也是为什么仓库把「切 Postgres」列成路线而不是现状：`drizzle-orm/node-postgres` + `numeric/timestamp` 列类型 + 迁移工具换轨，是一次真正的架构变更，不是改个连接串。

## 4. N+1：ORM 换了，病没换

| 场景 | Eloquent | Drizzle | 修法 |
|---|---|---|---|
| 列表带关联 | `Product::with('items')` | 显式 join 或二次查询 + Map 装配 | 一次 join / 一次 IN 查询 |
| 循环里查 | `foreach → $p->items` | `for → await db.select…` | 批量 IN + 内存分组 |
| 懒加载陷阱 | 访问属性触发 SQL | Drizzle 无懒加载（显式是优点） | 保持显式 |

Drizzle 没有懒加载，反而把 N+1 从「隐蔽」变成「显式」：你能在代码里直接数出循环里有几次 `await db`。评审时 grep `for` / `map` 块内的 `db.` 调用，比看 ORM 文档快。

## 5. 评审清单

```text
[ ] 事务边界 = 用例；事务内无外部 IO / 无队列投递
[ ] 乐观锁 0 行有三分支区分（404 / 409 / 重试）
[ ] 驱动同步/异步与延迟预算匹配；网络 DB 不用同步驱动
[ ] 池大小 × 进程数 ≤ DB 上限 80%；事务有超时
[ ] 循环内无逐条查询；关联用 join / IN 批量
[ ] 迁移可回滚；schema 变更与代码发布顺序明确（先扩后缩）
```
