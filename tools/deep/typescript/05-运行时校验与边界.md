# 精讲：边界校验是一套「契约工程」，不是一个 pipe

第 05 章的结论是「类型会被擦除，所以边界必须校验」。这一节回答评审时的下一层问题：**校验放在哪几层、错误长什么样、契约怎么不被抄成四份、以及什么时候不该用 Zod**。

## 1. 一个服务至少有四条边界，别只守 HTTP body

| 边界 | 入站形态 | 仓库里的守卫 | 漏守的后果 |
|---|---|---|---|
| HTTP body / query / param | JSON / 字符串 | `ZodValidationPipe` + shared schema | 脏数据进业务层，NPE 式崩溃 |
| 环境变量 / 配置 | `process.env` 全是 string | `config/env.ts` 的 Zod schema，启动即失败 | 带着错配置跑半天才发现 |
| 外部服务响应 | 第三方 JSON | 应当再用 schema 解析（仓库未做，评审 finding） | 对方改字段 → 你的 `undefined` 一路飘到 UI |
| 持久层读出 | DB row | Drizzle 列类型 + 迁移约束 | 历史脏数据（迁移前写入的）绕过校验 |

PHP 对照：Laravel 的 `FormRequest` 守第一条，`config()` + 枚举守第二条，Guzzle 响应通常**不守**第三条（和 Node 一样的坑），Eloquent casts 守第四条的一半。

**启动即失败**是第二条边界最重要的性质：

```ts
const Env = z.object({
  PORT: z.coerce.number().int().min(1).max(65535).default(8080),
  DATABASE_URL: z.string().min(1),
  LOG_LEVEL: z.enum(["silent", "normal", "verbose"]).default("normal"),
});
export const env = Env.parse(process.env);   // 写错 → 进程起不来，而不是跑起来再错
```

对照 PHP：`declare(strict_types=1)` 管不了 `getenv()` 返回的字符串；你通常靠 `.env` 注释和祈祷。Zod 把祈祷变成启动断言。

## 2. DTO 的三种形态，别混用

同一个「商品」在系统里有三个形状，混淆它们是 bug 的温床：

```ts
// ① 入站契约（用户能传什么）：stock 可缺省 → default(0)
CreateProductRequestSchema = z.object({ sku, name, price, stock: z.int().min(0).default(0) })

// ② 领域记录（内部真相）：price 是品牌字符串 DecimalAmount，version 存在
interface ProductRecord { id; sku; name; price: DecimalAmount; stock; version }

// ③ 出站契约（对外承诺）：price 回到 JSON number，version 暴露给乐观锁
ProductResponseSchema = z.object({ id, sku, name, price: PositiveAmountSchema, stock, version })
```

| 形态 | 谁消费 | 允许缺省？ | 允许未知字段？ | 金额形态 |
|---|---|---|---|---|
| 入站 | 客户端 | 是（default） | strip（或 strict） | number / 字符串都收，规范化 |
| 领域 | 服务 / 仓储 | 否 | 否 | 品牌字符串 + 整数分 |
| 出站 | 客户端 / 前端 | 否 | 否 | number（scale 由出口函数负责） |

评审时看到「一个 interface 走天下」（入站出站领域共用一个类型），基本可以断定缺省值和未知字段策略是糊的。

## 3. 错误载荷：把「字段 → 第一条消息」当成 API 的一部分

仓库的 400 载荷与 Java 版逐字段一致：

```json
{
  "title": "参数错误",
  "status": 400,
  "detail": "请求参数校验失败",
  "errors": { "customerName": "不能为空", "items[0].quantity": "必须小于或等于 99" }
}
```

三个设计决定值得抄：

1. **嵌套路径用 `items[0].quantity`**：前端能直接定位到第几行第几个输入框。拍平规则在 `field-errors.ts`：数字段 → `[i]`，字符串段 → `.name`，空路径 → `_`。
2. **同字段保留第一条**（`putIfAbsent` 语义）：避免一个字段刷出十条消息淹没 UI。
3. **Content-Type 是 `application/problem+json`**（RFC 9457）：客户端可以按类型分流「业务错误」与「传输错误」。

PHP 对照：Laravel 默认 422 + `{"message":…, "errors":{field:[messages]}}`。语义相近但**状态码与数组形态不同**——跨语言团队要先统一这一层，否则前端要写两套解析。

## 4. 契约只写一次：schema 是值，类型是影子

```ts
export const OrderLine = z.object({ productId: z.int().positive(), quantity: z.int().min(1).max(99) });
export type OrderLine = z.infer<typeof OrderLine>;   // 类型从 schema 推导
```

这一行 `z.infer` 是整套 monorepo 的支点：

- 服务端 Pipe 用 `OrderLine`（值）做运行时校验；
- 前端表单用同一个值做提交前校验、用推导类型做 props；
- 契约测试用同一个值断言响应形状；
- 改一处，四端编译期一起红。

**什么时候不该用 Zod**：纯内部、无外部输入、性能极敏感的热点路径（schema 解析有成本）；以及需要「名义类型」语义时（Zod 管形状不管身份，身份用 branded type，见第 02 章）。

## 5. 评审清单

```text
[ ] 四条边界都有守卫，外部响应解析不是裸 as
[ ] 环境变量 schema 启动即 parse，失败即退出
[ ] 入站 / 领域 / 出站三形态分离，缺省值只出现在入站
[ ] 400 载荷是 problem+json，errors 键含嵌套路径
[ ] schema 与类型同源（z.infer），没有手抄第二份 interface
[ ] 有契约测试：用 schema 断言真实响应，而不是只断言 status
```
