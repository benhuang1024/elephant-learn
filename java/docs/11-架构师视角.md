# 11 架构师视角

## 1. 生态地图：Laravel 组件 → Spring 生态

| 能力 | Laravel | Spring 生态 |
|---|---|---|
| 缓存 | `Cache::remember` | Spring Cache（`@Cacheable`）+ Caffeine（本地）/ Redis |
| Redis | `Redis::` | Spring Data Redis（Lettuce 客户端）/ Redisson（分布式锁等） |
| 队列 | Laravel Queue + Horizon | Spring AMQP（RabbitMQ）、Spring Kafka、RocketMQ |
| 事件 | Event / Listener | `ApplicationEventPublisher` + `@EventListener` / `@TransactionalEventListener` |
| 定时任务 | `schedule()` + cron | `@Scheduled`；多实例下用 ShedLock 防重复执行；复杂调度用 Quartz / XXL-JOB |
| 异步任务 | `dispatch()` | `@Async`（进程内）、消息队列（跨进程） |
| 邮件 | Mail | Spring Mail |
| 文件存储 | Storage | AWS SDK / MinIO SDK |
| 全文搜索 | Scout | Spring Data Elasticsearch / OpenSearch |
| 批处理 | Artisan 命令 + chunk | **Spring Batch**（分片、断点续跑、重试） |
| 管理后台 | Nova / Filament | 无直接对应，通常前后端分离 |
| 限流 | `RateLimiter` | Bucket4j / 网关限流；单机并发限制用 `@ConcurrencyLimit` |
| 熔断重试 | — | Spring Framework 7 `@Retryable` / Resilience4j |
| AI 集成 | Prism 等 | Spring AI |

### 缓存示例

```java
@Configuration
@EnableCaching
class CacheConfig { }

@Service
class ProductQueryService {
    @Cacheable(cacheNames = "product", key = "#id")
    public ProductResponse get(Long id) { ... }        // ≈ Cache::remember("product:$id", ...)

    @CacheEvict(cacheNames = "product", key = "#id")
    public void update(Long id, UpdateProductRequest req) { ... }
}
```

```yaml
spring:
  cache:
    type: redis              # 或 caffeine（进程内，最快，但多实例间不一致）
  data:
    redis:
      host: localhost
```

本地缓存 + Redis 的二级缓存在 Java 中很自然：PHP 里没有长生命周期进程内存，只能依赖 APCu。

### 定时任务

```java
@Configuration
@EnableScheduling
class SchedulingConfig { }

@Component
class OrderTimeoutJob {
    @Scheduled(cron = "0 */5 * * * *")         // 6 位 cron：秒 分 时 日 月 周
    @SchedulerLock(name = "orderTimeout")       // ShedLock：多实例只有一个执行
    void closeUnpaidOrders() { ... }
}
```

和 Laravel 的重要区别：任务在 **应用进程内** 执行，不依赖系统 crontab；多实例部署时每个实例都会执行，必须加分布式锁。

## 2. 架构风格

### 推荐起点：模块化单体（Modular Monolith）

```
com.acme.shop
├── catalog/        # 商品
│   ├── CatalogApi.java          ← 对外暴露的接口（模块的唯一入口）
│   └── internal/                ← 其他模块禁止访问
├── order/
├── payment/
└── shared/
```

**Spring Modulith** 可以：

- 在测试中校验模块之间的依赖规则（`ApplicationModules.of(ShopApplication.class).verify()`），某个模块访问了别的模块的 `internal` 包时测试失败；
- 用事件在模块间解耦，并提供 **事件发布登记表**（Event Publication Registry），保证事务提交后的事件至少投递一次；
- 生成模块关系文档。

这让“先单体、边界清晰、需要时再拆服务”变得可执行，对多数从 PHP 单体迁移过来的团队，这是比直接上微服务更务实的路径。

### 分层还是六边形？

- 中小型 CRUD 系统：按特性分包 + Controller / Service / Repository 三层足够。
- 复杂领域：六边形 / 整洁架构，领域层不依赖 Spring（可放在独立 Maven 模块中强制约束，见第 03 章）。

### 微服务全家桶（Spring Cloud）

| 能力 | 组件 |
|---|---|
| API 网关 | Spring Cloud Gateway |
| 配置中心 | Spring Cloud Config / Nacos |
| 服务发现 | Kubernetes Service（首选）/ Nacos / Consul |
| 服务调用 | HTTP Interface / OpenFeign |
| 熔断限流 | Resilience4j / Sentinel |
| 分布式事务 | Seata（慎用）；更推荐 Saga + Outbox + 幂等 |
| 链路追踪 | Micrometer Tracing + OpenTelemetry |

国内常见组合是 **Spring Cloud Alibaba**（Nacos + Sentinel + RocketMQ + Seata）。如果运行在 Kubernetes 上，服务发现和配置交给 k8s，可以少引入很多组件。

## 3. 选型清单（新项目默认值）

| 决策点 | 建议默认值 |
|---|---|
| JDK | 25 LTS（Temurin） |
| 框架 | Spring Boot 4.x |
| 构建 | Maven + Wrapper |
| Web | Spring MVC + 虚拟线程（除非确有需要，不选 WebFlux 响应式） |
| 持久化 | 写：JPA；读/报表：JdbcClient 或 jOOQ（或团队更熟悉 MyBatis 时统一用 MyBatis） |
| 迁移 | Flyway |
| 数据库 | PostgreSQL |
| 缓存 | Caffeine + Redis |
| 消息 | Kafka（事件流）/ RabbitMQ（任务队列） |
| 测试 | JUnit + AssertJ + Mockito + Testcontainers |
| 可观测 | Actuator + Micrometer + OpenTelemetry |
| 代码质量 | Spotless（格式化）+ Error Prone / NullAway（空安全） |
| 样板代码 | 优先 record；需要时用 Lombok（团队统一规范） |

关于 **WebFlux**：响应式编程曾经是 Java 高并发的主要方案，学习和调试成本高。Java 21 虚拟线程出现后，绝大多数 IO 密集型业务用 MVC + 虚拟线程即可获得相近的吞吐量。除非是网关、流式推送等场景，不建议新团队从 WebFlux 起步。

## 4. PHP 团队迁移到 Java 的策略

### 技术路径

1. **绞杀者模式（Strangler Fig）**：在网关层按路由把流量逐步切到新的 Java 服务，PHP 系统继续服务其余部分。不要做大爆炸式重写。
2. **先迁移边界清晰、对性能/并发敏感的模块**：订单、库存、支付回调、消息消费者、定时批处理 —— 这些正是 PHP-FPM 模型的弱项、Java 的强项。
3. **共享数据库只作为过渡**：两边同时写一张表时，要明确表的所有权，尽快通过 API 或事件（CDC / Outbox）解耦。
4. **统一认证**：用 JWT 资源服务器（第 09 章）让 Java 服务信任现有的用户中心；BCrypt 密码哈希可直接兼容。
5. **统一可观测**：两侧使用相同的 traceId 头（W3C `traceparent`），日志与链路在同一套平台中可查。

### 团队路径

- 第 1 周：语言 + JVM 并发模型（本教程 01、02 章），每人用 Java 重写一个熟悉的小功能。
- 第 2 周：Spring 核心 + Web + 数据访问（04～07 章），团队共同完成一个内部 CRUD 服务。
- 第 3 周：测试、安全、生产化（08～10 章），把服务部署到预发环境。
- 制定团队规范：包结构、异常体系、DTO 约定、事务边界、日志格式、代码格式化，并用 Spotless + ArchUnit/Modulith 在 CI 中强制。
- 代码评审重点关注第 02 章（共享可变状态）和第 06、07 章（事务边界、N+1、代理失效）—— 这是 PHP 背景开发者在 Java 中最常出线上事故的三个地方。

### 常见反模式（来自 PHP 习惯）

| 反模式 | 正确做法 |
|---|---|
| `Map<String, Object>` 到处传（“PHP 数组思维”） | 定义 record / DTO |
| 静态工具类 + 静态状态（“Facade 思维”） | 注入的无状态 Bean |
| 单例 Bean 中保存请求数据 | 方法参数 / 局部变量 |
| 实体直接作为 API 响应 | 响应 DTO |
| Controller 中写业务逻辑和事务 | Service 层 + `@Transactional` |
| 捕获所有异常返回 `{"code": 500}` | 业务异常 + 全局 `@RestControllerAdvice` + ProblemDetail |
| 每个配置项用 `@Value` | `@ConfigurationProperties` record |
| 用 `==` 比较字符串 | `equals()` |
