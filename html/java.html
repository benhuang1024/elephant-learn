#php-fpm vs JVM：先换掉“进程模型”的直觉

PHP-FPMSpring Boot / JVM
进程每个请求由 FPM 分配一个 worker，请求结束内存基本释放一个常驻 JVM，启动时加载类、建立连接池，之后一直复用
并发多进程，进程间不共享内存（share-nothing）一个进程内多线程，共享堆上的对象
状态请求级全局变量、静态变量随请求结束消失单例 Bean 的字段、静态变量会被所有请求共享
部署换代码 + reload重启进程；启动要几秒到几十秒
内存按 worker 估算堆 + Metaspace + 线程栈 + 直接内存

由此产生两条最重要的规矩：

  1. 单例 Bean 必须无状态。需要请求级数据就放在方法参数或局部变量里，绝不能写进单例字段。

  2. 共享可变状态必须同步（Atomic*、synchronized、并发容器，或干脆不可变）。

第 02 章会用代码演示竞态；第 04 章会演示“单例里存用户信息”为什么是事故。

#编译型语言的工作流

PHP：改代码 → 刷新浏览器。
Java：改代码 → 编译（javac 把 .java 编译成 .class 字节码）→ JVM 加载运行。

日常开发中你几乎感受不到编译：

  • IntelliJ 保存即增量编译；

  • Spring Boot DevTools 检测到 class 变化会自动重启应用（1～2 秒）；

  • 写业务逻辑时更多是 跑单元测试 而不是重启服务验证。

编译带来的回报：重命名一个方法，IDE 能 100% 正确地改完所有调用方；PHPStan level 9 能做到的，Java 编译器默认就做到了。

#2. 变量、类型、基本语法

要点：

  • var 只是省略书写，不是动态类型。var x = 1; x = "a"; 编译失败。

  • int 是 32 位、long 是 64 位。数据库 BIGINT 主键对应 Long。整数溢出 不会 自动变成 float，会静默回绕。

  • List.of() / Map.of() 返回 不可变 集合，add 会抛异常。需要可变用 new ArrayList<>()。

  • Map.of 不保证顺序；需要 PHP 关联数组那样的插入顺序，用 LinkedHashMap。

#3. 类、接口、构造器

  • Java 没有构造器属性提升（constructor promotion），字段要单独声明。很多团队用 Lombok 的 @RequiredArgsConstructor 省掉样板代码；不想引入 Lombok 时，值对象优先用 record。

  • final 字段 ≈ readonly：只能在构造器里赋值一次。

  • 方法默认是 可覆盖 的（虚方法）。类上加 final 禁止继承。

  • 没有方法默认参数 —— 用 方法重载（同名不同参数）或 Builder 模式。

  • 没有命名参数 —— 参数多时用 record/Builder 封装。

#接口

#7. 泛型

见 Generics.java。

PHP 里你写 /** @return Collection<int, User> */，Java 里直接写 List<User>，并由编译器强制。

需要知道的三件事：

  1. 类型擦除：运行时泛型信息被擦除，List<String> 和 List<Integer> 是同一个 class。所以不能 new T()，不能 instanceof List<String>。

  2. 基本类型不能做泛型参数：List<int> 非法，要写 List<Integer>（自动装箱）。

  3. 通配符：读用 ? extends T，写用 ? super T（PECS）。业务代码里很少写，读框架源码时常见。

#8. null 与 Optional

见 NullSafety.java。

团队规范建议：

  • Optional 只作 返回值；不要用作字段、方法参数、集合元素。

  • 集合返回空集合（List.of()），永远不返回 null。

  • 参数校验用 Objects.requireNonNull(x, "x")。

  • Spring Framework 7 全面采用 JSpecify 的 @Nullable / @NullMarked 注解，配合 IDE 或 NullAway 可以得到接近 Kotlin 的空安全检查。

#9. 异常：受检 vs 非受检

见 Exceptions.java。

类型继承自编译器要求典型例子
受检异常 checkedException必须 catch 或 throws 声明IOException、SQLException
非受检异常 uncheckedRuntimeException不强制IllegalArgumentException、NullPointerException
错误Error不要捕获OutOfMemoryError

实践规则：

  • 业务异常继承 RuntimeException，在 Web 层用全局异常处理器统一转成 HTTP 响应（见第 05 章）。

  • Spring 把 JDBC 的 SQLException 转换成了非受检的 DataAccessException 体系，所以你在 Spring 项目里很少碰到受检异常。

  • 包装异常时 一定要传 cause：throw new BizException("...", e);，否则丢失堆栈。

  • try-with-resources 替代 finally { close() }。

  • 默认情况下，Spring 事务 只对 RuntimeException 和 Error 回滚，受检异常不回滚 —— 这是一个经典坑（第 06 章）。

最常见的坑：

  • PHP 数组是 值语义（赋值即复制，写时复制），Java 集合是 引用语义：把一个 List 传给方法，方法内修改会影响调用方。需要防御时返回 List.copyOf(list)。

  • Map.get(key) 不存在时返回 null，不会报 Undefined index。用 getOrDefault 或 computeIfAbsent。

  • 遍历时修改集合会抛 ConcurrentModificationException，用 removeIf 或迭代器删除。

#2. 线程安全：三条规则就够用

#规则一：单例 Bean 不要有可变的实例字段

Spring 的 Bean 默认是 单例（整个进程一个实例）。请求相关的数据只能放在 方法参数和局部变量 里（局部变量在线程栈上，天然线程隔离）。

#规则二：必须共享的可变状态，用并发工具

见配套代码中的 UnsafeCounter / AtomicCounter / SynchronizedCounter：

需求工具
计数器、序号AtomicInteger / AtomicLong / LongAdder
共享 Map / 进程内缓存ConcurrentHashMap（computeIfAbsent 原子加载）
临界区synchronized 或 ReentrantLock
不可变数据record + List.copyOf —— 最好的线程安全就是不可变

#规则三：跨实例（多台机器）的并发，用数据库或 Redis

synchronized 只在 一个 JVM 内 有效。部署 3 个实例时，扣库存这种操作仍需要数据库行锁、乐观锁（第 06 章）或 Redis 分布式锁。这一点和 PHP 是一样的。

#补充：可见性与有序性 —— 只有原子性还不够

count++ 除了“读-改-写不原子”，还有第二个问题：一个线程写入的值，另一个线程不保证立刻看见。CPU 缓存、编译器与 JIT 重排都可能让读线程一直读到旧值：

必须记住的几条：

  • volatile 只保证 可见性 + 有序性，不保证 i++ 的原子性。

  • synchronized、Atomic*、ConcurrentHashMap 的读写会建立 happens-before 关系 —— 原子性和可见性一起解决。

  • Thread.start() / Thread.join() / Future.get() 也建立 happens-before：主线程在 start() 前的写入，对新线程可见。

  • 不可变对象（final 字段 + 安全发布）不需要额外同步 —— 这是 record DTO 的最大优势之一。

  • 双重检查锁（DCL）单例的实例字段必须是 volatile，否则可能发布一个“构造未完成”的对象。

配套代码中的 AtomicCounter 与 SynchronizedCounter 都同时解决了原子性和可见性；
UnsafeCounter.count++ 两者都不满足。

#3. ThreadLocal：Java 版的“请求上下文”

PHP 里 $request、Auth::user() 天然是当前请求的。Java 中框架用 ThreadLocal（每个线程一份的变量）实现同样效果：

  • Spring Security 的 SecurityContextHolder —— 当前登录用户

  • RequestContextHolder —— 当前 HTTP 请求

  • Spring 事务管理器 —— 当前线程绑定的数据库连接

  • 日志 MDC —— 当前请求的 traceId

两个后果：

  1. 在新线程里（@Async、线程池、CompletableFuture）拿不到这些上下文，事务也不会传播过去。

  2. 自己用 ThreadLocal 时，线程是被线程池复用的，用完必须 remove()，否则下一个请求会读到上一个请求的数据。

Java 25 正式引入了 ScopedValue 作为更安全的替代（不可变、作用域结束自动失效），新代码优先考虑。

规则说明
默认只回滚 RuntimeException 和 Error受检异常 不回滚。需要时写 @Transactional(rollbackFor = Exception.class)

@Transactional、@Cacheable、@Async、@PreAuthorize、@Retryable 都只是标记。真正干活的是 Spring 在启动时为 Bean 创建的 代理对象：

注入到 Controller 里的 OrderService，其实是这个代理。

#2. 两种代理实现

方式条件原理
JDK 动态代理基于接口运行时生成实现同一接口的类
CGLIB（Spring Boot 默认）基于类运行时生成 子类，覆盖方法

CGLIB 生成子类，所以：

  • final 类、final 方法 不能被代理，注解失效；

  • private 方法无法覆盖，注解失效；

  • 这也是 JPA 实体不能是 final/record 的原因（Hibernate 用同样的方式生成懒加载代理）。

#常见坑 Top 15

  1. 用 == 比较字符串或 Integer。

  2. 在单例 Bean 的字段里保存请求相关数据。

  3. 同类内部调用 @Transactional / @Async / @Cacheable 方法，注解不生效。

  4. 事务中抛出受检异常，以为会回滚。

  5. catch 住异常后不重新抛出，事务照常提交。

  6. @ManyToOne 默认 EAGER，造成意外的关联查询。

  7. 开着 open-in-view，懒加载在序列化时触发 N+1 并长时间占用连接。

  8. 直接把 JPA 实体作为 JSON 返回。

  9. 用 double 处理金额。

  10. Map.of / List.of 返回不可变集合，后续 add 抛 UnsupportedOperationException。

  11. 以为 HashMap 保持插入顺序（PHP 数组习惯），需要时用 LinkedHashMap。

  12. ThreadLocal / MDC 用完不清理，线程复用导致数据串到下一个请求。

  13. 在事务中调用慢速外部 HTTP 接口，耗尽连接池。

  14. static 集合当缓存，无上限、无过期，最终 OOM。

  15. 多实例部署时 @Scheduled 任务在每个实例上都执行。
