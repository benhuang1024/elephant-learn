SSRF（服务端请求伪造）

约 6 分钟 5 段代码 1616 字
安全清单速查

方向：Web · 相关标准：OWASP A01:2025（2025 版并入访问控制）、CWE-918 · 最后更新：2026-10-22

#1. 核心要点

  • SSRF 是指：攻击者让你的服务器代替他去请求一个地址。服务器通常位于内网，能访问攻击者直接访问不到的东西。

  • 最危险的目标是云元数据服务（如 169.254.169.254），可能泄露云平台的临时凭证。

  • 防御首选目标白名单：只允许访问明确列出的域名，而不是去拦截“看起来像内网”的地址。

  • 必须校验解析后的 IP，并且实际连接时使用的必须就是校验过的那个 IP；重定向要关掉或逐跳校验。

  • 网络层兜底：发起外部请求的服务放在受限的网络出口后面，云上强制使用 IMDSv2 等加固措施。

#2. 为什么重要

  • 成因：功能需要服务端去取一个用户给的 URL，比如网页预览、头像 URL 导入、Webhook 回调、PDF 生成、文件导入。

  • 影响：

    • 访问内网管理后台、数据库、缓存等未鉴权服务

    • 读取云元数据，拿到云账号凭证，进一步控制云资源

    • 扫描内网、绕过防火墙

  • 为什么容易被绕过：只做字符串层面的黑名单，会被各种方式绕过。例如 IP 有多种写法（十进制、十六进制、IPv6 映射地址），一个域名可以解析到内网 IP，校验通过后的重定向，以及 DNS 重绑定（校验时解析到公网，连接时解析到内网）。

  • 标准：CWE-918

#3. 常见错误 vs 正确做法

错误：直接请求用户给的 URL

错误：字符串黑名单

正确思路一：业务允许时，只访问白名单域名

正确思路二：必须访问任意公网地址时，校验解析结果，并且连接时使用校验过的 IP

实际项目里，自己正确实现“固定 IP 连接 + TLS SNI”比较繁琐，更推荐：

  • 使用专门做了 SSRF 防护的 HTTP 库或出站代理，在连接阶段校验 IP（比如 Smokescreen 这类出站代理）

  • 关闭自动重定向（allow_redirects=False），确实需要时每一跳都重新校验

  • 只允许需要的协议（不要允许 file://、gopher://、ftp://）

  • 设置超时和响应体大小上限

#4. 如何识别

  • 搜索服务端发起 HTTP 请求的代码：requests.get(、urllib.request.urlopen、httpx、fetch(、axios、http.Get(、HttpClient，看 URL 是否部分或全部来自用户输入。

  • 特别关注这些功能：URL 预览、从 URL 导入图片或文件、Webhook、HTML 转 PDF/截图（无头浏览器会加载页面里的资源）、XML 解析（XXE 也能导致 SSRF）、SVG 处理。

  • 检查校验逻辑是不是字符串黑名单，有没有处理 DNS 解析和重定向。

  • 检查网络层面：发起请求的服务能否访问内网和元数据地址，云主机是否强制使用 IMDSv2。

#5. 防御清单

  • 能用白名单的场景（固定合作方、固定域名）一律使用白名单

  • 只允许 http/https 协议

  • 校验解析后的所有 IP，拒绝私网、回环、链路本地、保留地址，IPv4 和 IPv6 都要覆盖

  • 连接时使用校验过的 IP，防御 DNS 重绑定；或者使用在连接阶段做校验的出站代理

  • 关闭自动重定向，或者每一跳都重新校验

  • 设置超时、响应大小上限，不把原始错误信息和响应内容直接返回给用户

  • 发起外部请求的服务部署在隔离的网络环境中，出站流量经过受控代理

  • 云主机强制使用 IMDSv2（或对应云平台的等价机制），实例角色只授予最小权限

  • 内网服务本身也要有认证，不要因为“只在内网”就不设防

#6. 自测题

Q1. 为什么 SSRF 在云环境里特别危险？

云主机可以通过链路本地地址访问元数据服务，元数据里可能包含实例角色的临时凭证。如果服务端存在 SSRF，攻击者可能借服务器之手读到这些凭证，再用它们直接调用云 API，影响范围会从一个应用扩大到整个云账号的资源。

Q2. 校验时把域名解析成 IP，确认是公网地址后再用 requests.get(url) 发请求，还有什么问题？

requests.get(url) 会再解析一次域名。攻击者控制的 DNS 可以第一次返回公网 IP、第二次返回内网 IP（DNS 重绑定），校验和实际连接用的不是同一个 IP。另外，如果没有关闭重定向，目标服务器可以返回 302 跳转到内网地址。

Q3. 为什么推荐白名单而不是黑名单？

黑名单要穷举所有“不该访问”的地址和写法：各种 IP 编码方式、IPv6、解析到内网的域名、云厂商的特殊地址，很难做到完整。白名单只需要列出“该访问”的少数地址，未知的情况默认拒绝，更符合“默认拒绝”的原则。

Q4. AWS 的 IMDSv2 是如何降低 SSRF 风险的？

IMDSv2 要求先用 PUT 请求获取会话令牌，再在后续请求中带上这个令牌。大多数 SSRF 只能让服务器发出简单的 GET 请求，无法控制请求方法和请求头，所以拿不到令牌。再配合跳数限制为 1，容器等多一跳网络的环境也访问不到。它是缓解措施，不能替代应用层的修复。

Q5. 除了“URL 预览”，还有哪些常见功能可能引入 SSRF？

Webhook 回调地址、从 URL 导入文件或头像、HTML 转 PDF 或网页截图（渲染引擎会加载页面中的外部资源）、XML 解析中的外部实体、SVG/图片处理库加载外部引用、OAuth/OpenID 的元数据发现地址、各种“测试连接”功能。

应用代码写得再安全，如果跑在一台 SSH 允许密码登录的主机上，以 root 身份运行在特权容器里，或者用的是拥有管理员权限的云凭证，一个小问题就会变成整个系统被控制。本方向关注应用之下的各层：主机、网络、容器、Kubernetes、云平台，以及如何发现问题（日志与监控）。

  3. 纵深防御：假设某一层会被突破，下一层仍然能够限制影响范围

#1. 核心要点

  • XSS 是注入到浏览器里的注入：不可信数据被浏览器当作 HTML 或 JavaScript 执行。

  • 主要防御是按输出上下文编码：HTML 正文、HTML 属性、JavaScript、URL、CSS，各自的编码规则不同。

  • 优先依赖框架的自动转义（React、Vue、Jinja2、Django 模板默认都会转义），警惕绕过自动转义的接口：dangerouslySetInnerHTML、v-html、|safe、innerHTML。

  • 必须渲染用户提供的 HTML 时（如富文本），用成熟的净化库（DOMPurify 等）做白名单过滤。

  • CSP 是第二道防线：即使出现漏洞，严格的 CSP 也能阻止大部分注入脚本执行。

#2. 为什么重要

  • 成因：把用户输入原样输出到页面，或者在前端用 innerHTML、document.write 处理不可信数据。

  • 影响：脚本以受害者的身份在受害网站上运行，可以读取页面数据、发起请求、修改页面内容、钓鱼，在没有 HttpOnly 时还能窃取 Cookie。

  • 三种类型：

    • 反射型：恶意内容来自当前请求（如 URL 参数），服务端直接回显

    • 存储型：恶意内容被存进数据库，所有查看该内容的用户都会受影响，危害最大

    • DOM 型：问题完全在前端，JavaScript 把 location.hash 等不可信数据写进了危险的 DOM 接口

  • 标准：CWE-79

#3. 常见错误 vs 正确做法

前端 DOM 操作

React

服务端模板（Jinja2）

URL 上下文：转义不够，还要校验协议

CSP：推荐使用基于 nonce 的严格策略

上线严格 CSP 之前，先用 Content-Security-Policy-Report-Only 观察一段时间违规报告，确认不会影响正常功能。

#4. 如何识别

  • 前端搜索危险接口：innerHTML、outerHTML、insertAdjacentHTML、document.write、eval、setTimeout(字符串)、dangerouslySetInnerHTML、v-html。

  • 模板搜索关闭转义的写法：|safe、{% autoescape false %}、mark_safe、Markup(、{{{ }}}（Handlebars）。

  • 找出用户输入出现在 href、src、内联事件属性、<script> 块、style 中的位置，这些上下文的编码规则和 HTML 正文不同。

  • 检查响应头里是否有 CSP，策略中是否包含 'unsafe-inline'、'unsafe-eval' 或 * 这类会削弱防护的配置。

  • 用 CSP Evaluator 评估现有策略。

#5. 防御清单

  • 模板引擎开启自动转义，代码中关闭转义的地方都经过审查

  • 前端默认使用 textContent / 框架绑定，不用 innerHTML 处理不可信数据

  • 富文本使用 DOMPurify 等成熟库做白名单净化

  • 用户提供的 URL 校验协议，只允许 http/https

  • 部署基于 nonce 或 hash 的 CSP，禁用 'unsafe-inline' 和 'unsafe-eval'

  • 设置 object-src 'none'、base-uri 'none'

  • Session Cookie 设置 HttpOnly，减轻 XSS 的后果

  • 响应正确设置 Content-Type 和 X-Content-Type-Options: nosniff

  • 有条件的项目考虑启用 Trusted Types

#6. 自测题

Q1. 反射型、存储型、DOM 型 XSS 的主要区别是什么？

区别在于恶意数据来自哪里、在哪里被执行。反射型：数据来自当前请求，服务端直接回显。存储型：数据先被存储，之后展示给其他用户，影响面最广。DOM 型：服务端可能完全不参与，是前端 JavaScript 把不可信数据写进了危险的 DOM 接口。

Q2. 已经对 <、>、" 做了 HTML 转义，把用户输入放进 <a href="..."> 还安全吗？

不安全。javascript:alert(1) 里没有需要转义的字符，点击链接时仍会执行。URL 上下文必须额外校验协议，只允许 http: 和 https:。

Q3. 为什么说 CSP 是“第二道防线”，而不是 XSS 的主要防御？

CSP 是在漏洞已经存在的前提下限制脚本执行，策略写得不严格（如允许 'unsafe-inline'、允许托管任意内容的 CDN 域名）就会被绕过。而且 CSP 防不住所有危害，比如 HTML 注入导致的钓鱼表单。根本解决仍然要靠正确的输出编码和净化。

Q4. 为什么基于 nonce 的 CSP 比基于域名白名单的 CSP 更推荐？

域名白名单很容易被绕过：白名单里的 CDN 或域名上只要有一个可以被利用的 JSONP 接口或可上传的文件，就能加载攻击者控制的脚本。nonce 是每次请求随机生成的，攻击者注入的脚本拿不到正确的 nonce。配合 'strict-dynamic'，可信脚本动态加载的脚本也能正常运行。

Q5. React 默认就会转义，那么 React 应用里还可能出现 XSS 吗？

可能。常见原因：使用 dangerouslySetInnerHTML；把用户输入放进 href（javascript: 协议）；直接操作 DOM（ref.current.innerHTML）；服务端渲染时把数据序列化进 <script> 标签而没有正确转义；以及第三方组件内部的不安全实现。

云 IAM 与云配置安全

约 6 分钟 5 段代码 1671 字
安全清单速查

方向：基础设施 · 相关标准：CIS 云平台基线（AWS/GCP/Azure Foundations Benchmark）、OWASP A01:2025、A02:2025、CWE-269（权限管理不当） · 最后更新：2026-10-22

#1. 核心要点

  • 保护根账号/超级管理员：开启 MFA，不创建访问密钥，日常不使用，只在必须时登录。

  • 人用 SSO，程序用角色：人员通过身份提供方（SSO）登录并获取临时权限；程序使用实例角色、工作负载身份、OIDC 联合，避免长期访问密钥。

  • 最小权限：策略中避免 "Action": "*" 和 "Resource": "*"，从只读或具体权限开始，根据实际使用情况收紧。

  • 防止数据公开：对象存储默认阻止公开访问，数据库、快照、镜像不对外共享。

  • 全面审计：所有账号、所有区域开启审计日志（如 AWS CloudTrail），日志存到单独的、受保护的账号中，并对高危操作设置告警。

#2. 为什么重要

  • 成因：为了省事给了管理员权限；长期访问密钥写在代码或 CI 里，多年不轮换；对象存储为了分享文件设成了公开；没有开审计日志。

  • 影响：一个泄露的高权限密钥可以让攻击者删除所有资源、导出所有数据、大量创建资源（常用于挖矿）；公开的存储桶导致大规模数据泄露。云上的很多重大事件，根源都是身份与权限问题，而不是复杂的技术漏洞。

  • 标准：CIS AWS Foundations Benchmark、AWS IAM 最佳实践

#3. 常见错误 vs 正确做法

以下以 AWS 为例，GCP、Azure 和国内云厂商有对应的概念（角色、服务账号、托管身份、策略）。

策略过于宽泛

信任策略：限制谁能扮演这个角色（GitHub Actions OIDC）

如果漏写 sub 条件，任何 GitHub 仓库的工作流都可能扮演这个角色。

对象存储默认阻止公开访问

需要对外分享文件时，使用有过期时间的预签名 URL，或者通过 CDN 只暴露特定路径。

用组织级策略设置“护栏”

在 AWS Organizations 中可以用服务控制策略（SCP）设定所有账号都不能越过的边界，例如：禁止关闭 CloudTrail、禁止在未使用的区域创建资源、禁止删除日志存储桶。即使某个账号里有人拥有管理员权限，也无法违反这些限制。

#4. 如何识别

  • 用 IAM Access Analyzer 找出被共享到外部的资源，以及根据实际使用情况生成最小权限策略。

  • 查看“上次访问”信息（Last Accessed），删除长期未使用的权限、用户和角色。

  • 检查策略中的通配符、iam:PassRole 加上 Resource: "*"、能修改 IAM 本身的权限（可能被用来提升权限）。

  • 检查所有存储桶、快照、镜像的共享设置。

  • 用开源工具做整体评估，例如 Prowler、ScoutSuite（只在自己的或已授权的账号上运行）。

#5. 防御清单

  • 根账号开启 MFA（优先硬件密钥/Passkey），没有访问密钥，日常不使用

  • 人员通过 SSO 登录，使用临时凭证，按职责分配权限集

  • 程序使用角色、工作负载身份或 OIDC 联合，避免长期访问密钥

  • 必须存在的长期密钥定期轮换，并监控使用情况

  • 策略遵循最小权限，避免 Action: "*"、Resource: "*"

  • 严格控制 iam:*、iam:PassRole、sts:AssumeRole 等可能导致权限提升的操作

  • 角色的信任策略限制具体的主体和条件（如 OIDC 的 sub）

  • 账号级别阻止对象存储公开访问，对外分享使用预签名 URL

  • 所有区域开启审计日志，日志存放在单独的账号中，开启防篡改保护

  • 对高危操作设置告警：根账号登录、关闭审计日志、修改 IAM 策略、创建访问密钥

  • 用组织级策略（SCP 等）设置护栏

  • 开发、测试、生产使用不同的账号隔离

  • 设置费用告警，异常费用往往是被滥用的第一信号

#6. 自测题

Q1. 为什么推荐使用角色和临时凭证，而不是 IAM 用户的长期访问密钥？

长期访问密钥一旦泄露，在被发现和吊销之前一直有效，而且很容易被写进代码、配置、CI 中而长期遗忘。临时凭证有效期通常只有几十分钟到几小时，泄露后的窗口很短，也不需要存储和轮换。角色还可以通过信任策略限制谁能使用它。

Q2. iam:PassRole 权限为什么可能导致权限提升？

iam:PassRole 允许把一个角色交给云服务使用（如给 EC2 实例或 Lambda 函数绑定角色）。如果一个低权限用户可以把高权限角色交给自己能控制的服务（比如创建一台 EC2 并绑定管理员角色），他就能在这个服务里以高权限角色的身份执行操作，间接获得高权限。所以 PassRole 应该限定在具体的角色上。

Q3. 配置 GitHub Actions 的 OIDC 信任策略时，漏掉 sub 条件会怎样？

sub 条件限定了哪个仓库、哪个分支或环境可以扮演这个角色。漏掉它（或者只校验了 aud）意味着任何 GitHub 仓库的工作流都可能获取到这个角色的凭证，包括攻击者自己创建的仓库。

Q4. 为什么审计日志要存放在单独的账号中？

如果日志和业务资源在同一个账号，攻击者获得该账号的高权限后，可以删除或关闭日志来掩盖行踪。日志存到单独的、权限严格控制的账号中，再配合对象锁定等防篡改机制，即使业务账号被完全控制，日志依然可信，可以用于调查。

Q5. 需要把一个文件分享给外部合作方，应该怎么做，而不是把存储桶设为公开？

生成有过期时间的预签名 URL，只授权访问这一个对象；或者通过 CDN 加签名 URL/签名 Cookie 来分发；如果对方也在同一云平台，可以通过跨账号的资源策略只授权给对方的特定角色。存储桶本身保持“阻止公开访问”。

CSRF 与 CORS

约 5 分钟 6 段代码 1264 字
安全清单速查

方向：Web · 相关标准：OWASP A01:2025、CWE-352（CSRF）、CWE-942（过于宽松的跨域策略） · 最后更新：2026-10-22

#1. 核心要点

  • CSRF：浏览器会自动给请求带上目标站点的 Cookie，所以恶意网站可以诱导用户的浏览器向你的网站发出“用户本人身份”的请求。

  • CSRF 防御三件套：SameSite Cookie + CSRF Token（或校验 Origin 头）+ 改状态的操作不用 GET。

  • CORS 不是防护机制，而是“放宽”同源策略的机制。配置错误会让任意网站读到本该只有你的前端才能读到的数据。

  • 不要把请求的 Origin 原样反射到 Access-Control-Allow-Origin 里，更不要在这种情况下同时开启 Access-Control-Allow-Credentials: true。

  • 使用 Authorization 头携带令牌的纯 API，天然不受 CSRF 影响（浏览器不会自动带这个头），但仍要正确配置 CORS。

#2. 为什么重要

  • CSRF 成因：服务端只靠 Cookie 识别用户，没有确认请求确实来自自己的页面。

  • CSRF 影响：以受害者身份修改邮箱、转账、修改设置等。改了邮箱之后再走找回密码，就可能变成账号接管。

  • CORS 错配成因：为了“方便联调”配成允许所有来源，或者用不严谨的字符串匹配校验来源（如 endsWith("example.com") 会匹配到 evilexample.com）。

  • CORS 错配影响：攻击者的页面可以带着用户的 Cookie 读取 API 的响应，相当于跨站窃取数据。

  • 标准：CWE-352、CWE-942

#3. 常见错误 vs 正确做法

SameSite Cookie

SameSite 判断的是“站点”（注册域名，如 example.com），不是“源”。同一站点下的其他子域（如 blog.example.com）不受它限制，所以仍然需要 CSRF Token。

#4. 如何识别

  • 列出所有改变状态的接口，确认它们：不使用 GET，并且有 CSRF Token 或 Origin 校验。

  • 检查 Session Cookie 的 SameSite 属性。

  • 检查 CSRF 中间件的豁免列表（如 @csrf.exempt、csrf_exempt），每一项都要有合理理由。

  • 检查 CORS 配置：

    • Access-Control-Allow-Origin 是否为 * 或直接反射请求来源

    • 来源校验是否用了 startsWith、endsWith、includes、未锚定的正则

    • 是否允许 null

    • 带凭证的响应有没有 Vary: Origin

  • 动手验证：用 curl 带上 Origin: https://evil.example 请求自己的 API，看响应头是否放行。

#5. 防御清单

  • Session Cookie 设置 SameSite=Lax 或 Strict

  • 使用 Cookie 认证的站点，所有改状态的请求校验 CSRF Token（或严格校验 Origin/Referer）

  • 改状态的操作不使用 GET

  • 敏感操作（改邮箱、改密码、支付）要求重新输入密码或二次确认

  • CORS 允许的来源使用精确匹配的白名单，不反射、不允许 null

  • 只有确实需要时才开启 Access-Control-Allow-Credentials，开启时绝不能搭配通配

  • 带凭证的 CORS 响应设置 Vary: Origin

  • Access-Control-Allow-Methods 和 Access-Control-Allow-Headers 只列出实际需要的项

#6. 自测题

Q1. 为什么 CSRF 攻击能“以用户的身份”发出请求，但攻击者通常读不到响应？

浏览器发请求时会自动带上目标站点的 Cookie，所以请求本身是带用户身份的。但同源策略阻止攻击者页面读取跨源响应的内容（除非 CORS 放行）。所以 CSRF 的危害在于“让用户执行操作”，而不是“读取数据”。CORS 错配则恰好补上了“读取”这一块。

Q2. 设置了 SameSite=Lax 之后，还需要 CSRF Token 吗？

建议仍然保留。原因：SameSite 以站点为边界，同站的其他子域（可能被攻陷或存在 XSS）不受限制；Lax 会放行跨站的顶级 GET 导航，如果有用 GET 改状态的接口就会被利用；旧浏览器或特殊客户端可能不支持。CSRF Token 和 SameSite 配合使用是纵深防御。

Q3. Access-Control-Allow-Origin: * 和 Access-Control-Allow-Credentials: true 能一起使用吗？

浏览器不允许这种组合，带凭证的请求会被拒绝。正因如此，很多开发者改成“把请求的 Origin 反射回去”来绕开限制，而这实际上比 * 更危险，因为它真的允许任意站点带着 Cookie 读取响应。

Q4. 用 origin.endsWith("example.com") 校验来源有什么问题？

https://evilexample.com 也以 example.com 结尾，攻击者注册这个域名就能通过校验。应该对完整的来源字符串（协议 + 主机 + 端口）做精确匹配，或者使用严格锚定的正则表达式，比如 ^https://([a-z0-9-]+\.)?example\.com$。

Q5. 只使用 Authorization: Bearer 头认证的 API，还需要防 CSRF 吗？

一般不需要，因为浏览器不会自动给跨站请求加上 Authorization 头，攻击者的页面拿不到令牌。但前提是令牌不在 Cookie 里。如果令牌存在 Cookie 里、由服务端从 Cookie 读取，就又回到了需要防 CSRF 的情况。

注入（Injection）

约 6 分钟 9 段代码 1380 字
安全清单速查

方向：Web · 相关标准：OWASP A05:2025、CWE-89（SQL 注入）、CWE-78（OS 命令注入）、CWE-1336（模板注入） · 最后更新：2026-10-22

#1. 核心要点

  • 注入的本质是数据被当成了代码执行：不可信的输入被拼接进 SQL、Shell 命令、模板、LDAP 查询等解释器能执行的语句里。

  • 根本的防御是让数据和代码分离：SQL 用参数化查询，命令执行用参数数组而不是 Shell 字符串，模板只传变量不拼模板。

  • 转义和黑名单过滤只能作为补充手段，不能作为主要防御，因为很容易漏掉边界情况。

  • ORM 并不能自动防住所有注入，raw()、text()、字符串格式化拼出来的查询仍然有风险。

  • 数据库账号使用最小权限，即使注入成功，也要把影响限制在最小范围。

#2. 为什么重要

  • 成因：用字符串拼接或格式化构造查询或命令，开发者以为输入会“规规矩矩”。

  • 影响：SQL 注入可以导致数据泄露、篡改、绕过登录，严重时可以执行系统命令；命令注入和模板注入通常直接导致服务器被控制（RCE）。

  • 常见形态：SQL 注入、NoSQL 注入（如 MongoDB 的 $where、操作符注入）、OS 命令注入、服务端模板注入（SSTI）、LDAP/XPath 注入、日志注入。

  • 标准：OWASP A05:2025、CWE-89、CWE-78

#3. 常见错误 vs 正确做法

SQL 注入

无法参数化的部分（表名、列名、排序方向）用白名单

OS 命令注入

更好的做法是：如果有对应的语言库（比如用 Pillow 处理图片），就不要调用外部命令。

服务端模板注入（SSTI）

NoSQL 操作符注入（Node.js + MongoDB）

#4. 如何识别

  • 搜索字符串拼接后传给解释器的地方：

    • Python：execute(f"、execute("..." %、.format( 用于 SQL，shell=True、os.system、os.popen、render_template_string、eval、exec

    • JavaScript：模板字符串拼进 query(、child_process.exec、eval、new Function

    • Java：Statement.executeQuery("..." +、Runtime.exec(String)

  • 跟踪数据流：从请求参数出发，看它是否在没有参数化的情况下到达上面这些函数。

  • 注意二次注入：数据先被安全地存入数据库，之后又被取出并拼接进另一条查询。

  • 用 Semgrep、CodeQL 等工具辅助扫描（见 安全工具）。

#5. 防御清单

  • 所有 SQL 使用参数化查询或 ORM 的安全接口

  • 表名、列名、排序方向等无法参数化的部分使用白名单

  • 不使用 shell=True / exec 执行包含外部输入的命令，优先使用语言内置库

  • 模板固定，用户输入只作为模板变量

  • 禁止在业务代码中对外部输入使用 eval、exec、new Function

  • 对 NoSQL 查询的输入做类型校验，禁止客户端传入查询操作符

  • 数据库账号按最小权限分配，应用账号不能执行 DDL、不能读写无关的库

  • 数据库错误信息不返回给前端

  • 代码审计和 CI 中加入注入相关的 SAST 规则

#6. 自测题

Q1. 为什么参数化查询能防住 SQL 注入，而手动转义引号不够可靠？

参数化查询把 SQL 语句结构和数据分开发送，数据库先解析语句结构，再把参数作为纯数据填入，参数永远不会改变语句结构。手动转义依赖开发者考虑到所有特殊字符、编码方式和数据库方言，任何一个疏漏都会被绕过，比如数值型参数没有引号包裹时，转义引号根本没用。

Q2. 用户可以选择按哪一列排序，列名能用参数化查询传入吗？应该怎么处理？

不能。参数化查询只能用于值，不能用于表名、列名、SQL 关键字。应该用白名单：把允许的列名写成固定集合，输入不在集合里时使用默认值或报错。

Q3. 用了 ORM，就一定不会有 SQL 注入吗？

不一定。ORM 的常规查询接口是安全的，但 raw()、text()、extra()、原生 SQL 片段，以及用字符串格式化构造的过滤条件，都可能引入注入。审计时要专门找这些“逃生口”。

Q4. subprocess.run(["ping", host]) 还有风险吗？

不经过 Shell，所以不会出现 ;、| 这类 Shell 元字符注入。但仍然存在参数注入风险：如果 host 以 - 开头，可能被 ping 当作选项解析。应该校验 host 是合法的主机名或 IP，并在支持的命令中使用 -- 结束选项解析。

Q5. 什么是二次注入（Second-order Injection）？

恶意数据第一次写入时被安全处理（比如用了参数化查询），存进了数据库。之后另一段代码从数据库中取出这条数据，以为“来自自己的数据库就是可信的”，又直接拼接进新的查询，这时注入才真正发生。防御：所有进入解释器的数据都按不可信处理，无论来源是哪里。

#1. 核心要点

  • 不要自己设计加密方案，用成熟库的高层接口（如 Python 的 cryptography、libsodium/PyNaCl、Go 标准库、Google Tink）。

  • 加密优先使用 AEAD（AES-GCM、ChaCha20-Poly1305），它同时提供保密性和完整性。不要用 ECB 模式，不要用不带认证的 CBC。

  • Nonce/IV 不能重复：AES-GCM 在同一个密钥下重复使用 nonce 会导致严重的安全问题。

  • 安全相关的随机数只用 CSPRNG（Python secrets、os.urandom；Node crypto.randomBytes；Go crypto/rand），不要用 random、Math.random()。

  • 用对工具：密码用慢哈希（Argon2id 等），完整性校验用 HMAC，数据加密用 AEAD，传输用 TLS。哈希不是加密，Base64 更不是加密。

#2. 为什么重要

  • 成因：密码学 API 很容易“用起来能跑，但其实不安全”：ECB 模式能加解密，random 能生成令牌，MD5 能算哈希，没有任何报错。

  • 影响：数据泄露后可以被直接解密或破解；令牌可以被预测；签名可以被伪造；数据可以被篡改而不被发现。

  • 标准：OWASP A04:2025、CWE-327、CWE-330

  • 搜索弱算法：md5、sha1（用于安全场景时）、DES、RC4、ECB、AES.MODE_ECB、createCipher(（Node 中已移除的旧接口）。

  • 搜索不安全的随机数：random.、Math.random、rand.Intn（Go 的 math/rand），看它们是否被用于生成令牌、密码、验证码、ID。

  • 搜索关闭证书校验：verify=False、rejectUnauthorized: false、InsecureSkipVerify: true、CERT_NONE。

  • 检查密钥来源：是否硬编码在代码里、是否所有环境共用一个密钥。

  • 使用成熟库的高层接口，不自己实现加密算法或协议

  • 数据加密使用 AEAD（AES-GCM / ChaCha20-Poly1305），每次加密使用新的随机 nonce

  • 安全相关的随机数全部使用 CSPRNG

  • 密码使用 Argon2id / scrypt / bcrypt 存储

  • 完整性校验使用 HMAC 或数字签名，比较时使用常量时间比较

  • 不在生产代码中关闭 TLS 证书校验

  • 密钥来自 KMS 或密钥管理服务，不硬编码，按环境区分，支持轮换（见 密钥管理）

  • 密文中带上密钥版本号，便于密钥轮换后仍能解密旧数据

  • 传输层统一使用 TLS 1.2 及以上版本（推荐 TLS 1.3）

  • 关注后量子密码迁移：了解 ML-KEM、ML-DSA 等新标准，盘点系统中使用的公钥算法

#6. 自测题

Q1. 为什么说 ECB 模式不安全？

ECB 把明文按块分别独立加密，相同的明文块会得到相同的密文块。所以密文会暴露明文的结构和重复模式（经典例子是用 ECB 加密的图片仍然能看出轮廓），攻击者还可以重排、替换密文块。

Q2. 哈希、加密、编码有什么区别？

编码（如 Base64）是可逆的格式转换，不需要密钥，没有任何安全性。加密是用密钥进行的可逆变换，有密钥才能解密，用于保密。哈希是单向的，无法从结果还原输入，用于完整性校验和指纹（存储密码时要用专门的慢哈希）。

Q3. 为什么验证 Webhook 签名时要用 hmac.compare_digest 而不是 ==？

== 比较字符串时，一旦遇到不同的字符就会提前返回，比较耗时和“前面有多少个字符是对的”有关。攻击者理论上可以通过测量响应时间逐个字符地猜出正确的签名。compare_digest 的耗时与内容无关，避免了这种时序侧信道。

Q4. AES-GCM 重复使用 nonce 会怎样？

在同一密钥下用同一个 nonce 加密两条消息，攻击者可以得到两条明文的异或值，从而可能恢复明文；更严重的是可以恢复认证密钥，进而伪造任意密文的认证标签。所以 nonce 必须保证唯一，通常用 96 位随机值，或者使用可靠的计数器。

Q5. 已经用了 HTTPS，数据库里的敏感字段还需要加密吗？

HTTPS 只保护传输过程。数据库备份泄露、SQL 注入、运维人员越权访问、存储介质丢失时，HTTPS 都没有作用。对身份证号、银行卡号这类高敏感字段，应该做字段级加密，密钥由 KMS 管理，并且与数据库分开存放。

访问控制（Broken Access Control）

约 5 分钟 4 段代码 1338 字
安全清单速查

方向：Web · 相关标准：OWASP A01:2025、CWE-284、CWE-639（IDOR）、CWE-862（缺少授权） · 最后更新：2026-10-22

#1. 核心要点

  • 认证 ≠ 授权。认证回答“你是谁”，授权回答“你能不能做这件事”。登录了不代表什么都能访问。

  • 授权检查必须在服务端完成，而且要放在每一个接口上。前端隐藏按钮不算防护。

  • 不要信任客户端传来的身份和角色信息（如 user_id、role=admin），这些只能从服务端的会话或已校验的令牌里取。

  • 默认拒绝：没有明确允许的操作一律不允许。

  • 把授权逻辑集中到一处（中间件、装饰器、策略层），不要在每个接口里各写各的。

#2. 为什么重要

  • 成因：开发者只验证了用户已登录，却没有验证用户和被操作对象之间的归属关系。或者只在前端控制菜单可见性，后端接口没有任何检查。

  • 影响：读取或修改别人的数据（订单、病历、私信），普通用户执行管理员操作，批量拉取全部数据。在 2025 版 Top 10 里排第一。

  • 常见形态：

    • 水平越权 / IDOR：把 URL 里的 /orders/1001 改成 /orders/1002，就看到了别人的订单

    • 垂直越权：普通用户直接请求 /admin/users 也能成功

    • 批量赋值（Mass Assignment）：提交表单时多带一个 is_admin=true 字段，后端直接写进数据库

  • 标准：OWASP A01:2025、CWE-639

#3. 常见错误 vs 正确做法

IDOR：只按 ID 查询，不检查归属

垂直越权：角色检查集中处理

批量赋值：只接受白名单字段

#4. 如何识别

  • 找出所有接收对象 ID 的接口（路径参数、查询参数、请求体），逐个确认查询时有没有带上归属条件。

  • 检查是否存在只有前端控制的权限：菜单、按钮被隐藏了，但对应的 API 没有鉴权装饰器。

  • 搜索 update(**、Object.assign(model, req.body)、BeanUtils.copyProperties 这类整体赋值的写法。

  • 看鉴权逻辑是不是分散在各个接口里，分散的地方最容易漏。

  • 自测方法：准备两个普通账号 A、B 和一个管理员账号。用 A 的会话去请求 B 的资源、请求管理员接口，看是否都被拒绝。

#5. 防御清单

  • 除了明确的公开接口，所有接口默认需要登录

  • 所有按 ID 访问资源的查询都带上归属或权限条件

  • 角色和权限只从服务端会话或已校验的令牌中读取

  • 鉴权逻辑集中在中间件、装饰器或策略层，新接口默认继承

  • 写入接口使用字段白名单，拒绝未知字段

  • 无权访问时统一返回 403 或 404，不泄露资源是否存在

  • 对外暴露的 ID 考虑用不可枚举的 UUID（这是补充手段，不能替代授权检查）

  • 访问控制失败要记日志，同一账号短时间内大量 403 要能触发告警

  • 为越权场景编写自动化测试：用户 A 访问用户 B 的资源必须失败

#6. 自测题

Q1. 把订单 ID 从自增整数改成 UUID 之后，还需要做归属检查吗？为什么？

需要。UUID 只是让 ID 难以猜测，但 ID 仍可能通过分享链接、日志、Referer 头、其他接口的返回值等途径泄露。授权必须基于“当前用户是否有权访问这个对象”，而不是“对方猜不到 ID”。

Q2. 前端已经根据角色隐藏了“删除用户”按钮，后端接口还需要做角色检查吗？

必须做。攻击者可以绕过前端，直接用 curl 或代理工具构造请求。前端控制只影响用户体验，不构成安全边界。

Q3. 用户无权访问某个订单时，返回 403 和返回 404 各有什么考虑？

403 明确告诉对方“资源存在但你没有权限”，这会泄露资源是否存在的信息。404 不泄露这一点，常用于用户私有的资源。管理后台这类场景中，用户知道资源存在是合理的，用 403 更便于排查问题。两者的选择要在系统内保持一致。

Q4. 什么是批量赋值漏洞？给出一种防御方式。

后端把请求体里的所有字段直接映射到数据模型上，攻击者就可以额外提交本不该由用户修改的字段（如 role、is_admin、balance）。防御方式：使用显式的字段白名单，或者使用只包含可修改字段的 DTO/Schema 做反序列化。

Q5. 为什么推荐把授权逻辑集中到中间件或策略层？

分散在各个接口里的检查很容易在新增接口时被遗漏，也难以统一审计。集中处理可以做到“默认拒绝”：新接口自动继承检查，例外情况需要显式声明，审计时只需要看一处。

#1. 核心要点

  • SSH：只允许密钥登录，禁止 root 直接登录，限制允许登录的用户，有条件的放在堡垒机或 VPN 后面。

#6. 自测题

Q1. 为什么建议 SSH 禁止密码登录，只允许密钥登录？

暴露在网络上的 SSH 会持续受到自动化的密码爆破和撞库。密钥认证使用非对称加密，私钥不会在网络上传输，也无法被暴力猜出。即使服务器被冒充，攻击者也拿不到私钥。

Q2. 为什么不应该让 Web 服务以 root 身份运行？

如果服务存在漏洞（如命令注入），攻击者获得的权限就是服务进程的权限。以 root 运行意味着一个应用漏洞直接变成整台主机被控制。使用专用低权限账号，再配合 systemd 的沙箱选项，可以把影响限制在很小的范围内。需要绑定 1024 以下端口时，可以使用反向代理或授予 CAP_NET_BIND_SERVICE 能力。

Q3. 为什么 deploy ALL=(root) NOPASSWD: /usr/bin/vim 这样的 sudo 规则很危险？

vim 可以通过 :!sh 等方式启动 Shell，而这个 Shell 会继承 root 权限。很多常见程序（编辑器、less、find、tar、awk、各种解释器）都有类似的“逃逸”方式。sudo 规则应该只允许执行功能单一、参数受限的命令，或者使用专门的包装脚本。

Q4. systemd 的 NoNewPrivileges=yes 有什么作用？

它保证进程及其子进程无法通过 execve 获得新的权限，比如执行 SUID 程序时不会提升为文件所有者的权限，也不会获得文件能力（file capabilities）。这能有效阻止很多利用 SUID 程序提权的路径。

Q5. 为什么日志要发送到远端，而不只是保存在本机？

攻击者获得 root 权限后，通常会清除或篡改本机日志来掩盖痕迹。日志实时发送到远端的集中日志系统，本机被入侵后也无法修改已经发出去的记录。集中存储还便于跨主机关联分析和设置告警。

网络安全

约 6 分钟 4 段代码 1502 字
安全清单速查

方向：基础设施 · 相关标准：CIS Controls（网络基础设施管理）、NIST SP 800-207（零信任架构）、CWE-319（敏感信息明文传输） · 最后更新：2026-10-22

#1. 核心要点

  • 默认拒绝入站：只开放明确需要的端口，并尽量限制来源。数据库、缓存、管理端口不对公网开放。

  • 网络分段：按信任级别和功能划分网络区域（公网入口、应用、数据、管理），区域之间只开放必要的流量。

  • 出站也要控制：服务器不需要随意访问互联网，限制出站可以降低数据外泄和失陷主机“回连”的风险。

  • 所有传输加密：对外统一 HTTPS（TLS 1.2+，推荐 1.3），内部服务之间也尽量使用 TLS 或 mTLS。

  • 零信任：不因为“在内网”就信任一个请求，每个服务都做认证和授权。

#2. 为什么重要

  • 成因：为了调试临时开放的端口没有关；数据库绑定在 0.0.0.0；整个内网是一个扁平网络；内部流量用 HTTP 明文。

  • 影响：未鉴权的数据库、缓存、搜索引擎暴露在公网，导致数据被整库拖走或被勒索；一台主机被攻陷后，攻击者可以在扁平网络里横向移动；明文流量被窃听。

  • 标准：NIST SP 800-207

#5. 防御清单

  • 主机和云安全组默认拒绝入站，只开放必要端口

  • SSH、RDP、数据库、缓存、管理后台不对公网开放

  • 服务只监听需要的网卡地址

  • 按功能和信任级别划分网络区域，区域之间按需放行

  • 限制出站流量，必要时通过代理统一出口

  • 对外服务使用 TLS 1.2+，证书自动续期，开启 HSTS

  • 内部服务间通信使用 TLS 或 mTLS

  • 内部服务也要有认证，不依赖网络位置

  • 定期审查防火墙和安全组规则，删除临时和过期的规则

#6. 自测题

Q1. 为什么数据库已经设置了强密码，仍然不应该把端口开放到公网？

纵深防御。密码只是一层防护，数据库软件本身可能存在认证绕过或远程代码执行漏洞，暴露在公网会让任何人都能尝试利用。另外配置变更可能意外关闭认证。限制网络访问能确保即使认证层出问题，攻击者也接触不到服务。

Q2. 什么是横向移动？网络分段如何限制它？

横向移动是指攻击者拿下一台主机后，以它为跳板访问内网中的其他系统。在扁平网络中，一台被攻陷的 Web 服务器可以直接连接所有数据库、管理系统和办公网。网络分段把系统划分到不同区域，只允许必要的流量通过，攻击者就无法从一个区域随意进入另一个区域。

Q3. 为什么要限制服务器的出站流量？

很多攻击在得手后需要向外连接：下载更多工具、建立远程控制通道、把数据传出去。如果服务器只能访问少数必要的外部地址，这些行为就会被阻止或被发现。限制出站也能减轻 SSRF 的影响。

Q4. 零信任的核心思想是什么？

“永不信任，始终验证”。不因为请求来自内网就信任它，每次访问都要基于身份（用户身份、设备状态、服务身份）进行认证和授权，并且只授予最小的访问权限。网络位置不再作为信任的依据。

Q5. 为什么要禁用 TLS 1.0 和 1.1？

TLS 1.0 和 1.1 依赖已经过时的加密算法和构造方式，存在多个已知的协议层面弱点，并且已经被 IETF 正式弃用（RFC 8996）。主流浏览器也已经停止支持。保留它们只会扩大攻击面，并可能允许降级攻击。

道德与授权范围

约 5 分钟 1 段代码 1728 字
安全清单速查

方向：攻防 · 相关标准：ISO/IEC 29147（漏洞披露）、ISO/IEC 30111（漏洞处理流程）、RFC 9116（security.txt） · 最后更新：2026-10-22

#1. 核心要点

  • 授权是测试与攻击之间唯一的分界线。技术手段完全相同，有没有书面授权决定了它是安全工作还是违法行为。

  • 授权必须是书面的、明确的：谁授权、测试哪些目标、允许哪些方法、什么时间段、出问题联系谁。

  • 严格遵守范围：范围外的系统（包括第三方服务、云厂商的基础设施、同一网段的其他主机）即使“顺手”也不能碰。

  • 最小影响：证明问题存在即可，不读取或下载超过证明所需的数据，不做破坏性操作，不保留拿到的数据。

  • 负责任地披露：发现漏洞后通过正规渠道报告，给对方合理的修复时间，不公开细节直到修复完成或按约定时间。

#2. 为什么重要

  • 法律：大多数国家和地区都有针对未授权访问计算机系统的法律，例如中国《刑法》第 285、286 条和《网络安全法》、美国 CFAA、英国 Computer Misuse Act。“出于好意”“只是看看”通常不能作为免责理由。

  • 信任：安全从业者依赖客户和社区的信任。越界一次，可能失去职业生涯。

  • 安全：即使是授权测试，也可能导致服务中断或数据损坏，所以需要事先约定规则和应急联系方式。

#3. 常见错误 vs 正确做法

  • 授权方（有权限做决定的人）和测试方

  • 允许和禁止的测试类型（例如：禁止拒绝服务、禁止社会工程、禁止物理测试）

  • 时间窗口（日期和每天的时段）

  • 测试账号和测试数据的提供方式

  • 数据处理要求：拿到的数据如何保存和销毁

  • 紧急联系人：测试导致故障时立即联系谁

  • 发现严重问题时的报告方式（是否需要立即通知，而不是等到最终报告）

  • 我有书面授权吗？授权人是否真的有权批准对这个系统的测试？

  • 我将要做的操作在允许的测试类型里吗？可能影响生产服务吗？

  • 如果出了问题，我知道该立即联系谁吗？

  • 我在练习平台上的操作是否符合该平台的规则（例如有的平台禁止攻击其他用户或平台基础设施）？

Q1. 一个朋友说“你帮我测一下我们公司的网站吧”，你可以开始测试吗？

不可以。朋友可能没有权限代表公司授权，口头同意也无法界定范围和规则。需要由公司内有权限的负责人出具书面授权，明确范围、方式、时间和联系人之后才能开始。

Q2. 授权测试 app.example.com 时，发现它调用了 api.thirdparty.com，可以一起测试吗？

不可以。第三方服务不属于被测方所有，被测方也无权授权你测试它。应该把这个依赖关系记录在报告中。如果认为确有必要测试，需要由被测方去和第三方协调，取得第三方的授权。

Q3. 测试中发现一个 SQL 注入，为了证明影响，应该把用户表导出来吗？

不应该。只需要用最小的证据证明问题存在，例如获取数据库版本或当前数据库名称，并说明理论上可能造成的影响。读取或导出真实用户数据既没必要，也可能违反授权约定和数据保护法规。发现这类严重问题时应该立即通知授权方。

Q4. 什么是协调漏洞披露（Coordinated Vulnerability Disclosure）？

发现者私下向厂商报告漏洞，厂商确认并修复，双方约定一个时间点后再公开细节（业界常见是 90 天左右）。这样用户能在漏洞细节公开前获得补丁。如果厂商长期不回应，发现者可以通过 CERT 等第三方机构协调。

Q5. 企业为什么要发布漏洞披露政策和 security.txt？

让发现问题的人知道该向谁报告、怎样报告，以及企业承诺不会追究善意的报告者。没有明确的渠道时，报告者可能找不到联系人、担心被追究而选择不报告，或者直接公开。这两样东西能让企业更早、更安全地得知自己的漏洞。

  • 先求低误报，再求高覆盖。误报太多，团队很快就会忽略所有告警。从高置信度的规则开始，逐步扩大范围。

  • 局限：每种工具都有误报和漏报。SAST 不理解业务语义，SCA 只知道已公开的漏洞，DAST 只能覆盖它爬到的页面。

#6. 自测题

Q1. SAST、SCA、DAST 分别检查什么？各有什么局限？

SAST 分析源代码，能定位到具体代码行，但不理解业务语义，误报较多，也找不到运行时配置问题。SCA 检查依赖及其已知漏洞，误报少，但只能发现已公开的漏洞。DAST 从外部测试运行中的应用，能发现配置和运行时问题，但只能覆盖扫描到的页面，并且难以定位到代码。

Q2. 为什么建议先接入秘密扫描和 SCA，再接入 SAST？

秘密扫描和 SCA 的误报率低，结果明确（这里有一个密钥 / 这个版本有 CVE），修复方式也清楚（吊销密钥 / 升级版本），很容易让团队看到价值。SAST 误报较多，需要调规则、建基线，如果一开始就产生大量告警，团队可能会对安全工具产生抵触。

Q3. 秘密扫描为什么要扫完整的 Git 历史？

密钥即使在后来的提交中删除了，仍然保存在历史提交中，任何能克隆仓库的人都能找回来。只扫当前代码会漏掉这些已经“删除”但实际仍然可访问的密钥。

Q4. 遇到 SAST 误报时，为什么不建议直接全局关闭这条规则？

这条规则在别的地方可能发现的是真问题，全局关闭会让以后出现的同类真问题也被漏掉。应该在具体位置标注忽略并写明原因，这样既消除了这个误报，又保留了审查记录，规则继续保护其他代码。如果某条规则误报率确实太高，可以调整规则本身而不是彻底关闭。

Q5. 为什么扫描工具发现不了越权漏洞？应该怎么补？

越权漏洞的代码在模式上通常完全正常，问题在于少了一个业务相关的检查条件，工具不知道“谁应该能访问什么”。弥补方式：人工审计时重点检查；为项目的权限模式编写自定义规则（如上面的 Semgrep 规则）；为越权场景编写自动化测试。

安全清单速查

方向：基础设施 · 相关标准：CIS Docker Benchmark、NIST SP 800-190（应用容器安全指南）、CWE-250 · 最后更新：2026-10-22

#1. 核心要点

  • 容器不是安全边界很强的虚拟机，它和宿主机共享内核。配置不当时，容器内的问题可以直接影响宿主机。

  • 镜像：使用可信的、精简的基础镜像（distroless、Alpine、slim 版本、官方镜像），固定版本（最好固定到 digest），定期重建以获取补丁。

  • 运行时：以非 root 用户运行，不使用 --privileged，删除不需要的 Linux capabilities，根文件系统设为只读。

  • 不要挂载 Docker socket（/var/run/docker.sock）到容器里，这等于给了容器宿主机的 root 权限。

  • 扫描：构建流程中扫描镜像漏洞和 Dockerfile 配置问题，推送前拦截高危问题。

#2. 为什么重要

  • 成因：Dockerfile 默认以 root 运行；为了解决权限问题直接加 --privileged；基础镜像庞大且长期不更新；为了方便挂载宿主机目录和 Docker socket。

  • 影响：应用漏洞加上过高的容器权限，可能导致容器逃逸，进而控制宿主机和同一主机上的其他容器；镜像中的已知漏洞被利用；镜像层中残留的密钥泄露。

  • 标准：NIST SP 800-190、CIS Docker Benchmark

#3. 常见错误 vs 正确做法

Dockerfile

构建阶段的 Python 版本和发行版要和运行镜像一致（distroless 的 python3-debian12 基于 Debian 12 和它自带的 Python 3.11），否则编译出的原生扩展可能无法加载。生产中可以把 FROM 固定到 digest（image@sha256:...），由 Renovate/Dependabot 负责更新。

.dockerignore

运行参数

  • --cap-drop ALL：删除所有 Linux capabilities，确实需要的再用 --cap-add 单独加回

  • --read-only：根文件系统只读，需要写入的目录用 tmpfs 或卷挂载

  • --memory、--pids-limit：防止一个容器耗尽宿主机资源

  • -p 127.0.0.1:8080:8080：只在本机暴露端口。注意 Docker 发布的端口会绕过 ufw 等主机防火墙规则

扫描镜像和 Dockerfile

#4. 如何识别

  • 检查 Dockerfile：有没有 USER 指令？基础镜像是否固定版本？是否复制了不必要的文件？

  • 检查正在运行的容器：

    • docker inspect --format '{{.Config.User}}' <容器>：是否以 root 运行（空值表示 root）

    • docker inspect --format '{{.HostConfig.Privileged}}' <容器>：是否特权模式

    • docker inspect --format '{{json .Mounts}}' <容器>：是否挂载了 docker.sock 或宿主机敏感目录

  • 检查 docker-compose 文件中的 privileged: true、network_mode: host、pid: host、敏感目录挂载。

  • 用 Trivy 扫描镜像漏洞，用 docker history --no-trunc 检查镜像层中是否有密钥。

  • 运行 Docker Bench for Security 对照 CIS 基线检查宿主机配置。

#5. 防御清单

  • 使用官方或可信来源的精简基础镜像，固定版本或 digest

  • 使用多阶段构建，运行镜像中不包含编译器、包管理器和调试工具

  • 配置 .dockerignore，镜像中不包含 .git、.env、私钥等

  • 镜像中不包含密钥，构建时使用 BuildKit secret 挂载

  • 容器以非 root 用户运行

  • 不使用 --privileged，删除所有不需要的 capabilities

  • 开启 no-new-privileges，根文件系统只读

  • 设置 CPU、内存、进程数限制

  • 不挂载 Docker socket 和宿主机的敏感目录

  • CI 中扫描镜像和 Dockerfile，高危漏洞阻止发布

  • 定期重建镜像以获取基础镜像的安全更新

  • 宿主机保持更新，可以考虑开启 Docker rootless 模式或 user namespace 重映射

#6. 自测题

Q1. 为什么说容器的隔离性弱于虚拟机？

虚拟机有独立的内核，通过硬件虚拟化与宿主机隔离。容器共享宿主机的内核，隔离依赖于 namespace、cgroup、capabilities、seccomp 等内核机制。内核漏洞或配置不当（特权模式、危险挂载）都可能让容器内的进程影响宿主机。需要强隔离时可以使用 gVisor、Kata Containers 等方案。

Q2. 为什么挂载 /var/run/docker.sock 等于给了容器 root 权限？

通过 Docker socket 可以调用 Docker API，比如创建一个新的特权容器并挂载宿主机的根目录。所以能访问 socket 的容器可以间接完全控制宿主机。即使挂载为只读也没用，因为只读只限制文件本身，并不限制通过 socket 发送 API 请求。

Q3. 容器里以 root 运行有什么风险？已经在容器里了，root 不就只是“容器里的 root”吗？

默认情况下（没有开启 user namespace 重映射或 rootless 模式），容器里的 root 就是宿主机上 UID 为 0 的用户，只是被 capabilities、seccomp 等机制限制了。一旦出现容器逃逸漏洞，或者挂载了宿主机目录，容器内的 root 就能以 root 身份影响宿主机。以非 root 运行可以显著提高攻击难度。

Q4. 多阶段构建对安全有什么好处？

构建阶段需要的编译器、包管理器、源码、构建缓存不会出现在最终镜像里。最终镜像更小，包含的软件包更少，漏洞也更少，攻击者即使进入容器，也缺少可利用的工具。同时降低了构建过程中用到的凭证残留在最终镜像中的风险。

Q5. 为什么镜像扫描“今天没有漏洞”，也需要定期重建镜像？

漏洞会不断被发现。今天干净的镜像，几周后它包含的系统库可能就有了新的 CVE。定期用最新的基础镜像重建，才能获取这些修复。所以要持续扫描运行中的镜像，并且自动化地重建和发布。

#4. 如何识别（评估现有日志能力）

做一次“桌面推演”，问自己这些问题：

  • 我能知道某个管理员权限是谁、在什么时候授予的吗？

#5. 防御清单

  • 记录认证、授权失败、权限变更、高价值操作、管理操作等安全事件

  • 日志使用结构化格式，包含时间（UTC）、用户、来源 IP、操作、结果、请求 ID

  • 日志中不包含密码、令牌、会话 ID、完整的敏感个人信息

  • 对日志输入中的换行等控制字符做处理，防止日志注入

  • 日志实时发送到集中平台，业务系统无权删除或修改

  • 按合规和调查需要设置保留期

  • 所有系统时间同步

  • 为关键场景设置告警，每条告警有负责人和处理手册

  • 定期回顾告警质量，清理误报

  • 制定应急响应流程，并定期演练

应急响应的基本流程（NIST SP 800-61 r2 的经典生命周期；2025 年发布的 r3 改为按 CSF 2.0 的职能组织，核心环节一致）

  1. 准备：明确联系人和职责，准备好工具、权限、处理手册，提前确认日志可用

  2. 检测与分析：确认是否真的是安全事件，判断影响范围和严重程度，记录时间线

  3. 遏制：隔离受影响的系统，吊销泄露的凭证，阻断攻击来源，注意先保全证据

  4. 根除：找到并消除根本原因（漏洞、后门、被篡改的配置）

  5. 恢复：从可信的备份或镜像恢复，加强监控，确认没有复发

  6. 复盘：不追责、只改进，形成具体的改进事项并跟踪落实

#6. 自测题

Q1. 为什么说“只有日志、没有告警”不够？

日志只有在被查看时才有价值。没有告警，攻击可能持续数月都没人发现，直到外部通知或造成明显损失。告警把需要人立即关注的事件主动推送出来，大大缩短从攻击发生到被发现的时间。

Q2. 一条好的安全日志应该包含哪些字段？

至少包括：时间戳（带时区，建议 UTC）、事件类型、结果（成功/失败）、操作主体（用户 ID/服务身份）、来源（IP、User-Agent）、操作对象（资源 ID）、请求 ID 或追踪 ID。目标是能回答“谁、什么时候、从哪里、对什么、做了什么、结果如何”。

Q3. 什么是告警疲劳？如何避免？

告警太多、误报太多，处理人员逐渐习惯于忽略告警，真正重要的告警也会被淹没。避免方法：从少量高置信度的规则开始；每条告警必须可处理、有负责人和处理手册；定期复盘告警，调整阈值或删除没有价值的规则；按严重程度分级，只有高优先级的告警才实时通知。

Q4. 应急响应中，为什么“遏制”时要注意保全证据？

直接关机、重装或删除可疑文件，会丢失内存中的信息、进程状态和攻击者留下的痕迹，导致无法确定攻击的入口、范围和持续时间，也无法确认是否已经彻底清除。合适的做法是先隔离网络、做快照或内存镜像、收集日志，再进行清理。

Q5. 为什么复盘要强调“不追责”？

如果复盘的目的是找人担责，参与者会倾向于隐瞒细节，团队就无法了解真实情况，也就无法找到系统性的改进方向。大多数事件的根源是流程、工具和设计上的缺陷，而不是某个人的失误。不追责的复盘能让信息充分暴露，从而真正防止同类问题再次发生。

#1. 核心要点

  • 生产环境关闭调试模式，错误页面不向用户展示堆栈、SQL、内部路径和版本号。

  • 出错时要安全地失败（fail closed）：鉴权服务超时、校验抛异常时，应该拒绝请求，而不是放行。

  • 加上必要的安全响应头：HSTS、CSP、X-Content-Type-Options、frame-ancestors、Referrer-Policy。

  • 删除或禁用默认账号、示例应用、管理控制台、目录列表，不需要的功能和端口一律关掉。

  • 配置要可重复、可审计：用代码管理配置（IaC），各环境配置一致，变更有记录。

#2. 为什么重要

  • 成因：开发阶段为了方便而开的选项被带到了生产环境；默认配置不安全；环境之间配置不一致；异常处理只考虑了“正常失败”。

  • 影响：调试控制台可能直接执行代码；详细错误信息帮助攻击者了解系统内部；云存储桶被公开导致数据泄露；异常处理放行导致鉴权被绕过。

  • 2025 版变化：安全配置错误从第 5 位升到第 2 位；新增 A10“异常情况处理不当”，专门关注错误处理、逻辑错误和“失败时放行”。

  • 标准：OWASP A02:2025、A10:2025、CWE-209

  • 搜索 debug=True、DEBUG = True、NODE_ENV 未设置为 production、app.use(errorHandler()) 等开发配置。

  • 故意触发错误（访问不存在的路径、传错误类型的参数），看响应中是否有堆栈、SQL、内部路径、框架版本。

  • 检查 except 分支里是否有 return True、pass 后继续执行敏感操作等“失败放行”的写法。

  • 用 Mozilla Observatory 或 curl 检查自己网站的响应头。

  • 检查是否暴露了不该暴露的路径：/.git/、/.env、/actuator、/phpinfo.php、/server-status、Swagger/GraphQL 调试界面。

  • 检查云存储桶、数据库、缓存服务的访问策略是否公开（见 云 IAM）。

#5. 防御清单

  • 生产环境关闭调试模式和开发工具

  • 统一的错误处理：用户看到通用信息和错误 ID，详情只进日志

  • 异常、超时、未知状态一律按拒绝处理（fail closed）

  • 启用 HSTS、CSP（至少包含 frame-ancestors）、X-Content-Type-Options: nosniff、Referrer-Policy

  • 隐藏服务器和框架版本号

  • 关闭目录列表，确保 .git、.env、备份文件等不会被 Web 访问

  • 删除默认账号、示例应用和测试接口，修改所有默认密码

  • 管理后台、监控接口（如 Spring Actuator）不对公网开放，并且要求认证

  • 配置用代码管理（IaC），并用基线扫描工具定期检查

  • 各环境配置保持一致，差异只体现在明确的环境变量里

#6. 自测题

Q1. 为什么生产环境开启 Flask/Werkzeug 的调试模式是严重问题，而不只是“信息泄露”？

Werkzeug 调试器在出错页面上提供交互式控制台，可以执行任意 Python 代码。虽然有 PIN 码保护，但如果 PIN 可以被推算或者泄露，就相当于直接让攻击者在服务器上执行代码。

Q2. 什么是“失败时放行（fail open）”？举一个例子。

系统在出错或无法判断时选择允许操作。例子：调用权限服务超时后，except 分支返回 True；验证码服务不可用时直接跳过验证；签名校验抛异常时被捕获后继续处理请求。安全相关的判断应该在出错时拒绝。

Q3. HSTS 解决什么问题？

HSTS 告诉浏览器在一段时间内只通过 HTTPS 访问这个站点，即使用户输入的是 http:// 或点击了 HTTP 链接。这样可以防止首次请求被中间人降级为 HTTP（SSL 剥离）。加入 HSTS 预加载列表后，连第一次访问也受保护。

Q4. 返回给用户的错误信息里应该包含什么，不应该包含什么？

应该包含：对用户有用的通用描述（如“请求参数无效”），以及一个用于排查的错误 ID。不应该包含：堆栈信息、SQL 语句、内部文件路径、主机名、框架和组件的版本号、第三方服务返回的原始错误。

Q5. 为什么“只在内网访问”不能作为管理接口不设认证的理由？

内网边界并不可靠：SSRF、员工设备被攻陷、VPN 账号泄露、配置错误导致端口暴露到公网，都会让“内网”接口被访问到。零信任的原则是：每个服务都要自己做认证和授权，不依赖网络位置。

方向：基础设施 · 相关标准：CIS Kubernetes Benchmark、Kubernetes Pod Security Standards、NSA/CISA Kubernetes Hardening Guide · 最后更新：2026-10-22

#1. 核心要点

  • RBAC 最小权限：不给应用和用户 cluster-admin，避免在 Role 里使用 *，特别注意 secrets、pods/exec、create pods 这类高危权限。

  • Pod 安全标准：为命名空间启用 Pod Security Admission 的 restricted 级别，禁止特权容器、宿主机命名空间、hostPath 等。

  • 网络策略：Pod 之间默认可以互相访问。为每个命名空间设置默认拒绝的 NetworkPolicy，再按需放行。

  • 服务账号：不需要访问 API Server 的 Pod 关闭令牌自动挂载；每个应用使用独立的服务账号。

  • Secret：Kubernetes Secret 默认只是 Base64 编码，要开启 etcd 静态加密，并限制谁能读取；更推荐结合外部密钥管理服务。

#2. 为什么重要

  • 成因：为了快速跑起来直接给了宽泛的权限；Pod 安全设置没有统一要求；没有网络策略；Dashboard 或 API Server 暴露在公网。

  • 影响：一个 Pod 被入侵后，攻击者可以利用挂载的服务账号令牌调用 API，读取 Secret、创建特权 Pod，最终控制节点和整个集群；在扁平的 Pod 网络中横向移动到数据库等服务。

  • 标准：Pod Security Standards、CIS Kubernetes Benchmark

RBAC

#4. 如何识别

  • 检查高危权限：能读取 secrets、能创建 pods、能 pods/exec、能修改 RBAC 本身、能 impersonate，都可能被用来提升权限。

  • 检查工作负载：privileged: true、hostNetwork、hostPID、hostPath 挂载、以 root 运行、没有资源限制。

  • 运行 kube-bench 对照 CIS 基线检查节点和控制平面配置。

  • 用 trivy k8s 或 Kubescape 扫描集群和 YAML 中的配置问题。

#5. 防御清单

  • API Server 不暴露在公网，或者至少限制来源并开启认证

  • 不给应用和普通用户 cluster-admin，Role 中避免通配符

  • 严格控制 secrets 读取、pods/exec、创建 Pod、修改 RBAC 的权限

  • 每个应用使用独立的服务账号，不需要时关闭令牌自动挂载

  • 业务命名空间启用 Pod Security Admission 的 restricted 级别

  • 容器以非 root 运行，禁止特权提升，删除所有 capabilities，根文件系统只读

  • 每个命名空间设置默认拒绝的 NetworkPolicy，再按需放行

  • 开启 etcd 静态加密，或使用外部密钥管理（如 External Secrets Operator + 云 KMS）

  • 开启 API Server 审计日志

  • 及时升级 Kubernetes 版本和节点系统

  • 镜像只从可信仓库拉取，可以用准入控制器（如 Kyverno、OPA Gatekeeper）强制执行策略

  • 所有工作负载设置资源请求和限制

#6. 自测题

Q1. 为什么“能创建 Pod”这个权限很危险？

能创建 Pod 的主体可以创建一个特权 Pod、挂载宿主机根目录，或者挂载该命名空间里任意服务账号的令牌和任意 Secret，从而间接获得这些权限，甚至控制节点。如果没有 Pod 安全标准或准入策略的限制，“创建 Pod”几乎等同于获得节点的 root 权限。

Q2. Kubernetes Secret 是加密存储的吗？

默认不是。Secret 在 API 中以 Base64 编码表示，在 etcd 中默认以明文存储。需要配置 etcd 静态加密（最好使用 KMS 提供方）才会加密存储。即便如此，拥有 Secret 读取权限的主体仍然可以通过 API 读到明文，所以 RBAC 控制同样重要。

Q3. 为什么建议关闭 automountServiceAccountToken？

默认情况下 Pod 会挂载服务账号令牌，应用被入侵后，攻击者可以用这个令牌调用 API Server。大部分业务应用根本不需要访问 API Server，关闭自动挂载可以消除这条攻击路径。确实需要时，再为它单独开启，并授予最小权限。

Q4. 创建了 NetworkPolicy 但没有效果，可能是什么原因？

常见原因：集群使用的 CNI 插件不支持 NetworkPolicy（比如某些基础的 flannel 配置），这时策略对象可以创建但不会被执行；podSelector 的标签写错，没有选中目标 Pod；只写了 Ingress 而问题出在 Egress，或者反过来。

Q5. Pod 安全标准中的 privileged、baseline、restricted 三个级别有什么区别？

privileged 不做任何限制，用于系统级组件。baseline 阻止已知的提权配置，如特权容器、宿主机命名空间、hostPath 等，兼容大多数应用。restricted 在 baseline 的基础上进一步要求遵循加固最佳实践：必须以非 root 运行、禁止特权提升、删除所有 capabilities、必须设置 seccomp 配置等。业务命名空间推荐使用 restricted。

#1. 核心要点

  • 密钥不进代码、不进仓库、不进镜像。代码仓库会被复制、Fork、备份，进去了就很难彻底清除。

  • 使用集中的密钥管理服务（如 HashiCorp Vault、AWS Secrets Manager、GCP Secret Manager、Azure Key Vault），运行时获取。

  • 优先使用短期凭证和工作负载身份（如云上的实例角色、OIDC 联合身份），尽量不用长期的静态密钥。

  • 每个服务、每个环境使用独立的凭证，权限最小，能单独轮换和吊销。

  • 密钥泄露后的第一件事是吊销并更换，而不是删除提交记录。删除历史只是善后，不能替代吊销。

#2. 为什么重要

  • 成因：图方便把密钥写进配置文件；.env 被误提交；调试时把令牌打进日志；Docker 镜像层里残留了密钥；CI 日志打印了环境变量。

  • 影响：公开仓库里的云密钥可能在几分钟内被自动化工具发现并滥用，导致数据泄露、资源被用来挖矿、高额账单。

  • 标准：CWE-798、CWE-532

#4. 如何识别

  • 用秘密扫描工具扫描当前代码和完整的 Git 历史：gitleaks git .、trufflehog git file://.（见 安全工具）。

  • 搜索关键词：password =、secret、api_key、token、BEGIN RSA PRIVATE KEY、AKIA（AWS 访问密钥前缀）、sk_live_、ghp_。

  • 检查 Docker 镜像历史：docker history --no-trunc <image>，看构建指令里有没有密钥。

  • 检查 CI 配置：密钥是否用平台的加密变量，日志里是否会打印出来，是否在 Pull Request（尤其是来自 Fork 的）中暴露。

  • 检查日志：搜索日志中是否出现 Authorization、password、完整的令牌。

#5. 防御清单

  • 代码、配置文件、镜像中不包含任何密钥

  • .gitignore 包含 .env、私钥等文件，仓库只保留 .env.example

  • 开启 pre-commit 秘密扫描，并在 CI 中再扫描一次

  • 开启代码托管平台的秘密扫描和推送保护（如 GitHub Secret Scanning、Push Protection）

  • 密钥存放在密钥管理服务中，运行时获取

  • 优先使用工作负载身份和 OIDC，避免长期静态密钥

  • 每个服务、每个环境使用独立凭证，并且只授予最小权限

  • 制定轮换周期，并验证轮换过程不会导致服务中断

  • 日志和错误信息中对敏感字段做脱敏

密钥泄露处置流程

  1. 立即吊销/更换泄露的密钥（这是第一步，不要等）

  2. 检查该密钥的使用日志（如 AWS CloudTrail），确认泄露期间是否被滥用

  3. 评估影响范围，按需通知相关方

  4. 清理仓库历史（git filter-repo），并通知所有协作者重新克隆

#6. 自测题

Q1. 发现密钥被提交到了公开仓库，先删除提交记录还是先吊销密钥？为什么？

先吊销。公开仓库的内容可能已经被自动化工具抓取、被 Fork 或缓存，删除历史无法保证密钥没有被获取。只有吊销才能让泄露的密钥失效。清理历史是之后的善后工作。

Q2. 在 Dockerfile 中 COPY 了密钥文件，然后在下一条 RUN 里删掉它，镜像里还有密钥吗？

有。镜像由多层组成，每一层都会被保存下来。COPY 那一层里仍然包含这个文件，任何拿到镜像的人都可以提取出来。应该使用 BuildKit 的 --mount=type=secret，或者多阶段构建，并且确保最终镜像中不包含构建时用到的密钥。

Q3. 环境变量存放密钥是否就绝对安全？

比硬编码好，但有局限：环境变量可能被调试页面、错误报告、崩溃转储、/proc/<pid>/environ 读到，也可能被子进程继承，或被 CI 日志打印出来。更好的做法是从密钥管理服务按需获取，或者以文件形式挂载，并限制访问权限。

Q4. 为什么推荐用 OIDC 联合身份代替在 CI 中保存云平台的访问密钥？

OIDC 方式下，CI 每次运行时用平台签发的身份令牌换取有效期很短的临时凭证，仓库中不保存长期密钥，也就不存在“长期密钥泄露”的问题。还可以在云端的信任策略中限制只有特定仓库、特定分支才能获取凭证。

Q5. 如何避免密钥出现在日志中？

使用结构化日志，并在日志处理层统一对敏感字段（password、token、Authorization、Cookie 等）脱敏；不要整体记录请求头和请求体；错误处理时不把包含连接串的异常信息原样输出；CI 中使用平台的掩码功能；定期抽查日志。

认证与会话（Authentication & Session）

约 5 分钟 7 段代码 1330 字
安全清单速查

方向：Web · 相关标准：OWASP A07:2025、CWE-287、CWE-384（会话固定）、CWE-916（密码哈希强度不足）、NIST SP 800-63B · 最后更新：2026-10-22

#1. 核心要点

  • 密码只存慢哈希（Argon2id、scrypt、bcrypt），绝不明文存储，也不要用 MD5/SHA-256 这类快速哈希直接存。

  • 登录成功后重新生成 Session ID，防止会话固定攻击；登出时在服务端销毁会话。

  • Session Cookie 设置 HttpOnly、Secure、SameSite，并设置合理的过期时间。

  • JWT 要固定允许的算法，必须校验签名、exp、iss、aud。不要把敏感数据放进 JWT 的载荷里，载荷只是 Base64 编码，并没有加密。

  • 关键账号和敏感操作启用 MFA，并对登录接口做限速，防止撞库和暴力破解。

#2. 为什么重要

  • 成因：自研认证流程中细节很多，任何一处疏忽（错误提示区分“用户不存在”和“密码错误”、找回密码令牌可预测、JWT 不验签）都可能导致账号被接管。

  • 影响：账号接管、批量盗号（撞库）、长期潜伏（会话不失效）。

  • 常见形态：弱密码哈希、无登录限速、会话固定、JWT 接受 alg: none 或算法混淆、找回密码令牌泄露或不过期。

  • 标准：OWASP A07:2025、NIST SP 800-63B

密码存储

#4. 如何识别

  • 搜索密码相关代码：md5(、sha1(、sha256( 出现在密码处理附近就要警惕。

  • 检查登录接口：有没有限速或锁定，错误提示是否统一，登录成功后是否重新生成会话。

  • 检查 Cookie：浏览器开发者工具的 Application 面板里，看 Session Cookie 是否有 HttpOnly、Secure、SameSite。

  • 检查 JWT：解码 verify_signature=False、algorithms 参数缺失或接受多种算法、密钥硬编码或强度很弱、没有过期时间。

  • 检查找回密码流程：令牌是否用 CSPRNG 生成，是否一次性、是否短期过期，修改密码后其他会话是否失效。

#5. 防御清单

  • 密码使用 Argon2id / scrypt / bcrypt 存储

  • 密码策略参考 NIST：最小长度不低于 8 位（建议支持 64 位以上），检查是否在已泄露密码库中，不强制定期更换

  • 登录、注册、找回密码接口有限速和异常检测

  • 登录失败提示统一，不泄露账号是否存在

  • 登录成功、权限变化时重新生成会话 ID

  • 登出和修改密码时在服务端使会话失效

  • Session Cookie 设置 HttpOnly、Secure、SameSite

  • JWT 固定算法，校验签名、exp、iss、aud，密钥足够强且不硬编码

  • 找回密码令牌随机、一次性、短期有效，只存储令牌的哈希值

  • 管理员和高权限账号强制 MFA，优先支持 TOTP 或 WebAuthn/Passkey

#6. 自测题

Q1. 为什么不能用 SHA-256 加盐来存储密码？

SHA-256 是为“快”设计的，GPU 每秒可计算数十亿次。盐只能防彩虹表，不能减慢对单个哈希的暴力破解。Argon2id、scrypt、bcrypt 是专门设计的慢哈希，有可调的计算成本（Argon2id 和 scrypt 还有内存成本），能大幅提高离线破解的代价。

Q2. 什么是会话固定攻击？怎么防？

攻击者先拿到一个有效的会话 ID，然后诱导受害者用这个 ID 登录。如果服务端在登录后没有更换会话 ID，攻击者就可以用同一个 ID 冒充受害者。防御：登录成功后清除旧会话并签发新的会话 ID。

Q3. HttpOnly 能防止 XSS 吗？

不能防止 XSS 本身，只能防止脚本通过 document.cookie 读取 Cookie。攻击者的脚本仍然可以在受害者的页面里以受害者身份发起请求。修复 XSS 要靠输出编码和 CSP，HttpOnly 只是减轻影响的手段。

Q4. 服务端解码 JWT 时没有指定 algorithms 参数，可能有什么风险？

如果库根据令牌头部的 alg 字段选择算法，攻击者可以把算法改成 none 跳过签名，或者在 RS256 场景下改成 HS256，用公钥当作 HMAC 密钥伪造签名（算法混淆）。所以必须在服务端固定允许的算法。现在主流库大多要求显式传入 algorithms，但仍要确认。

Q5. 用户修改密码后，应该怎么处理已有的会话和令牌？

应该让该用户其他设备上的会话失效（可以保留当前会话），撤销已签发的刷新令牌。如果使用无状态 JWT，可以通过缩短访问令牌有效期、维护令牌版本号或撤销列表来实现。否则攻击者偷到的旧会话在改密后仍然有效。

#1. 核心要点

  • 审计不是逐行通读，而是先建立模型再找重点：系统有哪些入口、哪里是信任边界、敏感数据和危险操作在哪里。

  • 主线是数据流：从 Source（不可信输入）跟踪到 Sink（危险操作），检查中间有没有合适的校验、编码或参数化。

  • 第二条主线是控制流：每个敏感操作之前，是否检查了认证和授权。

  • 工具负责广度（找出所有可疑点），人负责深度（判断业务逻辑、权限模型这些工具不懂的问题）。

#2. 为什么重要

#6. 自测题

Q1. 什么是 Source 和 Sink？为什么审计时常从 Sink 开始反推？

Source 是不可信数据进入系统的位置（请求参数、请求头、文件、外部 API 响应等），Sink 是使用数据执行危险操作的位置（SQL 执行、命令执行、文件读写、反序列化等）。Sink 的数量通常比 Source 少得多，而且更容易用搜索找全，所以从 Sink 反推“参数是否可控”效率更高。

Q2. 为什么扫描工具很难发现越权漏洞？

越权漏洞的代码在语法和数据流上通常都“正常”：参数化查询、没有危险函数。问题在于业务语义——查询少了一个归属条件。工具不知道“这个订单应该只有它的主人能看”，需要人结合业务和权限模型来判断。

Q3. 数据库里取出的数据可以视为可信数据吗？

不能一概而论。如果数据最初来自用户输入（用户名、评论、文件名），它仍然是不可信的，输出到页面时要编码，拼进查询时要参数化，否则会导致存储型 XSS 或二次注入。判断可信与否要看数据的最初来源，而不是它当前存在哪里。

Q4. 列举三种常见的业务逻辑漏洞。

例如：下单时数量或金额传负数导致退款或余额增加；并发请求重复领取优惠券或重复提现（竞态条件）；多步骤流程（如找回密码、支付）可以跳过中间步骤直接请求最后一步；客户端提交价格而服务端没有重新计算。

Q5. 一份合格的漏洞报告应该包含哪些内容？

标题与严重等级、CWE 分类、代码位置、成因说明、影响范围、复现步骤（前置条件和请求示例）、修复建议（最好有示例代码），必要时附上参考资料。目标是让开发者不需要再来问你就能理解并修复。

输入输出处理（校验、编码、反序列化、文件路径）

约 6 分钟 8 段代码 1582 字
安全清单速查

方向：安全编码 · 相关标准：CWE-20（输入校验不当）、CWE-22（路径遍历）、CWE-434（危险文件上传）、CWE-502（不可信数据反序列化）、OWASP A08:2025 · 最后更新：2026-10-22

#1. 核心要点

  • 入口校验，出口编码：数据进入系统时按白名单校验格式，数据离开系统（输出到 HTML、SQL、Shell、日志）时按目标上下文编码或参数化。两者都要做，互相不能替代。

  • 校验用白名单（允许什么），不要用黑名单（禁止什么）。校验在服务端完成。

  • 不要反序列化不可信数据：pickle、yaml.load（非安全模式）、Java 原生序列化、PHP unserialize 都可能直接导致代码执行。只用 JSON 这类纯数据格式。

  • 文件路径：不要用用户输入拼路径。实在需要时，规范化后检查结果是否仍在允许的目录内。

  • 文件上传：文件名由服务端生成，类型按内容校验，文件存在 Web 根目录之外或独立的存储里，限制大小。

#2. 为什么重要

  • 成因：相信客户端已经做过校验；用字符串操作处理路径；为了方便直接序列化对象；按扩展名判断文件类型。

  • 影响：路径遍历可以读到配置文件和密钥；不安全的反序列化通常等于远程代码执行；上传可执行文件到 Web 目录可以导致服务器被控制；超大输入导致拒绝服务。

  • 标准：CWE-22、CWE-434、CWE-502

#3. 常见错误 vs 正确做法

用 Schema 做输入校验（Pydantic）

路径遍历

更好的做法是：数据库里只存服务端生成的文件 ID，用户只能通过 ID 访问，根本不接触路径。

文件上传

下载用户上传的文件时，设置 Content-Disposition: attachment 和准确的 Content-Type，加上 X-Content-Type-Options: nosniff。最好用独立的域名提供用户上传的内容，避免与主站同源。

反序列化

如果确实需要在系统之间传递结构化对象，用 JSON / Protocol Buffers，并且对数据做签名（HMAC）防止篡改。

XML：关闭外部实体

输出到日志：防止日志注入

#4. 如何识别

  • 搜索路径操作：open(、os.path.join、send_file、send_from_directory、fs.readFile、path.join，看参数里是否有用户输入。

  • 搜索反序列化：pickle.loads、yaml.load(、marshal.loads、shelve、ObjectInputStream、unserialize(、node-serialize。

  • 检查文件上传：文件名是否来自客户端，类型是否只看扩展名，存储位置是否可以被 Web 直接执行。

  • 检查 XML 解析是否禁用了外部实体（DTD）。

  • 检查解压缩代码：解压出的文件名可能带 ../（Zip Slip），解压后的大小可能远大于压缩包（压缩炸弹）。

  • 检查是否有输入长度、数量、嵌套深度的限制。

#5. 防御清单

  • 所有接口用 Schema（Pydantic、Zod、JSON Schema 等）在服务端做白名单校验

  • Schema 拒绝未定义的字段

  • 对字符串长度、数组大小、请求体大小、嵌套深度设置上限

  • 不使用用户输入拼接文件路径；必要时规范化并检查是否在允许目录内

  • 上传文件名由服务端生成，按内容校验类型，限制大小，存储在 Web 根目录之外

  • 用户上传的内容从独立域名提供，设置 nosniff 和合适的 Content-Disposition

  • 不反序列化不可信数据，只用 JSON 等纯数据格式；YAML 用 safe_load

  • 解析 XML 时禁用 DTD 和外部实体

  • 解压缩时检查每个条目的路径和解压后的总大小

  • 输出时按上下文编码（HTML、URL、JavaScript、SQL 参数化、Shell 参数数组）

#6. 自测题

Q1. 已经在前端用 JavaScript 校验了表单，服务端还需要校验吗？

需要。前端校验只是为了用户体验，攻击者可以直接用工具发请求，完全绕过前端。安全相关的校验必须在服务端完成。

Q2. 用 filename.replace("../", "") 防路径遍历有什么问题？

很容易绕过。例如 ....// 在替换一次后会变成 ../；还有 URL 编码、Windows 反斜杠、绝对路径（/etc/passwd 直接覆盖了基础路径）、符号链接等情况。正确做法是规范化路径之后，检查最终路径是否在允许的目录下，或者干脆不让用户控制路径。

Q3. 为什么 pickle.loads 处理不可信数据很危险？

pickle 格式可以描述“调用某个可调用对象并传入参数”来重建对象，反序列化时这些调用会被执行。所以构造的 pickle 数据可以在反序列化时执行任意代码。Python 官方文档明确警告不要 unpickle 不可信的数据。

Q4. 判断上传文件类型时，为什么不能只看扩展名或 Content-Type 请求头？

两者都由客户端控制，可以随意伪造。应该检查文件内容（文件头魔数，或者用对应的库尝试解析，比如用 Pillow 打开图片），并且只允许少数明确需要的类型。即便如此，也要把文件存在不会被当作代码执行的位置。

Q5. “入口校验”和“出口编码”为什么要同时做？

入口校验保证数据符合业务预期（格式、长度、范围），但很多合法数据本身就包含特殊字符，比如名字里的单引号 O'Brien、评论里的 <。入口无法也不应该把这些都拒绝掉。出口编码保证数据在特定上下文（HTML、SQL、Shell）里只被当作数据。两者解决的是不同的问题。

#1. 核心要点

  • 你的应用里绝大部分代码来自依赖，依赖的安全就是你的安全。2025 版 Top 10 新增“软件供应链失败”并排在第 3 位。

  • 锁定版本：提交锁文件（package-lock.json、poetry.lock、uv.lock、go.sum），CI 中用 npm ci 这类严格按锁文件安装的命令。

  • 持续扫描已知漏洞（SCA），并用 Dependabot / Renovate 自动发起升级。

  • 审查新依赖：维护是否活跃、下载量、维护者、权限需求；警惕名字相似的仿冒包（typosquatting）和依赖混淆。

  • CI/CD 也是供应链的一部分：第三方 Action 固定到提交 SHA，令牌权限最小化，谨慎处理来自 Fork 的 Pull Request。

#2. 为什么重要

  • 成因：依赖树很深，开发者不清楚自己到底引入了什么；版本范围过宽导致自动拉取到被篡改的新版本；CI 有发布权限但防护薄弱。

  • 影响：已知漏洞被利用；恶意包在安装时（postinstall 脚本）窃取环境变量和密钥；构建系统被入侵后，发布的产物本身就带有后门，影响所有下游用户。

  • 常见形态：

    • 已知漏洞：使用了有 CVE 的旧版本

    • 仿冒包：reqeusts 冒充 requests

    • 依赖混淆：公共仓库上出现了与公司内部包同名、版本号更高的包

    • 维护者账号被盗或恶意维护者：合法包的新版本被植入恶意代码

    • CI 被利用：不受信任的输入在有权限的工作流中执行

#6. 自测题

Q1. 什么是依赖混淆（Dependency Confusion）？如何防御？

公司内部有一个私有包 internal-utils，攻击者在公共仓库发布同名但版本号更高的包。如果包管理器同时查询内部仓库和公共仓库，并选择版本号最高的那个，就会安装攻击者的包。防御：内部包使用作用域（如 @mycompany/）；配置包管理器让特定作用域只从内部仓库获取；在公共仓库上预先注册同名包占位。

Q2. 为什么建议把 GitHub Action 固定到提交 SHA，而不是版本标签？

标签是可以移动的。如果 Action 的仓库被攻击，攻击者可以把 v4 标签指向包含恶意代码的提交，所有引用 @v4 的工作流下次运行时就会执行恶意代码。提交 SHA 不可变，可以保证运行的始终是审查过的代码。

Q3. npm install 和 npm ci 的区别是什么？为什么 CI 中应该用 npm ci？

npm install 会在版本范围内解析依赖，可能更新锁文件、安装到和开发者本地不一样的版本。npm ci 严格按照锁文件安装，锁文件与 package.json 不一致时直接报错，并且会先删除 node_modules。CI 中使用 npm ci 保证构建可重复，不会意外引入未审查的新版本。

Q4. SBOM 有什么用？

SBOM（软件物料清单）列出了软件包含的所有组件及其版本。当一个新的高危漏洞公开时，可以快速查出哪些产品、哪些版本受影响，而不需要逐个项目排查。它也是很多合规要求和客户审核的内容。

Q5. 一个依赖库被发现有高危漏洞，但你的代码没有调用到存在漏洞的函数，还需要升级吗？

一般仍然建议升级，或者至少记录风险评估结论。原因：判断“是否调用到”可能有误（间接调用、未来的代码改动）；扫描工具会持续报警，影响对其他问题的关注；有些工具（如 govulncheck）可以做可达性分析，帮助确定优先级，但不能作为永远不升级的理由。确实无法升级时，要记录原因并设定复查时间。
