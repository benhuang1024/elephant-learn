#学习建议

  1. 边读边跑。每个 code/ 工程都能独立运行；把测试当可执行笔记，改一处断言看它为什么失败。

  2. 用请求生命周期串知识：uvicorn → middleware → 路由 → 依赖（Session/认证）→ Service（事务）→ SQLAlchemy → 序列化 → 响应。能讲清楚这条链，就掌握了 shop-api。

  3. 不要逐行翻译 PHP。先问“这里的类型边界/并发模型/事务边界是什么”，再写 Python。尤其是 Session、GIL、异步——照抄 PHP 习惯会出事。

  4. 类型先于框架。Pydantic 管边界，mypy 管内部；这比背 FastAPI 语法更有长期价值。

  5. 读框架源码：Depends 的解析、SQLAlchemy Session.flush、selectinload 的 SQL，比十篇博客有用。

  6. 一个纵切面：选一个业务用例（如下单），从路由、校验、事务、锁、测试、日志、Docker 全部打通，再扩展。

#浮点数与金额

金额三原则：

  1. 入参用字符串构造 Decimal：Decimal(str(amount)) 或直接接收 "19.90"。

  2. 在值对象里统一 quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)。

  3. 不要用 float 做累计，也不要在业务代码里散落 round()。

完整实现见 money.py：frozen=True 保证不可变，__post_init__ 统一精度，__add__/__mul__ 保持币种一致。

#6. 函数

PHP 的 interface 是名义类型：必须 implements。Python 的 Protocol 只看“形状”：

#7. 多继承与 MRO vs trait

  • Python 支持多继承，方法解析顺序是 C3 线性化（Order.__mro__ 可查看）。

  • mixin 应是“小、无状态、可组合”的；不要用多继承做业务分类。

  • 与 PHP trait 的差异：trait 是编译期复制方法，Python 是真正的继承链；super() 会沿 MRO 继续调用。

  • 菱形继承时 super().__init__() 的协作式初始化容易出错；优先组合。

#8. 属性与封装

@property ≈ PHP 的 getter + 计算属性，但调用处不变（product.stock，不是 product.getStock()）。

  • 只读计算属性用 @property，不要加 setter。

  • 需要缓存的计算属性用 functools.cached_property（要求实例有 __dict__，slots 类不行）。

  • 真正的不可变用 frozen dataclass。

#9. 继承、super() 与构造

  • Python 3 的 super() 不需要参数。

  • 子类 __init__ 不会自动调用父类；必须显式。

  • 方法重写不需要注解；类型检查器会检查签名兼容性（参数逆变、返回值协变）。

#11. __eq__ 与 __hash__ 的陷阱

这是 PHP 架构师最需要“重装系统”的一章。PHP-FPM 的 share-nothing 模型帮你屏蔽了绝大多数并发问题；Python 应用是常驻进程，你必须自己决定并发模型、连接池、状态生命周期和优雅退出。

#1. PHP-FPM vs 常驻 Python 进程

维度PHP-FPMPython（uvicorn/gunicorn）
进程模型一请求一进程（或复用 worker 进程但每请求重建上下文）进程启动后长期运行，处理很多请求
内存状态请求结束即释放模块级变量、缓存、连接池跨请求存活
并发进程/线程池，由 FPM 管理线程池 / 事件循环 / 多进程，由你选
数据库连接每请求新建，通常无池进程内连接池，必须管理生命周期
内存泄漏请求结束自动回收长期累积，必须监控
全局可变状态天然隔离危险，并发请求共享
优雅重启平滑重启 worker需要处理信号、排空连接
阻塞影响只阻塞当前请求阻塞事件循环会拖垮同进程所有请求

#常驻进程的三条纪律

  1. 不要在模块级保存请求相关状态。用 contextvars（请求 ID、租户）或显式参数。

  2. 连接池按进程创建，进程退出时 dispose；fork 后不要复用父进程连接。

  3. 信号处理与优雅退出：停止接收新请求、等待在途请求、关闭连接池。

FastAPI 的 lifespan 就是做第 2、3 条的（见 main.py）。

#2. GIL 是什么

CPython 的全局解释器锁保证同一时刻只有一个线程执行 Python 字节码：

  • I/O 阻塞时释放 GIL：等待网络、磁盘、DB 时其他线程可以跑。

  • 纯 Python CPU 计算不释放：多线程做计算不会更快，甚至更慢。

  • C 扩展（NumPy、数据库驱动）在长计算里可能主动释放 GIL，视实现而定。

Python 3.14 的现状：

  • 默认构建仍然有 GIL。

  • 提供 free-threaded 构建（python3.14t），可以真正并行线程，但：

    • 需要单独安装/选择解释器；

    • 第三方扩展（尤其 C 扩展）需要兼容；

    • 单线程性能通常略低；

    • 生态仍在迁移。

  • 本仓库使用默认 GIL 构建（sys._is_gil_enabled() 为真）。

架构结论：不要把 free-threaded 当作默认方案。先用进程/异步解决问题，有明确收益再评估。

worker 数怎么定：

关键点：

  • Engine 必须在进程内创建一次，不能每请求 create_engine（会耗尽连接）。

#9. 常驻进程的五个坑

  1. 模块级缓存无上限：字典当缓存会无限增长；用 LRU/TTL 或外部缓存。

  2. 请求状态泄漏：不要用模块级变量保存当前用户/租户；用 contextvars。

  3. fork 后复用连接：gunicorn preload 时，父进程创建的连接被 fork 共享会导致协议错乱；在 worker 内创建 Engine。

  4. 阻塞事件循环：同步 HTTP 客户端、time.sleep、CPU 计算。

  5. 退出不优雅：没有处理 SIGTERM，正在处理的事务被硬杀；配置 graceful timeout，关闭连接池。

#1. GIL 到底锁了什么（以及没锁什么）

说法真相
「GIL 让 Python 多线程完全没用」错。IO 等待时 GIL 会释放：多线程做 IO 并发仍然有效
「GIL 让 CPU 密集多线程变慢」对：同一时刻只有一个线程执行字节码，CPU 密集多线程 ≈ 单核 + 切换开销
「asyncio 绕过了 GIL」错：asyncio 是单线程协作调度，根本不需要多核；它解决的是 IO 并发，不是 CPU 并行
「3.13+ 没有 GIL 了」半对：free-threaded 构建（python3.13t）可选去掉 GIL，但生态 C 扩展兼容性仍是代价；默认构建仍有

CPU 密集的正解和 Node 一样：换进程（multiprocessing / ProcessPoolExecutor / 独立 worker 服务），或换实现（C 扩展 / numpy 向量化 / Rust 扩展）。

PHP 对照：PHP-FPM 天然多进程，所以你从来没遇到过 GIL 问题——你的「绕过方案」就是平台默认。Python 需要显式选择。

#3. 容量数学：uvicorn worker × 并发，与 fpm 对齐

两个 PHP 老手最容易错的点：

  1. Django/FastAPI 常驻后内存不释放：OPcache 式的「请求结束全释放」没有了。模块级缓存、ORM identity map、未关闭的 client 都会累积。防线同 Node：上限 + TTL + 显式 close。

  2. 同步 ORM 混进 async 视图：SQLAlchemy 同步 Session 在 async 路由里调用 = 阻塞 loop。要么全 async（async_sessionmaker + await session.execute），要么把同步段扔进 run_in_executor / 独立线程池并限流。仓库 shop-api 走全 async 路线，评审时 grep 路由里的同步 Session() 是高效 finding。

#2. Engine 与 Session

对象生命周期职责

Session请求/用例级身份映射、变更跟踪、事务

Session ≈ Doctrine 的 EntityManager / JPA 的持久化上下文，不是数据库连接本身。它持有：

  • Identity Map：同一 Session 里 get(Product, 1) 两次返回同一对象。

  • Unit of Work：记录新增/修改/删除，flush 时统一发 SQL。

  • 事务边界：commit/rollback。

请求级依赖：

Session.close() 会回滚未提交事务并释放连接；所以 Service 必须显式 commit。

#连接池

  • pool_pre_ping：取连接前 ping 一次，避免数据库重启后的坏连接（有少量开销）。

  • pool_recycle：防止中间件/数据库断开空闲连接（如 30 分钟）。

  • 多 worker：worker × (pool_size + max_overflow) 要小于 DB 连接上限。

#3. Typed ORM 模型

  • Mapped[T] + mapped_column 让 mypy 知道属性类型。

  • Base 继承 DeclarativeBase，Base.metadata 是 Alembic 的入口。

  • 主键类型 BigInteger().with_variant(Integer, "sqlite")：SQLite 的自增主键必须是 INTEGER。

  • Decimal + Numeric(12, 2)：金额不要用 float。

  • 领域方法（deduct）放在模型里，规则不散落。

#关系与聚合

  • cascade="all, delete-orphan"：保存/删除订单时级联处理明细。

  • 明细保存 SKU 与单价快照：商品后续改名调价不影响历史订单。

  • 聚合根负责一致性：总价与库存扣减在 Order.add_item 里完成。

#懒加载的默认值

SQLAlchemy 关系默认 lazy="select"：访问 order.items 才发 SQL。这在 Web 序列化时非常危险：

  • Session 关闭后再访问 → DetachedInstanceError；

  • 列表 N 个订单 → N 次附加查询（N+1）；

  • 异步 Session 下更严格。

解决：在查询处显式 selectinload / joinedload，见第 7 节。

#4. Unit of Work：没有 save()

提交时 SQLAlchemy：

  1. 检测 Session 中所有脏对象；

  2. 按依赖顺序 flush（INSERT/UPDATE/DELETE）；

  3. 生成 UPDATE products SET ... WHERE id=... AND version=...；

  4. 提交事务。

与框架对照：

行为EloquentDoctrineSQLAlchemy
修改后保存$model->save()自动（flush）自动（flush）
新建Model::create()persist()session.add()
删除$model->delete()remove()session.delete()
查询Model::find()find()session.get()
事务DB::transaction()flush()+commit()commit()

不要在每个 Service 方法里 session.add(existing_object)；对已持久化对象是多余的。

#expire_on_commit=False 的取舍

默认 True：commit 后对象属性过期，下次访问重新查库（保证读到最新值）。本项目设为 False：

  • 响应序列化在 commit 之后，避免额外查询与 Detached 问题；

  • 代价是 commit 后对象可能是旧值（例如数据库触发器/其他会话的修改）；

  • 对“提交后立即返回自己刚写入的数据”的 API 是合理选择。

理解这个开关，比记住配置值重要。

#5. 事务

#一个用例一个事务

任何一步失败（库存不足、商品不存在、乐观锁冲突）都会回滚：

  • 已扣的库存恢复；

  • 已插入的订单/明细消失；

  • 不会出现“扣了库存但没订单”。

测试 test_transactions.py 明确验证了这一点。

#嵌套事务

  • session.begin_nested() → SAVEPOINT，适合“部分失败不影响外层”。

  • 不要在 Service 里随便嵌套 begin()；Session 已有事务时会报错。

  • Web 端推荐：依赖负责 Session，Service 负责 commit/rollback，不在路由里写事务。

#隔离级别

PostgreSQL 默认 READ COMMITTED；MySQL 默认 REPEATABLE READ。跨库迁移时要显式确认：

库存扣减这类“读-改-写”要么用乐观锁，要么用 SELECT ... FOR UPDATE（悲观锁），不能只依赖默认隔离级别。

#6. 乐观锁

行为：

  1. 读取时带出 version。

  2. UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?。

  3. 若 rowcount == 0，SQLAlchemy 抛 StaleDataError。

  4. Service 捕获并转成 HTTP 409。

为什么不用“先查再比”：

数据库层面的比较是原子的，应用层的“查完再比”有竞态窗口。

对照：

方案适用代价
乐观锁 version冲突少、读多写少冲突时重试
悲观锁 FOR UPDATE冲突多、强一致锁等待、死锁风险
原子 SQL（stock = stock - ? WHERE stock >= ?）简单扣减业务逻辑受限
队列串行化高冲突热点架构复杂

version 从 0 开始是为了与 Java @Version 对齐；SQLAlchemy 默认从 1 开始，所以用了自定义生成器。

#7. N+1 与预加载

反例：

1 + N 次查询。解决：

  • selectinload：先查主表，再用 WHERE order_id IN (...) 批量查关联，固定 2 条 SQL。

  • joinedload：一条 SQL JOIN，适合一对一/多对一；一对多会放大结果集。

  • subqueryload：另一种批量策略，通常 selectin 更优。

  • raiseload("*")：禁止懒加载，开发期尽早暴露问题。

test_queries.py 用事件监听统计 SQL：懒加载 3 个订单触发 3 次查询，selectinload 固定 2 次。

#序列化与 N+1

即使查询用了 selectinload，如果响应模型里又访问了未加载关系，仍会触发查询。原则：

  • 查询层明确“这个用例需要哪些关系”；

  • 响应模型只读已加载字段；

  • 用测试统计查询数，防止回归。

#6. 进程与 worker

决策：

应用类型worker 建议线程/连接
异步 I/O 密集核数~2×核数每 worker 一个事件循环
同步端点 + 同步 DB核数~2×核数线程池 × 连接池
CPU 密集进程数≈核数避免与 Web 混部

连接数守恒：

必须小于数据库 max_connections，并留 20% 余量。否则高峰期会雪崩。

优雅退出：

  • 接收 SIGTERM 后停止接新请求；

  • 等待在途请求完成（graceful timeout）；

  • 关闭连接池、队列消费者；

  • 超过超时时间强制退出。

本项目的 lifespan 在关闭时 database.dispose()；容器编排需给足 terminationGracePeriodSeconds。

  1. 向后兼容迁移（加列可空/默认值、建索引用并发）。

  2. 部署新代码（新旧代码都能跑）。

  3. 数据回填（后台任务/分批）。

  4. 收紧约束（非空/唯一/删旧列）。

禁止：

  • 应用启动自动 create_all；

  • 先删列再发代码；

  • 无备份直接在生产试迁移。

#2. 模块化单体优先

大多数业务系统不需要微服务。推荐模块化单体：

规则：

  1. 模块内高内聚：数据、规则、接口在一起。

  2. 模块间通过显式接口：Service/事件，不直接跨模块改表。

  3. 共享内核最小化：只放真正通用的基类与工具。

  4. 依赖方向：router → service → repository → model；模型不依赖 Web。

  5. 一个模块一个事务边界；跨模块用事件/最终一致性。

何时拆服务：

  • 独立伸缩需求（例如图像处理）；

  • 独立发布节奏/团队边界；

  • 不同的数据存储/合规要求；

  • 明确的故障隔离收益；

  • 有成熟的观测、部署、契约测试能力。

否则拆服务只会把复杂度从代码搬到网络。

#3. 分层怎么落

以商品用例为例：

Service事务、用例、跨聚合编排HTTP 细节、直接拼 JSON
Repository查询、加载策略、分页业务判断
Model映射、局部领域行为跨聚合编排、外部调用

小项目可以省掉 Repository（Service 直接用 Session）；一旦查询变复杂、需要复用/替换数据源，再引入。不要为了“架构完整”预建空抽象。

#4. 类型边界

架构上把类型分成三层：

边界工具失败处理

原则：

  • 边界强校验，内部强类型，不做重复校验。

  • DTO 与 ORM 分离，API 不随表结构漂移。

  • 金额/时间/ID 用值对象或明确类型，不用裸 float/str 满天飞。

  • 枚举用 StrEnum，数据库/JSON 统一值。

  • Any 是债务，出现就要有理由。

#5. 异步选型

不要问“Python 异步快不快”，要问“我的瓶颈是什么”。

场景建议
CRUD + 同步 ORM，QPS 一般同步端点 + 线程池，简单可靠
高并发外部 API 聚合asyncio + httpx
WebSocket/SSE/流式ASGI 异步
CPU 密集进程池/独立服务，不要塞事件循环
混合Web 同步 + 长任务队列

迁移到异步的隐藏成本：

  • 全链路库要异步（DB、缓存、HTTP、文件）；

  • 事务/连接池语义变化；

  • 调试与性能分析工具不同；

  • 团队需要理解事件循环与取消。

判定标准：同步实现能否在目标 QPS/延迟下达标？能，就不要异步。需要异步时，一次迁一层（先外部调用，再 DB），用压测验证。
