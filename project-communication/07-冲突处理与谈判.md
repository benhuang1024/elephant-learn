# 07 冲突处理与谈判

> 项目中的冲突不可避免。冲突本身不是坏事，**处理不好的冲突**才是。
> 谈判不是你死我活，好的谈判是双方都觉得"可以接受"，并且愿意继续合作。

---

## 1. 冲突的来源

| 冲突类型 | 典型场景 |
|---|---|
| 利益冲突 | 甲方想多要功能少花钱，乙方想控制成本 |
| 认知冲突 | 对需求的理解不一致 |
| 优先级冲突 | 甲方要先做 A，乙方认为先做 B 更合理 |
| 资源冲突 | 多个项目抢同一个人 |
| 风格冲突 | 甲方喜欢面面俱到，乙方喜欢简单直接 |
| 角色冲突 | 甲方业务部和 IT 部意见不一，乙方夹在中间 |
| 情绪冲突 | 积累的不满突然爆发 |

---

## 2. 冲突处理的五种模式（托马斯-基尔曼模型）

```
        高 │  竞争          合作
  坚持     │ (我赢你输)    (双赢)
  自己     │
  的利益   │       妥协
           │     (各让一步)
        低 │  回避          迁就
           │ (都不处理)    (我输你赢)
           └──────────────────────
             低   关注对方利益   高
```

| 模式 | 什么时候用 | 乙方示例 |
|---|---|---|
| **竞争** | 原则问题、安全合规、对方明显错误且后果严重 | "这个改动会导致数据泄露风险，违反等保要求，我们不能这么做。" |
| **合作** | 双方利益都很重要、有时间深入沟通 | 一起找到既满足业务需求又不增加成本的方案 |
| **妥协** | 时间紧、双方势均力敌、需要快速达成 | "这个功能我们做，工期各让一步，延期 3 天" |
| **迁就** | 对方更在意、维护关系更重要、问题不大 | 甲方坚持某个界面颜色，虽然你觉得丑，但无关紧要 |
| **回避** | 问题不重要、时机不对、情绪太激动 | 甲方在气头上，先不谈，第二天再说 |

**乙方的常见问题**：过度使用"迁就"（什么都答应）和"回避"（有问题不敢说），很少使用"合作"。

**训练目标**：识别每个冲突应该用哪种模式，**而不是习惯性地用同一种**。

## 3. 艰难对话：说出难以开口的话

### 3.1 艰难对话的三层（《关键对话》《高难度谈话》）

每一场艰难对话下面，其实有三层对话在同时进行：
1. **"发生了什么"**：事实层面，谁对谁错
2. **情绪层面**：双方的感受（愤怒、委屈、焦虑）
3. **身份层面**：这件事对"我是谁"的冲击（"我是一个称职的项目经理吗？"）

**大多数人只处理第一层**，所以对话总是谈崩。

### 3.2 艰难对话的步骤

**第一步：准备**
- 我的目标是什么？（不是"赢"，而是"达成什么结果"）
- 对方可能怎么想？他的立场和感受？
- 最好的结果是什么？可接受的底线是什么？

**第二步：开场——从"第三方故事"开始**

不要从"我的看法"开始，而是从中立的描述开始：
> ❌ "你们的测试太慢了，拖累了整个进度。"
> ✅ "王经理，我想跟您聊聊测试进度的事。目前我们这边和测试这边对时间的预期好像不太一样，想一起看看怎么对齐一下。"

**第三步：探询对方的视角**
> "您那边是怎么看这个情况的？"
> "测试那边有什么困难吗？"

**第四步：表达自己的视角（用"我"开头）**
> "从我的角度看，……让我比较担心的是……"

**第五步：一起解决问题**
> "我们看看有没有办法……"

### 3.3 STATE 法则（《关键对话》）

当你需要说出对方可能不爱听的话：
- **S**hare your facts 分享事实："过去三周，需求变更了 15 次。"
- **T**ell your story 说出你的想法："我担心这样下去，月底上线会有风险。"
- **A**sk for others' paths 询问对方观点："您怎么看？"
- **T**alk tentatively 试探性表达："我可能理解得不对……"
- **E**ncourage testing 鼓励质疑："如果您觉得我说得不对，请直接告诉我。"

## 4. 谈判

### 4.1 谈判前的准备（最重要）

| 准备项 | 内容 |
|---|---|
| **目标** | 我最想要什么？（理想目标） |
| **底线** | 最低能接受什么？（低于这个就不谈） |
| **BATNA** | 如果谈崩了，我的最佳替代方案是什么？ |
| **对方的 BATNA** | 如果谈崩了，对方的替代方案是什么？（他有多需要我？） |
| **对方的利益** | 对方真正关心的是什么？（不是他的立场，而是背后的利益） |
| **交换筹码** | 我能给什么？什么对我成本低但对他价值高？ |
| **开场** | 我先提什么？ |

**BATNA（谈判协议的最佳替代方案）是谈判力量的来源**：
- 你的 BATNA 越好，你越有底气
- 对方的 BATNA 越差，你越有优势
- **不要暴露你的 BATNA 很差**

### 4.2 立场 vs 利益（哈佛谈判法）

**立场**是对方说出来的要求；**利益**是要求背后的原因。

| 立场 | 背后的利益 |
|---|---|
| "价格必须降 20%" | 预算只有这么多 / 要向领导证明自己谈下来了 / 竞争对手报价低 |
| "必须 15 号上线" | 15 号有领导视察 / 和其他系统配套 / 只是习惯性压时间 |
| "这个功能必须做" | 领导要求 / 某个业务场景真的需要 / 别的系统有 |

**关注利益，而不是立场**——利益层面往往有多种满足方式。

**例子**：
> 甲方："价格必须降 20%！"
> 乙方："能理解您的压力。方便说一下是预算方面的限制吗？"
> 甲方："今年预算就批了 80 万。"
> 乙方："明白了。那我们能不能这样：今年先做核心模块，80 万以内；剩下的模块放到明年预算里做二期？这样功能不打折，您的预算也能控制住。"

### 4.3 交换而不是让步

**原则：每次让步都要换回点什么**。

> ❌ "好吧，那我们降 5%。"
> ✅ "如果降 5%，那付款方式能不能调整为上线后付 70%？"
> ✅ "价格我们可以再看看，但如果工期能放宽两周，我们的成本能降下来一些。"

**低成本高价值的筹码（乙方可以给的）**：
- 延长免费维保期（如果系统质量好，维保成本很低）
- 增加培训次数
- 提供额外的文档、报告
- 优先响应
- 在行业会议上联合发布案例（甲方领导有面子）

**可以向甲方要的**：
- 付款节点提前 / 比例调整
- 工期放宽
- 范围缩减
- 甲方提供更多资源（人员、环境）
- 案例授权、推荐信
- 后续项目的优先合作

### 4.4 谈判中的常用技巧

| 技巧 | 说明 | 示例 |
|---|---|---|
| **沉默** | 对方提出要求后，不急着回应，让对方填补沉默 | （对方报价后停顿 5 秒） |
| **请示上级** | 不当场做决定，给自己留余地 | "这个超出我的权限了，我回去请示一下领导" |
| **打包** | 把多个问题一起谈，便于交换 | "价格、工期、付款方式我们一起看" |
| **蚕食** | 主要条件谈完后，再要一些小条件 | "那培训的费用就包含在里面了吧？" |
| **最后通牒（慎用）** | 表明底线 | "这已经是我们能做到的极限了" |
| **红脸白脸** | 一个人强硬，一个人温和 | 乙方销售温和，项目总监强硬 |
| **条件句** | 用"如果……那么……"提出交换 | "如果你们能……那么我们可以……" |

### 4.5 应对甲方的谈判招数

| 甲方招数 | 识别 | 应对 |
|---|---|---|
| "别家才报 X 万" | 可能是真的，也可能是诈 | "能理解。方便说一下他们的方案范围吗？我们对比一下，看看差异在哪里" |
| "这是最后的价格，不行就算了" | 可能是真底线，也可能是试探 | "理解您的立场，我们回去再评估一下，看看有没有别的方式" |
| "我们领导说了……" | 拿领导压人 | "李总的要求我们很重视，能不能约个时间我们直接向李总汇报一下方案？" |
| "先做着，钱的事以后再说" | 典型的坑 | "我们很愿意先启动，但为了双方都有保障，变更的范围和费用我们先书面确认一下" |
| "这次你们让一让，后面项目多着呢" | 画饼 | "非常感谢您的信任。这次我们在 X 方面做了让步，也希望后续合作能考虑这一点。能不能在会议纪要里体现一下？" |
| 拖延 | 用时间压你 | 设定期限："这个报价有效期到月底，之后人力成本会调整" |
| 情绪化 | 发火、威胁 | 先暂停："我理解您很着急，要不我们休息 10 分钟再继续？" |

## 5. 几个经典谈判场景

### 5.1 谈工期

**甲方**："一个月必须上线！"
**乙方评估**：需要两个月。

**策略**：
1. **探询原因**："一个月这个时间点，是有什么特别的安排吗？"
2. **如果有硬性原因**（如领导视察）：
   > "明白了，那一个月我们重点保证视察时能演示的核心功能，确保效果好。完整功能两个月上线。您看行吗？"
3. **如果没有硬性原因**：
   > "一个月的话，我们评估了一下，需要在测试上压缩很多，上线后出问题的风险比较大。如果出问题，影响的是您这边的业务。我们建议 6 周，把测试做充分。"
4. **交换**：
   > "如果必须一个月，我们需要甲方这边：业务专家全程驻场、需求在第一周内全部确认不再变更、测试环境第一天就到位。这几个条件能满足的话，我们全力冲。"

### 5.2 谈追加费用

**场景**：需求变更导致工作量增加 30%，需要追加费用。

**步骤**：
1. **平时积累**：变更清单持续登记，让甲方看到积累
2. **时机**：在完成一个阶段性成果、甲方满意时谈
3. **铺垫**：
   > "王经理，这几个月咱们配合得挺好的。有个事想跟您商量一下：从变更清单来看，到目前为止新增的需求有 25 项，其中 18 项小调整我们都免费做了。剩下 7 项工作量比较大，加起来大概 80 人天。"
4. **提方案**：
   > "这部分我们想跟您商量一下怎么处理。一是走补充协议；二是如果预算有困难，我们可以把其中 3 项放到二期；三是……"
5. **给对方台阶**：
   > "我知道追加预算流程比较麻烦，需要我们准备什么材料，我们来准备。"

### 5.3 谈验收标准

**场景**：甲方验收时提出很多"不满意"，有些是新需求。

**策略**：
1. **回到基线**：拿出签字的需求文档，逐条对照
2. **分类处理**：
   - 确实是 bug：立即修复
   - 是新需求：登记变更，不影响本次验收
   - 是体验优化：协商，可以作为验收后的优化项
3. **话术**：
   > "王经理，您提的这 15 个问题，我们对照需求文档分了一下类：5 个是 bug，我们本周内修完；7 个是新的优化需求，我们记录下来，放到运维期做；3 个是使用方式的问题，我们安排一次培训。您看这样，先把这 5 个 bug 修了就组织验收，其他的作为验收后的跟进事项，写进验收报告附件？"
