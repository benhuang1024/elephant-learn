# 03 需求管理与变更控制

> 乙方 80% 的冲突，根源都在需求：需求没说清、需求变了、对需求理解不一致。
> 需求管理做得好，后面的沟通会轻松一半。

---

## 1. 需求为什么总出问题

| 根源 | 表现 | 对策 |
|---|---|---|
| 甲方自己没想清楚 | "先做出来看看""你们专业你们定" | 用原型、样例倒逼他想清楚 |
| 说的和想的不一样 | 他说"导出报表"，其实想要的是"能发给领导看的漂亮报表" | 追问使用场景和目的 |
| 不同人需求冲突 | 业务部要灵活，IT 部要规范 | 让甲方内部先对齐，乙方不当裁判 |
| 隐性需求没挖出来 | 没说要权限控制，上线后说"这不是常识吗" | 用检查清单覆盖常见隐性需求 |
| 领导意志 | 领导看完一眼"不对，我要的是……" | 关键原型尽早给领导看 |
| 外部变化 | 政策变了、业务调整了 | 接受变化，但走变更流程 |

## 2. 需求调研：挖掘真实需求

### 2.1 5W2H 追问法

甲方说："我们需要一个审批系统。"

| 问题 | 追问 |
|---|---|
| What 做什么 | 审批哪些事项？有多少种审批类型？ |
| Why 为什么 | 现在是怎么审批的？痛点是什么？做完后希望达到什么效果？ |
| Who 谁用 | 谁发起、谁审批、谁查看？大概多少人？ |
| When 什么时候 | 什么时候必须上线？为什么是这个时间？审批有时效要求吗？ |
| Where 在哪用 | 电脑还是手机？内网还是外网？ |
| How 怎么做 | 审批流程是固定的还是要能配置？有会签、或签吗？ |
| How much 多少 | 每天多少审批单？预算大概多少？ |

### 2.2 "为什么"追问 3 层

> 甲方：我们要一个导出 Excel 的功能。
> 乙方：导出之后主要用来做什么呢？
> 甲方：要给领导汇报。
> 乙方：领导一般看哪些内容？是看汇总数据还是明细？
> 甲方：主要看各部门的汇总和趋势。
> 乙方：那如果系统里直接有一个图表看板，领导手机上就能看，是不是比导出 Excel 再整理更方便？
> 甲方：那当然更好。

**真实需求不是"导出 Excel"，而是"让领导方便地看到汇总和趋势"**。

### 2.3 隐性需求检查清单

每次需求调研，对照这个清单逐项确认：

- [ ] 权限：谁能看、谁能改、谁能删？数据权限按部门还是按人？
- [ ] 日志：操作记录要不要留？留多久？
- [ ] 性能：多少人同时用？响应时间要求？
- [ ] 数据量：现有多少数据？每年增长多少？
- [ ] 历史数据：老数据要不要迁移？
- [ ] 集成：要和哪些系统对接？单点登录？
- [ ] 兼容：浏览器版本？手机型号？信创环境？
- [ ] 安全：等保级别？数据脱敏？加密？
- [ ] 导入导出：有没有批量导入需求？
- [ ] 通知：短信、邮件、企业微信？
- [ ] 打印：要不要打印？格式要求？
- [ ] 异常：网络断了怎么办？数据错了怎么回滚？
- [ ] 运维：谁来运维？要不要监控告警？
- [ ] 培训：要不要培训？培训多少人？
- [ ] 文档：要哪些文档？格式要求？
- [ ] 验收：验收标准是什么？谁来验收？

## 3. 需求确认：把模糊变清晰

### 3.1 原型优先

**"一图胜千言"在需求阶段是真理**。
- 线框图 / 低保真原型：快速确认流程和布局
- 高保真原型：确认交互和视觉
- 可点击 Demo：确认关键体验

> 让甲方在原型阶段改 10 次，比在开发完成后改 1 次便宜得多。

### 3.2 需求规格说明书（签字确认）

**关键要素**：
1. 需求编号（便于后续追踪变更）
2. 需求描述（用户故事格式："作为 XX，我希望 XX，以便 XX"）
3. 验收标准（可测试、可量化）
4. 优先级（必须 / 应该 / 可以 / 不做，即 MoSCoW）
5. **明确不做的范围（Out of Scope）**——这一条最容易被忽略，但最能保护乙方

**验收标准的写法**：
- ❌ "系统响应要快" → ✅ "95% 的页面请求在 2 秒内返回（100 并发）"
- ❌ "界面要美观" → ✅ "按照已确认的 UI 设计稿 v2.1 实现"
- ❌ "支持大数据量" → ✅ "支持单表 1000 万条数据的查询，查询时间 < 3 秒"

### 3.3 签字的话术

甲方常常不愿意签字（怕担责）。

> "王经理，这个需求文档我们整理好了，麻烦您确认签字一下。主要是为了**咱们双方理解一致**，后面开发和测试都按这个来，**验收的时候您向领导汇报也有依据**。如果后面业务有调整，我们走变更流程更新就行，不是说定死了不能改。"

如果实在不签：
> "那这样，我把文档发邮件给您，如果三个工作日内没有修改意见，我们就按这个版本开始开发了，您看可以吗？"

（邮件发出后，默认确认，留痕。）

## 4. 范围蔓延：最隐蔽的杀手

### 4.1 范围蔓延的典型话术（甲方说的）

- "这个很简单，顺手加一下吧"
- "这不是本来就应该有的吗？"
- "就改个按钮颜色，几分钟的事"
- "别的系统都有这个功能"
- "领导说了要加"
- "这个不算新需求，是原来需求没做好"

### 4.2 为什么乙方会放任范围蔓延

- 怕得罪甲方
- 觉得"确实不难，做了吧"
- 一线开发直接答应了（项目经理不知道）
- 没有基线文档，说不清是不是新需求

### 4.3 应对策略

**策略一：建立需求基线**
- 签字的需求文档 = 基线
- 所有新增、修改都和基线对比

**策略二：统一入口**
- 对甲方：所有需求通过项目经理提出，不直接找开发
- 对内：开发人员不能私下答应甲方任何需求，统一回复"我记下来，跟项目经理确认后回复您"

**策略三：小需求也登记**
- 哪怕是"改个颜色"，也登记到需求变更清单
- 不一定都要收费，但要**让甲方看到积累**
- 月底汇报："本月共受理变更 23 项，其中 18 项小调整已免费完成，5 项涉及工作量的待评估"

> 这样做的好处：甲方会意识到"原来我们提了这么多"，后续提需求会更克制；同时你积累了"人情"，后续谈判时可以用。

**策略四：变更做"交换"**
- "加这个可以，那我们把 X 功能挪到二期？"
- "加这个可以，上线时间需要往后 3 天"

### 4.4 "这不是本来就应该有的吗？"怎么回应

这是最难应对的，因为甲方觉得理所当然。

> "您说得对，从业务角度看这个功能确实挺必要的。我们回头看了一下需求文档，当时确认的是 XX，这一块没有包含在内，可能是调研时没覆盖到。
>
> 我们双方都有责任（**不推责**）。我建议这样：这个功能我们评估了需要 5 人天，考虑到咱们的合作关系，我们承担一半，另外一半走一个小变更。或者如果工期允许，放到一期收尾阶段来做，不额外收费，但上线时间要顺延 3 天。您看哪种合适？"

## 5. 变更控制流程

### 5.1 标准流程

```
甲方提出变更
     │
     ▼
乙方登记（变更编号、提出人、时间、描述）
     │
     ▼
乙方影响评估（工作量、工期、成本、风险、对其他功能的影响）
     │
     ▼
双方评审 ── 不同意 ──► 关闭，记录原因
     │
   同意
     │
     ▼
签字确认（变更单）
     │
     ▼
更新基线（需求文档、计划、合同如需要）
     │
     ▼
执行 & 跟踪
```

### 5.2 变更分级（让流程不至于太重）

| 级别 | 标准 | 处理方式 |
|---|---|---|
| 微小 | < 0.5 人天，不影响工期 | 项目经理直接处理，登记即可 |
| 一般 | 0.5-5 人天，或影响工期 < 3 天 | 双方项目经理确认，邮件留痕 |
| 重大 | > 5 人天，或影响里程碑、或涉及费用 | 正式变更单，双方领导签字，必要时补充协议 |

### 5.3 变更评估要回答的问题

- 需要多少人天？
- 影响哪些已完成的功能？要不要回归测试？
- 影响上线时间吗？影响多少？
- 需要增加费用吗？
- 有什么技术风险？
- 不做的话会怎样？

## 6. 需求冲突：甲方内部意见不一

**场景**：业务部 A 要求流程灵活可配置，IT 部 B 要求固化流程便于维护。

**原则**：**乙方不当裁判**。你判谁对，另一方都会记恨你。

**做法**：
1. 分别了解双方诉求背后的原因
2. 整理成对比材料，客观呈现利弊
3. 提请甲方的**共同上级**或**对接人**组织决策
4. 话术：

> "王经理，关于审批流程的设计，业务部和 IT 部有两种不同的考虑，都有道理。我们把两种方案的利弊整理了一下（附表）。这个需要贵司内部定一下方向，我们两种都能实现。您看是不是约个会，请两边一起定一下？我们可以在会上做技术说明。"

## 7. 本章练习

1. 拿你当前项目的需求文档，检查是否有"Out of Scope"章节，如果没有，补上。
2. 用隐性需求检查清单过一遍你当前项目，看有几项没确认过。
3. 统计你当前项目近一个月的"小改动"，做成清单，思考怎么在周报里呈现。
4. 演练：甲方说"这个很简单，你们顺手做一下"，写出你的回应。
