## 1. 构建产物与部署形态

| | PHP / Laravel | Spring Boot | NestJS（本仓库后端） | Vite SPA（web-react / web-vue） | Next（web-next） |
|---|---|---|---|---|---|
| 产物 | 源码目录 + `vendor/` | 一个 fat jar | `dist/` 里的 JS + `node_modules/` | 静态资源（hash 文件名） | `.next/` + 服务端代码 |
| 起进程 | nginx + php-fpm | `java -jar app.jar` | `node dist/main.js` | 无进程，nginx/CDN 发文件 | `next start -p 3100` |
| TS 何时参与 | — | — | **只在构建期**：`tsc`，运行时纯 JS | 同左 + Vite 打包 | 同左 + Turbopack |
| 类型检查在哪 | — | 编译期 | `tsc --noEmit` | 同左（`.vue` 用 `vue-tsc`） | 同左 |
| 热更新 | 改文件即生效 | 不支持 | 不支持（`dev` = 先 build 再跑） | HMR | HMR |
| 优雅停机 | fpm 自然跑完 | `server.shutdown: graceful` | `app.enableShutdownHooks()` | — | 同 Node |
| 健康检查 | 自己写 | Actuator 内置 | 手写 `/actuator/health` | — | — |

后端脚本（[package.json](../code/shop-api/package.json)）就交代了「TS 项目怎么跑」：

```json
"build": "pnpm --filter @shop/shared build && tsc -p tsconfig.build.json",
"typecheck": "pnpm --filter @shop/shared build && tsc --noEmit",
"start": "node dist/main.js",
"dev": "pnpm build && node dist/main.js"
```

- **每条都以 `pnpm --filter @shop/shared build` 开头**：`@shop/shared` 的 `types` 指向 `./dist/index.d.ts`，而它自己的 `typecheck` 是 `--noEmit`（不产出 dist）。类型检查依赖包这件事必须显式做，不能指望 `pnpm -r` 顺手替你构建（第 16 章把这个坑讲透）。
- **`tsc` 只做 `rootDir: src` → `outDir: dist`**（见 [tsconfig.build.json](../code/shop-api/tsconfig.build.json)）：不打包、不 tree-shake、不注入 polyfill、不压缩、不处理 `.env`。服务端建议**不要**bundle——堆栈和 source map 才干净。
- **`dev` 没有文件监听**。等价体验是 `tsc --watch` + `node --watch dist/main.js`（Node 24）。

前端：`vite build` 出静态目录（[vite.config.ts](../code/web-react/vite.config.ts) 里 `sourcemap: true`）、`next build` 出 `.next/`。生产要交接的一件事是 dev proxy：`server.proxy["/api"]` 只在 dev 存在，线上必须由 nginx `location /api` 反代，或后端开 CORS（第 10 章讲为什么演示项目两边都没开）。

| 坑 | 现象 | 解法 |
|---|---|---|
| 「产物就是 dist」的错觉 | 只拷 `dist/` → `Cannot find module '@shop/shared'` | 产物 = `dist/` + **依赖树**：Docker 分层装依赖，或 `pnpm deploy` 出自包含目录 |
| ESM 说明符 | 源文件 `.ts`，产物里 import 带 `.js` | `"type": "module"` + `module: nodenext` 时**必须**写 `.js`；别让 bundler 改掉它，会破坏 `emitDecoratorMetadata` |
| 类型检查 ≠ 构建 | `vite build` 过了但代码一堆类型错误 | esbuild/Vite 只擦类型不检查；CI 单独跑 `tsc --noEmit`（本仓库把它写进 `build` 正是为此） |
| 前端 `.map` 下发 | `sourcemap: true` 把源码映射发到公网 | 构建后上传 Sentry 再从 `dist/` 删除 |

## 2. Docker 多阶段构建

对照 Spring 那版（[java/code/shop-api/Dockerfile](../../java/code/shop-api/Dockerfile)）：Maven 出 fat jar，运行层只留 JRE，一次 `COPY` 完事。Node 的难点不在编译（`tsc` 很快），而在 **pnpm 的符号链接布局 + 原生依赖**：`node_modules` 是软链树，直接 `COPY` 换镜像就断；`better-sqlite3` 13.0.3 是 native addon（要么命中平台预编译包，要么需要 `python3/make/g++` 现编）；本仓库还是 workspace，`@shop/api` 依赖 `workspace:*` 的 `@shop/shared`（[pnpm-workspace.yaml](../code/pnpm-workspace.yaml)），两个包的产物都要进镜像。

仓库里的 [shop-api/Dockerfile](../code/shop-api/Dockerfile) 是**最简可用版**（`node:24-alpine` 两阶段、`corepack enable` 固定 pnpm、先拷 manifest 再 `pnpm install --frozen-lockfile --filter @shop/api...`、运行层 `apk add libc6-compat` + `USER node` + `VOLUME /data`），文件头就写了「本仓库没有实际执行过 docker build」。**它未被构建验证过**，下面的加固版是同一思路的完整写法（Debian slim + 独立 deps 层 + 显式 `pnpm deploy` 备选），抄完请先跑一遍（构建上下文是 `code/` 目录）：

```dockerfile
# syntax=docker/dockerfile:1.7
FROM node:24-bookworm-slim AS build
ENV CI=1 COREPACK_ENABLE_DOWNLOAD_PROMPT=0
RUN apt-get update && apt-get install -y --no-install-recommends python3 make g++ ca-certificates \
 && rm -rf /var/lib/apt/lists/*
# corepack 按根 package.json 的 "packageManager": "pnpm@9.15.9" 取版本；
# 若把它指到 pnpm 10，先用 --frozen-lockfile 验证 lockfile 兼容性
RUN corepack enable
WORKDIR /repo
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY packages/shared/package.json packages/shared/
COPY shop-api/package.json shop-api/
# pnpm fetch 只按 lockfile 灌 store（不建 node_modules）；cache mount 让依赖层几乎免费
RUN --mount=type=cache,id=pnpm-store,target=/root/.local/share/pnpm/store pnpm fetch
# 建 node_modules，native 依赖在这一步编译
RUN --mount=type=cache,id=pnpm-store,target=/root/.local/share/pnpm/store \
    pnpm install --frozen-lockfile --offline
# 先依赖后源码，顺序反了则每改一行代码重装全部依赖
COPY tsconfig.base.json ./
COPY packages ./packages
COPY shop-api ./shop-api
RUN pnpm --filter @shop/shared build && pnpm --filter @shop/api build

FROM node:24-bookworm-slim AS deps
ENV CI=1 COREPACK_ENABLE_DOWNLOAD_PROMPT=0 NODE_ENV=production
RUN apt-get update && apt-get install -y --no-install-recommends python3 make g++ && rm -rf /var/lib/apt/lists/*
RUN corepack enable
WORKDIR /app
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY packages/shared/package.json packages/shared/
COPY shop-api/package.json shop-api/
RUN --mount=type=cache,id=pnpm-store,target=/root/.local/share/pnpm/store \
    pnpm fetch --prod && pnpm install --frozen-lockfile --offline --prod

FROM node:24-bookworm-slim AS runtime
ENV NODE_ENV=production PORT=8080 DB_FILE=/data/shop.db
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --from=deps /app/package.json /app/pnpm-workspace.yaml ./
COPY --from=deps /app/packages/shared/package.json ./packages/shared/
COPY --from=build /app/packages/shared/dist ./packages/shared/dist
COPY --from=deps /app/shop-api/package.json ./shop-api/
COPY --from=build /app/shop-api/dist ./shop-api/dist
RUN useradd --system --uid 10001 app && mkdir -p /data && chown -R app /app /data
USER app
EXPOSE 8080
VOLUME ["/data"]
HEALTHCHECK --interval=15s --timeout=2s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:8080/actuator/health').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"
WORKDIR /app/shop-api
ENTRYPOINT ["node", "dist/main.js"]
```

`.dockerignore` 至少要这几行，否则 `COPY packages ./packages` 会把宿主 `node_modules`/`dist` 塞进构建上下文：

```
**/node_modules
**/dist
**/.next
**/*.db
**/coverage
.git
```

| 变体 | 什么时候用 | 代价 |
|---|---|---|
| 上面的三层结构 | workspace + native 依赖，生产默认 | Dockerfile 长，需要 BuildKit |
| `pnpm deploy --filter=@shop/api --prod out/` | 要**一个自包含目录**（塞任意镜像 / Serverless） | `workspace:` + native 组合仍需实测，pnpm 版本行为有差异 |
| `.npmrc` 里 `node-linker=hoisted` | 团队不熟软链布局，想退回 npm 式扁平目录方便 `COPY` | 丢掉 pnpm 严格隔离，「幽灵依赖」回归 |
| `node:24-alpine` / distroless | 体积与合规要求 | alpine 是 musl，native 预编译包常需现编；distroless 里没有 shell，`HEALTHCHECK` 要改 exec 形式 |

| 坑 | 说明 |
|---|---|
| `npm ci` 不可用 | `workspace:*` 协议 npm 不认，也不存在 `package-lock.json`；CI 只有 `pnpm install --frozen-lockfile` 一条路 |
| 本地 corepack 被禁 | 根 [package.json](../code/package.json) 写死 `pnpm@9.15.9`，用别的版本安装会产出大面积 lockfile diff |
| 跨架构构建 | Apple Silicon 上 `--platform linux/amd64` 时 QEMU 里的 `node-gyp` 结果不可信；在原生 amd64 runner 上构建 |
| 密钥进镜像 | 别 `COPY .env`；`--mount=type=secret` 才是唯一安全的注入方式 |

## 3. 进程模型与扩容

```
PHP:  1 请求 = 1 个 fpm 进程，跑完即销毁；并发 = pm.max_children
Java: 1 请求 = 1 个线程（Tomcat 池 / 虚拟线程）
Node: 1 进程 = 1 个主线程 + 事件循环 + libuv 线程池（I/O）；并发 = await 交错
      → CPU 密集代码阻塞该进程上的**所有**请求
```

第 03 章的 [withdraw 演示](../code/lang-basics/src/async-event-loop.ts) 给出两个结论：`await` 之后再检查状态时世界已经变了（所以余额/库存的真相只能在数据库里），而同步 CPU 循环会拖住同进程其它请求。本仓库还叠了一层：`better-sqlite3` 是**同步驱动**，`db.transaction(cb)`（[order.repository.ts](../code/shop-api/src/order/order.repository.ts)）执行期间事件循环停摆，进程内请求被天然串行化——好处是几乎撞不出乐观锁冲突（[e2e 测试](../code/shop-api/test/shop-api.e2e.spec.ts) 里明说了这点），代价是吞吐被单条 SQL 的上限锁死。换异步 `pg` / `postgres.js` 后冲突窗口才真实存在。

| 概念 | PHP | Spring | Node | K8s |
|---|---|---|---|---|
| 「同时有多少执行单元」 | `pm.max_children` | `server.tomcat.threads.max` | **进程数**（1 进程 = 1 核） | `replicas` |
| 默认值 | 20 左右 | 200 | **1**——很多人以为「Node 高并发」自动用了多核，其实没有 | 1 |
| 怎么调 | `www.conf` | `application.yml` | `node:cluster` / PM2 `instances` / 多容器 | `kubectl scale` / HPA |
| 谁管重启 | systemd / fpm master | 编排系统 | PM2 / K8s | K8s |

三种落地写法（本仓库**都未实现**，只有一份单进程 `main.ts`）：`node:cluster` 主进程 `for (availableParallelism()) cluster.fork()`，worker 各自 `listen` 同一端口，零运维组件；PM2 `{ name, script: "dist/main.js", instances: "max", exec_mode: "cluster", wait_ready: true, kill_timeout: 20000, max_memory_restart: "512M" }`，适合无编排单机；K8s 把副本数交给 `replicas`/HPA：

```yaml
spec:
  replicas: 4                      # ← 这就是 pm.max_children 的当代写法
  template:
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: acme/shop-api:1.0.0
          livenessProbe:  { httpGet: { path: /actuator/health, port: 8080 }, periodSeconds: 10 }
          readinessProbe: { httpGet: { path: /actuator/health, port: 8080 }, periodSeconds: 5 }
          lifecycle: { preStop: { exec: { command: ["sh", "-c", "sleep 5"] } } }
```

**优雅停机是真实实现的**，链路只有两处代码：[main.ts](../code/shop-api/src/main.ts) 的 `app.enableShutdownHooks()`，加上 [database.ts](../code/shop-api/src/db/database.ts) 的：

```ts
/** 优雅停机时释放文件句柄（Spring 的 @PreDestroy / Laravel 的 destructor）。 */
onModuleDestroy(): void {
  this.connection.close();
}
```

`SIGTERM` → Nest 触发 `onApplicationShutdown` → 各模块 `onModuleDestroy` → SQLite 句柄关闭（WAL 落盘）。对照 Java 的 `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 20s`（[java application.yml](../../java/code/shop-api/src/main/resources/application.yml)）。

| 坑 | 现象 | 解法 |
|---|---|---|
| 没开 shutdown hooks | 默认 `SIGTERM` **立即退出**，在途请求被砍 | `enableShutdownHooks()` 是必选项 |
| 只关连接不关 HTTP | 句柄关了但 Express 还收新请求 | 生产用 `await app.close()`（Nest 内部会 `httpServer.close()`），keep-alive 还要 `closeIdleConnections()` + 超时兜底 |
| K8s 时序 | Pod 已 SIGTERM，endpoints 还没撤，最后几秒 502 | `preStop: sleep 5` + readiness + `terminationGracePeriodSeconds > 最长请求耗时` |
| 进程内状态不共享 | `Metrics` 是 `Map<string, number>`，`@Timed` 计数器每个 worker 各算各的；`/actuator/metrics` 只返回「接了这个请求的那个 worker」的数字 | 单线程模型的直接后果，演示项目故意把它挂到端点上才好讲。生产：计数器交给 Prometheus `sum by (...)` 或搬 Redis；限流/缓存/会话同理别放进程内存 |
| 以为 `async` 等于多核 | 加了 `await` 还是只用一个核 | `await` 只解决 I/O 等待；CPU 并行只有 cluster / `worker_threads` |
| 一个 `Promise.all` 打爆下游 | 1000 个并发 fetch | 用现成限流器 [mapWithLimit](../code/lang-basics/src/async-event-loop.ts)，语义等于「别指望调大 max_children 就能打 DB」 |

## 4. 日志与可观测性

**现状（诚实版）**：本仓库用 Nest 内置 `Logger`，输出是给人看的行文本，**不是 JSON**。`X-Request-Id` 由 [request-id.middleware.ts](../code/shop-api/src/common/request-id.middleware.ts) 挂到 `request.requestId` 并写回每个响应头，但**没有任何一条日志带上它**。仓库里没有 `pino`：[package.json](../code/shop-api/package.json) 的依赖表只有 Nest、Drizzle、better-sqlite3、reflect-metadata、rxjs、zod —— 日志能力就是「内置 Logger」这一层，没有隐藏依赖。日志/指标/追踪三条线都只有演示级实现。

对照 Java 版：那边 `RequestIdFilter` 把 id 写进 `MDC`，于是**每条日志自动带 requestId**。差距清单：

| 能力 | Java 版 | 本仓库现状 | 生产该做 |
|---|---|---|---|
| 结构化 JSON 日志 | `logging.structured.format` 一行 | 无 | pino（默认 JSON、级别判断零开销）——**缺口** |
| 请求 id 贯穿日志 | MDC 自动 | 只在响应头 + `request.requestId` | 请求级 child logger / nestjs-cls——**缺口** |
| 应用异常日志 | `@RestControllerAdvice` | 有：[problem.filter.ts](../code/shop-api/src/common/problem.filter.ts) 里 `logger.error` 带堆栈，且不外泄给客户端 | 保留，补 requestId |
| 指标导出 | `/actuator/prometheus` | 无导出器；`GET /actuator/metrics`（需认证）只返回进程内计数器 | prom-client / OTel Metrics——**缺口 + 未验证** |
| 链路追踪 | Micrometer Tracing + `traceparent` | 只有 `X-Request-Id`，不传播 `traceparent` | OTel Node SDK——**缺口** |
| liveness/readiness | 探针可一键开 | 只有单个 `/actuator/health` | 拆两个端点，见第 6 节 |

生产配方（**不在仓库中**，Node 24 + Nest 12 可抄版）：

```ts
import pino from "pino";
import { pinoHttp } from "pino-http";

const rootLogger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  base: { app: "shop-api", env: process.env.NODE_ENV, pid: process.pid },
  redact: ["req.headers.authorization", "req.headers.cookie", "*.password"],
  timestamp: pino.stdTimeFunctions.isoTime,
});

// pino-http 挂在最外层（早于业务中间件），genReqId 复用它已实现的「网关 id 优先」规则
app.use(pinoHttp({
  logger: rootLogger,
  genReqId: (req, res) => {
    const incoming = req.headers["x-request-id"];
    const id = typeof incoming === "string" && incoming.trim() ? incoming : crypto.randomUUID();
    res.setHeader("X-Request-Id", id);
    return id;
  },
  customProps: (req) => ({ requestId: req.id, path: req.url, method: req.method }),
  autoLogging: { ignore: (req) => req.url?.startsWith("/actuator/health") ?? false },
}));
```

业务代码里拿「带 requestId 的日志器」三档选择：

| 方案 | 心智 | 代价 |
|---|---|---|
| `nestjs-cls` + `LoggingInterceptors` | ≈ Spring 的 MDC：一个 AsyncLocalStorage 上下文，把日志器换成自动带 requestId 的 child logger | 多一个依赖；AsyncLocalStorage 不跨 `worker_threads` 传播 |
| 把 `req.log` 一路透传（Fastify 风格） | 最明确，`share-nothing` 直觉不失效 | 函数签名要带 logger，改造量大 |
| `console.log` + 采集侧正则 | 零改造 | 把本该你做对的事推给 Loki/ELK，字段一多就崩 |

> PHP 对照：Laravel `Log::withContext([...])` / Monolog Processor 是同一件事。差别是 Node 的上下文活在进程里——必须请求入口建立、随请求自然丢弃；当「模块级变量」用 = 跨请求串数据。

| 信号 | 回答什么 | Node 工具 | 顺序 |
|---|---|---|---|
| 日志 | 这一刻发生了什么 | pino + Loki | 第 1 步：结构化 + request id |
| 指标 | 这半小时整体怎么样 | prom-client（HTTP 时延直方图、`nodejs_eventloop_lag`、堆内存） | 第 2 步：RED 三件套 |
| 追踪 | 这次请求慢在哪一跳 | OTel Node SDK + Jaeger/Tempo，用 W3C `traceparent` 与 PHP/Java 侧互通 | 第 3 步：跨语言系统成型后 |

**事件循环 lag 是 Node 特有、PHP/Java 没有对应物的指标**：它直接量化「CPU 任务把请求堵住了」的严重程度，值得作为第一条告警。

## 5. 配置与密钥

三者形状完全一致，只是校验发生在哪一刻：

```
Laravel: .env → env() → config('shop.max_order_items')，键名写错要到运行时才炸
Spring : 环境/JVM args → @ConfigurationProperties + @Validated → 启动时绑定并校验
Nest   : 环境/.env → ConfigModule.forRoot({ validate: validateEnv }) → Zod 启动时收敛成强类型对象
```

[config/env.ts](../code/shop-api/src/config/env.ts) 就是这份契约，它把 Spring 的三个注解翻译了过来：

```ts
PORT: z.coerce.number().int().positive().default(8080),
SHOP_MAX_ORDER_ITEMS: z.coerce.number().int().min(1).max(100).default(20),
SHOP_SEED_DEMO_DATA: z.string().default("true").transform((value) => value === "true"),
```

不合法就让进程启动失败（`validateEnv` 抛错并逐条列出 `issue.path`），[app.module.ts](../code/shop-api/src/app.module.ts) 里 `cache: true` 避免每次 `get()` 重跑校验，思路等价于 `php artisan config:cache`。

仓库里有 [.env.example](../code/shop-api/.env.example)（`cp .env.example .env` 就能起），内容和 `EnvSchema` 一一对应：

```bash
# 复制成 .env 后按需修改；所有键都由 src/config/env.ts 的 Zod schema 校验，写错启动即失败。
NODE_ENV=development
PORT=8080
# SQLite 文件；:memory: 为内存库（测试用）
DB_FILE=shop.db

# 演示账号（与 java/code/shop-api 的 SecurityConfig 一致）。生产请改成 Secret 注入。
ADMIN_USERNAME=admin
ADMIN_PASSWORD=admin123
CUSTOMER_USERNAME=customer
CUSTOMER_PASSWORD=customer123

# 业务配置（对应 Spring 的 shop.* 属性）
SHOP_CURRENCY=CNY
SHOP_MAX_ORDER_ITEMS=20
SHOP_SEED_DEMO_DATA=true
```

**注意它没有被 `.env` 加载测试覆盖**：`ConfigModule` 只读环境变量与 `.env`，本仓库的 e2e 用 `process.env` 直接注入，
所以这个文件是「给人看的样板」，不是运行时真值来源。生产要改成 `ADMIN_PASSWORD=`（空 = 必填项缺失 → 启动失败），凭据走 Secret。

| 坑 | 为什么危险 | 正确写法 |
|---|---|---|
| `process.env.PORT!` | 非空断言是**编译期谎言**，运行时照样 `undefined` | 全部过 `validateEnv`，代码只读 `ConfigService` / `Env` 类型 |
| `config.get<number>("PORT")` | 泛型参数不转换值，环境变量永远是 string | 让 `z.coerce.number()` 做转换（仓库已经做了） |
| `"true"` 当 boolean | `Boolean("false")` 恒为 `true` | 照抄仓库：`z.string().transform(v => v === "true")` |
| 密钥写进 `default()` | `ADMIN_PASSWORD: z.string().default("admin123")` 是演示项目为了 `pnpm dev` 一步能跑；生产等于把口令写进代码库 | 生产环境的必填项不给 default；用 K8s `Secret` + `envFrom`，或 External Secrets / Vault |
| 前端变量泄密 | [web-react/src/api.ts](../code/web-react/src/api.ts) 里 `import.meta.env.VITE_SHOP_PASSWORD` —— 演示用 Basic 账号，任何浏览器都能读出密码 | 只有非密钥配置才允许 `VITE_` / `NEXT_PUBLIC_`；真实凭据留服务端 |
| profile 思维 | Spring 有 `application-postgres.yml`，本仓库**没实现任何 profile**（只有 SQLite） | 别指望「换个 profile 就换库」 |

优先级建议（低→高）：镜像内建默认值 → `ConfigModule` 的 `load` → ConfigMap → Secret → 平台/CLI 覆盖；任一层不合法就启动失败。

## 6. 错误预算与告警

[main.ts](../code/shop-api/src/main.ts) 只处理了启动失败（`bootstrap().catch(...)` → `process.exitCode = 1`），请求内异常由 [problem.filter.ts](../code/shop-api/src/common/problem.filter.ts) 兜底。但**进程级**的三条通道本仓库没接——这是 PHP 人最不适应的地方：PHP 一个请求崩了只影响那一个请求，Node 一个未处理拒绝掀翻该进程上所有在途请求。

| 事件 | Node 默认 | 生产策略 | 理由 |
|---|---|---|---|
| `unhandledRejection` | Node 15+ **直接崩溃** | 记日志（带 requestId + 堆栈）→ 让进程退出，交给编排重启 | 「记完继续跑」= 带着未知损坏状态服务 |
| `uncaughtException` | 崩溃 | 记日志 → 关 HTTP server → 兜底超时后 `exit(1)` | V8 官方口径：进程状态已不可信，别假装能恢复 |
| OOM | 被 cgroup kill | 显式 `--max-old-space-size` + `--abort-on-oom-error` + 告警 | 与 Java `ExitOnOutOfMemoryError` 同一意图 |

```ts
// 生产入口补充（不在仓库中）：优雅停机与致命错误的分工
process.on("SIGTERM", () => { rootLogger.info("SIGTERM：优雅停机"); void app.close(); });
process.on("uncaughtException", (err) => { rootLogger.fatal({ err }, "uncaught"); process.exit(1); });
```

健康检查应该拆成三种问法，本仓库只有最后一种的一半：

| 探针 | 该问什么 | 绝不能问什么 | 本仓库 |
|---|---|---|---|
| liveness | 进程还活着吗、事件循环还转吗 | **不要**查 DB/Redis/下游——依赖抖动会 kill 掉好端端的实例，制造雪崩 | 缺 |
| readiness | 能接流量吗：DB 连接、迁移版本、预热 | 不要因偶发慢就翻，会频繁摘流 | 缺（可用现有 `/actuator/health`） |
| startup | 启动完成了吗 | — | 缺 |
| `/actuator/health` 现状 | `db`（`select 1`，失败 503）+ `memory`（rss/heap MB）+ `ping`，`@Public()` | — | 已实现 |

`@Res({ passthrough: true })` 那段体现了 Nest 特有手感：状态码要随运行时结果变化时不能用 `@HttpCode`（编译期常量），得像 Spring 用 `ResponseEntity` 那样自己 `response.status(...)`。

告警起步（错误预算视角）：

| 信号 | 阈值直觉 | 说明 |
|---|---|---|
| 5xx 比例、`/api/orders` 的 409 比例 | 5 分钟内超 SLO 预算燃尽速率 | 读写分开看 |
| P99 时延 | 相对基线漂移 | 注意 `X-Elapsed-Ms` 只覆盖 `/api/**`，Guard 短路的 401 不带它 |
| 事件循环 lag | 持续 > 100ms | CPU 任务混进了请求路径 |
| RSS/堆增长斜率 | 只涨不落 | 模块级 Map/数组被当缓存 |
| 重启次数 / `uncaughtException` | 任何一次都要有人看 | 错误预算的直接消耗项 |

## 7. 性能

顺序和 Java 版一致：数据库 → 外部调用 → 进程/线程模型 → 运行时参数。但 Node 有两条自己的规矩。

**CPU 密集任务必须外移**（PHP 的 CPU 活儿只影响一个 fpm worker，Node 影响整个进程）：

| 任务 | 做法 | 什么时候不要用 |
|---|---|---|
| 报表 / Excel 导出 / 图片处理 / 哈希 | **BullMQ + 独立 worker 进程**（≈ Laravel Queue + Horizon，Redis 当队列） | 需要低延迟同步返回时 |
| 一次请求内的 CPU 爆发 | `worker_threads` | 高频小任务：启动与序列化开销吃掉收益 |
| 调外部程序（ffmpeg 等） | `child_process.spawn` + 流式 | 绝不要用 `execSync`——它就是「同步阻塞事件循环」的原语 |

**连接与池**（本仓库单文件 SQLite 不存在池，生产 Postgres 才要算）：`总连接数 = replicas × 每进程池大小`，`8 × 20 = 160` 直接打爆 Postgres 默认 `max_connections=100`。`postgres.js` 单连接多路复用可以把池压到很小；外部调用一定给超时（`AbortSignal.timeout(2000)`，或像 [waitAborted](../code/lang-basics/src/async-event-loop.ts) 那样自己接 signal）——`fetch` 默认不超时等于连接被永久占住。

`cache: "no-store"` 的代价，[web-next/src/lib/api.ts](../code/web-next/src/lib/api.ts) 是仓库里唯一的性能反例实物：

```ts
const response = await fetch(`${API_BASE}/api/products${query}`, {
  headers: { Accept: "application/json" },
  // no-store：演示项目要立刻看到库存变化；生产请按读扩散/缓存策略调整（docs/13）
  cache: "no-store",
});
```

它强制 Next 每次 SSR 真打一次后端，等于把首页访问量 1:1 传导给 shop-api。生产按数据性质选：商品目录 `revalidate`/ISR，订单列表 `no-store`，跨实例热数据进 Redis——而不是靠删掉这一行。

| 需求 | Java | Node |
|---|---|---|
| CPU 火焰图 | JFR / async-profiler | `node --cpu-prof`、clinic-js / 0x |
| 事件循环卡在哪 | `jcmd Thread.print` | `--inspect` + DevTools，或 `perf_hooks.monitorEventLoopDelay` |
| 内存泄漏 | heap dump + MAT | `--heap-prof` / memlab；`process.memoryUsage()`（[health 端点已在返回它](../code/shop-api/src/health/actuator.controller.ts)） |

## 8. 发布与回滚

| 维度 | 后端（Nest） | SPA（Vite） | Next |
|---|---|---|---|
| 版本化 | 镜像 tag = git sha（别用 `latest`）；`/actuator/info` 返回 `version`/`node`/`pid`（演示里 version 硬编码 `"1.0.0"`） | `dist/` 上传 CDN，hash 文件名可长缓存 | 保留 `.next` 或打 standalone 镜像 |
| 生效方式 | 滚动替换 Pod | 覆盖 `index.html`（`no-cache`） | `next start -p 3100` |
| 回滚 | `kubectl rollout undo` | `index.html` 指回上一版（hash 资源仍在 CDN） | 同左，但必须与后端 API 兼容 |
| 前后端耦合 | — | 老页面 + 新 API：新增字段可以，**删/改不行** | RSC 与 API 同仓同发，耦合最紧 |

三条发布纪律：

1. **API 只做加法。** 响应 DTO（[toProductWire](../code/shop-api/src/product/product.repository.ts)、[shared/product.ts](../code/packages/shared/src/product.ts)）删字段或改类型，会让 CDN 上的老 SPA 在 `ProductResponseSchema.parse` 处直接抛错——这是 Zod 契约在部署层的含义，比「前端记得同步」可靠。
2. **迁移先于代码：expand → migrate → contract。** 本仓库有 [drizzle.config.ts](../code/shop-api/drizzle.config.ts)，`pnpm db:generate` 真能生成迁移文件（`drizzle/0000_amused_phil_sheldon.sql` + `meta/` 快照）——但**运行期建表走的仍是** [SCHEMA_SQL](../code/shop-api/src/db/database.ts) 里的 `create table if not exists`，两者并存且没有 `drizzle-kit migrate` 接线，`db:push` 也没跑过。也就是说「能生成」不等于「在用」：把它变成真正的版本化迁移，还差 boot 阶段的 `migrate()` 调用与 `__drizzle_migrations` 表。别把脚本当能力。
3. **`next build` 三种出口提前选。** `next start`（默认，需 `.next/` + Node 进程）最省心；`output: "standalone"` 镜像小很多但边界要自测；`output: "export"` 纯静态，用了 Server Action（[actions.ts](../code/web-next/src/app/actions.ts)）直接出局。
