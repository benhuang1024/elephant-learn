## 1. 生态地图：Laravel 组件 → Node 生态

这张表是本教程最「架构师」的一页。右列的**成熟度**指「在 Node/TS 世界里这套东西是否已经收敛到一个事实标准」；**PHP 人最常踩的选择误区**是我看你一定会踩的那一脚。

| 能力 | Laravel | Node / TS 生态 | 成熟度 | PHP 人最常踩的选择误区 |
|---|---|---|---|---|
| 路由 | `routes/web.php` | Nest `@Controller`（Express/Fastify 底层）；Next App Router 文件路由 | ★★★ | 在 Express 上手写 `app.get(...)` 散落各处 → 没有 DI、没有 Guard/Pipe 挂载点 |
| 中间件 | `Kernel.php` + 路由组 | `app.use()`（Express 层）/ `NestMiddleware` / Guard / Interceptor | ★★★ | 把鉴权写进 Middleware 而不是 Guard，导致拿不到 `ExecutionContext` 的元数据（`Reflector`） |
| 依赖注入 | Service Container | Nest 容器（**默认单例作用域**） | ★★★ | 遇事就 `REQUEST` scope：性能塌方；正确解法是 AsyncLocalStorage/`nestjs-cls` 传上下文 |
| ORM | Eloquent | Prisma（DX 最好）/ Drizzle（最接近 SQL 与 Laravel Query Builder）/ TypeORM（Active Record 派） | ★★★ | 用 Prisma 却想要 Eloquent 的「关系自动加载」→ N+1；Drizzle 的同步驱动（本仓库 `better-sqlite3`）会串行化请求 |
| 迁移 | `artisan migrate` | Drizzle Kit（`generate`/`migrate`）/ Prisma Migrate / Knex / node-pg-migrate | ★★★ | 以为 `db:push` 是生产迁移工具——它是原型工具，会丢数据 |
| 队列 | Horizon + Redis | **BullMQ**（Redis，最接近 Laravel Queue 的手感）/ **Buster**（Postgres 后端，少一个中间件） | BullMQ ★★★ / Buster ★★ | 把 BullMQ 的 job 当 fpm worker 用：worker 进程里塞 HTTP 服务器；或忘了 `concurrency` 与事件循环阻塞的关系 |
| 定时任务 | `schedule()` + crontab | 每分钟一次的 **Bull repeatable job**（多实例只跑一次）/ `node-cron`（进程内，多副本会重复） / 外部 cron + HTTP 端点 | ★★★ | 用 `node-cron` 部署 3 个副本 = 任务跑 3 次。这正是 Laravel `withoutOverlapping()` 替你挡掉的那件事 |
| 缓存 | `Cache::remember` | `ioredis` 手搓 / `@nestjs/cache-manager`（+ Caffeine 的等价物：**进程内 LRU**） | ★★★ | 以为进程内缓存在多副本下可用——它是「每个副本一份真相」，容量与一致性都要单独设计 |
| 邮件 | Mail + Mailable | Nodemailer + React Email / 各家 SaaS SDK | ★★★ | 自己实现重试与退避；直接交给队列或交易型邮件服务 |
| 文件存储 | `Storage::disk('s3')` | `@aws-sdk/client-s3` / `@google-cloud/storage` / MinIO | ★★★ | 把上传流读进内存（`await file.buffer`）→ 大文件 OOM；应流式转发 |
| 验证 | FormRequest + `Validator` | **Zod**（本仓库）/ class-validator + DTO 类 / Valibot / ArkType | ★★★ | 只用 TS 类型不用运行时校验——类型会被擦除，边界必须校验；把 Zod schema 写进 Controller 而不是共享包，四端各写一份 |
| 测试 | PHPUnit / Pest | **Vitest**（本仓库）/ Playwright（E2E）/ supertest（HTTP 断言） | ★★★ | 只测 Controller 层；忘给 `--coverage` 门禁；E2E 里依赖「干净状态」（[e2e spec](../code/shop-api/test/shop-api.e2e.spec.ts) 的注释就直说了这个取舍） |
| 认证 | Sanctum / Breeze / Fortify | **Auth.js**（原 NextAuth，Next 场景）/ Lucia（会话式，偏底层）/ `@nestjs/passport`（策略式）/ 自建 JWT | 各 ★★～★★★ | Next 里选 Auth.js、Nest API 里选 Passport，两套会话体系互不认识；应在一处发 token，另一处只验 |
| 授权 | Gate / Policy | CASL / 自写 Guard + `SetMetadata`（本仓库 [roles.decorator.ts](../code/shop-api/src/auth/roles.decorator.ts)） | ★★ | 把权限规则散写进每个 Controller；Spring/Laravel 是「集中式 matcher」，Nest 是「路由旁装饰器 + 全局 Guard」，选一种并贯彻 |
| 事件 | Event / Listener | Nest `EventEmitter2`（进程内）/ Redis Pub-Sub / NATS | ★★ | 进程内事件当作可靠的投递：请求结束就没了；持久化要用 Outbox + 队列 |
| 广播 / WS | Echo + Pusher | `socket.io` / `ws` / SSE（`@nestjs/platform-socket.io`） | ★★★ | 没设计 sticky session 或多副本下的 Redis adapter → 用户连到不同副本收不到消息 |
| 国际化 | `lang/*.json` | `node-intl` / `typesafe-i18n` / Lingui / Format.js | ★★ | 手写 `t()` 字符串映射；TS 侧的复数与性别屈折比 PHP 更依赖 Intl |
| 审计 / 软删除 | OwenIt/auditable、SoftDeletes | 无统一标准：中间件写审计表 / Drizzle 的 `deletedAt` / 事件溯源 | ★ | 以为 ORM 会顺手给你软删除；实际要自己写查询过滤，忘了就泄数据 |
| 全文搜索 | Scout | Meilisearch / Typesense / OpenSearch 客户端 | ★★★ | 用 SQL `LIKE` 顶替（本仓库 [product.repository.ts](../code/shop-api/src/product/product.repository.ts) 的 `lower(name) like lower(...)` 就是演示级方案） |
| 限流 | `RateLimiter` | `@nestjs/throttler` / 网关侧限流 | ★★★ | 在进程内做全局限流：多副本各限各的，等于没限 |
| HTTP 客户端 | `Http::get()` | 全局 `fetch`（undici）/ `axios` / `got` | ★★★ | 不设超时、不设 keep-alive、不重试幂等 GET；`fetch` 默认永不超时 |
| 模板 | Blade | JSX（React）/ SFC（Vue）/ EJS / Handlebars | ★★★ | 服务端渲染 Blade 的心智搬到 Next 却不标 `"use client"`，把服务端代码打进浏览器包 |
| 前端装配 | Inertia | Next RSC / Qwik / HTMX | — | 把 Inertia 直接映射成「RSC 就等价」：RSC 是渲染模型，Inertia 是控制器→页面 props 的路由协议 |
| 包管理 | Composer + Packagist | **pnpm + npm**（本仓库 workspace，pnpm 9.15.9 via corepack） | ★★★ | 用 npm 装 workspace（`workspace:*` 协议不认）；lockfile 与 `packageManager` 版本不一致导致大面积 diff |
| 配置 | `.env` + `config()` | 环境变量 + [config/env.ts 的 Zod 校验](../code/shop-api/src/config/env.ts) | ★★★ | `process.env.X!`（详见第 15 章第 5 节） |
| 管理后台 | Nova / Filament | react-admin / Refine / 自建 | ★★ | 以为有「装一下就有后台」的标准答案；Node 侧这块比 PHP 生态碎片得多 |
| 日志 | Monolog (PSR-3) | pino / winston / Nest `LoggerService` | ★★★ | 用 Nest 内置 Logger 上生产（本仓库现状，见第 15 章第 4 节缺口清单） |

三个最值得抄的落地片段（**本仓库未实现队列/定时/缓存，以下是给架构评审用的配方**）：

```ts
// BullMQ：≈ Laravel dispatch + Horizon，但 worker 必须是独立进程
import { Queue, Worker } from "bullmq";
const queue = new Queue("mail", { connection });              // ≈ dispatch(new SendOrderMail($order))
new Worker("mail", async (job) => sendMail(job.data), { connection, concurrency: 5 });

// 定时任务 ≈ $schedule->job(...)->everyMinute()->withoutOverlapping()
await queue.add("close-unpaid-orders", {}, {
  repeat: { pattern: "* * * * *" },
  jobId: "close-unpaid-orders",      // 固定 jobId + Redis 锁 ⇒ 多副本只有一份日程
});
```

```ts
// 缓存：Cache::remember 的等价物是「自己写」，没有 @Cacheable 那种声明式注解
const value = await redis.get(key);
if (value) return JSON.parse(value) as ProductResponse;
const fresh = await products.findById(id);
await redis.set(key, JSON.stringify(fresh), "PX", 60_000);
return fresh;
```

## 2. 什么时候该选 Node，什么时候继续用 PHP

这是架构师真正要回答的问题。别信「Node 更快」这种话——它只在**I/O 等待密集**且**单进程要扛很多并发连接**时成立。

| 场景 | 选 Node/TS | 继续 PHP | 判据 |
|---|---|---|---|
| WebSocket / SSE / 长连接推送 | ✅ | | PHP 常驻连接吃 fpm worker，长连接密度上去就崩 |
| BFF / 聚合层（给前端拼装 5 个下游） | ✅ | | 纯 I/O、扇出大、逻辑薄；TS 还能和前端共用 DTO |
| 边缘/服务端渲染（Next） | ✅ | | SSR 就是 Node 的主场，且和前端同仓同语言 |
| 需要「一份契约四端复用」 | ✅ | | 类型 + 运行时校验同源，这是 PHP 拿不到的红利 |
| CPU 密集：图像、转码、报表、批量计算 | | ✅（或 Go/Rust） | Node 单线程会阻塞整进程；PHP 至少只影响一个 worker，且 SaaS/离线队列才是正解 |
| 大事务、复杂批处理、幂等重放 | | ✅ | PHP + 队列 + chunk 的手感成熟；Node 侧要自己搭 Outbox/幂等 |
| 团队 10 年 PHP，业务比技术重要 | | ✅ | 迁移成本 = 人月；别把「学 TS」排进业务路线图 |
| 已有 Laravel 单体，前端要 SPA 化 | 混合：SPA + `laravel-echo`/API | | 只换前端不搬后端，是风险最低的一档 |
| 需要 worker 内长生命周期状态（连接池、编译产物缓存） | ✅ | | 常驻进程是优势也是负债；PHP 里你做不到「热」 |
| CRUD 后台 + 表单 + 权限 + 报表 | | ✅ | Laravel 这块生态密度无人能敌（Nova/Filament/Sanctum/Scout） |

一句话决策：**Node 拿「I/O 密集 + 长连接 + 端到端类型」，PHP 拿「生态成熟 + 团队储备 + 批处理与表单业务」**。你的直觉里「PHP 是脚本、Node 是服务端」这条已经过时；真正过不去的是**常驻进程 + 单线程**这两件事带来的心智重建（第 03 章）。

## 3. `any` 治理

`any` 的地位 ≈ PHP 里那个「什么都能塞的关联数组」。区别是：PHP 的数组只是丢失 IDE 提示，TS 的 `any` 会**双向兼容**，一个 `any` 能把整条调用链的类型传染掉。

本仓库当前的真实状态（[tools/eslint-config/index.mjs](../code/tools/eslint-config/index.mjs)）：

```js
...tseslint.configs.recommended,      // 注意：这是「非类型感知」那一档
rules: {
  "@typescript-eslint/no-unused-vars": ["error", { argsIgnorePattern: "^_", varsIgnorePattern: "^_" }],
  "@typescript-eslint/no-explicit-any": "warn",   // warn，不是 error
  eqeqeq: ["error", "always"],
}
```

也就是说：**本仓库的 lint 不会拦住 `any`**，只在 test 目录把它关掉，用 `warn` 做提示。真实豁免点就在代码里：[timed.decorator.ts](../code/shop-api/src/common/timed.decorator.ts) 文件头一行 `/* eslint-disable @typescript-eslint/no-explicit-any */`，因为方法装饰器必须替换 `descriptor.value`，签名绕不开 `any`；[utility-types.ts](../code/lang-basics/src/utility-types.ts) 里 `as Listener<E>[]` / `as never` 是泛型写入的经典妥协。

治理阶梯（从低到高，团队按人力选一档）：

| 规则 | 拦住什么 | 打开的代价 |
|---|---|---|
| `no-explicit-any: error` | 你主动写 `any` | 老代码一批红点，先 `warn` 再逐步 `error` |
| `recommendedTypeChecked` / `strictTypeChecked` | 类型层面的错误用法（`switch` 不穷尽、Promise 没 await…） | **需要 parserOptions.projectService**，全量类型分析，CI 时间涨 |
| `no-unsafe-assignment` / `-argument` / `-call` / `-member-access` / `-return` | **从第三方 JS 渗进来的** `any`（无 `.d.ts` 的包） | 这是真正的收益来源：`any` 多数不是你写的，是依赖给的 |
| `no-restricted-syntax` + `no-import-type-side-effects` | 禁止 `as any`、强制 `import type` | 需要配套 lint 说明文案，否则 PR 里吵不完 |

**`unknown` 优先**是本仓库已经在贯彻的一条，可以直接当范例（[problem.filter.ts](../code/shop-api/src/common/problem.filter.ts)）：

```ts
const body = exception.getResponse();                       // body: unknown（Nest 给的类型就是 unknown）
const detail = typeof body === "string" ? body : String((body as { message?: unknown }).message ?? "请求失败");
// 收窄在 error-handling.ts 里更标准：value instanceof Error ? value.message : String(value)
```

四件套怎么选：

| 手段 | 语义 | 什么时候用 |
|---|---|---|
| `unknown` + 收窄 | 「我不知道，但我会检查」 | **默认选择**，一切外部输入（HTTP body、JSON、env） |
| `as T`（断言） | 编译期改标签，运行时**什么都不做** | 只用于「编译器信息不足」的窄范围；配合 brand/schema 时立刻转回运行时校验 |
| `as any` | 关掉这个表达式的全部检查 | 只在装饰器/框架签名绕不开时，加一行注释说明为什么 |
| `@ts-expect-error` | 「下一行必须有错，没错就报 unused」 | 写测试反例、验证某个赋值确实不合法；比 `@ts-ignore` 安全得多 |
| `@ts-ignore` | 静默，永不回退 | **code review 红线**：禁止 |

review 红线清单（可直接进 CONTRIBUTING）：新代码里的 `any` / `@ts-ignore` / 非空断言 `!` / `as unknown as` 出现时必须在同一段解释理由；`as` 只允许出现在两个位置——边界 schema 解析之后、框架签名要求的窄范围；跨包传递的数据类型必须来自 `@shop/shared` 的 `z.infer`，不许手写 interface 复制字段。

**TS 7 的现实约束**（这是本仓库最重要的一条工程决策，见 [index.mjs 的注释](../code/tools/eslint-config/index.mjs)）：

```
typescript-eslint 8.x 依赖 TS 的 JS 编译器 API，而 TS 7（Go 原生编译器）不再提供它，
加载时会直接抛 "typescript-eslint does not support TS 7.0"。
```

本仓库的处理是 **side-by-side**：`@ts/eslint-config` 自己把 `typescript: 6.0.3` 写进 `dependencies`（[package.json](../code/tools/eslint-config/package.json)，typescript-eslint 8.72.0 的 peer 是 `>=4.8.4 <6.1.0`），pnpm 的隔离布局让 typescript-eslint 解析到这份 TS 6，而各业务包的 `tsc` 仍是 TS 7.0.2 —— **两套编译器并存**。`vue-tsc` 3.3.13 同样需要 TS 6，所以 [web-vue/package.json](../code/web-vue/package.json) 直接把 `typescript` 降成 `6.0.3`，代价是 `.vue` 的类型检查与 `tsc` 有细微语义差（这是**已知取舍**，不是 bug）。

架构师视角的结论：**「linter 落后于语言大版本」在 TS 生态是常态，不是事故**。规划升级窗口时把它当依赖项排进去：TS 大版本 → 等 typescript-eslint / vue-tsc 跟进 → 再统一抬 TS 版本。中间用 side-by-side 而不是「把 tsc 也降回 6」。

## 4. 渐进迁移策略（Strangler）

大爆炸式重写是禁忌。五步，每步都能独立回滚：

| 步 | 做什么 | 为什么先做这个 | 回滚方式 | 典型坑 |
|---|---|---|---|---|
| ① | **Next 承接页面**，PHP 继续当 API | 前端是唯一「必须换语言」的部分；后端零改动 | DNS/网关把路由切回 Blade | 会话打通：cookie 域 / SameSite；CSRF 双系统各一套 |
| ② | **新功能一律写 Nest**，旧功能不搬 | 让团队在有安全网的地方练手 | 新接口下线即可 | 两套鉴权体系互不认识 → 从第一步就统一发 token 的地方 |
| ③ | **shared 包承接契约** | 把「后端改字段，前端编译报错」变成机制而非约定 | 契约包只加不减，随时可回 | schema 写在 Controller 里，PHP 侧没有对应物 → 必须以 OpenAPI 为唯一源，用 `openapi-typescript` 生成 TS 类型，或反过来由 Zod 生成 OpenAPI |
| ④ | **按路由灰度**切流量 | 绞杀者模式的心脏：切的是流量不是代码 | 网关一键回切 | 灰度粒度用「用户 id 哈希」而不是随机百分比，否则同一用户在两套系统间跳 |
| ⑤ | **表所有权交接**：读旧写新 → 双写 → 事件同步 | 数据库是唯一不能「灰度」的共享状态 | 双写期可回 | 长期共享库 = 双写不一致；尽快用 CDC/Outbox 解耦，明确每张表只有一个写者 |

本仓库已经把第 ③ 步做出来了，可以直接当模板：[packages/shared/src/index.ts](../code/packages/shared/src/index.ts) 一句 `export * from "./decimal"` 把 schema 与推导类型同时导出，注释写的是「**类型不是契约，schema 才是**」。[decimal.ts](../code/packages/shared/src/decimal.ts) 里 `DecimalAmount` 是品牌字符串、`PositiveAmountSchema` 是入站校验、`toWireDecimal` 是出口格式化——同一段代码被后端与三套前端复用，这就是「共享包承接契约」的实物。

## 5. 团队与工程实践

**tsconfig 基线**。[tsconfig.base.json](../code/tsconfig.base.json) 是给 PHP 人的安全带，逐条看值：

| 选项 | 作用 | 对 PHP 人意味着 |
|---|---|---|
| `strict: true` | 打包 7 个 strict 子开关（含 `strictNullChecks`） | 唯一真相来源。任何包关掉 `strict` 都要写注释 |
| `noUncheckedIndexedAccess` | `arr[0]` 类型是 `T \| undefined` | 逼你处理 PHP 里「未定义索引 notice」的同一件事（本仓库到处 `[0]!`，是显式代价） |
| `noImplicitOverride` / `noImplicitReturns` / `noFallthroughCasesInSwitch` | 漏 return、忘 `default` 编译报错 | ≈ 静态分析前置 |
| `noUnusedLocals` / `noUnusedParameters` | 死变量 | 测试与 Next 页面里常关（本仓库 web-next 就关掉了） |
| `isolatedModules` + `verbatimModuleSyntax` | 每个文件能独立编译；类型导入必须 `import type` | 这是 bundler 时代的强制项，也是 `const enum` 的死刑 |
| `module/moduleResolution: nodenext` + `target ES2023` | 按 Node 真实 ESM 规则解析 | `.js` 说明符的来源 |
| `useDefineForClassFields: false`（仅 shop-api） + `experimentalDecorators` + `emitDecoratorMetadata` | Nest 的 DI 靠 `reflect-metadata` 读构造函数参数类型 | 别「顺手现代化」这两项，容器会瞎 |

**PR 门禁**（本仓库没有 CI 配置文件，以下是建议的最小集）：

```bash
pnpm -r typecheck   # 每个包：tsc --noEmit（web-vue 是 vue-tsc --noEmit）
pnpm -r lint        # eslint .（由 @ts/eslint-config 统一）
pnpm -r test        # vitest run
pnpm --filter @shop/api test:e2e   # 先 build 再 supertest
```

两个必须写进团队文档的现实：一是 `pnpm -r` 虽然按 workspace 拓扑序执行同一个脚本名，但**拓扑序 ≠ 依赖先构建**——`typecheck` 脚本本身不 emit，所以 `@shop/shared/dist/*.d.ts` 不会被它产出来。本仓库的解法很直白：**每个包的 `typecheck`/`test` 脚本前面都挂 `pnpm --filter @shop/shared build &&`**（见 [shop-api/package.json](../code/shop-api/package.json)、[web-react/package.json](../code/web-react/package.json)、[web-next/package.json](../code/web-next/package.json)）。如果你嫌重复，用 `pnpm --filter @shop/api... build`（`...` 后缀 = 连依赖一起构建）在门禁里先统一构建一次。二是**类型检查与测试分开**：Vitest 转译不检查类型，`pnpm test` 全绿不代表 `pnpm typecheck` 能过。

**代码所有权**：`packages/shared/` 必须有明确的 owner（它是四端的公共依赖，改动等于改 API 契约）；任何往 `shared` 加东西的 PR 要求两个包各一人 approve；`shop-api/src/db/schema.ts` 与 `shared` 的 DTO 不一致时，**以 shared 为准**，schema 是它的下游。

**类型体操的边界**——「够用即可」的三条判据：

1. 一个类型别名如果超过 3 行嵌套映射，先问「能不能用运行时 schema 换掉它」。`@shop/shared` 全部是 `z.infer` 推导，所以没有一行手写映射类型需要维护。
2. 出现 `as never` / 双重断言 = 你在跟编译器吵架。本仓库把它放进 [utility-types.ts](../code/lang-basics/src/utility-types.ts) 的「教学示例」区（`TypedEventBus.on` 里那句「泛型写入的经典问题：编译器无法证明 list 的形状就是 handlers[E]」），生产代码里应改成 `Record<string, unknown>` + 边界收窄，或引入函数重载。
3. 品牌类型（[branded-ids.ts](../code/lang-basics/src/branded-ids.ts) 的 `ProductId` / `OrderId`）是**低成本高收益**的那一类：一个 `unique symbol` 假字段，挡住「两个 number 传错」。递归 `DeepReadonly<T>` 是高成本低收益的那一类。

**升级窗口规划**（把「工具链落后」当常态）：

| 层 | 本仓库现状 | 落后时的处置 |
|---|---|---|
| 语言 | TypeScript 7.0.2（Go 原生编译器） | 先升 `tsc`，业务收益立现（构建快） |
| Lint | ESLint 10.13.0 + typescript-eslint 8.72.0，**锁 TS 6.0.3** | side-by-side：让 `@ts/eslint-config` 自带旧 TS；等上游支持再抬 |
| 模板类型检查 | `vue-tsc` 3.3.13，**需要 TS 6** | web-vue 独立降 TS；不要在 workspace 里全局降版本 |
| 构建 | Vite 8.3.5（依赖里是 **rolldown**，不是 esbuild）/ Next 16.4.3（Turbopack） | 换打包器时最先是 source map 与产物体积，灰度一条流水线 |
| 运行时 | Node v24.21.0，pnpm 9.15.9（corepack 按 `packageManager` 取版本） | `engines.node: ">=24"` 已经在根 package.json，CI 必须锁同一版本 |

## 6. 本仓库的架构：三套前端 + 一个后端

```
code/
├─ pnpm-workspace.yaml          # 7 个包：lang-basics, packages/*, shop-api, tools/*, web-*
├─ tsconfig.base.json           # 全 workspace 共享基线（各包只写差异）
├─ tools/eslint-config/         # @ts/eslint-config：唯一 lint 真相源，自带 TS 6.0.3
├─ packages/shared/             # @shop/shared：Zod 契约 + 品牌金额 + problem+json（ESM）
├─ lang-basics/                 # 可执行笔记（每主题一文件 + 一测试），不产出 dist
├─ shop-api/                    # @shop/api：Nest 12，端口 8080，ESM（"type": "module"）
├─ web-react/                   # @shop/web-react：Vite 8 + React 19 + TanStack Query，端口 3000
├─ web-vue/                     # @shop/web-vue：Vite 8 + Vue 3.5 + Pinia 4，端口 3010
└─ web-next/                    # @shop/web-next：Next 16 RSC + Server Action，端口 3100
```

| 包 | 演示什么 | 数据获取方式 | 对照 Laravel |
|---|---|---|---|
| `lang-basics` | 语言与运行时直觉（金额、异步、branded、Result、工具类型） | — | 单文件脚本 `node scripts/hello.ts` 靠 Node 24 原生擦类型 |
| `packages/shared` | **契约即代码**：schema 一次写，四端复用 | — | DTO + FormRequest + Resource 三合一 |
| `shop-api` | Nest 的模块边界、Guard/Interceptor/Pipe/Filter、Drizzle 事务与乐观锁 | — | Laravel 的 `app/` + Eloquent |
| `web-react` | CSR + 服务端状态缓存（`staleTime`/`retry`） | `useQuery` + [queryClient.ts](../code/web-react/src/queryClient.ts) | 无（PHP 视角是「一个会缓存的 axios 层」） |
| `web-vue` | 手写 store：跨组件共享状态 + `computed` 派生 | [stores/catalog.ts](../code/web-vue/src/stores/catalog.ts)（Pinia composition 写法） | Blade + session 的「服务端有状态」在这里换成客户端有状态 |
| `web-next` | RSC + Server Action：服务端直接 `await` 数据 | [lib/api.ts](../code/web-next/src/lib/api.ts) + [actions.ts](../code/web-next/src/app/actions.ts) | 最像 Laravel：`Controller → Blade`，只是渲染单元是组件、跳转换成 `revalidatePath` |

三套前端刻意用三种不同范式打同一个 API，是为了让你比较「同一契约在不同渲染模型下的成本」。共同点是**四个入口都 import `@shop/shared`**：`fetchProducts` 在 React / Vue / Next 三处都写 `z.array(ProductResponseSchema).parse(...)`（[web-react/src/api.ts](../code/web-react/src/api.ts)、[web-vue/src/api.ts](../code/web-vue/src/api.ts)、[web-next/src/lib/api.ts](../code/web-next/src/lib/api.ts)），后端则用同一批 schema 做入站校验（[zod.pipe.ts](../code/shop-api/src/common/zod.pipe.ts)）。这是本仓库最该被搬进你项目的部分。

**为什么现在这样摆，以及怎么演进**：`pnpm-workspace.yaml` 目前是混合列表（业务包 + `packages/*` + `tools/*` 混在顶层）。项目一大就改成标准布局：

```yaml
packages:
  - "apps/*"        # shop-api、web-react、web-vue、web-next、worker-mail
  - "packages/*"    # shared（契约）、api-client（fetch 封装，见下）、config（tsconfig/eslint 基线）
```

演进触发条件（不要提前做）：① 三套前端里出现第二份「API 客户端」代码 → 抽 `packages/api-client`（现在三份 `ApiProblem` 是刻意重复，用来讲对比）；② 出现跨前端复用的组件 → `packages/ui`；③ 队列 worker 上线 → `apps/worker`；④ 第二个后端服务 → 先做**模块化单体**（按 `product/`、`order/` 这类特性目录已经成型），别急着拆服务。反向建议：`lang-basics` 这类教学包不要进 `apps/`，它的 `noEmit` 与 `.ts` 扩展名导入（[tsconfig.json](../code/lang-basics/tsconfig.json)）是刻意的。

## 7. 横向对比：同一请求在 java/ 与 typescript/ 里

两个 shop-api 是逐字段对齐着写的，所以这张表可以直接当「运行时模型差异表」读。行为均经 curl/e2e 验证。

| 观察点 | Java 版（Spring Boot 4 / JPA / H2→PG） | 本仓库（Nest 12 / Drizzle / SQLite） | 差异根因 |
|---|---|---|---|
| `GET /api/products` 的价格字段 | `"price": 599.00` | `"price": 599` | **同一个真实差异**：`BigDecimal` 有 scale，Jackson 原样输出；JS `number` 无「几位小数」概念，`JSON.stringify(599.00)` 必为 `599`（[decimal.ts 的 `toWireDecimal`](../code/packages/shared/src/decimal.ts) 注释里就写着这条）。语义等价、字面不同 |
| 金额在类型系统里的样子 | `BigDecimal` 一路到 DTO | `DecimalAmount` 品牌字符串 + 整数分运算 | TS 没有 BigDecimal，`0.1 + 0.2` 教训搬到库里同样成立，所以 [schema.ts](../code/shop-api/src/db/schema.ts) 用 `text("price")` 存 `"599.00"` |
| `POST /api/products`（无认证） | `401` + `WWW-Authenticate: Basic realm="Realm"` | 完全一致 | Java 由 Security 在 DispatcherServlet 前短路；Nest 由 Guard 在 Interceptor 前短路 |
| 401 是否带 `X-Elapsed-Ms` | 不带 | 不带 | 两边同构，[timing.interceptor.ts](../code/shop-api/src/common/timing.interceptor.ts) 注释里专门点了这条「自动对齐」 |
| `Accept: application/json` 的 401 | 空 body、无 `WWW-Authenticate` | 同 | [problem.filter.ts 的 `writeSecurityError`](../code/shop-api/src/common/problem.filter.ts) 手工复刻了 Spring 的 Accept 分支 |
| 下单成功 | `201`，库存 `20→18`，商品 `version 0→1`，`Location: /api/orders/{id}` | 同 | `@HttpCode(201)` + `response.location()` vs `ResponseEntity.created(uri)` |
| 库存不足 | `409` problem+json，含 `sku/requested/available` | 同（文案逐字一致 `库存不足 sku=SKU-003 需要=… 剩余=…`） | 两边都是「领域异常 + 全局兜底」：`@RestControllerAdvice` vs `@Catch()` Filter |
| 校验错误的字段路径 | `items[0].quantity` | 同（[field-errors.ts](../code/packages/shared/src/field-errors.ts)） | Bean Validation 级联 vs Zod issue.path |
| 乐观锁 | Hibernate 在 `UPDATE ... WHERE` 自动追加 `version=?`，失败抛 `ObjectOptimisticLockingFailureException` | 手写 `where(and(eq(id), eq(version)))` + `changes === 0` | [order.repository.ts](../code/shop-api/src/order/order.repository.ts)：少一层魔法，也少一类「为什么注解没生效」 |
| 乐观锁冲突能否**测出来** | 能（多连接真并发） | **e2e 里几乎造不出来** | better-sqlite3 同步驱动 + 单线程 ⇒ 事务串行化；换异步 `pg` 后窗口才真实存在 |
| 事务写法 | `@Transactional`（自调用会失效，见 Java 第 07 章） | `db.transaction(cb)` 显式包住；`@Timed` 装饰器直接替换原型方法，**自调用照样生效** | TS 没有运行时代理，少了一整类经典坑 |
| `request-id` 的去向 | Filter 写入 **MDC** → 每条日志自动带 | 挂 `request.requestId` + 回显响应头 → **不进日志** | 第 15 章第 4 节的缺口；仓库里连 `pino` 依赖都没有，日志就是 Nest 内置 `Logger` 的行文本 |
| 建表 | Flyway `V1__init.sql`，版本化迁移 | 启动时 `SCHEMA_SQL` 的 `create table if not exists`；[drizzle.config.ts](../code/shop-api/drizzle.config.ts) 已配好、`db:generate` 跑过并产出 `drizzle/0000_*.sql`，但 boot 阶段没有 `migrate()` | Node 侧迁移「能生成」但没接管运行期，这是真实差距 |
| 配置 | `application.yml` + profile（含 `postgres` profile） | [env.ts](../code/shop-api/src/config/env.ts) 的 Zod schema，**无 profile**，SQLite only | Spring 的 profile 是框架特性，Node 要自己搭 |
| 运维端点 | Actuator 内置；`health,info,metrics` 放开；prometheus 可加 | 手写 [actuator.controller.ts](../code/shop-api/src/health/actuator.controller.ts) 三个端点，`metrics` 需认证 | Node 生态没有内置 Actuator；`@nestjs/terminus` 是常规选择 |
| 指标实现 | Micrometer + `LongAdder`（线程安全） | 普通 `Map<string, number>`（[users.service.ts 的 `Metrics`](../code/shop-api/src/auth/users.service.ts)） | **单线程 ⇒ 不需要并发容器**，这是语言模型给的最直观红利之一；代价是多副本不共享 |
| 密码 | BCrypt（`InMemoryUserDetailsManager`） | SHA-256 + `timingSafeEqual`（只为了定长比较） | 两边都**不是**生产方案；本仓库没有安全专章，认证只做到演示级（[basic-auth.guard.ts](../code/shop-api/src/auth/basic-auth.guard.ts)），真实项目用 argon2id/bcrypt + 集中发 token |
| 时间字段 | `LocalDateTime` → `2026-…T09:33:41.123456`（6 位） | `nowLocalIso()` → 毫秒 3 位、无时区后缀 | JS 的 `Date` 永远带时区，为了对齐才手拼本地字段（[time.ts](../code/packages/shared/src/time.ts)） |
| 前端 | 无（只有 curl + README 走查） | 三套真实前端 + 共享契约包 | TS 教程的既有目标不同 |
| 测试 | JUnit + MockMvc + `@DataJpaTest` + Testcontainers | Vitest + supertest（[e2e](../code/shop-api/test/shop-api.e2e.spec.ts) 断言集合与 Java README 的 curl 表基本一一对应） | — |
| 并发容量旋钮 | `server.tomcat.threads.max` / 虚拟线程 | 进程数：cluster / PM2 `instances` / `replicas` | Java 的「线程旋钮」到 Node 变成「进程旋钮」，见第 15 章第 3 节 |

## 8. 选型清单（新项目默认值）与反模式

| 决策点 | 建议默认 | 说明 |
|---|---|---|
| 运行时 | Node 24 LTS（`engines.node` 写进根 package.json） | 别用「最新非 LTS」；type stripping 只适合脚本 |
| 包管理 | pnpm + workspace + corepack（锁 `packageManager`） | monorepo 唯一不纠结的答案 |
| 语言配置 | 单一 `tsconfig.base.json`（strict 全家桶）+ 各包只写差异 | 关任何开关要有注释 |
| 后端框架 | NestJS（Express 或 Fastify 平台） | 需要极致 I/O 吞吐选 Fastify；生态兼容选 Express |
| 契约 | Zod + 独立 `shared` 包 | schema 即类型即校验即文档 |
| ORM | Drizzle（贴近 SQL）或 Prisma（DX 优先） | **异步驱动**（`pg` / `postgres.js`）用于生产 |
| 迁移 | Drizzle Kit / Prisma Migrate + 发布前置作业 | `push` 不上生产 |
| 队列 | BullMQ（Redis）或 Buster（Postgres） | 已有 Redis 选 BullMQ，想少一个组件选 Buster |
| 定时 | Bull repeatable job | 多副本只跑一次；`node-cron` 只在单副本工具里用 |
| 缓存 | Redis（`ioredis`）；进程内 LRU 只当「本地加速层」 | 想清楚一致性与副本数的关系 |
| 日志 | pino + 请求级 child logger + JSON | 第 15 章第 4 节 |
| 指标/追踪 | prom-client（RED 三件套 + 事件循环 lag）+ OTel | 分两步上 |
| 测试 | Vitest + supertest + Playwright | 类型检查是独立门禁，不由测试代劳 |
| 前端 | 内容/SEO 站点 → Next；内部系统 → Vite + React/Vue | 团队已有 Vue 经验就别换 |
| 代码质量 | ESLint（typescript-eslint）**类型感知档** + Prettier + `no-unsafe-*` | 注意上游对 TS 大版本的跟进延迟 |

来自 PHP 习惯的反模式（对照 Java 第 11 章那张表读）：

| 反模式 | 为什么是坑 | 正确做法 |
|---|---|---|
| `Record<string, any>` 到处传（「PHP 关联数组思维」） | 类型系统瞬间归零，重构靠运气 | 定义 interface / `z.infer` |
| 把请求级状态放进模块级变量 | 常驻进程 ⇒ 跨请求串数据 | 挂 `request` 上 / AsyncLocalStorage |
| 用 TS 类型当校验（「我声明了 `ProductResponse` 所以数据是对的」） | 类型运行时不存在 | 边界一律 `schema.parse` |
| 在 Service 字段上存当前用户 | 单例，全进程共享 | 参数传入 / `@CurrentUser()` |
| 实体直接当响应 | 字段泄漏 + 契约与表结构耦合 | `toProductWire` 这类显式 wire DTO |
| `@ts-ignore` 消错误 | 静默，永不回退 | 收窄 / `@ts-expect-error` + 理由 |
| 一个 `Promise.all` 扇出 1000 请求 | 打爆下游，且一坏全坏 | 限流器 + `allSettled` |
| 在 CPU 循环里服务请求 | 整个进程被堵 | 队列 / worker_threads |
| `process.env.X!` | 编译期谎言 | `validateEnv` + Zod |
| 多副本部署后 `node-cron` 跑 N 次 | 每个进程都有一份日程 | Bull repeatable / 分布式锁 |
