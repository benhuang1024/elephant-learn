# 05 运行时校验与边界 —— 类型会被擦除，所以边界必须校验

> 测试：[values-and-types.test.ts](../code/lang-basics/test/values-and-types.test.ts)、[branded-ids.test.ts](../code/lang-basics/test/branded-ids.test.ts)、[decimal.test.ts](../code/packages/shared/test/decimal.test.ts)、[schemas.test.ts](../code/packages/shared/test/schemas.test.ts)（`@shop/shared` 共 19 个用例）。

## 1. 论点：类型只存在于编译期

PHP 里 `function f(ProductView $p)` 是**运行时保证**：传错类型，`TypeError` 立刻抛出，即使你从 JSON 里 `json_decode` 出来的是一个 stdClass，转成数组后传进去也会当场失败。

TS 不是。类型在编译后被**完全擦除**（type erasure），运行时一个字节都不留 —— [values-and-types.ts](../code/lang-basics/src/values-and-types.ts) 里这段函数把证据打印出来，[对应测试](../code/lang-basics/test/values-and-types.test.ts)逐条锁住：

```ts
export function runtimeOnlyTruth(): string {
  const list = [1, 2, 3] as number[];
  return `编译期是 number[]，运行时只是 typeof list = ${typeof list} / Array.isArray = ${Array.isArray(list)}`;
}
// 测试断言：
expect(runtimeOnlyTruth()).toContain("typeof list = object");
const product: ProductView = { sku: "s", name: "n", priceCents: 1 };
expect(Object.keys(product)).toEqual(["sku", "name", "priceCents"]);  // 类型没往对象里加任何东西
```

[scripts/hello.ts](../code/lang-basics/scripts/hello.ts) 更直白：删掉所有类型注解，那段代码一模一样能跑。于是所有「运行时保证」必须由你自己在**边界**上实现：

| 边界 | 谁来保证 |
|---|---|
| HTTP 入参（body / query / params） | Zod + Pipe |
| HTTP 出参（前端消费的 JSON） | Zod（前端 parse 一次） |
| 环境变量 / 配置 | Zod（启动时一次） |
| 数据库读出来的行 | Drizzle 的表类型 + 必要时 Zod（见第 8 节） |
| 内部函数之间的调用 | **类型系统就够了**，别再加校验 |

## 2. `as` 不是校验

这是 PHP 人最容易犯的错，因为 `(array)` / `(int)` 在 PHP 里确实会**产生一个新值**。TS 的 `as` 什么都不做：

```ts
/** `as` ≈ PHP 的类型强转，但它只骗过编译器，不改变运行时值。 */
export function unsafeCastExample(payload: unknown): ProductView {
  return payload as ProductView;   // 没有 instanceof、没有遍历、没有默认值
}
```

对应测试（[values-and-types.test.ts](../code/lang-basics/test/values-and-types.test.ts)）：

```ts
it("as 只骗编译器，运行时字段一个都不会多出", () => {
  const fake = unsafeCastExample({ totally: "wrong" });
  expect(fake.sku).toBeUndefined();
});
```

| 操作 | 编译期 | 运行时 | PHP 里的对应直觉 |
|---|---|---|---|
| `x as T` | 通过（只要类型「部分重叠」） | **无任何字节码** | 像 `(array)`，但**不复制、不转换、不校验** |
| `T` 类型注解 | 检查赋值处 | 无 | 像参数类型声明，但**不拦截** |
| `z.TSchema.parse(x)` | 返回 `T` | **真的遍历 + 抛错** | `FormRequest::validate()` |
| `instanceof` / `typeof` | 收窄 | 真检查 | `instanceof`，但只能对 class 用 |

`as` 唯一正当的用法有两类：① 你已经用别的手段保证过（`toProductId` 里的 `value as ProductId`，工厂函数已校验）；② 告诉编译器你比它更懂（`items[0]!` 这类）。剩下的地方，`as` 就是「把运行时错误推迟到离现场很远的位置」。

## 3. Zod 4：schema 是值，类型是推导

Zod 的核心是**「校验器是一个普通 JS 对象（值）」**，这在 PHP 里没有完全对应的东西 —— Laravel 的 rule 数组是配置，Symfony 的 validator 是注解元数据，Spring 是注解；只有 Zod 同时给你值和类型。

[product.ts](../code/packages/shared/src/product.ts) 里的两个真实 schema：

```ts
export const ProductResponseSchema = z.object({
  id: z.int(), sku: z.string(), name: z.string(),
  price: PositiveAmountSchema, stock: z.int(), version: z.int(),
});
export type ProductResponse = z.infer<typeof ProductResponseSchema>;

export const CreateProductRequestSchema = z.object({
  sku: z.string().trim().min(1, "不能为空").max(64, "个数必须在 0 和 64 之间"),
  name: z.string().trim().min(1, "不能为空").max(200, "个数必须在 0 和 200 之间"),
  price: PositiveAmountSchema,
  stock: z.int().min(0, "必须大于或等于 0").default(0),
});
```

| Zod 4 写法 | 做什么 | Laravel / Symfony / Spring 对照 |
|---|---|---|
| `z.object({...})` | 定义 DTO 形状 | `FormRequest::rules()` 的键集合 / record 的字段 |
| `z.int("必须是整数")` | 必须是整数，带自定义消息 | `assert_int` / `@NotNull` + 消息 |
| `.trim()` | **会改值**：解析结果已去掉空格 | Laravel `TrimStrings` 中间件 |
| `.min(1, "不能为空")` | 最小长度 + 消息 | `required\|min:1` / `@NotEmpty` |
| `.max(64, "...")` | 最大长度 | `max:64` / `@Size(max = 64)` |
| `.positive("必须是正数")` | > 0 | `positive` / `@Positive` |
| `.default(0)` | 缺省补值（缺 `stock` → 0） | 无直接对应，靠模型属性默认值 |
| `.optional()` | 允许不存在 | `sometimes` / `@Nullable` |
| `z.enum(ORDER_STATUSES)` | 字面量联合 | `in:PAID,CANCELLED` / Java `enum` |
| `.refine(fn, msg)` | 自定义谓词 | 自定义 Rule / `@AssertTrue` |
| `.transform(fn)` | **改类型**：number 进、字符串出 | 无（最像 Laravel 的 `cast` + 校验合体） |
| `.loose()` | 保留未知字段（`ProblemDetail` 的业务附加字段） | Laravel 允许额外键；Spring 的 `FAIL_ON_UNKNOWN_PROPERTIES=false` |
| `z.record(z.string(), z.string())` | Map 型 | `array<string,string>` |
| `z.iso.datetime({ offset: true, local: true })` | ISO 字符串 | `date` / `@DateTimeFormat` |
| `z.coerce.number()` | 字符串→数字再校验 | env 里 `NUMBER` cast |

三个 Zod 4.6.7 的实测 API 事实（从旧教程抄代码会踩）：① 顶层函数化了，`z.email()`、`z.int()`、`z.iso.datetime()` 是正解，`z.string().email()` 只是保留的旧别名；② 未知字段的策略叫 `.loose()` / `.strict()`，`passthrough` 是旧名；③ 错误对象上的字段是 **`error.issues`**，`error.errors` 在这个版本上已经不存在（`'errors' in err === false`）。

### `as const` + `z.enum` = 一处声明两个用途

```ts
export const ORDER_STATUSES = ["PENDING", "PAID", "CANCELLED"] as const;
export const OrderStatusSchema = z.enum(ORDER_STATUSES);
export type OrderStatus = z.infer<typeof OrderStatusSchema>;
```

新增一个状态时改一行，运行时校验、TS 联合类型、前端下拉框三处同时对齐。在 PHP 里这是 backed enum `enum OrderStatus: string` 的看家本领，Zod 靠推导达到同样效果。

## 4. 一次定义，四处复用

这是 `@shop/shared` 这个包存在的全部理由：

```
                  ┌─ shop-api 的 ZodValidationPipe：校验 body / query，产出领域 DTO
@shop/shared ─────┼─ shop-api 的 ProblemDetailsFilter：ProblemDetailSchema 定义错误契约
（Zod schema +    ├─ web-react / web-vue：响应到达后 parse 一次，把 599 收回 "599.00"
  z.infer 类型）  └─ web-next：Server Component 里 parse 同一个 schema
```

| 校验层 | Laravel | Symfony | Spring | Nest + Zod（本仓库） |
|---|---|---|---|---|
| 声明位置 | `FormRequest::rules()` | `#[Assert*]` 注解 | `@NotNull` 注解在 record 上 | **Zod schema 常量** |
| 触发点 | 路由自动解析 FormRequest | `@Valid` + 参数解析器 | `@Valid` + `MethodArgumentNotValidException` | 自定义 `Pipe`（`@nestjs/common` 不带 Zod） |
| 失败产物 | 重定向 / `{"message","errors"}` | ViolationList | `ProblemDetail.errors` | `ValidationFailure` → `problem+json` |
| 前端复用同一份规则 | ❌（要装 `@laravel-validation-spa` 之类） | ❌ | ❌（除非生成 OpenAPI + 客户端） | ✅ **同一份 JS 包，`z.infer` 顺带给类型** |
| 类型来自校验 | ❌ | ❌ | 注解本身带类型 | ✅ `z.infer` |

最后一行是真正的差异：**Laravel/Symfony/Spring 的校验规则和类型系统是两套东西，会漂移；Zod 的 schema 是唯一真相，类型从它推导。** shared 的 [index.ts](../code/packages/shared/src/index.ts) 顶部注释写的就是这句：「类型不是契约，schema 才是」。工程代价是 `@shop/shared` 必须是**被编译的包**（`exports` 指向 `dist/`），所以每个下游都要 `pnpm --filter @shop/shared build` 打头 —— 见第 04 章第 5 节。

## 5. `transform` + `refine`：金额校验的等价翻译

Java 侧的 price 字段带三个注解 —— `@NotNull @Digits(integer = 10, fraction = 2) @DecimalMin("0.01") BigDecimal price`（[product.ts](../code/packages/shared/src/product.ts) 的注释里就写着这组对照）。TS 侧的等价实现，[decimal.ts](../code/packages/shared/src/decimal.ts)：

```ts
export const DecimalInputSchema = z
  .union([z.number(), z.string()])
  .transform((raw, ctx): DecimalAmount => {
    const parsed = parseDecimal(raw);
    if (parsed === null) {
      ctx.addIssue({ code: "custom", message: "金额必须是最多两位小数的数字（整数部分最多 10 位）" });
      return "0.00" as DecimalAmount;   // addIssue 之后本次解析一定失败，返回值只是占位
    }
    return parsed;
  });

/** 带下限的金额，等价于 `@DecimalMin("0.01")` + `@Digits` 的组合。 */
export const PositiveAmountSchema = DecimalInputSchema.refine(
  (amount) => decimalToCents(amount) >= 1,
  { message: "必须大于或等于 0.01" },
);
```

对应关系：

| Jakarta | Zod | 落点 |
|---|---|---|
| `@Digits(integer=10, fraction=2)` | `transform` + 正则 `^-?\d{1,10}(\.\d{1,2})?$` + `ctx.addIssue` | `parseDecimal` → `DECIMAL_RE` |
| `@DecimalMin("0.01")` | `.refine((a) => decimalToCents(a) >= 1)` | `PositiveAmountSchema` |
| `BigDecimal` 的 scale 保持 | `transform` 的**输出类型**是品牌字符串 `"599.00"` | `DecimalAmount` |
| 「同时接受 number 和 string」 | `z.union([z.number(), z.string()])` | 入站宽容，内部严格 |

三个关键手法值得单独记住：

1. **`transform` 里的校验必须走 `ctx.addIssue`**，不能只 `return null` —— 返回值会被当成成功结果。`addIssue` 之后这次解析一定失败，所以那个占位返回值永远不会被业务读到。
2. **`refine` 挂在 `transform` 之后**，所以它拿到的已经是规范化的 `DecimalAmount`，可以放心 `decimalToCents`。顺序反过来就是 bug。
3. **精度判断不用浮点比较**。`parseDecimal(1.005)` 会先看 `toFixed(2)` 能否还原原值（`formatNumberForDecimal`），不能还原就判非法 —— 这等于 Java 里「BigDecimal 必须从字符串构造」那条纪律。

[decimal.test.ts](../code/packages/shared/test/decimal.test.ts) 实测：

```ts
expect(DecimalInputSchema.parse(1999)).toBe("1999.00");
expect(DecimalInputSchema.parse("1999.0")).toBe("1999.00");
expect(() => DecimalInputSchema.parse("1.999")).toThrow(/最多两位小数/);
expect(PositiveAmountSchema.parse(0.01)).toBe("0.01");
const failure = PositiveAmountSchema.safeParse(0);
if (!failure.success) expect(failure.error.issues[0]?.message).toBe("必须大于或等于 0.01");
```

注意 `parse` 和 `safeParse`：前者抛 `ZodError`，后者返回 `{ success, data | error }`。服务端 Pipe 用 `safeParse`（要把错误变成响应体），测试断言和一次性初始化用 `parse`。

## 6. 把 ZodError 拍平成 problem+json `errors`

Laravel 给前端的错误是 `{"message": "...", "errors": {"sku": ["不能为空"]}}`（值数组），Spring 给的是 `ProblemDetail.errors` 的「字段路径 → 单条消息」。本仓库选了 Spring 那种形状 —— [field-errors.ts](../code/packages/shared/src/field-errors.ts)：

```ts
export function formatPath(path: readonly PropertyKey[]): string {
  let out = "";
  for (const segment of path) {
    if (typeof segment === "number") out += `[${segment}]`;
    else { const text = String(segment); out += out === "" ? text : `.${text}`; }
  }
  return out;
}

export function toFieldErrors(error: ZodError): Record<string, string> {
  const result: Record<string, string> = {};
  for (const issue of error.issues) {
    const key = formatPath(issue.path);
    const field = key === "" ? "_" : key;   // 表单级问题（path 为空）用 "_" 作键
    if (!(field in result)) result[field] = issue.message;   // 首条胜出
  }
  return result;
}
```

四条与既有生态对齐的决定：

| 决定 | 原因 |
|---|---|
| 嵌套用 `.`，数组用 `[i]` | `items[0].quantity` —— 和 Spring `@Valid` 级联后的 `PropertyPath` 字面一致，Laravel 的前端组件也认这个 |
| 同一字段多条问题**只留第一条** | Java 侧用 `putIfAbsent`，行为必须一致，否则两个后端给同一个错误码会产生不同响应 |
| `path` 为空（表单级问题）用键 `"_"` | 避免出现 `""` 这个前端无法定位的键 |
| 值是 `string` 而不是 `string[]` | 与 `ProblemDetail.errors: Record<string,string>` 的 schema 对齐（[problem.ts](../code/packages/shared/src/problem.ts)） |

完整链路（三个文件接力）：

```
请求 → ZodValidationPipe.transform() → safeParse 失败
     → throw new ValidationFailure(toFieldErrors(error), error)   [zod.pipe.ts]
     → ProblemDetailsFilter.catch()                                [problem.filter.ts]
     → writeProblem(response, 400, validationProblem(fieldErrors)) [problem.ts]
     → {"title":"参数错误","status":400,"detail":"请求参数校验失败","errors":{"sku":"不能为空"}}
```

[schemas.test.ts](../code/packages/shared/test/schemas.test.ts) 里锁住这段的两端：

```ts
const errors = toFieldErrors(failure.error);
expect(Object.keys(errors)).toEqual(["sku", "name", "price"]);       // 顺序 + 键名
expect(errors["items[0].quantity"]).toBe("必须大于或等于 1");        // 嵌套下标
```

还有一条常被忽略的行为，也写进了测试：**未知字段被剥掉**（`"hackMe" in parsed === false`），对应 Spring 的 `FAIL_ON_UNKNOWN_PROPERTIES=false`。这就是 mass assignment 防护 —— 等价于 Laravel 的 `$fillable`，只不过它长在 schema 上而不是模型上。

Pipe 本体只有 6 行，值得逐字读：

```ts
transform(value: unknown, _meta: ArgumentMetadata): TOutput {
  const result = this.schema.safeParse(value ?? {});
  if (result.success) return result.data;
  throw new ValidationFailure(toFieldErrors(result.error as ZodError), result.error);
}
```

入参类型是 `unknown` —— 这就是「边界」的定义：从这一行开始，数据才从「运行时才知道的任意值」变成「有类型的 DTO」。

## 7. 环境变量：第二类外部输入，启动即失败

Laravel 的现实是：`env('DB_URL')` 写错键名，要到第一次用到时才炸，而且是在某个请求里炸。Spring 的做法是 `@ConfigurationProperties` + `@Validated` —— **启动时**绑定并校验，不合法就不让应用起来。Nest + Zod 走的是 Spring 那条路。

[env.ts](../code/shop-api/src/config/env.ts)：

```ts
export const EnvSchema = z.object({
  NODE_ENV: z.enum(["development", "production", "test"]).default("development"),
  PORT: z.coerce.number().int().positive().default(8080),
  DB_FILE: z.string().default("shop.db"),
  SHOP_CURRENCY: z.string().length(3).default("CNY"),
  SHOP_MAX_ORDER_ITEMS: z.coerce.number().int().min(1).max(100).default(20),
  SHOP_SEED_DEMO_DATA: z.string().default("true").transform((value) => value === "true"),
});
export type Env = z.infer<typeof EnvSchema>;   // 四个演示账号字段同理，见源文件

/** ConfigModule 的 validate 回调：不合法就让进程启动失败，而不是带病运行。 */
export function validateEnv(raw: Record<string, unknown>): Env {
  const result = EnvSchema.safeParse(raw);
  if (!result.success) {
    const details = result.error.issues
      .map((issue) => `  - ${issue.path.join(".")}: ${issue.message}`).join("\n");
    throw new Error(`环境变量校验失败：\n${details}\n请检查 .env 或容器注入的变量。`);
  }
  return result.data;
}
```

挂上去只有一行（[app.module.ts](../code/shop-api/src/app.module.ts)）：

```ts
ConfigModule.forRoot({ isGlobal: true, validate: validateEnv, cache: true })
```

| 维度 | Laravel `env()` + config | Spring `@ConfigurationProperties` | 本仓库 |
|---|---|---|---|
| 声明 | 无（字符串键散落各处） | 类字段 + 注解 | Zod object schema |
| 类型转换 | cast（`config('x')` 拿到字符串） | Binder 自动 | `z.coerce.number()` / `.transform()` |
| 校验时机 | 运行时，用到才炸 | **启动时** | **启动时**（`validate` 回调） |
| 校验失败 | 首个请求 500 | `BindValidationException`，进程起不来 | `throw`，进程起不来 |
| 默认值 | `env('X', 'fallback')` | 字段初始值 | `.default(...)` |
| 下游取值 | `config('app.x')` 无类型 | 强类型 bean | `ConfigService.get<Env>` + `z.infer` |

注意 `SHOP_SEED_DEMO_DATA` 的写法：环境变量只有字符串，`"false"` 在 JS 里是 truthy，直接 `if (process.env.X)` 是一个会陪你很久的 bug —— `z.coerce` 和显式 `transform` 就是这道防线。而「启动即失败」这个纪律对常驻进程尤其值钱（第 03 章）：配置错误的代价从「每个请求 500」变成「部署时容器一直重启，告警立刻打给你」。**校验放得越早，你能看到的现场越接近错误本身。**

## 8. DTO 的三种类型 + branded type 的边界

### 三个类型，对应三段旅程

[order.ts](../code/packages/shared/src/order.ts) / [product.ts](../code/packages/shared/src/product.ts) 里对同一个 schema 导出了两个类型，这不是强迫症：

```ts
export type CreateProductRequest = z.input<typeof CreateProductRequestSchema>;  // 客户端**能发**什么
export type CreateProductInput   = z.infer<typeof CreateProductRequestSchema>;  // 校验**后**是什么
export interface ProductRecord { id: number; price: DecimalAmount; /* ... */ }  // 存储层是什么
```

| 类型 | 来自 | 用在哪 | 差异来源 |
|---|---|---|---|
| `z.input<S>` | schema 的输入侧 | 前端构造请求体、OpenAPI 文档 | `.default()` 的字段在这里是**可选**的，`.transform()` 的入参在这里是**原始**类型（`price: number \| string`） |
| `z.infer<S>` | schema 的输出侧 | 服务端 Pipe 之后、业务代码 | `stock` 变必有、`price` 变 `DecimalAmount` |
| 领域类型（`ProductRecord` / `Money`） | 手写的 interface/class | DB 行、领域方法 | 与 HTTP 形状无关，不该被校验细节污染 |

Laravel 里这三段对应 `$request->validated()`（≈ `z.input`）、`$request->safe()->all()` + casts（≈ `z.infer`）和 Eloquent 模型（≈ 领域类型）；只是 Laravel 的 cast 发生在「保存到模型」时，而 Zod 把它提前到边界那一行。

一个真实例子（[schemas.test.ts](../code/packages/shared/test/schemas.test.ts)）：

```ts
expect(CreateProductRequestSchema.parse({ sku: "S", name: "N", price: 1 }).stock).toBe(0);
// z.input<typeof CreateProductRequestSchema> 里 stock?: number | undefined
// z.infer   <typeof CreateProductRequestSchema> 里 stock: number
```

### branded type：编译器的名义类型，运行时依然裸

结构化类型有个漏洞：`type ProductId = number` 和 `type OrderId = number` 是同一个类型，可以互相传错。[branded-ids.ts](../code/lang-basics/src/branded-ids.ts) 的解法是交叉一个谁也构造不出来的假字段：

```ts
declare const BRAND: unique symbol;
export type Branded<T, B extends string> = T & { readonly [BRAND]: B };
export type ProductId = Branded<number, "ProductId">;

export function toProductId(raw: number | string): ProductId | null {
  const value = typeof raw === "string" ? Number(raw) : raw;
  return Number.isInteger(value) && value > 0 ? (value as ProductId) : null;
}
```

[branded-ids.test.ts](../code/lang-basics/test/branded-ids.test.ts) 同时给出了它的**价值**和**边界**：

```ts
// ownerOf(3 as ProductId, orders) // ← 编译失败：ProductId 不是 OrderId
// const plain: ProductId = 5      // ← 编译失败：裸 number 不能当 ProductId
it("运行时仍然是裸值", () => {
  const id = toProductId(5) as ProductId;
  expect(typeof id).toBe("number");   // 不是 object
  expectTypeOf(id).not.toEqualTypeOf<number>();
});
```

| 维度 | branded type | PHP/Java 的 VO（`class ProductId { private int $v }`） |
|---|---|---|
| 编译期区分 | ✅ | ✅ |
| 运行时是独立对象 | ❌ 还是裸 `number`/`string` | ✅ `instanceof` 为真 |
| 防伪造 | 靠 `unique symbol` 无法构造 | 靠 `private` / 不可变 |
| 序列化 | 直接就是裸值，反序列化后要在边界重新「贴牌」 | 需要自定义 serializer 拆包/装包 |
| 成本 | 一个 `type` | 一个类 + mapper |

结论：branded 只补「名义」这半边的**编译期**，**边界仍然要 Zod**：`z.number().int().positive().transform(...)` 或在 `z.infer` 上交叉 brand。别指望它像 `ramsey/uuid` 那样在运行时保护你。

## 9. 什么时候不该用 Zod

Zod 不是免费午餐：一次 `parse` 会遍历整棵树、`transform` 会新建对象、失败时还要构造 issue 数组。

| 场景 | 该不该 | 原因 |
|---|---|---|
| HTTP body / query / params | ✅ | 唯一真正的边界，值只有在这里才是 `unknown` |
| 环境变量、配置文件 | ✅ | 第二类外部输入，且只在启动时跑一次，几乎零成本 |
| 前端消费外部 API 的响应 | ✅ | 服务端类型对前端而言只是「据说如此」 |
| 消息队列 / webhook 的 payload | ✅ | 同边界 |
| **同一个请求里 parse 两次** | ❌ | Pipe 已经给的是 `z.infer` 类型的值，Service 里再 `parse` 一遍是纯浪费，还制造「哪个才是真相」的困惑 |
| 内部函数之间的参数 | ❌ | 类型系统足够；`strict` 已经把可空、越界、`any` 管住了 |
| 大列表的每一个元素都做全字段校验 | ⚠️ 斟酌 | 10 万行订单导出时，schema 遍历会明显进火焰图。可以只校验不变量（分页尺寸、聚合值） |
| 已经由数据库 schema 保证的列（NOT NULL / 外键 / 枚举） | ⚠️ 斟酌 | Drizzle 的表定义已经把行类型推导出来了，重复 Zod 只在你怀疑脏数据时才值得 |
| 值域只有两三种的开关参数 | ❌ | `if/else` + 联合类型比 schema 更清楚 |

另一条纪律：**校验层级越低，错误越贵。** 前端 Zod 是为了用户体验（错误立刻显示），服务端 Zod 是为了安全（客户端永远不可信）。前端校验**不能替代**服务端校验，但服务端**不该**把同一份校验再跑三遍 —— 一份 schema 复用，而不是复写。

<details>
<summary>参考答案</summary>

1. `as` 只影响编译期的类型视图，不生成任何运行时检查，也不改变值；`payload` 与 `ProductView` 类型「重叠」到足以骗过编译器（`unknown` 更是可以 `as` 任何东西）。改法：`CreateProductRequestSchema.parse(payload)`。
2. `DecimalInputSchema` 的 `transform` + `parseDecimal` 里的 `DECIMAL_RE = /^-?\d{1,10}(\.\d{1,2})?$/` + `ctx.addIssue`。`refine` 挂在 `transform` 之后，才能拿到规范化的 `DecimalAmount` 去做 `decimalToCents` 比较；挂在之前拿到的是原始的 `number | string`。
3. `z.input` 是「客户端能发的形状」：带 `.default()` 的字段是可选的（`stock?: number`），带 `.transform()` 的字段是入参类型（`number | string`）。`z.infer` 是校验后的形状：`stock: number`、金额是 `DecimalAmount`。业务代码只应接 `z.infer`。
4. 因为要与 Java/Spring 版的 `ProblemDetail` 输出逐字段对齐 —— 那边用 `putIfAbsent`，一个字段只给一条消息。数组化会让同一个错误码在两个后端返回不同形状。
5. 配置错误立刻变成「进程起不来」而不是「每个请求 500」：现场就在启动日志里，且不会先用错误配置服务掉一批请求。见 `validateEnv` 与 `ConfigModule.forRoot({ validate })`。
