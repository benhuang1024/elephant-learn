## 1. 定位地图：Drizzle 到底是谁

| | Eloquent (Laravel) | Doctrine ORM | **JPA / Hibernate** | **Drizzle（本仓库）** | Prisma | jOOQ |
|---|---|---|---|---|---|---|
| 风格 | Active Record | Data Mapper + UoW | Data Mapper + UoW | **SQL 映射器**（Query Builder + 类型） | Data Mapper（生成客户端） | SQL DSL |
| 谁生成 SQL | 你（Builder 提示） | ORM（HQL/DQL） | ORM（JPQL/派生方法） | **你写的表达式≈SQL** | 生成器（Prisma Client） | 你（强类型 SQL） |
| 身份映射（同一事务同 id 同一对象） | ❌ | ✅ | ✅ | ❌ | ❌（`$transaction` 里也不保证） | ❌ |
| 脏检查（改字段自动 UPDATE） | ❌ 要 `save()` | ✅ Unit of Work | ✅ flush | ❌ **每次写都显式** | ❌ 要 `update()` | ❌ |
| 懒加载 / N+1 自动触发 | ✅ 随时 | ✅（Session 内） | ✅（事务内） | ❌ **必须自己写第二次查询** | ❌（`include` 是显式 join） | ❌ |
| Schema 事实来源 | 迁移文件 | 实体注解 | 实体注解 + 迁移 | **`schema.ts`（TS 代码）** | `schema.prisma` | 数据库 / codegen |
| 迁移工具 | `artisan migrate` | `doctrine:migrations` | **Flyway** / Liquibase | **drizzle-kit** | `prisma migrate` | Flyway |
| 类型检查时机 | 运行时才发现列名写错 | 运行时 | 编译期（JPQL 靠插件） | **编译期，列名/表名/类型都是 TS 符号** | 编译期 | 编译期 |
| 与 PHP 心智距离 | — | 近 | 中 | **最近**（≈ Query Builder + PDO） | 中 | 远 |
| 运行时 | 每次查询同步 | — | 线程池 + JDBC | **同步（better-sqlite3）** | Promise 池 | JDBC |

> 一句话给架构师：**Drizzle = 「带类型的 Query Builder」，不是 ORM。** 它不会替你做身份映射、脏检查、懒加载，因此也就没有 `LazyInitializationException`、没有「为什么我改了字段没落库」、没有 `open-in-view` 那类配置。你在第 06 章 Java 对照里读到的「持久化上下文」整节，在这里可以整体删掉——这是**减法**，不是缺失。
> Prisma 的差别在于「代码生成 + 自带迁移 + 引擎是 Rust 二进制」，重量与团队习惯都要更大；想在 TS 里复刻 JPA 的心智，Prisma 更近，想在 PHP 里复刻 Eloquent 的 Query Builder 手感，Drizzle 更近。

## 2. Schema：与 Flyway DDL、Java 实体逐列对照

Java 侧的真相在 [V1__init.sql](../../java/code/shop-api/src/main/resources/db/migration/V1__init.sql)，TS 侧在 [schema.ts](../code/shop-api/src/db/schema.ts)：

```ts
export const products = sqliteTable(
  "products",
  {
    id: integer("id").primaryKey({ autoIncrement: true }),
    sku: text("sku").notNull(),
    name: text("name").notNull(),
    /** 定点小数字符串，形如 "599.00"，等价于 NUMERIC(12,2) */
    price: text("price").notNull(),
    stock: integer("stock").notNull(),
    version: integer("version")
      .notNull()
      .default(0),
  },
  (table) => [
    uniqueIndex("uq_products_sku").on(table.sku),
    index("idx_products_name").on(table.name),
  ],
);
```

| 列 | Postgres（Flyway） | Java 实体 | Drizzle | 运行时 JS 值 |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `Long` + `@Id @GeneratedValue(IDENTITY)` | `integer("id").primaryKey({ autoIncrement: true })` | `number`（自增值取 `lastInsertRowid`） |
| `sku` | `VARCHAR(64) NOT NULL UNIQUE` | `@Column(nullable=false, unique=true, length=64) String` | `text("sku").notNull()` + `uniqueIndex("uq_products_sku")` | `string` |
| `price` | `NUMERIC(12,2)` | `BigDecimal`（scale 参与序列化） | `text("price").notNull()` | **`"599.00"` 字符串**（`DecimalAmount`） |
| `stock` | `INTEGER` | `int` | `integer("stock").notNull()` | `number` |
| `version` | `BIGINT DEFAULT 0` + `@Version` | Hibernate 自动维护 | `integer("version").notNull().default(0)` | `number`，**递增要自己写 `sql` 表达式** |
| `status` | `VARCHAR(20)` | `@Enumerated(EnumType.STRING)` | `text("status").notNull()` | `"PENDING"`；联合类型由 `as const` 数组给（[shared/order.ts](../code/packages/shared/src/order.ts) 的 `ORDER_STATUSES`） |
| `created_at` | `TIMESTAMP(6)` | `LocalDateTime` + `ISO_LOCAL_DATE_TIME` | `text("created_at").notNull()` | `"2026-10-25T10:05:49.216"`（本地、无 Z） |
| `order_items.product_id` | `REFERENCES products(id)` | `@ManyToOne(fetch = LAZY)` | `.references(() => products.id)` | `number`；**没有“关系对象”，只有外键值** |
| 索引 | `CREATE INDEX idx_products_name` | — | `index("idx_products_name")` | — |

三个刻意的取舍，说清楚：

**① `NUMERIC(12,2)` → `text`。** SQLite 没有 decimal 类型；`real` 就是 double，`0.1 + 0.2` 的教训在数据库层照样成立。所以本仓库把它存成规范化字符串（`DECIMAL_RE = /^-?\d{1,10}(\.\d{1,2})?$/`），读写全走 [shared/decimal.ts](../code/packages/shared/src/decimal.ts)：

```ts
declare const DECIMAL_BRAND: unique symbol;
/** 规范化后的定点小数字符串：整数部分最多 10 位，小数部分固定 2 位。 */
export type DecimalAmount = string & { readonly [DECIMAL_BRAND]: "DecimalAmount" };
```

品牌类型让 `"599.00"` 不会和任意字符串互换，`parseDecimal()` 是唯一入口——连 `DemoDataSeeder` 里写死的字面量也要走它（`parseDecimal(row.price) as DecimalAmount`）。加法乘法全部换算成整数分：`decimalToCents()` / `centsToDecimal()`，所以 `multiplyDecimalByInt()` 不需要 `HALF_UP`（Java 版需要）。换成 PostgreSQL 时这一层**可以原样保留**（`numeric` 映射成 string 也是 Drizzle 的默认行为之一），也可以换成 `decimal.js` / `big.js`；保留字符串定点的意义在于：`schema.ts` 与 `SCHEMA_SQL` 都不用改。

**② `TIMESTAMP(6)` → 本地 ISO 串。** [shared/time.ts](../code/packages/shared/src/time.ts) 的注释交代了动机，实现里逐字取本地字段而不是 `toISOString()`：

```ts
/** `YYYY-MM-DDTHH:mm:ss.SSS`（本地时间，无时区后缀、无 Z）。 */
export function localIsoDateTime(date: Date): string {
  const date_ = `${date.getFullYear()}-${pad(date.getMonth() + 1)}-${pad(date.getDate())}`;
  const time = `${pad(date.getHours())}:${pad(date.getMinutes())}:${pad(date.getSeconds())}`;
  return `${date_}T${time}.${pad(date.getMilliseconds(), 3)}`;
}
```

实测下单响应 `"createdAt":"2026-10-25T10:05:49.216"`——Java 侧 `LocalDateTime` 输出也是这个形状（只是尾数位数不同：PG 给 6 位微秒，JS 给 3 位毫秒）。**这是「对齐到可读，而不是对齐到字节」的第二个例子**（第一个是 [docs/07 的金额](./07-NestJS-Web与REST.md)）。
真实项目建议：存 `TIMESTAMPTZ` / `text` 存 UTC ISO，展示层再做时区。JS 的 `Date` 内部永远是 UTC 毫秒，**没有 LocalDateTime 概念**，靠 `getFullYear()` 这套取「本地字段」只在单机演示里安全；服务器时区一换，历史数据的含义就飘了。

**③ 行的类型从 schema 反推。** `export type ProductRow = typeof products.$inferSelect;` / `NewProductRow = …$inferInsert`：前者 ≈ Eloquent 的模型属性（但编译期可查），后者给 insert 用。写 `db.insert(products).values({ sku: "A", nmae: "x" })` 会**编译不过**——这在 PHP/JS 两侧都是最省钱的一类 bug 拦截。

## 3. 迁移：drizzle-kit vs Flyway vs `artisan migrate`——以及本仓库的第三条路

| 维度 | Laravel | Flyway（Java 侧） | drizzle-kit | 本仓库实际用的 |
|---|---|---|---|---|
| 命令 | `php artisan make:migration` / `migrate` | 放一个 `V{n}__x.sql` 文件，启动即执行 | `pnpm db:generate` / `db:push` / `db:migrate` | **什么都不跑** |
| 事实来源 | PHP 写 schema | SQL 文件 | TS 写 schema → 生成 SQL | `SCHEMA_SQL` 字符串常量 |
| 版本记录 | `migrations` 表 | `flyway_schema_history` | `drizzle/migrations` + `__drizzle_migrations` 表 | 无 |
| 回滚 | `migrate:rollback`（down 存在） | 社区版无 down，「回滚=新迁移」 | `generate` 出的 SQL 手写 down（studio/migrate 不自动回滚） | 删文件重建 |
| 生产可用 | ✅ | ✅（DBA 友好，纯 SQL 可审计） | ✅（用 `generate` + 版本化） | ❌ |

[drizzle.config.ts](../code/shop-api/drizzle.config.ts) 的注释自己就把代价说完了：

```ts
 * 注意：本仓库的运行期建表走的是 database.ts 里的 SCHEMA_SQL（`create table if not exists`），
 * 目的是让 README 的「零依赖启动」和 Java 版的 H2 内存库一样简单。
 * 真正的团队项目会二选一：要么 Flyway 式迁移文件 + 版本化，要么 drizzle-kit migrate。docs/08 讲了取舍。
```

具体代价清单（[database.ts](../code/shop-api/src/db/database.ts) 里的 DDL）：

```ts
/** 建表 DDL：与 java 的 Flyway V1__init.sql 一一对应（SQLite 用 TEXT 表达 DECIMAL/LocalDateTime）。 */
export const SCHEMA_SQL = `
create table if not exists products (
  id      integer primary key autoincrement,
  sku     text    not null unique,
  ...
```

1. **`if not exists` 会让 schema 漂移静默发生**：改了 `schema.ts` 里的列类型，老库不会被更新，Drizzle 的查询却按新类型解释数据——只有测试会偶然发现。
2. **没有版本号**：无法回答「这库跑到第几版」，也就无法在 CI 里卡「实体与表结构一致」（Java 侧靠 `spring.jpa.hibernate.ddl-auto=validate`）。
3. **DDL 与 `schema.ts` 是两份手写真相**：本仓库靠注释和 review 保持同步。`drizzle-kit generate` 存在的意义恰恰是它从 `schema.ts` 单源生成 SQL。注意 DDL 里 `sku text not null unique` 是内联唯一约束，而 `schema.ts` 声明的是 `uniqueIndex("uq_products_sku")` —— 名字与形状都已经不一致了，这就是「两份真相」的现场成本。
4. **多实例并发启动会同时跑 DDL**：SQLite 上表现为偶发 `SQLITE_BUSY`；PG 上要 `advisory lock` 或独立迁移步骤（Flyway 有 lock 表，drizzle-kit 有 `--force` 交互，CI 里更常见的是把 migrate 做成 job）。

## 4. 连接、生命周期与「同步驱动的代价」

[database.ts](../code/shop-api/src/db/database.ts) 里那个类就是 Spring 的 `DataSource` Bean：

```ts
@Injectable()
export class DatabaseService implements OnModuleDestroy {
  readonly db: ShopDatabase;
  private readonly connection: Database.Database;

  constructor(config: ConfigService) {
    const { db, raw } = createDatabase(config.get<string>("DB_FILE") ?? "shop.db");
    this.db = db;
    this.connection = raw;
  }

  /** 优雅停机时释放文件句柄（Spring 的 @PreDestroy / Laravel 的 destructor）。 */
  onModuleDestroy(): void { this.connection.close(); }
}

/** 独立于 Nest 的工厂：测试里直接造一个内存库，不需要启动容器。 */
export function createDatabase(file: string): { db: ShopDatabase; raw: Database.Database } {
  const raw = new Database(file === ":memory:" ? undefined : file);
  raw.pragma("journal_mode = WAL");
  raw.pragma("foreign_keys = ON");
  raw.exec(SCHEMA_SQL);
  return { db: drizzle(raw, { schema }), raw };
}
```

| 关注点 | PHP / Laravel | Java / Spring | Node（本仓库） |
|---|---|---|---|
| 连接形态 | 每进程一条 PDO，请求结束归还 | **HikariCP 池**（默认 10） | **一条 better-sqlite3 连接，进程内所有请求共享** |
| 并发上限来源 | `pm.max_children` × 每子进程 | 池大小 + 线程数 | 进程数 × 每进程连接（当前 = 1） |
| 阻塞语义 | 阻塞只影响当前子进程 | 阻塞只影响当前线程（池耗尽才排队） | **阻塞事件循环 = 所有请求一起等** |
| 池参数 | 无 | `maximumPoolSize` / `connectionTimeout` | 无（换成 `pg.Pool` 才有） |
| 失败面 | 子进程崩，其他继续 | 线程崩，池补 | **未捕获异常直接带走整个进程** |

`foreign_keys = ON` 是 SQLite 每连接都要显式打开的开关（默认关），不开的话 `order_items.product_id` 的引用完整性就是个装饰——这就是 repository 里那个 `isForeignKeyViolation()` 能命中的前提。`journal_mode = WAL` 让读不阻塞写、写串行。

> **同步驱动的真实代价（本章最要紧的一条）**。`better-sqlite3` 的 `.all()/.get()/.run()` 是同步的，一次查询期间事件循环完全停住。本机演示数据只有 3 行、查询 < 1ms（实测 `X-Elapsed-Ms: 0`），所以感觉不到。放到真实规模：一条 200ms 的报表查询，会让**同一进程里所有正在处理的请求都停 200ms**——在 Java 里这只伤一个线程，在 PHP 里这只伤一个子进程。
> 因此「Node 天生异步」的说法在这里必须打折：**异步的是你的代码，不是驱动。** 只要链路上有任何同步 IO（SQLite、`fs.readFileSync`、同步压缩、CPU 密集解析），事件循环就不是你的并发模型了。这是从 php-fpm（每请求一进程、天然隔离）过来的人最容易低估的风险。
> 附带红利（下一节要用）：因为串行，**同一进程内两个并发订单不可能同时读到同一行旧值**，乐观锁冲突在 HTTP 层几乎造不出来。

## 5. 事务：`db.transaction(cb)` 的边界

[order.repository.ts](../code/shop-api/src/order/order.repository.ts) 就是 Nest 版的 `@Transactional`：

```ts
  place(input: PlaceOrderInput): OrderWire {
    return this.db.transaction((tx) => {
      let total: DecimalAmount = ZERO_AMOUNT;
      ...
      for (const line of input.items) {
        const product = tx.select().from(products).where(eq(products.id, line.productId)).get();
        if (!product) throw new NotFoundException("商品", line.productId);

        const price = product.price as DecimalAmount;
        if (line.quantity > product.stock) {
          throw new InsufficientStockException(product.sku, line.quantity, product.stock);
        }
        ...
      }
```

| 维度 | Laravel `DB::transaction(fn)` | Spring `@Transactional` | Drizzle `db.transaction(cb)` |
|---|---|---|---|
| 声明方式 | 显式包裹 | **注解**（代理织入） | 显式包裹（最接近 Laravel） |
| 回调可否异步 | 可（Promise 版） | 方法返回后提交 | **同步回调**：`better-sqlite3` 用 `client.transaction(fn)`，回调必须同步返回 |
| 回滚触发 | 抛异常 | 默认只回滚 `RuntimeException`/`Error`，受检异常不回滚（要 `rollbackFor`） | **抛出任何异常就回滚**，没有「受检/非受检」区别 |
| 吞掉异常 | 照样提交 | 提交但可能 `UnexpectedRollbackException` | 你自己 `try/catch` 了就提交——**没有 rollback-only 概念**，所以也没有那个 Java 经典坑 |
| 传播行为 | 无（嵌套=保存点） | `REQUIRED`/`REQUIRES_NEW`/`NESTED`… 七种 | **无**；`tx.transaction(cb)` 在 drizzle 里发 `SAVEPOINT sp1` / `RELEASE SAVEPOINT` / `ROLLBACK TO SAVEPOINT` |
| 起始语句 | 由驱动决定 | 由 JDBC 决定 | 默认 `BEGIN`（deferred）；`db.transaction(cb, { behavior: "immediate" })` 立刻拿写锁，避免读后升级死锁 |
| 只读事务 | `->transaction(fn)` 无只读版 | `readOnly = true`（跳脏检查、可路由从库） | 无（本来就没有脏检查可跳） |
| 隔离级别 | 无 API | `Isolation` 枚举 | **无 API**，跟随 SQLite（WAL 下读快照 + 写串行，≈ SERIALIZABLE） |
| 事务边界归属 | 写事务的那层 | 注解所在的方法（跨类调用才生效） | **谁调用谁负责**——本仓库放在 Repository，Service 只做规则校验 |
| 提交后动作 | `DB::afterCommit()` | `@TransactionalEventListener(AFTER_COMMIT)` | 无内置相位；在 `transaction()` 返回后自己调用（或用 `EventEmitter2`，但**它不知道事务成没成**） |

> 注意最后一行的坑：`@TransactionalEventListener` 之所以有价值，是因为它能保证「通知发出去了但数据回滚了」不发生。Drizzle 里你把 `emit('order.placed')` 写在 `transaction()` 内部就会踩到这个雷——事件在 COMMIT 之前发出，回滚后消费者已经在处理一个不存在的订单。正确写法：`const order = db.transaction(...); events.emit(order)`，把「发事件」放到事务边界**外面**。

回滚是**测过**的，不是文档承诺的（[order.service.spec.ts](../code/shop-api/src/order/order.service.spec.ts)）：

```ts
  it("库存不足 → 409，整单回滚，没有订单也没有库存变化", () => {
    expect(() =>
      service.place({
        customerName: "ben",
        items: [
          { productId: 1, quantity: 1 }, // 先成功扣一行
          { productId: 3, quantity: 5 }, // 再失败
        ],
      }),
    ).toThrow(InsufficientStockException);

    const keyboard = db.select().from(products).where(eq(products.id, 1)).get();
    expect(keyboard?.stock).toBe(20); // 回滚
    expect(keyboard?.version).toBe(0);
```

业务规则留在 Service、事务留在 Repository，这个分层和 Java 版一致（`OrderService.place` 上 `@Transactional`；这里 `OrderService.place` 只做 `max-order-items` 校验，见 [order.service.ts](../code/shop-api/src/order/order.service.ts)）。少的那一层「魔法」是：Nest 里没有 `@Transactional` 注解，所以**不存在**「同类里 `this.place()` 自调用导致事务失效」这个 Java 经典事故——事务的作用域就是那个箭头函数，看得见的就是生效的。

## 6. 并发扣库存的三种写法

| 方案 | 谁在用 | 代码形状 | 冲突时的表现 | 适用 |
|---|---|---|---|---|
| 悲观锁 | `lockForUpdate()` / `@Lock(PESSIMISTIC_WRITE)` | `SELECT ... FOR UPDATE` 后改实体 | 后到者**等待**，不报错 | 热点行、冲突频繁 |
| 乐观锁（框架版） | Hibernate `@Version` | 实体加注解，**Hibernate 自动在 UPDATE 的 WHERE 追加 `version=?`** | `ObjectOptimisticLockingFailureException` | 冲突少、要版本语义 |
| 乐观锁（手写条件） | 本仓库 | `where(and(eq(id), eq(version)))` + 看 `changes` | 自己抛 `OptimisticLockException` → 409 | 想看清框架做了什么 |
| 原子条件更新 | 高并发常见 | `UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?` | 影响行数 0 → 库存不足 | 只做计数，不需要版本 |

本仓库选中间那种，代码全在 [product.repository.ts](../code/shop-api/src/product/product.repository.ts)——注释原话是「Drizzle 没有版本列的魔法，这里手写同样语义，看懂这段就看懂了乐观锁到底做了什么」：

```ts
  update(input: UpdateProductInput, id: number, expectedVersion: number): ProductRow {
    try {
      const result = this.db
        .update(products)
        .set({ name: input.name, price: input.price, stock: input.stock,
               version: sql`${products.version} + 1` })
        .where(and(eq(products.id, id), eq(products.version, expectedVersion)))
        .run();
      if (result.changes === 0) throw new OptimisticLockException("商品");
      return this.findById(id);
    } catch (error) {
      if (error instanceof OptimisticLockException || error instanceof NotFoundException) throw error;
      if (isUniqueViolation(error)) throw new ConflictException(`SKU 已存在: ${input.name}`);
      throw new DataIntegrityException(error);
    }
  }
```

对照 Hibernate 生成的语句形状（两边其实是**同一条 SQL**）：

```sql
-- 手写（本仓库）
update products set name = ?, price = ?, stock = ?, version = version + 1
 where id = ? and version = ?;
-- Hibernate @Version
update products set name=?, price=?, stock=?, version=? where id=? and version=?;
```

差别只剩「新的 version 值是 SQL 算的还是应用算的」，以及异常由谁抛。下单路径同理（`order.repository.ts` 里 `stock: product.stock - line.quantity` + version 条件），所以**库存的安全性完全来自 version 守卫**，而不是 `stock >= ?`——这是与 Java 版对齐后的必然结果：`@Version` 方案本来也不用 `stock >= ?`。如果你的场景不需要「版本号可观察」（前端不做并发编辑、不做审计），`UPDATE ... WHERE stock >= ?` 更简单也更快，代价是丢掉了「谁改了这行」的能力，且读-改-写别的字段时没有保护。

**`@Version` 语义下可观察到的结果**（都是实测/测试断言，不是推断）：

| 场景 | `stock` | `version` |
|---|---|---|
| 初始（演示数据） | 20 | 0 |
| `POST /api/orders` 买 2 件后 | 18 | **1** |
| 同一商品在一张订单里出现两行（各买 1 件） | 0 | **2**（一次事务里两次条件更新，第二次看到已扣减后的版本） |
| `PUT /api/products/2` 连改两次 | — | 1 → **2** |
| 用旧版本号 0 再改一次 | 不变 | 抛 `OptimisticLockException` → 409 `并发冲突` |

同一商品两行不合并这件事，`order.service.spec.ts` 里有断言（`mouse?.version).toBe(2)`），Java 版行为相同——横向对比的价值就在这里：两边不是各自「合理实现」，而是逐条对齐。

**为什么 409 并发冲突只能在 Repository 层测？**（[product.repository.spec.ts](../code/shop-api/src/product/product.repository.spec.ts)）

```ts
  it("乐观锁：版本不匹配 → 409 并发冲突", () => {
    const created = repo.create({ sku: "SKU-1", name: "键盘", price: d("599.00"), stock: 3 });
    const updated = repo.update({ name: "键盘 Pro", price: d("699.00"), stock: 4 }, created.id, 0);
    expect(updated.version).toBe(1);
    // 用旧版本号再更新一次：模拟「另一个请求已经改过这一行」
    expect(() => repo.update({ name: "过期写入", price: d("1.00"), stock: 99 }, created.id, 0)).toThrow(
      OptimisticLockException,
    );
  });
```

e2e 文件里也留了同一句话的注释：「better-sqlite3 是同步驱动，两个 HTTP 请求会被事件循环串行化，在 e2e 里几乎造不出冲突窗口——这本身就是 docs/08 的一个结论」。

这不是偷懒，而是**同步驱动下的诚实结论**：读-改-写整个发生在一次事件循环 tick 内，两个 HTTP 请求必然串行，冲突窗口不存在。换到 `pg`（异步驱动）之后，「A 读到 version=0 → 让出事件循环 → B 读到 version=0」这个窗口是真实存在的，届时才需要：① 用 `Promise.all([place, place])` 写并发测试；② 决定重试策略（乐观锁的标准后续是「重读 + 重试 N 次」，本仓库直接 409 让客户端重试，和 Java 版一致）。

## 7. 关联与 N+1：`@EntityGraph` 的手写替代

Java 侧一条注解解决（[OrderRepository.java](../../java/code/shop-api/src/main/java/study/shop/order/OrderRepository.java) 的 `@EntityGraph(attributePaths = {"items", "items.product"})`）。TS 侧没有「关系」这一层，所以 [order.repository.ts](../code/shop-api/src/order/order.repository.ts) 老老实实写第二次查询，并且**批量取、在内存里分组**，而不是逐订单查：

```ts
  list(): OrderWire[] {
    const orderRows = this.db.select().from(orders).orderBy(desc(orders.createdAt)).all();
    if (orderRows.length === 0) return [];
    // 一次取全部行，避免 Java 版用 entity graph 解决的问题在这里变成 N+1
    const items = this.db.select().from(orderItems).all();
    return orderRows.map((order) => toOrderWire(order, items.filter((item) => item.orderId === order.id)));
  }
```

`findById()` 是同一套路的单条版：先 `where(eq(orders.id, id)).get()`（没有就抛 `NotFoundException("订单", id)`），再 `where(eq(orderItems.orderId, id)).all()` 取明细——两条 SQL，永远不会变成 N+1。

| 需求 | Eloquent | JPA | Drizzle |
|---|---|---|---|
| 列表带明细（1 + 1 条 SQL） | `Order::with('items')` | `@EntityGraph` / `join fetch` | **手写第二条查询**（本仓库做法），或 `leftJoin` + 手工聚合 |
| 按父 id 批量取子行 | `whereIn('order_id', $ids)` | 由 join 完成 | `inArray(orders.orderId, ids)` + `Map` 分组 |
| 懒加载兜底 | 随时可用（可能 N+1） | 事务内可用 | **不存在**——想少写一次查询都不会有魔法帮你 |
| 防 N+1 报警 | `Model::preventLazyLoading()` | `spring.jpa.open-in-view=false` + SQL 计数 | 打开 SQL 日志（`drizzle(raw, { schema, logger: true })`，本仓库没开）或在测试里数查询次数 |
| 声明式关系 | `hasMany()` 方法 | `@OneToMany` | `sqliteTable(..., (t) => ({ items: many(orderItems) }))` —— 本仓库**没有**用它 |

Drizzle 的 relational query API（`db.query.orders.findMany({ with: { items: true } })` + `many()`/`one()` loader）是可用的，而且 [database.ts](../code/shop-api/src/db/database.ts) 已经把 `schema` 传给了 `drizzle(raw, { schema })`（这是 loader 生效的前提）。本仓库没用它，原因值得学：`list()` 目前是「全表取明细」的演示写法，loader 会把它变成**一条 `IN (...)` 查询**并按 `orderId` 关联，语义更精确；但在只有 3 条数据的库里，多这套抽象只换来可读性下降。真要上生产，`db.query` 是唯一能同时保住类型与 N+1 防线的写法——它生成的仍是两次查询，不是 join。

> **`OrderItem.product` 快照是另一件事**：`order_items` 里冗余存了 `sku`/`unit_price`（[schema.ts](../code/shop-api/src/db/schema.ts) 注释「下单时的快照，后续改价不影响历史订单」）。JPA/Eloquent 会引诱你把这写成 `@ManyToOne product` 然后靠 join 读当前价——那是错的建模。快照列 + 一个 `product_id` 外键才是订单该有的形状，两种语言都得手写。

## 8. 报表：`sql` 模板标签是逃生舱，不是耻辱

Java 侧有 `CatalogReportDao` + `JdbcClient`；TS 侧对应 [schema.ts](../code/shop-api/src/db/schema.ts) 的模板 + [product.repository.ts](../code/shop-api/src/product/product.repository.ts) 的执行：

```ts
export const topProductsSql = (limit: number) => sql`
  select p.sku as sku, p.name as name, coalesce(sum(oi.quantity), 0) as units_sold
  from products p
  left join order_items oi on oi.product_id = p.id
  group by p.id, p.sku, p.name
  order by units_sold desc, p.name asc
  limit ${limit}
`;

  rawTopProducts(limit: number): { sku: string; name: string; unitsSold: number }[] {
    const rows = this.db.all<{ sku: string; name: string; units_sold: number }>(topProductsSql(limit));
    return rows.map((row) => ({ sku: row.sku, name: row.name, unitsSold: Number(row.units_sold) }));
  }
```

| 维度 | Laravel | Spring | Drizzle |
|---|---|---|---|
| 手写 SQL | `DB::select('...', [$id])` | `JdbcClient.sql("""...""").param("from", f)` | `db.all(sql`... ${limit}`)` |
| 参数绑定 | `?` / `:name` | `:name` | `${value}` **是参数化插值，不是字符串拼接**（生成 `?` + 值），所以 `${limit}` 不构成注入面 |
| 结果列名 | 原始列名（`units_sold`） | record 字段自动映射（`unitsSold`） | 原始列名，**要自己 `as` 或手工映射**（上面那段 `rows.map`） |
| 编译期校验 | 无 | 无（SQL 字符串） | 无（模板里的表/列是纯文本，Drizzle 表达式 `from(products)` 才有类型检查） |
| 何时用 | 聚合、窗口函数、`WITH`、批量 | 同 | 同；**写模型仍走 Drizzle 表达式** |

`ProductService.topProducts()` 只是把它透出（注释写明「没有 HTTP 入口」），所以这条链的用途是演示「同一项目里 ORM 写模型 + 裸 SQL 读模型」的 CQRS-lite 混搭——和 Java 版 `CatalogReportDao` 完全同构。
一个小坑：`db.all()` / `db.get()` / `db.run()` 是**同步驱动专属**的收尾方法名，异步驱动（`pg`）没有它们，要写 `await db.execute(...)`。这是第 9 节迁移清单里最容易漏的一处。

## 9. 换 PostgreSQL 的路线

本仓库用 SQLite 只为了「零依赖启动 + 和 Java 的 H2 内存库对等」。上生产（或想要真正的并发）就换 `node-postgres`：

| 改动点 | 现在（SQLite） | 换成 PG |
|---|---|---|
| 依赖 | `better-sqlite3` + `@types/better-sqlite3` | `pg`（+ `@types/pg`），或 `postgres` |
| 导入 | `drizzle-orm/better-sqlite3`、`drizzle-orm/sqlite-core` | `drizzle-orm/node-postgres`、`drizzle-orm/pg-core` |
| 表定义 | `sqliteTable("products", ...)`、`integer/text` | `pgTable(...)`、`bigint({mode:"number"})`、`numeric({precision:12, scale:2})`、`timestamptz` |
| 建连 | `new Database(file)` | **`new Pool({ connectionString, max: 10 })`** —— 池回来了，`connectionLimit` 这类容量旋钮也回来了 |
| 执行 | `.all() / .get() / .run()`（同步） | `await`（`db.select()...`、`db.execute(...)`），Repository 全部方法要变 `async`，`OrderWire` 返回值变 `Promise<OrderWire>` |
| 事务 | `db.transaction((tx) => {...同步...})` | `await db.transaction(async (tx) => {...})`；隔离级别可在连接或 `SET TRANSACTION` 上指定 |
| 冲突窗口 | 事件循环串行化 → 造不出 409 | **真实存在** → 并发测试 + 重试策略要补 |
| 约束错误识别 | `err.code.includes("SQLITE_CONSTRAINT_UNIQUE")` / `..._FOREIGNKEY` | `err.code === "23505"`（unique_violation）/ `"23503"`（foreign_key_violation），即 SQLSTATE；`isUniqueViolation()` / `isForeignKeyViolation()` 两个函数要重写 |
| 自增主键 | `inserted.lastInsertRowid` | `.returning({ id: products.id })` 取回 |
| DDL | 启动期 `raw.exec(SCHEMA_SQL)` | 必须换成版本化迁移：`drizzle-kit generate`（dialect: `"postgresql"`）+ 部署流程里独立一步 |
| 金额 | `text` 存定点字符串 | 可保留 `text`；或 `numeric` 并在 `DecimalInputSchema` 侧不变（PG 驱动把 `numeric` 返回成字符串，正好对上 `DecimalAmount`） |
| 时间 | `text` + `nowLocalIso()` | 推荐 `timestamptz` + `new Date()`；与 Java 的 `TIMESTAMPTZ` 对齐（`application-postgres.yml` 那条路） |

顺序建议：先把 Repository 的返回类型改成 `Promise`（这一步会传染 Service/Controller/测试，改动最大），再把 `SCHEMA_SQL` 换成 drizzle-kit 迁移，最后加连接池与 `busyTimeout` 等价物（PG 里是 `statement_timeout` / 池的 `connectionTimeoutMillis`）。乐观锁那节讨论的并发测试，是这步完成之后才**有可能**写出来的。

## 10. 本章自测

1. 为什么本仓库的 `ProductService.update()` 需要「先 `findById` 拿 version，再 `update(..., version)`」两次查询，而 Java 版的 `productService.update()` 不需要显式读版本？
2. 把 `db.transaction((tx) => {...})` 的回调改成 `async (tx) => {...}` 会发生什么？（提示：`createDatabase` 里的 `client.transaction`）
3. 有人在 `place()` 的事务回调里 `events.emit("order.placed", order)`，压测时偶发「发了通知但订单不存在」。请给出两种正确修法。

<details>
<summary>参考答案</summary>

1. Hibernate 有持久化上下文：`findById` 返回的是**托管实体**，`@Version` 的值它自己知道，flush 时自动把 `version=?` 拼进 WHERE。Drizzle 没有身份映射，`update()` 只是一个表达式，框架不知道「你读到的那一行的版本是多少」，所以 expectedVersion 必须由应用层传进去——这多出来的一次读，就是「显式 SQL 映射器」为透明性付的税。
2. 直接抛错，不会静默出错。`better-sqlite3` 的 `transaction.js` 里写死了这段：`const result = apply.call(fn, this, arguments); if (result && typeof result.then === "function") throw new TypeError("Transaction function cannot return a promise")`。原因是它的实现是 `begin.run(); fn(); commit.run()` 三步同步执行——如果 `fn` 返回 Promise，COMMIT 就会在异步语句跑完之前发出。Drizzle 的 `BetterSQLiteSession.transaction` 只是把这个 native 包装转交给你，所以「同步驱动 + async 回调」是非法组合（Nest 侧的表现是 `Promise` 版 Repository 必须整体改异步驱动）。要么保持同步（本仓库），要么换 `pg`。
3. ① 把事件挪到事务边界外：`const order = this.db.transaction(...); this.events.emit("order.placed", order);`（`OrderService.place` 里发，Repository 只负责事务）。② 用「同事务的 outbox 表」：在回调内 `insert into outbox ...`，提交后由独立的轮询/CDC 进程投递——这是 Java 侧 `@TransactionalEventListener(AFTER_COMMIT)` 覆盖不到的那类可靠性需求（回滚后 outbox 行也回滚，天然一致）。
</details>
