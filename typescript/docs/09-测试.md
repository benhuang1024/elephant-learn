命令层面的差别只有一处需要记住：**`vitest` 是 watch 模式，`vitest run` 才是一次性跑。** 所有 CI 脚本里都写 `vitest run`，本仓库每个包的 `test` 脚本都是它，`test:watch` 才是裸 `vitest`（见 [lang-basics/package.json](../code/lang-basics/package.json)）。

```jsonc
// code/shop-api/package.json —— 单测与 e2e 是两个脚本，因为 e2e 需要先有 dist
"test": "pnpm --filter @shop/shared build && vitest run src",
"test:e2e": "pnpm build && vitest run --dir test",
```

`vitest run src` / `--dir test` 这个「按目录切两拨」的做法，对位 PHP 里 `tests/Unit` 与 `tests/Feature` 两个 suite directory；差别是 Vitest 不需要 `phpunit.xml` 的 `<testsuite>` 声明，默认 include 规则就是 `**/*.{test,spec}.?(c|m)[jt]s?(x)`。本仓库没有一份 vitest 配置文件——**目录约定 + CLI 参数就够了**，这本身是个值得学的手感。

## 3. 断言与 mock：从 assertSame 到 expect

| PHPUnit/Pest | Vitest | 陷阱 |
|---|---|---|
| `assertSame(3, $x)`（`===`） | `expect(x).toBe(3)` | 引用相等 |
| `assertEquals($a, $b)`（宽松） | `expect(x).toEqual(y)` | `toEqual` 递归比较且**忽略 undefined 属性**；要严格请用 `toStrictEqual` |
| `assertNull` / `assertNotNull` | `toBeNull()` / `toBeTypeOf("string")` | — |
| `assertCount(3, $arr)` | `toHaveLength(3)` | — |
| `assertInstanceOf(X::class, $e)` | `toBeInstanceOf(X)` | — |
| `expectException(X::class)` | `expect(fn).toThrow(X)` | 必须传**函数**，`expect(service.place(...)).toThrow()` 是错的（表达式先炸） |
| `expectExceptionMessage('库存不足')` | `toThrow(/库存不足/)` | 字符串是「包含」匹配，正则更清楚 |
| `$this->fail()` | `expect.unreachable("应该抛出")` | 真实用法见 [error-handling.test.ts](../code/lang-basics/test/error-handling.test.ts) 第 43 行 |
| `assertMatchesRegularExpression` | `toMatch(/^\d{4}-\d{2}-\d{2}T/)` | 见 [order.service.spec.ts](../code/shop-api/src/order/order.service.spec.ts) 第 83 行 |
| `$m->shouldReceive('find')->andReturn($p)` | `vi.mocked(fetchProducts).mockResolvedValue([keyboard])` | 见下方 |
| `Mockery::close()` / 每个用例重建 mock | `beforeEach(() => vi.clearAllMocks())` | 真实写法在 [web-vue/test/catalog.test.ts](../code/web-vue/test/catalog.test.ts) 第 41–44 行 |

`toMatchObject` / `toEqual` 的区别最像 `assertArraySubset`（已废弃）与 `assertEquals`：前者只断言关心的键，后者要求全等。e2e 里两种都用，选择标准是「这个响应的形状是不是契约」——problem+json 全部字段写死所以 `toEqual`，订单响应只关心几个字段所以 `toMatchObject({ total: 1198, items: [...] })`。

mock 的粒度对照：`vi.fn()` 是「一个可断言调用的函数」，对位 `createMock(X::class)` 里只保留一两个方法；`vi.mock("../src/api", factory)` 是**整模块替换**，对位 PHP 里没有的东西——最接近的是给容器 rebind 一个 binding。前端 store 测试只用后者：

```ts
// code/web-vue/test/catalog.test.ts
vi.mock("../src/api", () => ({
  ApiProblem: class ApiProblem extends Error { /* ... */ },
  fetchProducts: vi.fn(),
  placeOrder: vi.fn(),
  formatAmount: (value: string) => `¥${value}`,
}));

const { fetchProducts, placeOrder, ApiProblem } = await import("../src/api");
```

这里有两个非显然的点：① `vi.mock` 会被**提升到文件顶部**，所以拿被 mock 的模块要用 `await import()`（或顶层 import 后再 `vi.mocked()`）；② `vi.mocked(x)` 只是类型助跑——把 `x` 从「函数签名」改标成「mock 签名」，`.mockResolvedValue` 才有类型。这是 PHP 没有的问题，因为 PHP 没有 mock 的类型。

## 4. Nest TestingModule ↔ `@SpringBootTest` + `overrideProvider`

| Spring | Nest | Laravel |
|---|---|---|
| `@SpringBootTest` | `Test.createTestingModule({ imports: [AppModule] })` | `createApplication()` |
| `@MockitoBean ProductService` | `.overrideProvider(ProductService).useValue(fake)` 或 `{ provide: X, useValue }` | `$this->swap(X::class, $fake)` |
| `@Autowired private OrderService s` | `moduleRef.get(OrderService)` | `app()->make(OrderService::class)` |
| `@ActiveProfiles("test")` + `application-test.yml` | 直接写 `process.env.X = "..."`（见 §5） | `.env.testing` |
| 上下文缓存（同配置共享容器） | 无缓存：每个 `createTestingModule` 都是新容器 | 每次 `refreshApplication()` |

Java 版靠注解扫描，Nest 版靠**显式列出 providers**——所以单元测试不需要任何「魔法」，一眼能看出这个测试装配了什么：

```ts
// code/shop-api/src/order/order.service.spec.ts
db = createDatabase(":memory:").db;
db.insert(products)
  .values([
    { sku: "SKU-001", name: "机械键盘", price: d("599.00"), stock: 20, version: 0 },
    { sku: "SKU-002", name: "人体工学椅", price: d("1299.00"), stock: 5, version: 0 },
    { sku: "SKU-003", name: "限量版鼠标", price: d("399.00"), stock: 2, version: 0 },
  ])
  .run();

const moduleRef = await Test.createTestingModule({
  providers: [
    OrderService,
    OrderRepository,
    Metrics,
    { provide: DatabaseService, useValue: { db } },
    {
      provide: ConfigService,
      useValue: {
        get: (key: string): unknown =>
          key === "SHOP_MAX_ORDER_ITEMS" ? 20 : key === "SHOP_CURRENCY" ? "CNY" : undefined,
      },
    },
  ],
}).compile();

service = moduleRef.get(OrderService);
```

对照 [OrderServiceTest.java](../../java/code/shop-api/src/test/java/study/shop/order/OrderServiceTest.java)：Java 那边是 `@SpringBootTest` + `@BeforeEach cleanDatabase()`（`deleteAll()`），起整个容器；这里只装配 5 个 provider，`beforeEach` 直接**换新内存库**。这是 Nest/Drizzle 组合的回报：容器成本几乎为零，所以「每个用例一个新数据库」这种奢侈事在 TS 侧是默认写法。

`{ provide: ConfigService, useValue: { get: ... } }` 值得单独说一句：**替换的是整个类的实例，但我们只实现了用到的一个方法**。TS 不介意——`useValue` 的声明类型允许 `as any` 级别的结构宽松（Nest 的 provider 类型签名如此）。代价是如果 `ConfigService` 的其他方法被间接调用，你要到运行时才发现。PHP 的 `Container::instance()` 一模一样。

## 5. e2e：supertest 而不是 `@WebMvcTest`

```ts
// code/shop-api/test/shop-api.e2e.spec.ts
process.env.DB_FILE = ":memory:";
process.env.SHOP_SEED_DEMO_DATA = "true";
process.env.SHOP_MAX_ORDER_ITEMS = "20";

describe("shop-api e2e", () => {
  let app: INestApplication;
  let http: unknown;

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile();
    app = moduleRef.createNestApplication();
    app.use(requestIdMiddleware);
    await app.init();
    http = app.getHttpServer();
  });

  afterAll(async () => {
    await app.close();
  });

  it("GET /api/products 公开返回 3 件演示商品", async () => {
    const response = await request(http).get("/api/products").expect(200);
    expect(response.headers["content-type"]).toContain("application/json");
    expect(response.body).toHaveLength(3);
    expect(response.headers["x-request-id"]).toBeTypeOf("string");
  });
});
```

三个必须记住的细节：

1. **`process.env` 要在 `createTestingModule` 之前设好。** 顶部那三行不是装饰：`ConfigModule.forRoot({ validate: validateEnv })`（[app.module.ts](../code/shop-api/src/app.module.ts)）在容器编译时就读环境变量，`DB_FILE` 晚一步就变成磁盘上的 `shop.db`。对位 PHP 的是 `.env.testing` 必须在 `bootstrapping` 前就位，只是这里显式得多。
2. **`app.use(requestIdMiddleware)` 与生产入口同一行代码**（[main.ts](../code/shop-api/src/main.ts) 第 23 行）。中间件是 Express 层的，不在 Nest 容器里，所以 e2e 必须自己装——这类「装配缺口」是 Laravel 里 `Kernel::$middleware` 漏配的同源问题。
3. **`app.init()` 不能省。** 没有它 `onModuleInit`/seed 不执行，`app.getHttpServer()` 也还没监听。`await app.close()` 放在 `afterAll`，对应 `DatabaseService.onModuleDestroy()` 真正释放 SQLite 句柄（[database.ts](../code/shop-api/src/db/database.ts)）。

Java 版用 `@WebMvcTest(ProductController.class)` 只起 MVC 层；**Nest 没有官方的「切片测试」等价物**。本仓库的选择是：不做切片，只做两端——要么纯单元（自己装配 5 个 provider），要么整个 `AppModule` + supertest。中间那一层用「Repository 直接 `new`」（§6）补上。取舍写在这里，是因为它决定了断言的写法：e2e 起一次 app，17 个用例共享状态，**所以断言必须容忍顺序**（文件注释里就写着这条）。这与 Laravel feature test 不做 `RefreshDatabase` 时的行为完全同构，也是为什么文件里第 216 行的乐观锁用例只断言 version 递增：

```ts
// 真正的「版本不匹配 → 409 并发冲突」在 src/product/product.repository.spec.ts 里测：
// better-sqlite3 是同步驱动，两个 HTTP 请求会被事件循环串行化，
// 在 e2e 里几乎造不出冲突窗口
```

## 6. Repository 的测法：不需要容器

| | Java `@DataJpaTest` | Laravel + `RefreshDatabase` | 本仓库 [product.repository.spec.ts](../code/shop-api/src/product/product.repository.spec.ts) |
|---|---|---|---|
| 启动什么 | Spring 测试上下文 + 内嵌 H2 | 完整 app + 真实 DB 连接 | 一个函数 `createDatabase(":memory:")` |
| 拿 repository | `@Autowired` | `$this->app->make()` | `new ProductRepository(...)` |
| 回滚 | 每个用例后自动 rollback | 事务包裹 | **换新库**，不需要回滚 |
| 成本 | 秒级 | 秒级 + 依赖 DB 服务 | 毫秒级，无外部依赖 |

```ts
function repositoryWith(db: ReturnType<typeof createDatabase>["db"]): ProductRepository {
  // 只依赖 .db 一个字段，所以用结构等价对象代替 DatabaseService
  return new ProductRepository({ db } as unknown as DatabaseService);
}

it("乐观锁：版本不匹配 → 409 并发冲突", () => {
  const repo = repositoryWith(createDatabase(":memory:").db);
  const created = repo.create({ sku: "SKU-1", name: "键盘", price: d("599.00"), stock: 3 });
  const updated = repo.update({ name: "键盘 Pro", price: d("699.00"), stock: 4 }, created.id, 0);
  expect(updated.version).toBe(1);
  // 用旧版本号再更新一次：模拟「另一个请求已经改过这一行」
  expect(() => repo.update({ name: "过期写入", price: d("1.00"), stock: 99 }, created.id, 0)).toThrow(
    OptimisticLockException,
  );
});
```

`{ db } as unknown as DatabaseService` 是本仓库唯一的「结构桩」：**只满足用到的那个字段，多余的一律不管**。它比 `vi.mock` 好，因为 Drizzle 的 `db` 是真实对象，mock 掉它就等于什么都没测。对照 [ProductRepositoryTest.java](../../java/code/shop-api/src/test/java/study/shop/product/ProductRepositoryTest.java) 里那个用 `entityManager.detach()` + `saveAndFlush` 手动制造脏版本的写法——Java 侧要绕过持久化上下文才能测到同一件事，这里没有上下文可绕。

## 7. 类型测试：`expectTypeOf` 是编译期断言

Vitest 的 `expectTypeOf` 写在运行时测试文件里，但**它不产生任何运行时断言**：编译时不成立就报错，运行时只是空操作。这一层在 PHP 里对位 PHPStan/Psalm 的 `@param-assert` 注释和 [tsd](https://github.com/SamVerschueren/tsd)（`expectType<Foo>()`），在 Java 里几乎找不到对应物。

```ts
// code/lang-basics/test/generics.test.ts
expect(pluck(rows, "id")).toEqual(["1", "2"]);           // 运行时
expectTypeOf(pluck(rows, "id")).toEqualTypeOf<string[]>(); // 编译时

// code/lang-basics/test/branded-ids.test.ts
expectTypeOf(id).not.toEqualTypeOf<number>();            // 品牌类型必须 ≠ 裸 number

// code/packages/shared/test/decimal.test.ts
expectTypeOf<DecimalAmount>().toEqualTypeOf<string>();
expectTypeOf(PositiveAmountSchema.parse(1)).toEqualTypeOf<DecimalAmount>();
```

| expectTypeOf API | 含义 | 什么时候用 |
|---|---|---|
| `.toEqualTypeOf<T>()` | 完全等同（双向可赋值 + 同名可选性） | 推导结果是否精确（首选） |
| `.toMatchTypeOf<T>()` | 左侧可赋给 T（允许更多字段） | 结构兼容检查，如 `"POST /api/products/9"` 对 `Route` |
| `.not.toEqualTypeOf<T>()` | 反向断言 | 证明品牌类型/no-any 生效 |
| `.parameters` / `.returns` / `.properties` | 反射签名 | 断言 API 表面（`utility-types.test.ts` 用它测 `Unwrap`） |

为什么值得写：`z.infer`、`Partial<T>`、条件类型这类东西**改了 schema 就悄悄变了类型**，运行时测试永远发现不了。类型测试是这条链路上唯一的哨兵。

另一半「类型即测试」由 `tsc --noEmit` 承担，本仓库每个包都有 `typecheck` 脚本：

| 检查 | 命令 | 对应 PHP |
|---|---|---|
| 类型全量检查 | `pnpm -r typecheck`（每个包 `tsc --noEmit`，Vue 包是 `vue-tsc --noEmit`） | `phpstan analyse` / `psalm` |
| 严格度来源 | [tsconfig.base.json](../code/tsconfig.base.json)：`strict` + `noUncheckedIndexedAccess` + `noImplicitReturns` + `noFallthroughCasesInSwitch` + `verbatimModuleSyntax` | PHPStan level 8~MAX |
| 编译失败也是断言 | 测试文件里的注释：`// pluck(rows, "missing") 会编译失败：字段名不存在` | PHPStan 的 `@expect-error`（需配合 baseline） |

`strict: true` + `noUncheckedIndexedAccess: true` 大致落在 PHPStan level 8：数组越界返回 `T | undefined`，于是 [null-safety.test.ts](../code/lang-basics/test/null-safety.test.ts) 里那句 `expectTypeOf(secondOrNone(["a", "b"])).toEqualTypeOf<string | undefined>()` 才有意义——`$arr[1]` 在 PHP 里只是运行时 warning，TS 把它压进了类型。

**「注释掉的编译失败」是这仓库的一个风格约定**（`// const bad: Route = "PATCH /api/products" // 编译失败`），它不进入编译流程，所以不会真的保证失败——想强保证就交给 `expectTypeOf`。

## 8. 真实踩坑一：TS1477，`expectTypeOf<X>` 必须带括号

写 `expectTypeOf<Required<{ a?: number }>>.toEqualTypeOf<...>()`（漏掉 `()`）会报：

```text
TS1477: An instantiation expression cannot be followed by a property access.
```

`expectTypeOf<T>()` 是「显式类型实参 + 空调用」的组合，叫 instantiation expression；TS 规定它后面**不能直接接属性访问**，`.toEqualTypeOf` 正好撞上。正确写法（[utility-types.test.ts](../code/lang-basics/test/utility-types.test.ts) 第 42 行）：

```ts
expectTypeOf<Required<{ a?: number; b?: string }>>().toEqualTypeOf<{
  a: number;
  b: string;
}>();
```

第二个坑更麻烦：**Vitest 遇到这个错误时不会给你一条干净的类型错误，而是整个测试文件报 transform 失败**（因为类型检查与转译在同一条管线上撞了）。现象是「我明明只写了一个 `it`，为什么这个文件全红了」——先跑 `pnpm typecheck` 定位，比在 `vitest` 输出里翻要快得多。这也是本章把 `typecheck` 排在 `test` 之前的原因（§13）。

## 9. 真实踩坑二：`.spec.ts` 里为什么 import `.js`

```ts
// code/shop-api/src/order/order.service.spec.ts —— 文件是 .ts，说明符写 .js
import { Metrics } from "../auth/users.service.js";
import { DatabaseService, createDatabase, type ShopDatabase } from "../db/database.js";
import { OrderService } from "./order.service.js";
```

不是笔误。[shop-api/package.json](../code/shop-api/package.json) 里 `"type": "module"`，[tsconfig.json](../code/shop-api/tsconfig.json) 里 `module`/`moduleResolution` 都是 `nodenext`：Node 的 ESM 解析要求**说明符指向真实文件名**，而 `tsc` 产出的真实文件是 `.js`。于是「源码 `.ts`、import 写 `.js`」成了 ESM + nodenext 的固定写法，测试文件也一样（Vitest 会自己把 `.js` 解析回 `.ts` 源文件）。

三个包三种写法，都在这个仓库里，对比记忆最牢：

| 包 | 模块设置 | import 写法 | 出处 |
|---|---|---|---|
| `@shop/api`（含 spec） | `type: module` + `nodenext` | `../db/database.js`（必须带扩展名，写 `.js`） | [order.service.spec.ts](../code/shop-api/src/order/order.service.spec.ts) |
| `@ts/lang-basics` | `nodenext` + `allowImportingTsExtensions: true` + `noEmit` | `../src/generics.ts`（写 `.ts`，因为永不产出） | [generics.test.ts](../code/lang-basics/test/generics.test.ts) |
| `@shop/shared` | `nodenext`，`"type": "module"`（ESM 包） | `../src/index.js` | [decimal.test.ts](../code/packages/shared/test/decimal.test.ts) |

PHP 里 `use App\Models\Product;` 与文件名无关，所以这条差异对你完全是新的。**唯一可靠的判断方式：改一个包之前先看它的 `package.json` 有没有 `"type": "module"` 和 tsconfig 的 `moduleResolution`。**

## 10. mock 策略：什么时候 mock，什么时候用内存 SQLite

| 依赖 | 做法 | 仓库里的真实例子 | 理由 |
|---|---|---|---|
| 数据库 | **内存 SQLite**，`createDatabase(":memory:")` | product.repository.spec.ts、order.service.spec.ts | SQL 语义（外键、`LIKE`、`WHERE version=?`）无法 mock；一 mock 就变成「测我写的假数据库」 |
| 配置 | 结构桩 `{ provide: ConfigService, useValue: { get: ... } }` | order.service.spec.ts 第 54–60 行 | 只有一个方法被用，且要测「不同限额」→ 第二个 module 用 `useValue: { get: () => 1 }` 再造一次（同文件第 167–175 行） |
| 认证/HTTP | 不 mock，走真实 supertest | e2e 用 `.auth("admin", "admin123")` | Basic 认证的分支逻辑本身就是被测对象 |
| 前端 API 层 | `vi.mock("../src/api")` + `vi.fn()` | web-vue/test/catalog.test.ts | 网络是不可控外部世界；store 的价值就在「拿到数据后怎么变状态」 |
| 时间/事件循环 | 真实 `setTimeout` + `await` | [async-event-loop.test.ts](../code/lang-basics/test/async-event-loop.test.ts)（串行 ≥35ms、并行更短） | 测的就是时序本身；用 fake timers 会测不到微任务顺序 |
| 环境变量 | `process.env.X = "..."` 放在容器编译前 | e2e 顶部三行 | 见 §5 |

一条经验：**mock 的数量应该与「这个测试想验证的边界」成正比，与「测试的层级」成反比。** e2e 里 0 个 mock（全是真的），Service 单元里 2 个（Config、Database 的真实实例其实来自 `createDatabase`），前端 store 里整模块替换 API。Java 版把 `@MockitoBean ProductService` 放进 `@WebMvcTest` 是同一个道理：切片越深，替身越少。

`@Timed` 的断言属于「Service 单元」这一层，但它顺带解决了一个 Java 老兵的经典疑问：

```ts
// code/shop-api/src/order/order.service.spec.ts
it("@Timed 装饰器在自调用下也生效（对比 Java 的 @Transactional 代理失效）", () => {
  service.place({ customerName: "ben", items: [{ productId: 1, quantity: 1 }] });
  expect(metrics.count("OrderService.place")).toBe(1);
  expect(Object.keys(metrics.snapshot())).toEqual(["OrderService.place"]);
});
```

TS 的方法装饰器是**直接替换原型上的 `descriptor.value`**（[timed.decorator.ts](../code/shop-api/src/common/timed.decorator.ts)），没有 Spring 那种「注入的是代理对象」的间接层，所以 `this.inner()` 自调用照样生效。对照 [SelfInvocationTest.java](../../java/code/shop-api/src/test/java/study/shop/common/SelfInvocationTest.java) 里那两条「外部调用生效 / 自调用失效」的断言：**在 TS 侧这个坑不存在，于是那条测试也就不必存在**——这是「少一层魔法 = 少一类测试」的实例。

## 11. 值得被钉住的契约：401 的两个分支

```ts
// code/shop-api/test/shop-api.e2e.spec.ts
it("未认证写入 → 401 + WWW-Authenticate（与 Spring Security 的行为一致）", async () => {
  const response = await request(http)
    .post("/api/products").set("Accept", "*/*").send({ sku: "SKU-100" }).expect(401);
  expect(response.headers["www-authenticate"]).toBe('Basic realm="Realm"');
  expect(response.body).toMatchObject({ status: 401, error: "Unauthorized", path: "/api/products" });
});

it("Accept: application/json 时 401 是空 body 且不带 WWW-Authenticate", async () => {
  const response = await request(http)
    .post("/api/products").set("Accept", "application/json").send({}).expect(401);
  expect(response.headers["www-authenticate"]).toBeUndefined();
  expect(response.text).toBe("");
});
```

401/403 由 [problem.filter.ts](../code/shop-api/src/common/problem.filter.ts) 特判（`writeSecurityError`），其余领域异常走 problem+json——因为 Spring 版的 401 是 Security 在 DispatcherServlet 之前返回的，**不是** problem+json。这段测试的价值不在测 Nest，而在钉住「两个后端行为一致」。对位 PHP：给同一个错误码断言两种 `Accept` 分支，等于在测中间件而非控制器，很值得抄进自己的 Laravel 项目。

## 12. 数据提供者、并行、隔离池、覆盖率

| 需求 | PHPUnit/Pest | Vitest 5 | 本仓库状态 |
|---|---|---|---|
| 数据驱动 | `#[DataProvider]`、`with()` | `it.each([[1, 2]])("...", (a, b) => {})`、`describe.each` | **未使用**；改写成显式循环（如 error-handling.test.ts 的 `for (const thrown of ["bare string", 42, null, { a: 1 }])`） |
| 文件级并行 | `--processes=4` | 默认开，`pool: "forks"`（子进程），可 `--pool=threads` | 用默认值，无 vitest 配置文件 |
| 关掉隔离提速 | 无对应 | `--no-isolate` 或 `poolOptions.threads.isolate: false`；代价是模块级状态跨文件泄漏 | 不需要（`pnpm -r test` 共 118 个用例，e2e 另算） |
| 单线程排障 | `--processes=1` | `--pool=forks --poolOptions.forks.singleFork` / `--no-file-parallelism` | 值得记住：出现「单独跑绿、一起跑红」时用它定位 |
| 分片 | 无内置 | `--shard=1/4`（配合 CI 矩阵） | 未使用，`pnpm -r` 已按包切分 |
| 只跑受影响 | 无内置 | `--changed [ref]`、`vitest related <file>` | 值得在 CI 上用 |
| 覆盖率 | xdebug/pcov + `--coverage` | `vitest --coverage`，Provider 是 `@vitest/coverage-v8` 或 istanbul | **未安装**，`node_modules` 里只有 `vitest`/`@vitest/spy`/`@vitest/mocker`；要用请 `pnpm add -D @vitest/coverage-v8` |
| 快照 | `spatie/phpunit-snapshot-assertions` | `toMatchSnapshot()` / `toMatchFileSnapshot()` + `-u` | 未使用；前端刻意不装 jsdom（下节） |

前端为什么这么薄，是本章最需要说清的一个决定：三个前端加起来只有 **11 个用例**，全打在「纯边界逻辑」上——schema 解析、`formatAmount`、store 动作。[web-react/test/api.test.ts](../code/web-react/test/api.test.ts) 的注释就是这么写的：这一层最值得测的是边界而不是 DOM。理由不是「组件测不了」，而是**收益/成本比**：

- 组件测试需要 `jsdom` + `@testing-library/react`（或 `@vue/test-utils`），本仓库刻意不装——多两个依赖 + 一套配置，只为断言「表格里有三行」。
- 真正会咬人的是 `ApiProblem` 的字段映射、`PlaceOrderRequestSchema` 客户端拦截、以及金额格式化不做浮点运算：这些用 4 个断言就能钉住。
- Vue 侧把 `useCatalogStore` 的 `submit()` 写成 store 测试（成功重拉列表 → `expect(fetchProducts).toHaveBeenCalledTimes(2)`，失败把 problem+json 的 `fieldErrors` 搬进状态），这就是「测 service 而不是测 Blade」的翻译。

要补的话，优先级从高到低：① `vitest + jsdom + @testing-library/react`，测「409 → 页面出现『库存不足』和字段错误」这条用户路径；② Playwright 做跨端 e2e（Next 官方推荐它测 Server Action，本仓库未装）；③ `@vue/test-utils` 只测 `OrderPanel` 的 emits 契约。

## 13. 脚本约定与 CI 视角

每个包的四个动词是一样的（[code/package.json](../code/package.json) 是 workspace 根，没有 test 脚本，靠 `pnpm -r` 递归）：

| 动词 | lang-basics | @shop/shared | @shop/api | web-react | web-vue | web-next |
|---|---|---|---|---|---|---|
| `typecheck` | `tsc --noEmit` | `tsc --noEmit` | `shared build && tsc --noEmit` | `shared build && tsc --noEmit` | `shared build && vue-tsc --noEmit` | `shared build && tsc --noEmit` |
| `lint` | `eslint .` | `eslint .` | `eslint .` | `eslint .` | `eslint .` | `eslint .` |
| `test` | `vitest run` | `vitest run` | `vitest run src` | `vitest run` | `vitest run` | `vitest run` |
| `build` | 无（不产出） | `tsc -p tsconfig.build.json` | `pnpm build`（shared + tsc） | `shared build && tsc --noEmit && vite build` | `shared build && vue-tsc --noEmit && vite build` | `shared build && next build` |

两条约定值得抄走：

1. **`@shop/shared` 的 `exports` 指向 `dist/`**（[packages/shared/package.json](../code/packages/shared/package.json)），所以任何包的 `typecheck`/`test`/`build` 都必须先 `pnpm --filter @shop/shared build`。忘记加的那一步，报错现象是「Cannot find module '@shop/shared'」——非常像依赖没装，实际是产物没建。
2. **`vite build` 之前先 `tsc --noEmit`**（或 `vue-tsc`）：Vite 用 esbuild/rolldown 只做类型**剥离**，不做类型检查。少了这一步，类型错误会一路带到产物里。

CI 的顺序应当与依赖图一致，每一步都是一条独立命令，方便定位：

```bash
pnpm install --frozen-lockfile
pnpm --filter @shop/shared build     # 契约包的产物是所有人的前置
pnpm -r typecheck                    # 最快、最能定位问题，放最前
pnpm -r lint
pnpm -r test                         # 含 shop-api 单测；e2e 需要显式下一步
pnpm --filter @shop/api test:e2e
pnpm -r build
```

顺序为什么是 typecheck → lint → test → build：TS 的 `typecheck` 覆盖的是 PHP 里没有的那一类错误（§8 的 TS1477 就是「typecheck 先抓到、vitest 只报 transform 错」的活教材），所以它跑得最早、最便宜。`lint` 与 `test` 谁先都行，但 `build` 一定在最后——而 `test:e2e`（§5）本身依赖 `pnpm build`，所以它排在 build 之后。
