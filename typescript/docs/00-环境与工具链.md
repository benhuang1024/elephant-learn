# 00 环境与工具链

> 配套代码：[code/package.json](../code/package.json)、[pnpm-workspace.yaml](../code/pnpm-workspace.yaml)、[tsconfig.base.json](../code/tsconfig.base.json)、[tools/eslint-config](../code/tools/eslint-config/)、[lang-basics/scripts/hello.ts](../code/lang-basics/scripts/hello.ts)
> 本章只给「地图」：装什么、为什么这么装、日常四个命令跑什么。`tsconfig` 每一项的逐个讲解放在第 04 章。

## 1. 工具链对照：把 composer/phpunit 的直觉换掉

| 用途 | PHP / Laravel | 本仓库的 Node 侧 |
|---|---|---|
| 运行时 | `php` (Zend Engine) | `node`（V8 + libuv，**常驻单进程**） |
| 版本管理 | phpenv / brew `php@8.3` | **nvm**（本机用 v24.21.0） |
| 包管理 | Composer | **pnpm**（9.15.9，经 corepack 锁定） |
| 锁文件 | `composer.lock` | `pnpm-lock.yaml` |
| 包仓库 | Packagist | npm registry |
| 项目内多包 | `path` 仓库 + composer 命名空间 | **pnpm workspace**（`pnpm-workspace.yaml` + `workspace:*`） |
| 静态分析 | PHPStan / Psalm | **`tsc` 本身**（编译即检查，没有单独的分析器） |
| 代码风格 | PHP-CS-Fixer / Pint | **ESLint 10**（`eslint.config.mjs` 扁平配置；排版工具为什么没装见第 04 章 §10） |
| 测试 | PHPUnit / Pest | **Vitest 5**（API 几乎照抄，见每个 `test/*.test.ts`） |
| 构建/打包 | 无（解释执行） | `tsc`（类型擦除）/ Vite / Turbopack |
| 脚手架 | `laravel new` | 手工建 workspace，或 `create-next-app` / `create-vite` |
| IDE | PhpStorm | **VS Code**（TS 官方编辑器，语言服务内置） |

一句话心智差：**PHP 没有“编译”这一步，TS 有；但 TS 的“编译”只是删类型，不产出新逻辑。** 理解这点，下面所有配置都不拧巴。

## 2. Node 24 LTS + corepack：像 `packageManager` 那样钉死版本

[package.json](../code/package.json) 里两行决定了“任何人 clone 下来用哪套工具”：

```json
{
  "packageManager": "pnpm@9.15.9",
  "engines": { "node": ">=24.0.0" }
}
```

- `packageManager` 由 **corepack**（Node 自带，无需 `npm i -g pnpm`）读取：进入本目录执行任何 `pnpm` 命令时，corepack 自动切到 9.15.9。这是 composer 没有的能力——**包管理器版本也被钉进了仓库**。
- `engines.node` 是声明，Node 默认不强制；靠 CI / `engine-strict` 兜底。

实测本机取证（只读命令）：

```bash
export PATH=/Users/ben/.nvm/versions/node/v24.21.0/bin:$PATH
node --version   # v24.21.0
pnpm -v          # 9.15.9
node_modules/.bin/tsc --version   # Version 7.0.2
```

## 3. pnpm workspace：对照 composer 的多包仓库

PHP 里把公共代码拆成子包，通常靠 `composer.json` 的 `repositories: [{ "type": "path" }]` + `symlink`。pnpm 把这件事做成了一等公民，根目录一个 [pnpm-workspace.yaml](../code/pnpm-workspace.yaml) 声明成员：

```yaml
packages:
  - lang-basics
  - packages/*
  - shop-api
  - tools/*
  - web-react
  - web-vue
  - web-next
```

成员之间用 `workspace:*` 互相引用，例如 [shop-api/package.json](../code/shop-api/package.json) 依赖本地共享包：

```json
"dependencies": {
  "@shop/shared": "workspace:*"
}
```

`@shop/shared` 就是 [packages/shared](../code/packages/shared/src/index.ts)，一份 Zod schema 被后端（NestJS）和三个前端同时复用——**这是 TS 全栈“一处定义、四端复用”的物理基础**，也是第 05、06 章反复用到的包。

pnpm 相对 npm/yarn 的关键差异，正好解决 PHP 人熟悉的“依赖地狱”：

| 维度 | npm（提升式） | pnpm |
|---|---|---|
| `node_modules` 结构 | 扁平提升，幽灵依赖满天飞 | 内容寻址软链，**只能 import 你在 package.json 里声明过的包** |
| 磁盘 | 每个项目各存一份 | 全局 store 硬链接，装一次到处用 |
| 对 composer 的直觉 | 不像 | 更接近“必须 require 才能用”的严格性 |

> 软链布局还带来一个副作用，第 4 节的“两套 TypeScript 并存”正是利用它。

本仓库目录（`ls` 可见）：

```
typescript/
├── .gitignore                 # node_modules/ dist/ .next/ *.db coverage/ 等
├── docs/                      # 你正在读的教程
└── code/                      # pnpm workspace 根（package.json + pnpm-workspace.yaml）
    ├── tsconfig.base.json     # 所有包 extends 的基座
    ├── lang-basics/           # 语言与运行时示例，12 个 src + 12 个 test（80 用例）
    ├── packages/shared/       # Zod schema + 品牌类型，四端复用
    ├── shop-api/              # NestJS 12 + Drizzle，ESM-only
    ├── tools/eslint-config/   # 共享 ESLint 扁平配置（锁 TS 6）
    ├── web-react/             # React 19 + Vite
    ├── web-vue/               # Vue 3 + vue-tsc（锁 TS 6）
    └── web-next/              # Next.js 16（Turbopack）
```

## 4. 现实：TS 7 原生编译器与 TS 6 并存

本机 `tsc` 是 **TypeScript 7.0.2**——那个用 Go 重写的原生编译器，比 JS 版 `tsc` 快一个数量级。但它不是“无脑升级就好”，本仓库里有三处绕不过去的现实：

1. **TS 7 删掉了 `moduleResolution: "node10"`**，只剩 `node16` / `nodenext` / `bundler`。老教程里满屏的 `"moduleResolution": "node"` 现在直接报错。
2. **TS 7 要求：设了 `outDir` 就必须显式写 `rootDir`**，否则报 `error TS5011`。所以 [shop-api/tsconfig.json](../code/shop-api/tsconfig.json) 和 [packages/shared/tsconfig.json](../code/packages/shared/tsconfig.json) 里都写了 `"rootDir": "./src"`。
3. **生态工具链还没跟上 TS 7 的编译器 API**：
   - `typescript-eslint` 8.72.0 加载时抛 `typescript-eslint does not support TS 7.0`；
   - `vue-tsc` 3.3.13 崩溃，因为 TS 7 不再暴露 `typescript/lib/tsc`。

解法是 **两套 TypeScript 并存**，靠 pnpm 的隔离布局实现（见 [tools/eslint-config/package.json](../code/tools/eslint-config/package.json)）：

```json
// tools/eslint-config/package.json —— 只管 lint，钉死 TS 6
"dependencies": {
  "typescript": "6.0.3",
  "typescript-eslint": "8.72.0"
}
```

```json
// lang-basics/package.json —— 类型检查/构建仍是 TS 7
"devDependencies": {
  "typescript": "7.0.2",
  "@ts/eslint-config": "workspace:*"
}
```

结果：每个业务包自己的 `tsc` 走 TS 7，`eslint` 通过依赖解析拿到 `tools/eslint-config` 里那份 TS 6，`vue-tsc` 在 [web-vue/package.json](../code/web-vue/package.json) 里也自带 TS 6。[tools/eslint-config/index.mjs](../code/tools/eslint-config/index.mjs) 顶部注释写得很直白：

> pnpm 的隔离布局让 typescript-eslint 解析到本包的 TS 6，而各业务包自己的 `tsc` 仍然是 TS 7 —— 两套编译器并存。

**给架构师的判断**：这是过渡期的工程妥协，不是常态。不要把“TS 7 更快”当成唯一事实；先确认你的 lint / 脚手架 / 框架插件支持的 TS 版本，再决定 `typescript` 装哪个。

## 5. 运行 TS 的三种方式：tsc / tsx / node 原生 type stripping

| 方式 | 干什么 | 类型检查？ | 适用 |
|---|---|---|---|
| `node --version` 里的 `tsc`（TS 7） | 删类型、按 tsconfig 产出 `.js` 到 `outDir` | **是** | 正式构建：`shop-api` 的 `build` = `tsc -p tsconfig.build.json` |
| `tsx`（第三方，本仓库未装） | esbuild 式的即时运行/热更，容忍语义型语法 | 否 | 大型项目 dev server |
| **`node file.ts`（原生 type stripping）** | Node 24 直接“擦掉类型”跑单文件 | **否** | 脚本、临时验证 |

Node 24 的原生类型擦除可以真跑，取证：

```bash
node lang-basics/scripts/hello.ts
```

```
你好, PHPer! 当前 Node v24.21.0，正在学 TypeScript
运行时信息: { node: 'v24.21.0', platform: 'darwin', pid: 26998 }
list 的编译期类型是 number[]，运行时是 [object Array]
```

它的限制写在 [hello.ts](../code/lang-basics/scripts/hello.ts) 注释里，务必记住：

- **不能“有语义”的类型语法**：`enum`、`namespace`、参数属性 `constructor(private x: T)` 都需要生成运行时代码，原生擦除做不到；
- **import 必须写全扩展名**（`.ts` / `.js`），因为它就是一份 ESM；
- **不做类型检查**——想检查跑 `pnpm typecheck`。

> 第 01 章会讲为什么社区劝你别用 `enum`；这里先记一条：原生 `node file.ts` 直接和 `enum` 冲突，是同一个理由的运行时版本。

## 6. tsconfig：先看地图，细节留给第 04 章

本仓库是“一个基座 + 各包 `extends` 覆盖”，等价于 composer 里 base config + per-project override 的思路。基座是 [tsconfig.base.json](../code/tsconfig.base.json)，关键几项先眼熟，逐项剖析在第 04 章：

```jsonc
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "nodenext",              // TS7 只认 node16/nodenext/bundler，没有旧的 node
    "moduleResolution": "nodenext",
    "strict": true,                    // 一揽子严格开关的总闸
    "noUncheckedIndexedAccess": true,  // 数组越界返回 T | undefined
    "exactOptionalPropertyTypes": false,
    "isolatedModules": true,           // 每个文件可单独编译（禁 const enum 等）
    "verbatimModuleSyntax": true,      // import 写成什么就按什么发，禁隐性 CJS 互操作
    "skipLibCheck": true
  }
}
```

两种典型派生：

- **纯检查、不产出**（[lang-basics/tsconfig.json](../code/lang-basics/tsconfig.json)）：`"noEmit": true` + `"allowImportingTsExtensions": true`，于是 `import ... from "./generics.ts"` 合法（见 [utility-types.ts](../code/lang-basics/src/utility-types.ts) 第 20 行）。
- **真构建**（[shop-api/tsconfig.json](../code/shop-api/tsconfig.json)）：`"rootDir": "./src"` + `"outDir": "./dist"`，并打开 `experimentalDecorators` / `emitDecoratorMetadata`、关掉 `useDefineForClassFields`——这是 NestJS 能跑的关键，第 07 章细讲。

## 7. 编辑器与四个日常命令

**编辑器**：用 VS Code。TS 语言服务内置，无需装插件；右下角能看到当前用的 `typescript` 版本，可 “Select TypeScript Version” 在 workspace 的 TS 7 与 TS 6 之间切。保存即得波浪线（类型错误），这相当于 PHPStan 常驻，只是它是编译器本体。

四个日常命令（全部在 `typescript/code` 下执行；`lang-basics` 脚本见 [package.json](../code/lang-basics/package.json)）：

| 目的 | 命令 | 背后 |
|---|---|---|
| 类型检查（不产出） | `pnpm typecheck` | `tsc --noEmit`（TS 7） |
| 静态规则 + 风格 | `pnpm lint` | `eslint .`（走 @ts/eslint-config，TS 6） |
| 跑测试 | `pnpm test` | `vitest run`（11 文件 / 71 用例，全绿） |
| 跑单个脚本 | `pnpm hello` | `node scripts/hello.ts`（原生擦除） |

对照 PHP：`typecheck` ≈ `phpstan analyse`，`lint` ≈ `pint`/`ecs`，`test` ≈ `pest`/`phpunit`。差别是 **`tsc` 的类型检查是“法律”，跑不起来就报；PHPStan 是“建议”，可以配 baseline 绕过**。

**没有排版工具**：本仓库不带 Prettier，代码风格由 ESLint 管「会不会出事」，不管「长什么样」。为什么一个教学仓库故意不装格式化器（以及真实项目里接线的顺序），第 04 章 §10 专门讲这件事。
