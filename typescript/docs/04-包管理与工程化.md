# 04 包管理与工程化 —— composer 的心智模型能复用多少

> 配套代码：[code/package.json](../code/package.json)、[pnpm-workspace.yaml](../code/pnpm-workspace.yaml)、[tsconfig.base.json](../code/tsconfig.base.json)、[tools/eslint-config/index.mjs](../code/tools/eslint-config/index.mjs)、[packages/shared/package.json](../code/packages/shared/package.json)、[shop-api/package.json](../code/shop-api/package.json)、[lang-basics/tsconfig.json](../code/lang-basics/tsconfig.json)。
> 实测环境：Node v24.21.0、pnpm 9.15.9（corepack）、TypeScript 7.0.2、Vitest 5.0.5、ESLint 10.13.0 + typescript-eslint 8.72.0、Zod 4.6.7、NestJS 12.2.0。

## 1. composer ↔ npm/pnpm 逐个对照

| Composer | pnpm / npm | 差异与坑 |
|---|---|---|
| `composer.json` | `package.json` | 后者同时是**脚本入口** + 模块系统声明（`"type"`）+ 导出契约（`exports`） |
| `composer.lock` | `pnpm-lock.yaml` | 结构等价；但 lock 文件里记的是**解析结果 + peer 组合**，同一份 lock 换 registry 会重下 |
| `vendor/` | `node_modules/` | composer 的 vendor 是**扁平**的；pnpm 是 `.pnpm/` 内容寻址 + 软链，见第 3 节 |
| `composer install` | `pnpm install` | pnpm 默认按 lock 精确安装；`composer install` 也按 lock，`composer update` 才重新求解 |
| `composer update` | 改 `package.json` 后 `pnpm install` + 写回 lock | npm 生态没有「SAT 求解器」这个概念，冲突表现为 ERESOLVE（npm）或直接装两份（pnpm） |
| `require` / `require-dev` | `dependencies` / `devDependencies` | 语义一致；此外还有 `peerDependencies`（≈「宿主必须提供」，composer 只能用 `provide`/`conflict` 间接表达） |
| `autoload.psr-4` | `exports` + `types` | **本质差异**：PHP 有 autoload 映射（命名空间→目录），JS 不需要，包名直接查目录 |
| `bin` | `bin` | 一样，装进 `node_modules/.bin` |
| `scripts` | `scripts` | package.json 的 scripts 是**默认入口**，`pnpm <name>` 直接跑；composer 要写 `composer <name>` |
| `packagist.org` | `registry.npmjs.org` | 私有源：composer 用 `repositories` + `composer auth config`；npm 用 `.npmrc` + `//registry/:_authToken`（本仓库无 `.npmrc`，全走公共源） |
| `~/.composer/cache` | pnpm **全局 store**（内容寻址硬链接） | 见第 3 节，这是 pnpm 相对 npm 的核心优势；`composer why` ↔ `pnpm why` 一样好用 |
| `path repository` | `workspace:*` | monorepo 方案，见第 6 节 |

### 版本区间：`^` 相同，`~` 完全不同

这是从 composer 迁移过来**唯一真正会踩的语义差异**：

| 约束 | Composer 含义 | npm/pnpm 含义 |
|---|---|---|
| `^1.2.3` / `^0.2.3` | `>=1.2.3 <2.0.0` / `>=0.2.3 <0.3.0` | 完全一致 ✅（`^0` 的特殊处理两边相同） |
| `~1.2` | `>=1.2 <2.0` | ❌ `>=1.2.0 <1.3.0` |
| `~1.2.3` | `>=1.2.3 <1.3.0` | `>=1.2.3 <1.4.0` ❌ |
| `1.2.*` | `>=1.2 <1.3` | `>=1.2.0 <1.3.0` ✅ 一致 |

`~` 是「波浪号后面保留几位，就精确到那一位」，composer 和 npm 的这段直觉正好相反，务必记住。

本仓库的选择是**能钉死就钉死**：`"typescript": "7.0.2"`、`"vitest": "5.0.5"`、`"zod": "4.6.7"`、`"@nestjs/common": "12.2.0"` 全都没有区间号，只有 `@types/node` 这类无运行时影响的类型包用了 `^` —— 因为第 11 节要讲的 TS 6/TS 7 双栈让「编译器版本一变，全仓 lint/typecheck 行为都变」，不允许自动升级。`package.json` 里还有两件 composer 没有的事：`"private": true`（≈ 禁止 `npm publish` 这个包）、`"packageManager": "pnpm@9.15.9"` + `"engines": { "node": ">=24.0.0" }`（corepack 决定哪台机器上跑哪个 pnpm）。

## 2. 一个包 = 三个契约

Laravel 的包作者关心 `composer.json` 的 `autoload`；Node 包作者要同时声明**运行时入口**、**类型入口**、**发布内容**：

```json
{
  "name": "@shop/shared",
  "type": "module",
  "types": "./dist/index.d.ts",
  "exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" } },
  "files": ["dist"]
}
```

| 字段 | 谁读 | 作用 | 对应 PHP |
|---|---|---|---|
| `main` | 老的 CJS 解析器 | 兜底入口（本包改 ESM 后已删掉，见第 5 节） | 无（PHP 靠 autoload） |
| `exports` | 现代 Node/Vite/TS | **真正的**入口表，支持条件解析与子路径白名单 | `autoload` + 隐含的「私有内部文件」概念 |
| `types` | TypeScript | 类型入口（`exports.types` 条件优先于它） | 无 |
| `files` | 发布器 | 只发这些目录 | `.gitattributes export-ignore` |
| `"type": "module"` | Node | 本包 `.js` 按 ESM 还是 CJS 解释 | 无对应物，**这是最大的文化差异** |

`exports` 的**条件解析**（conditional exports）值得单独记：同一份产物可以按 `types` / `import` / `require` / `browser` / `default` 给不同入口。条件顺序有意义 —— `types` 必须写在最前面，否则 TS 拿不到类型。这比 PSR-4「命名空间映射到目录」严格得多：包外的人**看不见**你没导出的路径。

## 3. pnpm 的存储布局与「幽灵依赖」

composer 和 npm/yarn 的 `vendor/`、`node_modules/` 都是**扁平**的：所有包（含传递依赖）躺在一级目录下。于是 PHP 里 `use` 一个没写进 `composer.json` 的包照样能跑，JS 里 `import` 一个只在依赖树里、没在自己 `package.json` 声明的包本地也能跑 —— 后者有个名字叫「幽灵依赖」（phantom dependency），直到 CI 换个安装器才炸。

pnpm 的解法是**内容寻址存储 + 隔离软链**：

```
全局 store（`pnpm store path` 可查）  ← 按内容哈希存文件（≈ composer cache，但去重到文件级）
node_modules/
├── typescript         → .pnpm/typescript@7.0.2/node_modules/typescript
├── typescript-eslint  → .pnpm/typescript-eslint@8.72.0_eslint@10.13.0_typescript@6.0.3/…
└── .pnpm/
    ├── typescript@7.0.2/…  ├── typescript@6.0.3/…       ← 同一棵树并存两个版本
    └── typescript-eslint@8.72.0_eslint@10.13.0_typescript@6.0.3/node_modules/
        ├── typescript → ../../../typescript@6.0.3/…      ← 每个包只看得到自己的依赖
        └── eslint …
```

三个后果：

1. **幽灵依赖直接编译/运行失败** —— 没声明就解析不到，这是好事。
2. **磁盘去重**：同一版本全局只存一份，硬链接进项目。
3. **同一棵树里可以并存两个版本**：上面这个目录名里的 `_typescript@6.0.3` 后缀就是证据 —— 本仓库正是靠这一点让 TS 7 和 TS 6 共存（第 11 节）。这是 composer 的 SAT 求解器做不到的（composer 一个包只能有一个版本；npm 可以嵌套安装多版本）。

## 4. workspace：本仓库的 7 个包

[pnpm-workspace.yaml](../code/pnpm-workspace.yaml) 只做一件事 —— 列出包：

```yaml
packages: [lang-basics, packages/*, shop-api, tools/*, web-react, web-vue, web-next]
```

跨包引用用协议前缀，语义是「必须解析到本 workspace 里的这个包，不去 registry 找」：`"dependencies": { "@shop/shared": "workspace:*" }`。对照 composer 的 `path repository` + symlink —— pnpm 的 workspace 天生就是 symlink，不用配置。

| 写法 | 含义 |
|---|---|
| `workspace:*` | 链接本地包，发布时替换成 `*`（本仓库全是 `private: true`，不发布） |
| `workspace:^` | 发布时替换成 `^<当前版本>` |
| 裸 `*` | 会去 registry 找一个叫 `@shop/shared` 的包 —— **忘了加前缀的经典事故** |

### `catalog:` 为什么本仓库没用

pnpm 9.5+ 允许在 `pnpm-workspace.yaml` 里集中声明版本、各包写 `catalog:` 引用（≈ Maven BOM）。本仓库的 workspace 文件**只有 `packages:` 一个键**，是刻意选择：一共 6 个业务包 + 1 个工具包，版本重复的只有 `typescript` / `vitest` / `@types/node`，收益小；更关键的是 `typescript` 需要**故意不统一**（业务包 7.0.2，`tools/eslint-config` 和 `web-vue` 6.0.3），catalog 反而会把这两个不同值拆回各包写，等于白装一层。等你有 20 个包、要一次升 Zod 时再上它。

## 5. `pnpm -r` 不会先构建依赖 —— 本仓库最实用的一条

`pnpm -r test` 会按拓扑顺序跑各包的 `test` 脚本，但**不会**先跑依赖包的 `build`。而 `@shop/shared` 是编译产物包（`exports` 指向 `dist/`），所以任何引用它的包在 typecheck 前必须先有 `dist/`，否则 TS 找不到类型。

于是每个下游包的脚本都显式带一句：

```json
"typecheck": "pnpm --filter @shop/shared build && tsc --noEmit",
"build": "pnpm --filter @shop/shared build && tsc -p tsconfig.build.json"
```

见 [shop-api/package.json](../code/shop-api/package.json)、[web-next/package.json](../code/web-next/package.json)。第一次看到会觉得啰嗦，但它把「依赖必须先构建」这条隐式契约写在了显式位置 —— 等价于 Maven 多模块里 `./mvnw install` 先装 domain 再编 app。`pnpm --filter <name> <script>` ≈ 走进子包再跑 composer，但可以从根目录调用，还支持范围表达式。

### `@shop/shared` 也必须是 ESM：一个真实的互操作踩坑

这个包最初是**故意编成 CommonJS** 的（没有 `"type"` 字段 + `main`/`types` 指向 `dist/`），
理由看起来很强：Nest（ESM）可以 `import` 一个 CJS 包，Vite/Next 也都会做 CJS 兼容。
后端和测试确实全绿 —— **直到在浏览器里打开前端**，控制台什么都没报，页面一片空白，实际错误是：

```
The requested module '/@fs/.../packages/shared/dist/index.js'
does not provide an export named 'OrderResponseSchema'
```

原因：workspace 里的**链接依赖**（symlink 到本仓库目录）会被 Vite 当作源码用 `/@fs/` 直接引入，
**不走 optimizeDeps 的 CJS→ESM 预打包**，于是浏览器按 ESM 规则去读一个 CJS 文件，
具名导出根本不存在。Node 侧能跑是因为 Nest 走的是 `require`/`import(esm)` 的 CJS 兼容路径，两边机制不同。

修法只有一条路是干净的：**把 shared 也改成 ESM**（`"type": "module"`、`module: nodenext`、
相对导入补 `.js`、去掉 `main` 只留 `exports`）。这也与 NestJS 12 全面 ESM-only 的方向一致。

| 消费方 | 现在怎么吃这个包 |
|---|---|
| `shop-api`（ESM + Node） | 原生 ESM import，具名导出直接可用 |
| `web-react` / `web-vue`（Vite 8） | 直接按 ESM 引入，链接依赖不再需要预打包 |
| `web-next`（Next 16） | 服务端与客户端都按 ESM 解析 |

反过来讲清另一条硬约束：CJS **不能** `import` ESM-only 包，所以 NestJS 12（纯 ESM）逼着 `shop-api`
写了 `"type": "module"`，否则撞 `TS1479: The current file is a CommonJS module whose imports will
produce 'require' calls; however, the referenced file is an ECMAScript module`。这就是第 7 节的双栈现实。

## 6. tsconfig.base.json 逐选项讲解

[tsconfig.base.json](../code/tsconfig.base.json) 全文只有 21 个选项，但每一个都在解决具体问题。各包 `extends` 它，只覆盖差异部分。

### 输出目标与模块系统

| 选项 | 值 | 为什么开 | PHP 对照 |
|---|---|---|---|
| `target` | `ES2023` | 语法降级目标；Node 24 全支持，写高不降更快 | 无（PHP 无编译期） |
| `lib` | `["ES2024"]` | **`Object.groupBy` 是 ES2024 的 API**，`target` 不会自动带上它。改成 ES2023 就报 `TS2550: Property 'groupBy' does not exist on type 'ObjectConstructor'. Do you need to change your target library? Try changing the 'lib' compiler option to 'es2024' or later.` | 相当于声明「有哪些内置函数可用」 |
| `module` | `nodenext` | 让 TS 按 Node 的真实解析规则判断每个文件是 ESM 还是 CJS（看最近的 `package.json` 的 `"type"`） | 无 |
| `moduleResolution` | `nodenext` | 同上，只管解析。**TS 7 已删掉 `node10`**：配了会直接 `TS5108: Option 'moduleResolution=node10' has been removed. Please remove it from your configuration.` —— composer 时代那些老 `tsconfig.json` 全都要改 |
| `moduleDetection` | `force` | 所有 `.ts` 都按模块处理，不给「一个文件里有全局 `var` 污染另一个文件」的机会（PHP 每个文件自带命名空间，没这问题） |

`target: ES2023` 还带来一个隐藏默认值：**`useDefineForClassFields` 在 target ≥ ES2022 时默认为 `true`**，这直接影响装饰器，见下文。

### 严格性开关（这是 TS 的价值所在）

| 选项 | 值 | 解决什么 | 实测感受 |
|---|---|---|---|
| `strict` | `true` | 打开 `strictNullChecks` 等一系列开关 | 一条开关 ≈ 「给所有函数签名补上 `?`」，本章之前讲过 |
| `noUncheckedIndexedAccess` | `true` | `arr[i]` 类型变成 `T \| undefined` | 更接近 PHP「越界 warning + null」的现实；代价是到处要 `!` 或收窄，见 [null-safety.ts](../code/lang-basics/src/null-safety.ts) 的 `secondOrNone` |
| `noImplicitOverride` | `true` | 子类覆盖必须写 `override` | 和 Java 的 `@Override` 同一条纪律；[domain-errors.ts](../code/shop-api/src/common/domain-errors.ts) 里 `override readonly cause: unknown` 就是它逼出来的 |
| `noImplicitReturns` | `true` | 不允许「有的分支返回值、有的返回 undefined」 | 防 Laravel 里 `function` 有时返回 `null` 有时不写 return 的那种模糊 |
| `noFallthroughCasesInSwitch` | `true` | `switch` 忘写 `break` 报错 | 与 PHP 一致地危险，但 PHP 只在运行时才发现 |
| `noUnusedLocals` / `noUnusedParameters` | `true` | 未使用的局部与参数报错 | 生产包（`tsconfig.build.json`）里关掉，因为 DTO 装饰器参数常见 `_meta` 这种占位；共享约定是 `^_` 前缀豁免（见 eslint 配置） |
| `exactOptionalPropertyTypes` | **`false`** | 显式关掉，注释也要写清楚为什么 | 打开后 `{a?: string}` 与 `{a: string \| undefined}` 彻底分离，对接 Zod 推导出来的 DTO 时噪音极大。这是本仓库唯一「关掉的严格开关」，属于实用主义妥协 |
| `strictPropertyInitialization`（shop-api） | `false` | Nest 的依赖注入字段是 `constructor(private readonly svc: X) {}` 或装饰器属性，开启会对「框架负责赋值」的属性报错 | 只在 [shop-api/tsconfig.json](../code/shop-api/tsconfig.json) 关 |

### 模块互操作与打包器友好性

| 选项 | 值 | 为什么 |
|---|---|---|
| `isolatedModules` | `true` | 声明「每个文件可以被单独转译」。这是 SWC / esbuild / rolldown 的前提条件：它们不做全程序类型分析，所以 `export =`、非模块的 `namespace`、跨文件的类型重导出等写法直接禁用。**打开它等于提前发现自己用了打包器编不动的语法** |
| `verbatimModuleSyntax` | `true` | 强制 `import type { X }` 写清 `type`，转译器不会「猜」哪些 import 该删。`isolatedModules` 的最佳搭档：单文件转译时无法判断 `import { Foo }` 是值还是类型，可能把类型留在产物里导致运行时 `undefined` |
| `esModuleInterop` | `true` | 让 `import express from "express"` 在 CJS 包上工作（补 `_interopRequireDefault` helper） |
| `allowSyntheticDefaultImports` | `true` | 允许对没有默认导出的模块写默认导入（类型层面），配合上面 |
| `resolveJsonModule` | `true` | 允许 `import pkg from "./package.json"` —— Nest 的 `@nestjs/config` 之类的包会用到 |
| `skipLibCheck` | `true` | 不检查 `.d.ts` 内部。本仓库同时存在 TS 6/TS 7 两套 `.d.ts`，不开这个会在 `node_modules` 里爆一堆无关错误。代价：第三方类型包的 bug 你看不到 |
| `forceConsistentCasingInFileNames` | `true` | 大小写敏感，防止 macOS 本地跑得好、Linux CI 报「找不到模块」（和 composer 的 PSR-4 大小写纪律同一个动机） |
| `declaration` | `false`（base） | 只有**被别包引用**的库才需要产出 `.d.ts`；`shared` 在 `tsconfig.build.json` 里打开 |
| `sourceMap` | `true` | 调试用；Vite/Next 自己也有 sourcemap 配置 |
| `declarationMap`（shared build） | `true` | 让「跳到定义」从前端代码一路跳进 `@shop/shared` 的 `.ts` 源码，而不是停在生成的 `.d.ts`。一处定义四端复用的体验全靠它 |
| `rootDir` / `outDir`（各 build 配置） | `./src` / `./dist` | **TS 7 强制要求**：设了 `outDir` 就必须显式写 `rootDir`，否则 `TS5011: The common source directory of 'tsconfig.json' is './src'. The 'rootDir' setting must be explicitly set to this or another path to adjust your output's file layout.`。连带第二个坑：`rootDir` 只能覆盖真正会产出的文件，所以**类型检查的 tsconfig 与产出的 tsconfig.build.json 必须分开** —— 把 `test/**/*.ts` 放进带 `rootDir: ./src` 的配置里会得到 `TS6059: File '.../test/decimal.test.ts' is not under 'rootDir'`（本仓库就是这么撞的） |

### 两个包级例外，正好讲清 ESM/CJS 与装饰器

**`lang-basics/tsconfig.json`**（可执行笔记，不产出）：

```json
{ "compilerOptions": { "types": ["node"], "allowImportingTsExtensions": true, "noEmit": true } }
```

`module: nodenext` 下相对导入必须带扩展名，否则 `TS2835: Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './a.js'?`。这个包不产出 JS（`node scripts/hello.ts` 靠 Node 24 原生类型擦除直接跑），所以它选择写 `.ts` 扩展名 + `allowImportingTsExtensions`；测试里就能看到 `from "../src/async-event-loop.ts"`。
**其余会产出代码的包一律写 `.js` 扩展名**（如 [problem.filter.ts](../code/shop-api/src/common/problem.filter.ts) 里的 `from "./domain-errors.js"`）—— `.js`  specifier 指向的是编译后的产物，这才是发布包的正确写法。一个仓库两种风格，规则很简单：`noEmit` 才允许 `.ts`。

**`shop-api/tsconfig.json`**（只管类型检查）与 **`shop-api/tsconfig.build.json`**（只管产出）：

```json
// tsconfig.json：typecheck 用，覆盖 src + test，不产出
{
  "module": "nodenext", "moduleResolution": "nodenext",
  "verbatimModuleSyntax": false,
  "experimentalDecorators": true, "emitDecoratorMetadata": true,
  "useDefineForClassFields": false, "strictPropertyInitialization": false,
  "types": ["node"], "noEmit": true
}

// tsconfig.build.json：build 用，只含 src，rootDir/outDir 在这里
{ "extends": "./tsconfig.json",
  "compilerOptions": { "noEmit": false, "rootDir": "./src", "outDir": "./dist" },
  "include": ["src/**/*.ts"] }
```

- `useDefineForClassFields: false` 与装饰器的关系是**必须的**：默认 `true` 时，类字段用 `Object.defineProperty` 语义初始化，会**覆盖**装饰器在原型/构造期种下的值，Nest 的属性注入和 `emitDecoratorMetadata` 反射会静默失效。target ES2023 默认是 `true`，所以这里显式关掉。
- `verbatimModuleSyntax: false`：**只有 `shop-api` 显式关掉**（base 与其余包都是 `true`）。硬原因是 `emitDecoratorMetadata`：
  开着它，`import type { UsersService }` 会被彻底擦除，而 `@Injectable()` 构造器参数需要那个**运行时的值**才能发射
  `design:paramtypes`，擦掉之后元数据变成 `[Object]`，Nest 启动时直接 `Can't resolve dependencies`。
  代价是类型导入若忘了写 `type`，产物里会留下一次真实的运行时 import —— 这条只能靠 lint 和 code review 守。
  `@shop/shared` 不需要这个例外：改 ESM 之后它原样继承 base 的 `true`，全仓 7 个包里只有 shop-api 一个例外。
  顺带一条相关的硬规则：如果某个包真的编成 CJS，开着它会在顶层值导出上直接报 `TS1287: A top-level 'export' modifier cannot be used on value declarations in a CommonJS module when 'verbatimModuleSyntax' is enabled.` —— 很多 CJS 库别无选择，只能关掉（shared 最初就是这条的受害者，见第 5 节）。
- `experimentalDecorators` + `emitDecoratorMetadata` 是**旧式装饰器**（TS 的标准装饰器还不支持 `design:paramtypes` 这类元数据发射，而 Nest 的 DI 靠它）。这是 Nest 生态目前对工程化链的最大约束。

**前端两包**：`moduleResolution: "bundler"` + `noEmit: true`。`bundler` 是第三种解析模式（允许扩展名省略、支持 `exports` 的 `browser`/`import` 条件），前提是打包器会帮你解析 —— 只有 Vite/Next 环境下才合法。`web-next` 额外要 `jsx: "preserve"`（JSX 交给 Turbopack/SWC 而不是 tsc）和 `incremental: true`（所以仓库里能看到 `tsconfig.tsbuildinfo`）。

## 7. ESM 与 CJS：双栈现实与 TS 7 的取舍

| | ESM | CommonJS |
|---|---|---|
| 语法 | `import` / `export` | `require` / `module.exports` |
| 判定方式 | `.mjs`，或 `.js` + 最近 `package.json` 的 `"type": "module"` | `.cjs`，或 `.js` + 无 `"type"` |
| 加载 | 异步、静态分析、可 tree-shaking | 同步、运行时任意位置 |
| 互操作 | **ESM 可以 import CJS** | **CJS 不能 require ESM**（除非 `await import()`） |
| PHP 对照 | 像「有静态分析意识的 autoload」 | 像 `require_once` |

本仓库的真实分布：

| 包 | `"type"` | 原因 |
|---|---|---|
| `lang-basics` | `module` | 纯笔记，Node 24 直跑 `.ts` |
| `@shop/shared` | `module` | 见第 5 节：链接依赖在浏览器里按 ESM 解析，编成 CJS 会直接空页面 |
| `@shop/api` | `module` | NestJS 12 全部 ESM-only，CJS 消费会撞 TS1479 |
| `@ts/eslint-config` | `module` | ESLint 10 的扁平配置就是 ESM `.mjs` |
| 三个 web 包 | `module` | Vite / Next 生态 |

TS 7 在这件事上的取舍很明确：**不做任何「帮你兼容」的魔法**。`module: nodenext` 就是老老实实读 Node 的解析规则，一个仓库里 ESM 包和 CJS 包各按自己的 `package.json` 解释；这也意味着 `moduleResolution: node10` 那种「假装 Node 还活在 2016」的兼容模式被删除了（TS5108）。迁移老项目时，第一个要改的就是这两行。

## 8. 谁做什么：tsc / SWC / esbuild / Vite / Turbopack

PHP 只有一台引擎（opcache 只是缓存）。JS 工具链是**分工**的，混着理解就会一直困惑「为什么我改了 tsconfig 但 build 没变慢/变快」：

| 工具 | 做什么 | **不做什么** | 本仓库哪里在用 |
|---|---|---|---|
| `tsc`（TypeScript 7.0.2，Go 原生） | 类型检查 + 产出 `.js`/`.d.ts`/`.d.ts.map` | 不做打包、不做 dev server | 所有包的 `typecheck`；`shared` 和 `shop-api` 的 `build` |
| SWC | Rust 写的转译器/打包器 | **完全不做类型检查**（只看语法） | Next 16 的编译层（`@next/swc-darwin-arm64@16.4.3`） |
| esbuild | Go 写的转译器/bundler | 同上，且不支持装饰器等有语义的语法 | Vite / Vitest 依赖链里（`esbuild@0.28.2`） |
| Vite 8.3.5 | dev server（原生 ESM 按需编译）+ 生产打包 | 类型检查靠你自己跑 `tsc --noEmit` | `web-react` / `web-vue` 的 `dev`、`preview` |
| rolldown 1.2.15 | Rust 打包器，**Vite 8 的生产构建引擎**（Rollup 的继任者） | 不做类型检查 | `web-react` 的 `vite build` |
| Turbopack | Rust 增量打包器，**Next 16 默认的 dev 与 build 引擎** | 不做类型检查 | `web-next`，配置零声明（`next dev` / `next build`） |
| `vue-tsc` 3.3.13 | 给 `.vue` SFC 做类型检查 | 不打包 | `web-vue` 的 `typecheck` / `build` |
| Vitest 5.0.5 | 测试运行器，跑在 Vite 的转译管道上 | 不做类型检查（类型错误不挡测试） | 全部包的 `test` |

**唯一一条纪律：`vite build` 和 `next build` 都不会帮你查类型。** 所以 [web-react/package.json](../code/web-react/package.json) 把 build 写成 `pnpm --filter @shop/shared build && tsc --noEmit && vite build`，`web-vue` 换成 `vue-tsc --noEmit`。这就是 Laravel 里「`vite build` 通过 ≠ PHPStan 通过」的同一条常识。

## 9. ESLint 10 扁平配置 + typescript-eslint 撞上 TS 7：现场记录

### 配置长什么样

ESLint 10 只有扁平配置（`eslint.config.mjs` 默认导出一个数组/配置），`eslintrc` 那套 extends 层级已经废了。对照 Laravel 的 `phpstan.neon` + `.php-cs-fixer.php`：一份文件、显式数组、每条规则自己带 severity 和 options。各包的配置只有一行 `export { default } from "@ts/eslint-config";`，真身在 [tools/eslint-config/index.mjs](../code/tools/eslint-config/index.mjs)：

```js
import js from "@eslint/js";
import tseslint from "typescript-eslint";
import globals from "globals";

export default tseslint.config(
  { ignores: ["**/node_modules/**", "**/dist/**", "**/.next/**", "**/coverage/**"] },
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    languageOptions: { globals: { ...globals.node, ...globals.browser } },
    rules: {
      "@typescript-eslint/no-unused-vars": ["error", { argsIgnorePattern: "^_", varsIgnorePattern: "^_" }],
      "@typescript-eslint/no-explicit-any": "warn",
      eqeqeq: ["error", "always"],
    },
  },
  { files: ["**/*.test.ts", "test/**/*.ts"], rules: { "@typescript-eslint/no-explicit-any": "off" } },
);
```

要点：`ignores` 现在是**一条配置对象**而不是 `.eslintignore` 文件；类型感知规则靠 `tseslint.configs.recommended` 引入；`files` 段可以按 glob 覆盖规则（测试里放开 `any`）。`eqeqeq` 是第 03 章 `undefined == null` 那道题的工程化落地。

### 现场：TS 7 直接把 linter 炸了

本仓库用 TypeScript 7.0.2（Go 原生编译器）。typescript-eslint 依赖 TS 的 **JS 编译器 API** 来构建 AST + 类型信息，TS 7 不再提供它。在没有本仓库这套锁版本方案之前，加载配置就报错，原文明确：

```
typescript-eslint does not support TS 7.0.
Please see https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6.0 to run typescript-eslint using the TS 6 API.
See also https://github.com/typescript-eslint/typescript-eslint/issues/10940 for tracking typescript-eslint's support for TS >=7.1

Error: typescript-eslint does not support TS 7.0.
```

（`typescript-eslint@8.72.0/dist/index.js` 里是一段加载期检查：`if (versionMajor >= 7) { console.error(...); throw new Error(...) }` —— 是**抛异常**，不是警告，所以 ESLint 完全跑不起来。）

### 解决：一个 workspace 包，专门用来锁 TS 6

[tools/eslint-config/package.json](../code/tools/eslint-config/package.json)：

```json
{
  "name": "@ts/eslint-config",
  "description": "共享 ESLint 扁平配置。注意：typescript-eslint 尚不支持 TS 7 的原生编译器 API，因此这里单独锁 TS 6。",
  "dependencies": { "@eslint/js": "10.0.1", "globals": "17.13.0", "typescript": "6.0.3", "typescript-eslint": "8.72.0" },
  "peerDependencies": { "eslint": ">=10" }
}
```

为什么这样就好了：pnpm 的隔离布局（第 3 节）让 `typescript-eslint` 沿着自己的依赖链**先**解析到 `tools/eslint-config` 的 TS 6.0.3，而各业务包里的 `tsc` 仍然是 TS 7.0.2。结果是两套编译器并存、互不干扰：

| 场景 | 用哪个 TS | 为什么 |
|---|---|---|
| `tsc --noEmit` / `tsc -p tsconfig.build.json` | 7.0.2 | 业务包的 devDependency |
| `eslint .` | 6.0.3 | 由 `@ts/eslint-config` 带进来，typescript-eslint 从它解析 |

同一个技巧用在 `web-vue`：`vue-tsc@3.3.13` 依赖 `typescript/lib/tsc` 这条 JS API 路径，TS 7 没有它，所以 [web-vue/package.json](../code/web-vue/package.json) 的 devDependencies 里单独写 `"typescript": "6.0.3"`。`web-react` / `web-next` 没有这个问题（用不到 JS API），保持 7.0.2。

**给 PHP 人的翻译**：这相当于「opcache 与 Xdebug 需要两个 PHP 二进制」，你不可能同时用两个版本的同一份运行时，于是给不同工具各建一个隔离环境。JS 生态靠 pnpm 的软链布局天然支持，composer 的扁平 vendor 做不到。

## 10. 格式化：Prettier 该放在哪（本仓库故意没装）

| 维度 | PHP 生态 | JS 生态 |
|---|---|---|
| 格式化器 | php-cs-fixer / Laravel Pint | **Prettier** |
| 与 linter 的关系 | 常常混在一个工具里（cs-fixer 既排版又查质量） | **严格分工**：Prettier 只管排版，ESLint 只管代码质量 |
| 冲突处理 | 关掉 cs-fixer 的排版规则 | 装 `eslint-config-prettier` 把 ESLint 里所有排版规则关掉，否则两边互相「修复」对方 |
| 配置文件位置 | 根 `.php-cs-fixer.php` | 根 `.prettierrc.json`（子包不再放），配 `.prettierignore` 排掉 `dist/`、`.next/`、`pnpm-lock.yaml` |
| 门禁写法 | `pint --test` 进 CI | `prettier --check .` 进 CI（`--write` 只在本地/修复分支跑） |

**这个仓库没有格式化器，是决定而不是遗漏。** 理由有两条，都和本仓库的性质有关：

1. 这里的注释、行内 PHP↔TS 对照、`// ⚠️` 段落是按**讲解需要**排版的（一条长注释折成两行是为了和下一段代码并排读）。跑一次 `prettier --write` 会把这些地方重排，而 18 章文档里成百条代码片段是**逐字从源码抄来的**，排版一变，文档与代码就对不上了。
2. 曾经试过接线：留下 `.prettierrc.json` + 根 devDependency，结果 `pnpm exec prettier --check .` 报了 **257 个文件**不一致（其中还包含 `dist/`、`.next/` 这些本就该 ignore 的产物）。一个「装了就红」的门禁比没装更糟——它训练人跳过检查，而不训练人遵守检查。所以配置和依赖都撤掉了，本节把它讲清楚该怎么做。

真实项目里我会装，并且顺序固定：先 `prettier --write .` 单独一个 commit（不看 diff 内容，只看排版），再装 `eslint-config-prettier` 加进 flat config 的**最后一项**（它靠覆盖生效，位置错了就没用），最后把 `prettier --check .` 与 `pnpm -r typecheck` 一起放进 CI。`singleQuote: false` 是我会保留的默认——JSON / YAML / HTTP body 里双引号才是原生的，不必在两种引号之间做美学判断。

> 一句话记法：**ESLint 管「这段代码会不会出事」，Prettier 管「这段代码长什么样」**。PHP 生态把两件事塞进一个工具，所以第一次进 JS 团队的人会困惑「为什么 lint 和 format 是两个命令」——这里没有坑，只有分工。

## 11. 脚本约定：四个动词

每个包都实现同一套（[tools/eslint-config](../code/tools/eslint-config/package.json) 除外，它没有代码要检查）：

| 命令 | 各包脚本 | 做什么 | composer 对照 |
|---|---|---|---|
| `pnpm -r typecheck` | `pnpm --filter @shop/shared build && tsc --noEmit` | **只查类型，不产出** | `composer phpstan` |
| `pnpm -r lint` | `eslint .` | 代码质量 | `php-cs-fixer --dry-run` |
| `pnpm -r test` | `vitest run`（shop-api 拆 `test` / `test:e2e`） | 单测 + 集成 | `composer test` / `phpunit` |
| `pnpm -r build` | `tsc -p tsconfig.build.json` / `vite build` / `next build` | 产出产物 | `composer dump-autoload -o` |

`pnpm -r <script>` 会按 workspace 拓扑序递归执行，**没有该脚本的包自动跳过**（所以 `tools/*` 不会报错）。根 [package.json](../code/package.json) 里**故意没有 scripts** —— 所有动词都下放到包，保证「单独构建一个包」和「全仓构建」用同一条命令。注意 `typecheck` 与 `build` 是两个动词，不要合并：前者只查类型（`tsc --noEmit`），后者才产生产物；`web-react` 的 `build` 把两件事串起来（`tsc --noEmit && vite build`），是因为 CI 上「一次 build 就够」，而本地反复跑时只想要快的那一个。

实测全绿（`pnpm -r test`）：

| 包 | 结果 |
|---|---|
| `@ts/lang-basics` | 80 个用例 / 12 个测试文件 |
| `@shop/shared` | 19 个用例 |
| `@shop/api` | 17 单测 + 17 e2e |
| `@shop/web-react` | 4 |
| `@shop/web-vue` | 3 |
| `@shop/web-next` | 4 |

## 12. 本章自测

1. `"~2.5.0"` 在 composer 和 npm 里分别是什么范围？
2. 为什么 `shop-api` 的 `typecheck` 脚本要先跑 `pnpm --filter @shop/shared build`？
3. `vite build` 成功能说明类型没问题吗？为什么？
4. 本仓库哪两个地方在用 TypeScript 6.0.3，各自的原因是什么？
5. `lang-basics` 里为什么可以 `from "../src/async-event-loop.ts"`，而 `shop-api` 里必须 `from "./domain-errors.js"`？

<details>
<summary>参考答案</summary>

1. composer 是 `>=2.5 <3.0`，npm 是 `>=2.5.0 <2.6.0`。`~` 的语义两边相反，是本仓最容易踩的迁移坑。
2. `pnpm -r <script>` 不会先构建依赖包；`@shop/shared` 的 `exports` 指向 `dist/`，不先编译就没有 `.d.ts` 可解析。
3. 不能。Vite（以及 rolldown）、Turbopack、SWC、esbuild 都只做转译和打包，**不做类型检查**；类型必须靠 `tsc --noEmit`（Vue 用 `vue-tsc`）。
4. `tools/eslint-config`（typescript-eslint 8.72.0 在 TS 7 下加载即抛 `does not support TS 7.0`）和 `web-vue`（vue-tsc 3.3.13 需要 `typescript/lib/tsc`）。两处靠 pnpm 隔离布局把 TS 6 只给需要的工具，`tsc` 仍走 TS 7。
5. `lang-basics` 是 `noEmit` + `allowImportingTsExtensions`，代码永远不产出 JS，所以 `.ts` 后缀合法；会产物的包必须写 `.js` specifier，因为编译后运行时解析的是 `dist/*.js`，写 `.ts` 会撞 TS2835/运行时找不到模块。
</details>
