## 1. 浏览器如何执行 JS：与 php-fpm 的一次请求对照

| | PHP（php-fpm + Blade） | 浏览器（本项目三个前端） |
|---|---|---|
| 谁执行代码 | 服务端 worker，每次请求从头执行 | **用户的设备**，下载后执行，进程（标签页）常驻 |
| 输出物 | HTML 字符串 | 一个空 `<div id="root">` + 一堆 JS/CSS |
| 状态寿命 | 请求结束全部清零（share-nothing） | 变量活到标签页关闭；DOM 是**全局可变状态** |
| 并发模型 | 多进程/多 worker，一个请求一个栈 | 单线程 + 事件循环（第 03 章），回调/微任务交错 |
| 「数据库在哪」 | 服务端直连 | 只能通过 HTTP 打到你的 API；**它连不上你的库** |
| 崩溃表现 | 500 + 日志 | 白屏 + Console 一条红字；用户刷新即「重试」 |
| 部署生效 | 切软链/reload，下一请求就是新代码 | 用户必须重新拿到 HTML（缓存了旧 JS 就没换） |

一次真实流程（React 版，端口来自 [vite.config.ts](../code/web-react/vite.config.ts)）：

1. 浏览器请求 `http://localhost:3000/` → dev server 返回 [index.html](../code/web-react/index.html)，里面只有一行关键代码：`<script type="module" src="/src/main.tsx"></script>`。
2. 浏览器解析到 `type="module"`，**沿 import 图递归下载**（dev 下是几百个小请求，每个模块一个），期间执行 [main.tsx](../code/web-react/src/main.tsx)：`createRoot(container).render(<StrictMode><QueryClientProvider client={queryClient}><App /></QueryClientProvider></StrictMode>)`。
3. 组件执行 → `useQuery` 登记一个待办 → 发 `fetch("/api/products")` → 命中 [vite.config.ts](../code/web-react/vite.config.ts) 的 proxy → 转发到 8080 的 Nest → 走 Guard/Pipe/Controller（[main.ts](../code/shop-api/src/main.ts) 里那套生命周期）。
4. JSON 回来 → [api.ts](../code/web-react/src/api.ts) 用 Zod 重新建立类型 → Query 缓存更新 → **组件函数被再次执行** → DOM 差异被打补丁。

第 4 步是最反直觉的一处：你写的「页面」不是一个模板，而是一个**会被反复调用的函数**，每次状态变化都重跑一遍。「渲染」= 再调一次。

## 2. 构建产物到底是什么：对照 Blade 渲染与 `@vite`

生产构建后（`pnpm --filter @shop/web-react build`，产物在 gitignore 的 `dist/` 里，见 [.gitignore](../.gitignore)），HTML 长这样：

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>shop · React + TypeScript</title>
    <script type="module" crossorigin src="/assets/index-CNYpVgyR.js"></script>
    <link rel="stylesheet" crossorigin href="/assets/index-DjpxX_1c.css">
  </head>
  <body>
    <div id="root"></div>
  </body>
</html>
```

三件事和 Blade 世界不同：

1. **HTML 里没有业务内容**。Blade 出来的 HTML 可以直接看源码读懂页面；SPA 的 HTML 只声明「谁负责渲染」。SEO/首屏可读性这件事要靠 SSR 解决（§3）。
2. **文件名里的 `CNYpVgyR` 是内容哈希**。内容变了才变名，所以这些文件可以放心设 `Cache-Control: immutable`——对位 Laravel Vite 的 `@vite(['resources/css/app.css'])` 生成的 `<script src="/build/assets/app-xxxx.js">`，机制一模一样，只是没人手写 manifest。
3. **CSS 是从组件里抽出来的**。[App.vue](../code/web-vue/src/App.vue) 的 `<style>` 块内容与 React 版 [styles.css](../code/web-react/src/styles.css) 完全相同，于是两个项目构建出的样式文件哈希相同（都叫 `index-DjpxX_1c.css`）——哈希由内容决定，不由来源决定，这个细节在排查「为什么 CDN 上还是旧样式」时很关键。

| Blade / Laravel | 本项目 | 说明 |
|---|---|---|
| `resources/views/*.blade.php` | `src/App.tsx`、`src/components/*.vue` | 模板 → 组件（带逻辑、带类型） |
| `@extends('layout')` + `@yield('content')` | [layout.tsx](../code/web-next/src/app/layout.tsx) 的 `children: ReactNode` | 只有 Next 有真正的「布局」；SPA 靠代码结构 |
| `@include('partials.panel')` | `<OrderPanel :product="..." />` | partial → 子组件，参数从共享包类型来 |
| `@vite([...])` + `mix-manifest.json` | `<script type="module" src="/assets/index-*.js">` | 同样内容哈希，dev 下 Vite 注入 HMR client |
| `public/index.php` 是唯一入口 | dev：`vite`；prod：静态目录 + nginx `try_files` | SPA 需要「所有路径回 index.html」这条路由规则 |
| `npm run dev`（Vite/Laravel 官方插件） | `pnpm --filter @shop/web-react dev` | 手感相同：一个常驻 dev server |

## 3. SPA / MPA / SSR / RSC：四种形态与取舍

| 形态 | 谁生成 HTML | 首屏 | SEO | 交互流畅度 | 后端要求 | 部署 | 本仓库 |
|---|---|---|---|---|---|---|---|
| MPA（Blade/Laravel 默认） | 服务端 | 最快（HTML 即内容） | 最好 | 每次跳转整页刷新 | 只要一个能渲染 HTML 的服务 | 常规 PHP 部署 | — |
| SPA | 浏览器 | 慢（先下 JS） | 需额外处理 | 最好（不重载） | 需要 REST/GraphQL API | 静态托管 + 回退路由 | [web-react](../code/web-react/src/main.tsx)、[web-vue](../code/web-vue/src/main.ts) |
| SSR | 服务端（每个请求） | 快 | 好 | 好（要 hydrate） | 需要一个 Node 服务 | `next start` / 容器 | [page.tsx](../code/web-next/src/app/page.tsx)（`export const dynamic = "force-dynamic"`） |
| RSC（React Server Components） | 服务端出「组件树」，只有客户端岛屿下 JS | 快 | 好 | 好 | Node 服务 + 序列化边界 | 同上 | [OrderForm.tsx](../code/web-next/src/components/OrderForm.tsx) 标 `"use client"`，其余保持服务端 |

Inertia 值得单独一行：它是「Blade 只做外壳、页面组件是 SPA、数据由 Controller 以 props 注入」的混合体，最接近你现有习惯。[OrderForm.tsx](../code/web-next/src/components/OrderForm.tsx) 的注释就在对比这条路线——Inertia 整页都是客户端组件，RSC 的交互边界可以只有一小块。

给后端人的决策简化版：

| 需求 | 选择 |
|---|---|
| SEO 重要 + 团队只有 PHP 后端 | Blade 或 Inertia，别上 SPA |
| 内部后台、交互密集、登录后才能看 | SPA（本仓库 React/Vue 版） |
| 公开页 + 需要 React 生态 + 想要服务端直连数据 | Next（SSR/RSC） |
| 已经有一个 REST API，只想多一个前端 | SPA + TanStack Query，API 不用改 |

## 4. 组件 = 函数 + props；状态 = 变量 + 订阅

| 概念 | React（[App.tsx](../code/web-react/src/App.tsx)） | Vue（[OrderPanel.vue](../code/web-vue/src/components/OrderPanel.vue)） | PHP 里最像什么 |
|---|---|---|---|
| 组件本体 | `export function App() { return <main/> }` | `<script setup>` + `<template>` | 一个返回 HTML 的函数（`render(array $data): string`） |
| 入参 | props：参数对象带上类型注解 | `defineProps<{ product: ProductResponse \| null; ... }>()` | 函数签名 / 关联数组 |
| 出参 | 返回值即视图 | 模板 | 拼接好的 HTML |
| 向外通信 | 回调 prop（`onClick={...}`） | `defineEmits<{ submit: [] }>()` | 事件/dispatcher |
| 局部状态 | `useState` | `ref` | **没有对应物**：PHP 函数没有跨调用的局部变量 |
| 派生值 | 直接算（`products.data?.length`） | `computed(...)`（[catalog.ts](../code/web-vue/src/stores/catalog.ts)） | accessor / 计算属性 |
| 共享状态 | Query 缓存 + Provider | Pinia store | session/配置对象（但作用域在浏览器） |

两个世界的关键差别在「订阅」：`setSearch("键盘")` 不改变任何东西，它只是**登记一次重新渲染**；`catalog.search = ...` 在 Vue 里则是写 `ref` 的内部值并触发依赖者。所以：

```ts
// code/web-react/src/App.tsx：受控输入，value 永远等于 state
const [search, setSearch] = useState("");
// ...
<input value={search} placeholder="例如：键盘" onChange={(event) => setSearch(event.target.value)} />
```

```vue
<!-- code/web-vue/src/App.vue：单向绑定 + 手写事件，Vue 不做自动受控 -->
<input placeholder="例如：键盘" :value="catalog.search" @input="onSearch" />
```

React 的「state 不可变 + 提交后重跑函数」和 Vue 的「ref 可变 + 依赖追踪」是同一问题的两种解法；对后端人的建议：**接受「代码会被反复执行」这一事实**，剩下的都是细节。

## 5. 服务端状态 vs 客户端状态：TanStack Query 为什么存在

| | 客户端状态 | 服务端状态 |
|---|---|---|
| 谁拥有真相 | 你的代码 | 数据库/别的进程 |
| 典型内容 | 输入框文本、选中行、弹窗开关 | 商品列表、库存、订单 |
| 会过期吗 | 不会（没人能在你之外改它） | **会**（另一个买家把库存拍光了） |
| 需要缓存/重试/去重/失效吗 | 不需要 | 全部需要 |
| 本仓库放哪 | `useState`（React）、Pinia `ref`（Vue） | `useQuery` + [queryClient.ts](../code/web-react/src/queryClient.ts)（React）、手写 `load()`（Vue） |

一句话定义：**`useQuery` 就是一次带缓存的 GET。**

```ts
// code/web-react/src/App.tsx
const products = useQuery({
  queryKey: ["products", search.trim()],
  queryFn: () => fetchProducts(search.trim() || undefined),
});

const order = useMutation({
  mutationFn: () => placeOrder({ customerName: "ben", items: [{ productId: Number(selected?.id), quantity }] }),
  onSuccess: async () => {
    // 下单改了库存 → 让商品列表缓存失效，等价于「提交后重查」
    await queryClient.invalidateQueries({ queryKey: ["products"] });
  },
});
```

| TanStack Query 概念 | Laravel 手感 | 本仓库的取值 |
|---|---|---|
| `queryKey: ["products", q]` | 缓存 key：`Cache::remember("products:$q", ...)` | key 里带上搜索词，**换 key 就是换缓存** |
| `staleTime: 5_000` | TTL 的反面：5 秒内认为新鲜，不发请求 | [queryClient.ts](../code/web-react/src/queryClient.ts) |
| `retry: 1` | 无对应（HTTP 客户端重试） | 同文件；4xx 重试没意义，所以压到 1 |
| `refetchOnWindowFocus: false` | 无对应（标签页聚焦就重拉） | 同文件，演示项目关掉更安静 |
| `invalidateQueries` | `Cache::forget("products:*")` 后自然重查 | App.tsx 的 `onSuccess` |
| `isPending / isError / data` | `$x ?? null` 三态散落在 Blade | 强制分开写，见下一段 |

为什么它值得引入：**服务端状态的三态（加载中/失败/有数据）不是可选分支，是必然存在的事实。** 不管理它的话，代码就长成 Blade 里 `@if(isset($items))` 那一堆防御性判断；`useQuery` 把它变成显式渲染分支：

```tsx
{products.isPending ? <p className="state">加载中…</p> : null}
{products.isError ? <p className="state error">加载失败：…</p> : null}
{products.data ? <table>{products.data.map((product) => <tr key={product.sku}>…)}</table> : null}
```

Vue 版没装 TanStack Query，而是把同一件事手写进 [catalog.ts](../code/web-vue/src/stores/catalog.ts)：`loading`、`error`、`products` 三个 `ref` + `try/finally`。这不是劣化选择——它正好说明 **store 是「客户端状态 + 手写的服务端状态编排」**，而 Query 库只是把后者自动化了。哪种更好，取决于你要不要重试/去重/失效这些策略。

## 6. 构建工具分工：谁做什么，谁不做类型检查

| 工具 | 职责 | 不负责 | 本仓库 |
|---|---|---|---|
| `tsc`（TypeScript 7.0.2） | 类型检查；可选地 emit JS/d.ts | **打包、tree shaking、压缩**（且慢） | `typecheck` 脚本一律 `tsc --noEmit`；shared/api 用 `tsc -p tsconfig.build.json` 真正产出 |
| esbuild | 单文件转译（剥类型）+ minify，Go 原生 | 类型检查、跨包 bundle 细节 | 作为 Vite 的底层能力存在 |
| **rolldown** | Vite 8 的打包器（Rust，替代 Rollup 的角色） | 类型检查 | `vite` 8.3.5 出现在三个前端的 devDependencies |
| Vite 8 | dev server（按需编译 + HMR）+ 生产构建 + `import.meta.env` 注入 + proxy | 类型检查 | [web-react/vite.config.ts](../code/web-react/vite.config.ts)、[web-vue/vite.config.ts](../code/web-vue/vite.config.ts) |
| `@vitejs/plugin-react` / `@vitejs/plugin-vue` | JSX 自动运行时 / SFC 拆成三块 | — | 两个配置里的 `plugins: [react()]` / `[vue()]` |
| `vue-tsc` | **连模板表达式一起做类型检查** | 打包 | [web-vue/package.json](../code/web-vue/package.json) 的 `typecheck` 用它而不是 `tsc` |
| Turbopack | Next 的打包器（Rust） | — | [web-next/package.json](../code/web-next/package.json)：`next dev -p 3100` / `next build` |
| Node 24 原生类型剥离 | 直接跑 `.ts` 脚本 | 检查、bundle | [lang-basics/scripts/hello.ts](../code/lang-basics/scripts/hello.ts)，脚本就是 `node scripts/hello.ts` |

最常见的坑，用一句话说清：**`vite build` 成功 ≠ 类型没问题**，因为它只做剥离。所以本仓库每个前端构建脚本都是三段式（[web-react/package.json](../code/web-react/package.json)）：

```jsonc
"build": "pnpm --filter @shop/shared build && tsc --noEmit && vite build",
"typecheck": "pnpm --filter @shop/shared build && tsc --noEmit",
```

先建契约包（`@shop/shared` 的 `exports` 指向 `dist/`），再查类型，最后打包。把这三步拆开跑，比一次「神秘失败」的 `npm run build` 好定位得多。

## 7. Blade / Inertia ↔ React / Vue 概念映射

| Blade / Laravel | React | Vue 3 | 备注 |
|---|---|---|---|
| `{{ $product->name }}` | `{product.name}` | `{{ product.name }}` | JSX 里必须**表达式**，不能是语句 |
| `@if($x) … @endif` | `{x ? <…/> : null}` | `<div v-if="x">` | React 没有指令，全靠表达式 |
| `@foreach($items as $i)` | `{items.map((i) => <tr key={i.sku}/>)}` | `<tr v-for="i in items" :key="i.sku">` | 只有 map 这一条路，且**必须给 key** |
| `@include('partials.panel', ['p' => $p])` | `<OrderPanel product={p} />` | `<OrderPanel :product="p" />` | partial → 组件，props 有类型 |
| `@slot` / `@section('sidebar')` | `children: ReactNode` | `<slot />` | 见 [layout.tsx](../code/web-next/src/app/layout.tsx) |
| `@extends/@yield` | 布局组件嵌套 | 布局组件嵌套 | 只有 Next 的文件路由把它做成约定 |
| `v-model` 双向绑定 | `value` + `onChange` | `v-model` | React 官方拒绝双向绑定 |
| `old('name')` / `$errors->first('sku')` | `problem.fieldErrors["sku"]`（[App.tsx](../code/web-react/src/App.tsx)） | `catalog.fieldErrors`（[OrderPanel.vue](../code/web-vue/src/components/OrderPanel.vue) 的上游） | 形状直接来自后端 problem+json 的 `errors` |
| `@csrf` + `route('orders.store')` | `fetch` + Basic 头（[api.ts](../code/web-react/src/api.ts)） | 同左 | 本项目前后端分离，没有 session/CSRF |
| 生命周期：`booted()`、middleware | `onMounted`、`useEffect` | `onMounted`、`watch` | 对照 [App.vue](../code/web-vue/src/App.vue) 的 `onMounted(() => void catalog.load())` |
| `@can('admin')` | 组件里条件渲染 + 服务端 Guard 再判 | `v-if` | 客户端的「看起来没权限」不是安全边界 |
| `php artisan serve` 的路由 | Vite `server.proxy` / Next `app/**` 文件路由 | 同 React | 见 §9 |

`<script setup lang="ts">` 值得单独解释一句（[App.vue](../code/web-vue/src/App.vue) 第 3–6 行注释也写了）：顶层声明的变量**自动**成为模板作用域，`defineProps<T>()` 是编译器宏——所以 Vue 侧类型检查必须用 `vue-tsc`，`tsc` 看不见 `.vue` 模板里的表达式。

## 8. `import.meta.env` 与 `VITE_` 前缀

```ts
// code/web-react/src/api.ts
const USERNAME = import.meta.env.VITE_SHOP_USERNAME ?? "customer";
const PASSWORD = import.meta.env.VITE_SHOP_PASSWORD ?? "customer123";
const basicAuth = (): string => `Basic ${btoa(`${USERNAME}:${PASSWORD}`)}`;
```

| 场景 | 写法 | 谁能看到 | 本仓库 |
|---|---|---|---|
| 前端运行时常量 | `import.meta.env.VITE_XXX` | **所有人**（构建期内联进 JS 产物） | [web-react/src/api.ts](../code/web-react/src/api.ts)、[web-vue/src/api.ts](../code/web-vue/src/api.ts) |
| 服务端配置 | `process.env.XXX` | 只有进程 | [web-next/src/lib/api.ts](../code/web-next/src/lib/api.ts)（`process.env.SHOP_API_URL`）、[shop-api/src/config/env.ts](../code/shop-api/src/config/env.ts) |
| Vite 自身行为 | `process.env.SHOP_API_URL`（配置文件里，Node 侧） | 只有构建者 | [vite.config.ts](../code/web-react/vite.config.ts) 的 proxy target |
| 构建期开关 | `import.meta.env.DEV` / `PROD` / `MODE` | 所有人（会被替换成字面量，利于死代码消除） | 未使用 |
| Laravel 对照 | `.env` → `config('app.x')` → Blade `{{ }}` 注入 | 只有渲染时服务端 | — |

三条必须记住的规则：

1. **没有 `VITE_` 前缀的变量不会进浏览器**。这是白名单，不是疏忽——它让「不小心泄露密钥」变成需要主动犯错。
2. `import.meta.env` 有类型，是因为 [web-react/tsconfig.json](../code/web-react/tsconfig.json) 里写了 `"types": ["vite/client"]`；换成别的宿主（比如 Next）就没有这个对象。
3. **前端里任何凭据都是公开信息。** 本仓库用 `VITE_SHOP_USERNAME/PASSWORD` 只是为了让演示站能跑 Basic 认证（代码里没有 `.env`，靠 `?? "customer"` 兜底）——这在真实项目里是不允许的做法：浏览器持有密码 = 任何人可查看源码拿到它。真实方案是登录换取 session/JWT，凭据永远留在服务端。

对照 `config/env.ts`：服务端用 Zod 在启动时校验环境变量（不合法就不启动），前端没有任何等价的「校验时机」——`import.meta.env` 的值在构建那一刻就被烤进产物，写错键名只会静默变成 `undefined`，然后走 `??` 的默认分支。这类 bug 的隐蔽程度和 PHP 里 `env('APP_KEYX')` 拼错键名一样，但 TS 侧连一条 warning 都没有。

## 9. 同源与 CORS：为什么本仓库用 dev proxy

| 前端 | dev 端口 | API 地址写法 | 是否跨域 | 机制 |
|---|---|---|---|---|
| [web-react](../code/web-react/vite.config.ts) | 3000 | `fetch("/api/products")`（相对路径） | **否** | Vite proxy：`/api` → `http://localhost:8080` |
| [web-vue](../code/web-vue/vite.config.ts) | 3010 | 同上 | **否** | 同一份 proxy 配置 |
| [web-next](../code/web-next/src/lib/api.ts) | 3100 | `${process.env.SHOP_API_URL}/api/products`（绝对） | **不适用** | 请求由 **Node 服务端**发出，浏览器不参与 |

`shop-api` 从头到尾**没有开启 CORS**（[main.ts](../code/shop-api/src/main.ts) 里没有 `app.enableCors()`，Java 版同样不开）。原因：这不是疏漏，而是演示项目保持两个后端可横向对比的前提。于是浏览器侧只有两条路：

```ts
// code/web-react/vite.config.ts
server: {
  port: 3000,
  proxy: {
    "/api": { target: process.env.SHOP_API_URL ?? "http://localhost:8080", changeOrigin: true },
  },
},
```

| 方案 | 用在哪 | 代价 |
|---|---|---|
| dev proxy（本项目） | 本地开发 | 只在 `vite dev` 有效；`vite preview` 与生产需要 nginx/网关同样规则 |
| 生产同源部署 | 大多数 SPA + API | 运维加一条 `location /api { proxy_pass ... }`，不用动代码 |
| 后端 `enableCors({ origin: [...] })` | 前后端真的分域名 | 要处理 preflight（`OPTIONS`）、`credentials`、`Authorization` 白名单；Basic 认证 + preflight 是常见的坑组合 |
| BFF（Next 服务端代理） | SSR 项目 | 服务端持有凭据，浏览器只见同源——本项目 `web-next` 就是这个形状 |

注意「同源」判定看的是 `协议 + host + port` 三元组：`localhost:3000` 调 `localhost:8080` 已经跨域，端口不同就算。PHP 侧几乎没有这个概念，因为 Blade 与 API 同源。

## 10. DevTools：Network / Sources / React Devtools

| 你要看的东西 | 面板 | 后端世界的对照 |
|---|---|---|
| 请求 URL、状态码、`Accept`/`Authorization` 头、响应 JSON | **Network**（勾 Fetch/XHR；Next 里还要看 `document` 请求的 RSC payload） | `storage/logs` + curl `-v`；Laravel Debugbar |
| 为什么 CORS 失败 | Network 里那条**红色的 `OPTIONS`** 或 Console 的 CORS 报错 | 你在 PHP 里从没见过这条请求 |
| 断点、单步、调用栈、hover 变量 | **Sources**（配合 sourcemap 能看到 `.tsx` 原文） | Xdebug + step debugger |
| 某个请求触发前发生了什么 | 右键 → **Copy fetch as cURL**，再打到 API | 直接读日志 |
| 组件树、每个组件的 props/state、re-render 高亮 | **React Devtools**（浏览器扩展）；Vue 用 Vue Devtools | 没有任何 PHP 工具能给你这个 |
| 全局状态快照 | Vue Devtools 的 Pinia 面板能直接看 `catalog` store | ≈ 往 session 里看了一眼 |
| DOM 结构与 CSS 层叠 | Elements | 服务端 HTML 只能 `view-source` |

Sources 断点前先看右下角有没有 sourcemap：本仓库 `build.sourcemap = true`（[vite.config.ts](../code/web-react/vite.config.ts)），dev 下天然有。生产构建关掉 sourcemap 时，断点会落在压缩后的 `index-CNYpVgyR.js` 里，调试体验差别巨大。

## 11. 前端调试为什么和在 php-fpm + Xdebug 里不一样

| 你的既有直觉 | 浏览器里的现实 | 应对 |
|---|---|---|
| 打个断点，看 `$request` 一路走到 Service | 断点停在**某个渲染函数**里，而它已经执行过 N 次 | 条件断点（右键 line → Add conditional breakpoint，写 `search === "键盘"`），或看 React Devtools 的 render 次数 |
| 调用栈一直往回追就到入口 | 异步栈被事件循环切断：`fetch` 回来时的栈里**没有当初发请求的那一帧** | 开「Async stack traces」/console 里保留 request-id，靠 `X-Request-Id` 串两端 |
| watch 数组看状态变化 | state 变量每次渲染都是**新的闭包副本**（第 11 章） | 在渲染函数体里打点看当次快照；不要指望「变量表」 |
| `error_log()` 只在服务端能看到 | `console.log` 用户也能看；DevTools 的 console 会保留同一表达式在多次渲染里的输出 | 前端日志当「临时调试」，别把业务信息烤进去 |
| 一次请求 = 一个隔离世界 | 一次会话 = 一个持续演进的世界，路由切换、缓存、订阅都还在 | 复现前先问「刷新过吗」；清 Application → Clear site data |
| 改代码要重新部署 | dev 有 HMR，但**模块级状态可能残留**（改 store 定义后行为怪） | 怀疑时硬刷新，而不是继续读代码 |
| 服务器 500 一定有日志 | 白屏常是「一个未捕获的 Promise rejection」，服务端日志干净 | Console + Network 优先；必要时加全局 `error` 监听上报 |
| 慢 = SQL/外部调用 | 慢可能是「每次渲染都重新算」或 800KB JS 的解析执行成本 | Performance 面板录制；React Devtools 打开 highlight updates |

顺带一条后端人常忽略的：**前端 console 里的报错和服务端日志之间，只有 request id 能把它们连上**。[request-id.middleware.ts](../code/shop-api/src/common/request-id.middleware.ts) 写出的 `X-Request-Id` 会被 e2e 断言（[shop-api.e2e.spec.ts](../code/shop-api/test/shop-api.e2e.spec.ts) 第 46 行），浏览器 Network 面板里也能直接复制它去 grep 服务端日志——这就是跨端排查的主键，值得在真项目里坚持。

## 12. 换脑子：三条要改掉的直觉

1. **「渲染完就销毁」→「变量一直活着」。** 这带来 PHP 里根本不存在的问题：内存泄漏（订阅没解绑）、状态陈旧（闭包捕获旧值）、跨路由脏数据（缓存要失效）。第 11 章用一个真实例子讲闭包。
2. **「模板是数据视图」→「组件是进程」。** 它有输入（props）、有私有状态、有生命周期、会重复执行。写组件时该问的问题和写类一样：状态放哪、谁负责清理、输入变了怎么办。
3. **「校验放在 FormRequest 里就够了」→「客户端校验只是 UX」。** [api.ts](../code/web-react/src/api.ts) 的 `placeOrder()` 在发请求前先 `PlaceOrderRequestSchema.parse(input)`，这**减少一次无用的往返**，但任何人都能绕过它直接 curl；服务端 [ZodValidationPipe](../code/shop-api/src/common/zod.pipe.ts) 仍然是唯一防线。共享包的价值就在「同一份规则，两边各跑一次」，这也是第 14 章的主题。

最后一条关于部署的心智修正：Blade 项目里「发布 = 换文件」；SPA 里 **HTML 不能被长期缓存，hash 资产必须被长期缓存**（`index.html` 设 `no-cache`，`/assets/*` 设 `immutable`）。配错这一条的后果是用户永远拿不到新版本，或者每次访问都重下 JS——对位 PHP 的 OPcache 刷新问题，只是更难在日志里发现。
