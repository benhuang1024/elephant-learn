# 道德与授权范围

> 方向：攻防 · 相关标准：ISO/IEC 29147（漏洞披露）、ISO/IEC 30111（漏洞处理流程）、RFC 9116（security.txt） · 最后更新：2026-10-22

## 1. 核心要点

- **授权是测试与攻击之间唯一的分界线**。技术手段完全相同，有没有书面授权决定了它是安全工作还是违法行为。
- 授权必须是**书面的、明确的**：谁授权、测试哪些目标、允许哪些方法、什么时间段、出问题联系谁。
- **严格遵守范围**：范围外的系统（包括第三方服务、云厂商的基础设施、同一网段的其他主机）即使“顺手”也不能碰。
- **最小影响**：证明问题存在即可，不读取或下载超过证明所需的数据，不做破坏性操作，不保留拿到的数据。
- **负责任地披露**：发现漏洞后通过正规渠道报告，给对方合理的修复时间，不公开细节直到修复完成或按约定时间。

## 2. 为什么重要

- **法律**：大多数国家和地区都有针对未授权访问计算机系统的法律，例如中国《刑法》第 285、286 条和《网络安全法》、美国 CFAA、英国 Computer Misuse Act。“出于好意”“只是看看”通常不能作为免责理由。
- **信任**：安全从业者依赖客户和社区的信任。越界一次，可能失去职业生涯。
- **安全**：即使是授权测试，也可能导致服务中断或数据损坏，所以需要事先约定规则和应急联系方式。

## 3. 常见错误 vs 正确做法

| 常见错误 | 正确做法 |
| --- | --- |
| 口头答应“随便测” | 签署书面授权书或工作说明书，明确范围和规则 |
| 范围写“公司的所有系统” | 逐项列出域名、IP 段、应用、账号，并写明明确排除的部分 |
| 发现范围外的相关系统，顺手测了一下 | 停下来，记录下来，联系授权方确认是否扩大范围 |
| 为了证明漏洞，把数据库导了出来 | 只读取证明问题所需的最少数据（如表名或一条记录的字段名），并立即报告 |
| 在公司网络里“练手” | 在自己的环境或正规练习平台上练习 |
| 发现漏洞后直接发到社交媒体 | 通过对方的安全联系渠道报告，遵守协调披露流程 |
| 参加漏洞赏金时忽略项目规则 | 仔细阅读并遵守项目的范围、禁止事项和披露政策 |

**授权书/工作说明书应该包含的内容**

- 授权方（有权限做决定的人）和测试方
- 范围：具体的目标列表，以及明确排除的目标
- 允许和禁止的测试类型（例如：禁止拒绝服务、禁止社会工程、禁止物理测试）
- 时间窗口（日期和每天的时段）
- 测试账号和测试数据的提供方式
- 数据处理要求：拿到的数据如何保存和销毁
- 紧急联系人：测试导致故障时立即联系谁
- 发现严重问题时的报告方式（是否需要立即通知，而不是等到最终报告）

## 4. 如何识别（测试前的自检）

开始任何测试之前，问自己：

- 我有书面授权吗？授权人是否真的有权批准对这个系统的测试？
- 这个目标在授权范围内吗？它是否属于第三方（如 SaaS 服务、CDN、云平台）？
- 我将要做的操作在允许的测试类型里吗？可能影响生产服务吗？
- 如果出了问题，我知道该立即联系谁吗？
- 我在练习平台上的操作是否符合该平台的规则（例如有的平台禁止攻击其他用户或平台基础设施）？

## 5. 防御清单

作为测试方：

- [ ] 测试前拿到书面授权，并确认授权人的权限
- [ ] 范围逐项列出，范围外的内容一律不测
- [ ] 遵守约定的时间窗口和测试类型
- [ ] 只获取证明问题所需的最少数据，测试结束后按约定销毁
- [ ] 全程记录操作日志，便于对账和排查
- [ ] 发现严重问题立即通知，不等最终报告

作为被测方/企业：

- [ ] 发布漏洞披露政策（VDP），说明如何报告、承诺不追究善意报告者
- [ ] 在网站上提供 `/.well-known/security.txt`（RFC 9116），写明安全联系方式
- [ ] 建立内部的漏洞接收、分级、修复和反馈流程

**security.txt 示例**

```text
Contact: mailto:security@example.com
Expires: 2027-10-22T00:00:00.000Z
Preferred-Languages: zh, en
Policy: https://example.com/security/disclosure-policy
```

## 6. 自测题

**Q1.** 一个朋友说“你帮我测一下我们公司的网站吧”，你可以开始测试吗？

<details><summary>答案</summary>

不可以。朋友可能没有权限代表公司授权，口头同意也无法界定范围和规则。需要由公司内有权限的负责人出具书面授权，明确范围、方式、时间和联系人之后才能开始。

</details>

**Q2.** 授权测试 `app.example.com` 时，发现它调用了 `api.thirdparty.com`，可以一起测试吗？

<details><summary>答案</summary>

不可以。第三方服务不属于被测方所有，被测方也无权授权你测试它。应该把这个依赖关系记录在报告中。如果认为确有必要测试，需要由被测方去和第三方协调，取得第三方的授权。

</details>

**Q3.** 测试中发现一个 SQL 注入，为了证明影响，应该把用户表导出来吗？

<details><summary>答案</summary>

不应该。只需要用最小的证据证明问题存在，例如获取数据库版本或当前数据库名称，并说明理论上可能造成的影响。读取或导出真实用户数据既没必要，也可能违反授权约定和数据保护法规。发现这类严重问题时应该立即通知授权方。

</details>

**Q4.** 什么是协调漏洞披露（Coordinated Vulnerability Disclosure）？

<details><summary>答案</summary>

发现者私下向厂商报告漏洞，厂商确认并修复，双方约定一个时间点后再公开细节（业界常见是 90 天左右）。这样用户能在漏洞细节公开前获得补丁。如果厂商长期不回应，发现者可以通过 CERT 等第三方机构协调。

</details>

**Q5.** 企业为什么要发布漏洞披露政策和 security.txt？

<details><summary>答案</summary>

让发现问题的人知道该向谁报告、怎样报告，以及企业承诺不会追究善意的报告者。没有明确的渠道时，报告者可能找不到联系人、担心被追究而选择不报告，或者直接公开。这两样东西能让企业更早、更安全地得知自己的漏洞。

</details>
