# 05 运行模型与并发

> **配套代码（lang-basics）**
> 线程 / 进程 / asyncio：[concurrency.py](../code/lang-basics/src/basics/concurrency.py)
> 测试：`tests/test_concurrency.py`
> 常驻进程示例：[shop-api/main.py](../code/shop-api/src/shop/main.py)、[db.py](../code/shop-api/src/shop/db.py)

这是 PHP 架构师最需要“重装系统”的一章。PHP-FPM 的 share-nothing 模型帮你屏蔽了绝大多数并发问题；Python 应用是**常驻进程**，你必须自己决定并发模型、连接池、状态生命周期和优雅退出。

## 1. PHP-FPM vs 常驻 Python 进程

| 维度 | PHP-FPM | Python（uvicorn/gunicorn） |
|---|---|---|
| 进程模型 | 一请求一进程（或复用 worker 进程但每请求重建上下文） | 进程启动后长期运行，处理很多请求 |
| 内存状态 | 请求结束即释放 | 模块级变量、缓存、连接池跨请求存活 |
| 并发 | 进程/线程池，由 FPM 管理 | 线程池 / 事件循环 / 多进程，由你选 |
| 数据库连接 | 每请求新建，通常无池 | 进程内连接池，必须管理生命周期 |
| 内存泄漏 | 请求结束自动回收 | 长期累积，必须监控 |
| 全局可变状态 | 天然隔离 | **危险**，并发请求共享 |
| 优雅重启 | 平滑重启 worker | 需要处理信号、排空连接 |
| 阻塞影响 | 只阻塞当前请求 | 阻塞事件循环会拖垮同进程所有请求 |

### 常驻进程的三条纪律

1. **不要在模块级保存请求相关状态**。用 `contextvars`（请求 ID、租户）或显式参数。
2. **连接池按进程创建**，进程退出时 dispose；fork 后不要复用父进程连接。
3. **信号处理与优雅退出**：停止接收新请求、等待在途请求、关闭连接池。

FastAPI 的 `lifespan` 就是做第 2、3 条的（见 [main.py](../code/shop-api/src/shop/main.py)）。

## 2. GIL 是什么

CPython 的全局解释器锁保证同一时刻只有一个线程执行 Python 字节码：

- **I/O 阻塞时释放 GIL**：等待网络、磁盘、DB 时其他线程可以跑。
- **纯 Python CPU 计算不释放**：多线程做计算不会更快，甚至更慢。
- C 扩展（NumPy、数据库驱动）在长计算里可能主动释放 GIL，视实现而定。

Python 3.14 的现状：

- 默认构建**仍然有 GIL**。
- 提供 free-threaded 构建（`python3.14t`），可以真正并行线程，但：
  - 需要单独安装/选择解释器；
  - 第三方扩展（尤其 C 扩展）需要兼容；
  - 单线程性能通常略低；
  - 生态仍在迁移。
- 本仓库使用默认 GIL 构建（`sys._is_gil_enabled()` 为真）。

架构结论：**不要把 free-threaded 当作默认方案**。先用进程/异步解决问题，有明确收益再评估。

## 3. 三种并发模型

| 模型 | 适合 | 不适合 | 代价 |
|---|---|---|---|
| 线程 `threading` / `ThreadPoolExecutor` | 阻塞 I/O、旧同步库、文件 | CPU 密集、共享可变状态 | GIL、锁、竞态 |
| 进程 `multiprocessing` / `ProcessPoolExecutor` | CPU 密集、隔离性 | 大量小任务、共享大对象 | 序列化、启动、内存 |
| asyncio | 高并发网络 I/O、WebSocket、流式 | 阻塞调用、CPU 密集 | 全链路异步、调试复杂 |

### 线程：共享内存 + 锁

```python
counter = 0
lock = threading.Lock()

def work() -> None:
    global counter
    for _ in range(1000):
        with lock:
            counter += 1
```

`counter += 1` 不是原子操作（读-改-写），必须加锁或用队列/原子结构。Python 的 `queue.Queue` 常比手写锁更安全。

线程池：

```python
with ThreadPoolExecutor(max_workers=8) as pool:
    results = list(pool.map(blocking_io, ids))
```

### 进程：绕过 GIL

```python
def square(value: int) -> int:      # 必须是模块顶层，能被 pickle
    return value * value

with ProcessPoolExecutor() as pool:
    results = list(pool.map(square, values))
```

- macOS / Windows 默认 `spawn`，子进程重新 import 模块；入口必须放在 `if __name__ == "__main__":` 下。
- 参数与返回值要可 pickle；大对象传输成本高。
- 进程池适合“少量大任务”，不适合高频小任务。

### asyncio：单线程协作式

```python
async def fake_fetch(identifier: int) -> int:
    await asyncio.sleep(0.02)
    return identifier

async def fetch_all(ids: list[int]) -> list[int]:
    return list(await asyncio.gather(*(fake_fetch(i) for i in ids)))
```

- `await` 处让出控制权；**不 await 的阻塞调用会卡死整个事件循环**。
- 常见阻塞源：`requests`、`time.sleep`、同步 DB 驱动、同步文件 I/O、CPU 计算。
- 解决：换异步库（httpx、asyncpg、aiosqlite）、`asyncio.to_thread(...)`、或进程池。

结构化并发：

```python
async with asyncio.TaskGroup() as group:
    for identifier in ids:
        group.create_task(worker(identifier))
```

任一任务失败会取消同组其他任务，错误聚合为 `ExceptionGroup`。比裸 `create_task` + 手工取消更安全。

超时：

```python
async with asyncio.timeout(2.0):
    await call_remote()
```

不要用 `asyncio.wait_for` 包一层再忘记处理 `CancelledError`；`timeout` 更现代。

## 4. ASGI vs WSGI

| 维度 | WSGI | ASGI |
|---|---|---|
| 接口 | 同步可调用 | 异步 `async def app(scope, receive, send)` |
| 并发 | 线程/进程 | 事件循环 |
| 协议 | HTTP/1 | HTTP/1、HTTP/2、WebSocket、SSE |
| 典型框架 | Django（传统）、Flask | FastAPI、Starlette、Django（ASGI 模式） |
| 服务器 | gunicorn、uWSGI | uvicorn、hypercorn、daphne |

FastAPI 是 ASGI；Django 可以 WSGI 也可以 ASGI。选型不是“谁先进”，而是看 I/O 模型与依赖生态。

## 5. uvicorn 与 gunicorn

单进程开发：

```bash
uv run uvicorn shop.main:app --reload --port 8000
```

多进程（生产简化版）：

```bash
uv run uvicorn shop.main:app --host 0.0.0.0 --port 8000 --workers 4
```

gunicorn 管进程 + uvicorn worker（需要额外安装；本仓库未内置）：

```bash
uv add gunicorn uvicorn-worker
gunicorn shop.main:app \
  -k uvicorn_worker.UvicornWorker \
  -w 4 \
  --timeout 30 \
  --graceful-timeout 30 \
  --access-logfile -
```

> uvicorn 自带的 `uvicorn.workers` 已弃用，新项目用 `uvicorn-worker` 包。

worker 数怎么定：

- **异步应用**：通常 `CPU 核数` 到 `2×核数`；单个 worker 已能承载大量连接，不要盲目开几十个进程。
- **同步端点**（FastAPI 里 `def` 而不是 `async def`）：每个 worker 用线程池执行，线程数受 anyio 默认限制；CPU 密集就要靠进程。
- **内存**：每个进程独立加载应用与连接池；worker 越多，DB 连接越多。
- 以压测为准，不要照搬公式。

本仓库的 `shop-api` 端点使用同步 `def` + SQLAlchemy 同步 Session，因此：

- uvicorn 在线程池中执行端点，不会阻塞事件循环；
- 每个进程维护自己的连接池；
- worker 数 × pool size 必须小于数据库最大连接数。

## 6. FastAPI 的同步与异步端点

```python
@router.get("/api/products")
def list_products(...):        # 同步：FastAPI 放入线程池
    ...

@router.get("/api/health")
async def health():            # 异步：直接在事件循环执行
    ...
```

| 写法 | 执行位置 | 适合 |
|---|---|---|
| `def` | 线程池 | 同步 DB/文件/旧库 |
| `async def` | 事件循环 | 异步 I/O，且内部全部 await |
| `async def` 里调用阻塞函数 | 事件循环 | **事故** |

规则：**异步端点里只调用异步 API**。不得不调用同步库时用 `await asyncio.to_thread(func, ...)`，并评估线程池大小。

## 7. 数据库与连接池

同步 SQLAlchemy + psycopg：

```
uvicorn worker 进程
  └── Engine（进程级）
        └── QueuePool（默认 5 + 10 overflow）
              └── 物理连接
```

关键点：

- Engine 必须在**进程内**创建一次，不能每请求 `create_engine`（会耗尽连接）。
- 多 worker 时，`worker 数 × (pool_size + max_overflow)` ≤ PostgreSQL `max_connections`（还要给运维/迁移留余量）。
- 长事务会占住连接；异步应用尤其要缩短事务。
- SQLite 默认单写者；并发写会锁库，只适合开发/小规模。
- 连接泄漏的表现：请求变慢、`Too many connections`、池耗尽超时。

`shop-api` 的 [db.py](../code/shop-api/src/shop/db.py) 每个请求创建一个 Session，请求结束 close；Engine 在 `app.state` 上进程级复用。

## 8. 定时任务与队列

| PHP / Laravel | Python |
|---|---|
| Laravel Queue（Redis/DB） | Celery、RQ、Dramatiq、arq |
| `php artisan queue:work` | `celery -A app worker` |
| Horizon | Flower（监控） |
| Scheduler | Celery Beat、APScheduler、系统 cron |
| 同步任务 | 直接函数调用（别伪装成队列） |

选型建议：

- **简单延迟任务**：RQ（Redis）或 arq（asyncio）。
- **复杂路由/重试/定时**：Celery（生态最大，运维复杂）。
- **云原生**：SQS + Lambda/Cloud Run Jobs、Temporal。

队列的语义（至少一次、幂等、死信）与 PHP 世界一样，不会因为换语言而消失。

## 9. 常驻进程的五个坑

1. **模块级缓存无上限**：字典当缓存会无限增长；用 LRU/TTL 或外部缓存。
2. **请求状态泄漏**：不要用模块级变量保存当前用户/租户；用 `contextvars`。
3. **fork 后复用连接**：gunicorn preload 时，父进程创建的连接被 fork 共享会导致协议错乱；在 worker 内创建 Engine。
4. **阻塞事件循环**：同步 HTTP 客户端、`time.sleep`、CPU 计算。
5. **退出不优雅**：没有处理 SIGTERM，正在处理的事务被硬杀；配置 graceful timeout，关闭连接池。
