前十章解决“会不会写”，本章解决“怎么选、怎么落地、怎么带团队迁移”。面向已有 10 年 PHP/Laravel 架构经验的人：你的架构判断力大部分可迁移，需要重估的是运行时、类型边界、并发模型与生态成本。

## 1. 语言迁移不是架构迁移

Laravel 的核心资产：

- 分层（Controller / Service / Repository / Model）；
- 请求生命周期与中间件；
- 事务、队列、缓存、事件；
- 契约测试与部署流程；
- 团队对业务的建模。

这些都能原样落地到 Python。**不要重新发明架构**：

| Laravel 资产 | Python 对应 |
|---|---|
| Controller | FastAPI router / DRF ViewSet |
| FormRequest | Pydantic / Serializer |
| Service 层 | Service 类（显式 Session 注入） |
| Repository | Repository 类（可选；ORM 复杂时加） |
| Eloquent | SQLAlchemy / Django ORM |
| Middleware | ASGI middleware / 依赖 |
| Event/Listener | 领域事件 + 进程内总线 / 消息队列 |
| Job | Celery / RQ / arq |
| Scheduler | Celery Beat / cron |
| Feature flag | 第三方或自建配置表 |
| API Resource | Pydantic Out / Serializer |

差异在于：Python 的 DI 更轻、类型更靠静态检查、并发要自己选。把 PHP 的“框架帮你做”逐项映射成“库 + 约定 + CI”。

## 2. 模块化单体优先

大多数业务系统不需要微服务。推荐模块化单体：

```
src/shop/
├── product/          # 模块：模型、schema、repository、service、router
├── order/            # 模块：聚合、事务、跨模块调用
├── identity/         # 认证/用户/权限
├── billing/          # 支付/账单
├── shared/           # 领域基类、错误、分页、时钟
└── main.py           # 组装：路由、中间件、生命周期
```

规则：

1. **模块内高内聚**：数据、规则、接口在一起。
2. **模块间通过显式接口**：Service/事件，不直接跨模块改表。
3. **共享内核最小化**：只放真正通用的基类与工具。
4. **依赖方向**：`router → service → repository → model`；模型不依赖 Web。
5. **一个模块一个事务边界**；跨模块用事件/最终一致性。

何时拆服务：

- 独立伸缩需求（例如图像处理）；
- 独立发布节奏/团队边界；
- 不同的数据存储/合规要求；
- 明确的故障隔离收益；
- 有成熟的观测、部署、契约测试能力。

否则拆服务只会把复杂度从代码搬到网络。

## 3. 分层怎么落

以商品用例为例：

```
HTTP 请求
  → router.py       解析/校验（Pydantic）、鉴权、状态码
  → service.py      用例编排、事务、业务规则
  → repository.py   查询封装（可选）
  → models.py       映射、领域行为
  → PostgreSQL
```

| 层 | 应该做 | 不应该做 |
|---|---|---|
| Router | 参数、鉴权、序列化、HTTP 语义 | 业务规则、SQL |
| Service | 事务、用例、跨聚合编排 | HTTP 细节、直接拼 JSON |
| Repository | 查询、加载策略、分页 | 业务判断 |
| Model | 映射、局部领域行为 | 跨聚合编排、外部调用 |

小项目可以省掉 Repository（Service 直接用 Session）；一旦查询变复杂、需要复用/替换数据源，再引入。**不要为了“架构完整”预建空抽象**。

## 4. 类型边界

架构上把类型分成三层：

| 边界 | 工具 | 失败处理 |
|---|---|---|
| HTTP/消息/配置 | Pydantic / Serializer | 400/422，统一错误 |
| 领域内部 | Python 类型提示 + mypy | CI 拦截 |
| 数据库 | ORM 映射 + 迁移 | 启动/测试暴露 |

原则：

- **边界强校验，内部强类型，不做重复校验。**
- DTO 与 ORM 分离，API 不随表结构漂移。
- 金额/时间/ID 用值对象或明确类型，不用裸 `float`/`str` 满天飞。
- 枚举用 `StrEnum`，数据库/JSON 统一值。
- `Any` 是债务，出现就要有理由。

## 5. 异步选型

不要问“Python 异步快不快”，要问“我的瓶颈是什么”。

| 场景 | 建议 |
|---|---|
| CRUD + 同步 ORM，QPS 一般 | 同步端点 + 线程池，简单可靠 |
| 高并发外部 API 聚合 | asyncio + httpx |
| WebSocket/SSE/流式 | ASGI 异步 |
| CPU 密集 | 进程池/独立服务，不要塞事件循环 |
| 混合 | Web 同步 + 长任务队列 |

迁移到异步的隐藏成本：

- 全链路库要异步（DB、缓存、HTTP、文件）；
- 事务/连接池语义变化；
- 调试与性能分析工具不同；
- 团队需要理解事件循环与取消。

**判定标准**：同步实现能否在目标 QPS/延迟下达标？能，就不要异步。需要异步时，一次迁一层（先外部调用，再 DB），用压测验证。

## 6. 性能：先找瓶颈

| 症状 | 常见原因 | 工具 |
|---|---|---|
| P99 高、CPU 低 | 外部调用/DB 等待 | trace、慢查询日志 |
| CPU 打满 | 序列化/计算/正则 | py-spy、cProfile |
| 内存涨 | 缓存无界、泄漏、响应过大 | tracemalloc、RSS 监控 |
| 连接耗尽 | 池配置/长事务/泄漏 | 池指标、DB 会话 |
| 突发 5xx | 无超时/重试风暴 | 网关指标、日志 |

优先顺序：

1. 消除 N+1（通常收益最大）；
2. 加索引/改查询；
3. 分页/限制响应大小；
4. 缓存热点（明确失效策略）；
5. 异步化长任务；
6. 水平扩展；
7. 最后才考虑换语言/重写。

## 7. 生态对照

| 领域 | PHP/Laravel | Python |
|---|---|---|
| Web | Laravel/Symfony | FastAPI、Django、Flask |
| ORM | Eloquent/Doctrine | SQLAlchemy、Django ORM |
| 校验 | FormRequest/Validator | Pydantic、Marshmallow |
| 任务队列 | Laravel Queue/Horizon | Celery、RQ、arq |
| 缓存 | Laravel Cache | redis-py、cachetools |
| 搜索 | Scout/Elasticsearch | elasticsearch-py、Meilisearch |
| 支付 | Stripe SDK | stripe-python |
| 邮件 | Mailables | smtplib、django-mailer、事务邮件服务 |
| 图像 | Intervention | Pillow |
| 数据/ML | 较弱 | **NumPy/Pandas/PyTorch（强项）** |
| 管理后台 | Nova/Filament | Django Admin |
| 观测 | Telescope | OpenTelemetry、Sentry、structlog |

结论：**Web 常规能力 PHP 生态很成熟**；Python 的优势在数据、AI、脚本化、异步 API。不要为了“换语言”而换，明确收益再动。

## 8. 团队迁移策略

### 阶段一：旁路试点（1–2 个月）

- 选一个边界清晰、流量可控的服务（报表 API、内部工具、异步任务）。
- 用 FastAPI + SQLAlchemy 写，复用 PostgreSQL。
- 建立基线：ruff、mypy strict、pytest、CI、日志、健康检查。
- 与 PHP 服务通过 HTTP/消息集成。
- 输出团队规范：目录结构、错误格式、测试模板。

### 阶段二：能力补齐（2–4 个月）

- 统一认证（OIDC/JWT）、配置、密钥、部署流水线。
- 建立共享库（错误、分页、观测、测试工具）。
- 训练团队：类型、Session、并发、Django/FastAPI 选型。
- 建立 on-call 手册与性能基线。

### 阶段三：规模化（按业务）

- 新服务默认 Python；旧服务按收益逐步迁移。
- 明确“什么不迁”（深度绑定 Laravel 生态的模块）。
- 建立架构评审：数据边界、事务、异步、依赖。

### 组织建议

- **不要双栈无限期并行**：公共能力（认证、日志、部署）必须统一，否则成本翻倍。
- 设一个平台小组维护模板、CI、基础库。
- Code review 看边界：事务、N+1、异常映射、类型逃逸。
- 用 ADR（架构决策记录）记录选型理由，半年后回看。

## 9. Django 还是 FastAPI（再谈一次）

| 维度 | Django | FastAPI |
|---|---|---|
| 起步速度 | 快（Admin/Auth/ORM） | 中（要组装） |
| 约定 | 强 | 弱 |
| 类型 | 弱（可加 stubs） | 强（Pydantic） |
| 异步 | 支持，但生态混用 | 原生 |
| 后台 | 内建 | 自建/第三方 |
| 定制 | 受框架约束 | 自由 |
| 适合团队 | 全栈/业务交付 | 平台/API/数据 |

架构建议：

- 后台/内容/运营型系统：Django。
- API/BFF/高并发/数据服务：FastAPI。
- 同一组织可以并存；共享数据库/认证/消息契约，不要共享 ORM 模型。

## 10. 常见反模式

| 反模式 | 后果 | 修正 |
|---|---|---|
| 模块级全局缓存 | 内存泄漏/串数据 | 进程级有界缓存/Redis |
| 每请求建 Engine | 连接耗尽 | 进程级 Engine |
| Router 里写 SQL/事务 | 难测试/难复用 | 下沉 Service/Repository |
| 返回 ORM 对象 | 懒加载/泄漏 | Out DTO |
| 用 float 存金额 | 精度事故 | Decimal/Numeric |
| 到处 `except Exception: pass` | 静默失败 | 精确捕获 + 日志 |
| `# type: ignore` 无错误码 | 掩盖新问题 | 带码 + 定期清理 |
| 为微服务而微服务 | 分布式复杂度 | 模块化单体优先 |
| 全异步但库是同步 | 事件循环阻塞 | 统一异步栈或同步端点 |
| 迁移不 review | schema 事故 | 迁移规范 + 演练 |

## 11. 技术决策清单

引入新依赖/新框架前问：

1. 解决什么具体问题？可量化收益是什么？
2. 维护状态、许可证、安全记录如何？
3. 团队能否在两周内独立排障？
4. 失败模式是什么？如何降级？
5. 是否增加第二个“真相源”（缓存/索引/副本）？
6. 迁移/退出成本？
7. 观测、测试、部署是否支持？
8. 三年后还会维护吗？

## 12. 90 天落地路线（建议）

| 周 | 目标 |
|---|---|
| 1–2 | 工具链统一：uv、ruff、mypy、pytest、CI |
| 3–4 | 试点服务上线：FastAPI + SQLAlchemy + 迁移 + 观测 |
| 5–6 | 认证/错误格式/分页/日志规范 |
| 7–8 | 队列 + 定时任务 + 失败重试 |
| 9–10 | 压测、容量、告警、回滚演练 |
| 11–12 | 团队培训、模板工程、ADR、下一批迁移清单 |

## 13. 本章验收

不看资料，画出你所在系统的“请求生命周期”与“数据一致性边界”，并标注：

- 哪一层负责事务？
- 哪些查询会 N+1？
- 哪些外部调用需要超时/重试/幂等？
- 认证与对象级授权在哪？
- 迁移与回滚怎么做？

能清楚回答，语言迁移就只剩工程执行问题。
