## 1. 配置

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    environment: Literal["dev", "test", "prod"] = "dev"
    log_level: str = "INFO"
    db_url: str = "sqlite+pysqlite:///./shop.sqlite3"
    seed_demo_data: bool = True
    max_order_items: int = 20
    cors_origins: list[str] = []
```

原则：

- **12-Factor**：配置来自环境变量，不打进镜像。
- 启动时校验；缺失/非法直接失败，不要带病运行。
- 生产关闭演示数据：`SEED_DEMO_DATA=false`。
- 敏感值用密钥管理，不写 `.env` 进仓库。
- 配置项有默认值时要保证默认值**在生产是安全的**（例如 `DEBUG=false`）。

本项目的 `Settings` 被 `create_app(settings)` 注入，测试可完全隔离；生产通过环境变量。

## 2. 日志

```python
logging.basicConfig(
    level=level.upper(),
    format="%(asctime)s %(levelname)s [%(request_id)s] %(name)s: %(message)s",
)
```

请求 ID 通过 `contextvars` 注入日志：

```python
request_id_var: ContextVar[str] = ContextVar("request_id", default="-")

class RequestIdLogFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True
```

生产建议：

| 项 | 建议 |
|---|---|
| 格式 | JSON（容器/ELK/Loki 友好） |
| 字段 | timestamp, level, logger, request_id, method, path, status, duration, user_id |
| 级别 | INFO 业务事件；WARNING 可恢复异常；ERROR 需告警 |
| 敏感信息 | 不记录密码/token/Authorization/身份证/银行卡 |
| 采样 | 高频访问日志可采样，错误全量 |
| 关联 | trace_id / span_id（OpenTelemetry） |

不要在日志里 `print`；不要用字符串拼接大对象；异常用 `logger.exception` 保留堆栈。

## 3. 健康检查

```python
@app.get("/health", tags=["ops"])
def health(response: Response) -> dict[str, str]:
    try:
        with database.engine.connect() as connection:
            connection.execute(text("SELECT 1"))
    except SQLAlchemyError:
        response.status_code = 503
        return {"status": "DOWN"}
    return {"status": "UP"}
```

区分：

| 检查 | 用途 | 是否查依赖 |
|---|---|---|
| liveness | 进程是否卡死，失败重启 | 否 |
| readiness | 能否接流量，失败摘除 | 是（DB/缓存） |
| startup | 启动是否完成 | 初始化资源 |

本项目的 `/health` 更接近 readiness。生产通常拆成 `/health/live` 与 `/health/ready`，并区分“依赖不可用”与“进程应重启”。

## 4. 容器：多阶段构建

```dockerfile
FROM ghcr.io/astral-sh/uv:python3.14-bookworm-slim AS builder
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
COPY src ./src
COPY alembic.ini ./
COPY migrations ./migrations
RUN uv sync --frozen --no-dev

FROM python:3.14-slim
RUN useradd --system --uid 10001 --create-home app \
    && mkdir -p /data && chown app:app /data
WORKDIR /app
COPY --from=builder --chown=app:app /app /app
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    DB_URL="sqlite+pysqlite:////data/shop.sqlite3"
USER app
EXPOSE 8000
CMD ["uvicorn", "shop.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

要点：

- **构建与运行分离**：运行镜像没有 uv、编译器、测试。
- **先依赖后源码**：利用层缓存。
- **非 root**：`USER app`。
- **可写数据目录**：`/data` 归 app 所有（否则 SQLite 无法创建文件——这是实际踩过的坑）。
- **`PYTHONUNBUFFERED=1`**：日志实时输出。
- 基础镜像固定版本/tag，生产建议再固定 digest。
- `.dockerignore` 排除 `.venv/`、测试、缓存、数据库文件。

构建与运行：

```bash
docker build -t shop-api-python:dev .
docker run --rm -p 8000:8000 shop-api-python:dev
```

> 本仓库已验证：镜像构建成功；容器内执行 `alembic upgrade head` 后，`/health` 返回 `{"status":"UP"}`，商品列表返回演示数据。

## 5. PostgreSQL 与 compose

```yaml
services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: shop
      POSTGRES_USER: shop
      POSTGRES_PASSWORD: shop
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U shop -d shop"]

  api:
    build: .
    environment:
      DB_URL: postgresql+psycopg://shop:shop@postgres:5432/shop
      SEED_DEMO_DATA: "true"
    depends_on:
      postgres:
        condition: service_healthy
    command: ["sh", "-c", "alembic upgrade head && uvicorn shop.main:app --host 0.0.0.0 --port 8000"]
```

生产注意：

- 数据库密码用 secret，不写 compose。
- `depends_on` 只保证启动顺序，不保证应用可用；应用要有重试/就绪探针。
- 迁移与应用同容器启动在小规模可行；大规模建议单独的迁移 Job。
- 数据卷、备份、监控、连接数都要配置。

本地：

```bash
# 只起数据库，应用在宿主机跑（便于热重载）
docker compose up -d postgres
DB_URL='postgresql+psycopg://shop:shop@localhost:5432/shop' \
  uv run alembic upgrade head
DB_URL='postgresql+psycopg://shop:shop@localhost:5432/shop' \
  uv run uvicorn shop.main:app --reload
```

或整栈：

```bash
docker compose up --build
```

## 6. 进程与 worker

```bash
# 单进程开发
uvicorn shop.main:app --reload

# 生产：uvicorn 多进程
uvicorn shop.main:app --host 0.0.0.0 --port 8000 --workers 4

# 或 gunicorn 管进程（需另装：uv add gunicorn uvicorn-worker）
gunicorn shop.main:app -k uvicorn_worker.UvicornWorker -w 4 --timeout 30
```

决策：

| 应用类型 | worker 建议 | 线程/连接 |
|---|---|---|
| 异步 I/O 密集 | 核数~2×核数 | 每 worker 一个事件循环 |
| 同步端点 + 同步 DB | 核数~2×核数 | 线程池 × 连接池 |
| CPU 密集 | 进程数≈核数 | 避免与 Web 混部 |

**连接数守恒**：

```
总连接 ≈ worker 数 × (pool_size + max_overflow) + 迁移/运维连接
```

必须小于数据库 `max_connections`，并留 20% 余量。否则高峰期会雪崩。

优雅退出：

- 接收 SIGTERM 后停止接新请求；
- 等待在途请求完成（graceful timeout）；
- 关闭连接池、队列消费者；
- 超过超时时间强制退出。

本项目的 `lifespan` 在关闭时 `database.dispose()`；容器编排需给足 `terminationGracePeriodSeconds`。

## 7. 迁移发布

推荐顺序：

1. **向后兼容迁移**（加列可空/默认值、建索引用并发）。
2. 部署新代码（新旧代码都能跑）。
3. 数据回填（后台任务/分批）。
4. 收紧约束（非空/唯一/删旧列）。

禁止：

- 应用启动自动 `create_all`；
- 迁移里长时间锁表；
- 先删列再发代码；
- 无备份直接在生产试迁移。

回滚：

- 代码回滚容易，schema 回滚难；优先“向前修复”。
- 破坏性变更分两次发布。
- 备份 + 演练恢复，别只写文档。

## 8. 队列与异步任务

| Laravel | Python |
|---|---|
| Queue + `queue:work` | Celery / RQ / arq |
| Horizon | Flower |
| Scheduler | Celery Beat / APScheduler |
| Failed jobs | 死信队列 + 重试策略 |
| 幂等 | 业务键 + 去重表 |

任务设计：

- **幂等**：至少一次投递意味着可能重复执行。
- **可重试**：区分瞬态错误与业务错误。
- **超时**：每个任务有上限，避免占满 worker。
- **可观测**：任务 ID、耗时、失败原因、重试次数。
- **隔离**：慢任务单独队列，避免拖垮关键任务。

Web 进程里不要起后台线程跑长任务；进程重启就丢。用独立 worker。

## 9. 可观测性

三件套：

| 信号 | 工具 | 关键指标 |
|---|---|---|
| Logs | Loki/ELK/CloudWatch | 错误率、slow requests、request_id 串联 |
| Metrics | Prometheus + Grafana | QPS、P95/P99、5xx、连接池、队列长度 |
| Traces | OpenTelemetry + Jaeger/Tempo | 跨服务调用链、DB 耗时 |

FastAPI 集成 OpenTelemetry 通常用 `opentelemetry-instrumentation-fastapi`；SQLAlchemy 也有 instrumentation。先保证：

- 每个请求有 request_id；
- 慢请求日志（阈值）；
- DB 连接池指标；
- 外部依赖调用耗时；
- 错误聚合（Sentry）。

告警要可行动：5xx 比例、P99、队列积压、连接池耗尽、磁盘/内存。不要为每个异常发告警。

## 10. 性能与容量

| 层 | 手段 |
|---|---|
| 网关 | 超时、限流、压缩、缓存静态资源 |
| 应用 | 连接复用、批量查询、避免 N+1、分页 |
| 数据库 | 索引、查询计划、读写分离、分区 |
| 缓存 | Redis（热点、会话、限流） |
| 序列化 | 避免巨大响应、流式导出 |
| 异步 | 长任务入队，不阻塞请求 |

先测量再优化：用 `EXPLAIN ANALYZE`、py-spy、cProfile、请求耗时分布。不要凭感觉加缓存。

## 11. 部署形态

| 形态 | 适合 | 说明 |
|---|---|---|
| 单容器 + 托管 DB | 小团队/MVP | 简单，注意备份 |
| K8s Deployment + HPA | 中大型 | 就绪探针、优雅退出、迁移 Job |
| Serverless（Lambda/Cloud Run） | 突发流量/低运维 | 冷启动、连接池受限 |
| 虚拟机 + systemd | 传统企业 | 可控，需自己管进程 |

无论哪种，**应用无状态**（会话/文件放外部），才能水平扩展。
