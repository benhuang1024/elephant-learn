# 06 包、模块与项目结构

> **配套代码**
> 语言工程：[lang-basics](../code/lang-basics)
> Web 工程：[shop-api](../code/shop-api)
> Django 工程：[django-shop](../code/django-shop)
> 锁文件：[shop-api/uv.lock](../code/shop-api/uv.lock)

PHP 用 PSR-4 把命名空间映射到目录，Composer 生成 autoload；Python 的 import 是**运行时查找模块**，包结构、安装方式、`sys.path` 共同决定能不能导入。

## 1. PSR-4 vs Python import

| PHP | Python |
|---|---|
| `namespace App\Shop;` | 目录/文件名本身就是命名空间 |
| `use App\Shop\Product;` | `from shop.product import Product` |
| `composer dump-autoload` | 安装包或把根目录放进 `sys.path` |
| 类名 = 文件名 | 模块名 = 文件名（`product.py`） |
| 一个文件一个类（惯例） | 一个模块可以多个类/函数 |
| `autoload-dev` | `dependency-groups.dev` + `pythonpath` |

Python 没有“一个类一个文件”的硬约定；语言教程里的“每主题一个模块”是因为便于教学，不是因为 import 要求。

## 2. 包、模块、`__init__.py`

```
shop/
├── __init__.py
├── main.py
├── db.py
├── product/
│   ├── __init__.py
│   ├── models.py
│   ├── schemas.py
│   ├── repository.py
│   ├── service.py
│   └── router.py
```

- 目录 + `__init__.py` = 普通包。
- 模块 = `.py` 文件。
- `shop.product.models` 是模块全名，`shop.product` 是包。
- `__init__.py` 可以为空，也可以暴露公共 API。

`__init__.py` 的常见用途：

```python
# shop/product/__init__.py
from shop.product.models import Product
from shop.product.service import ProductService

__all__ = ["Product", "ProductService"]
```

**慎用**：在 `__init__.py` 里导入太多会让 import 变慢，还可能造成循环导入。对外 API 明确时再 re-export。

### 命名空间包

没有 `__init__.py` 的目录也能成为 namespace package，适合大型组织拆分包。业务项目里不建议混用，容易让“为什么能导入”变得不可预测。

## 3. 绝对导入 vs 相对导入

```python
from shop.product.models import Product       # 绝对导入，推荐
from .models import Product                   # 相对导入，包内部可用
from ..db import Session                      # 上一级
```

规则：

- **跨包/对外**：绝对导入。
- **同一包内部**：相对导入可以，但团队要统一。
- 脚本不要用相对导入（它没有包上下文）。
- 直接运行 `python src/shop/main.py` 会把 `src/shop` 放进 `sys.path`，导致 `import shop` 失败；用 `python -m shop.main` 或 `uv run`。

## 4. src 布局

本仓库两个库工程都用：

```
shop-api/
├── pyproject.toml
├── src/
│   └── shop/
│       └── ...
├── tests/
├── migrations/
├── alembic.ini
├── Dockerfile
└── uv.lock
```

好处：

1. **强迫安装/显式路径**：测试不会“碰巧”导入仓库根目录的代码。
2. **打包干净**：构建工具只收 `src/shop`，不会把 `tests/`、`docs/` 打进去。
3. **与可编辑安装兼容**：`uv sync` 把项目装进 `.venv`，import 路径稳定。

Django 工程是**应用而不是库**，没有 `src/`，`manage.py` 在根目录，`config/` 与 `catalog/` 是顶层包。这是 Django 的惯例。

## 5. 依赖管理

### 版本约束

```toml
dependencies = [
    "fastapi>=0.162,<1.0",
    "sqlalchemy>=2.1,<3.0",
]
```

- 库：范围要宽，避免与下游冲突。
- 应用：可以更紧，甚至精确版本。
- `uv.lock` 锁定完整解析结果，**应用必须提交**；库通常不提交 lock。

### 依赖组与 extras

```toml
[dependency-groups]
dev = ["pytest", "mypy", "ruff"]

[project.optional-dependencies]
postgres = ["psycopg[binary]"]
```

| 概念 | Composer | Python |
|---|---|---|
| 运行时 | `require` | `project.dependencies` |
| 开发 | `require-dev` | `dependency-groups.dev` |
| 可选功能 | `suggest` / 手动 | `optional-dependencies` + extras |
| 锁文件 | `composer.lock` | `uv.lock` |

安装可选组：

```bash
uv sync --extra postgres
```

### 依赖冲突

uv 会在解析阶段报冲突。常见原因：

- 两个包要求同一库的不兼容大版本。
- 直接依赖与间接依赖版本范围无交集。
- Python 版本不满足 `requires-python`。

排查：

```bash
uv tree
uv lock --verbose
uv add "package==1.2.3"     # 临时试探
```

不要用 `--no-deps` 掩盖冲突；那只是把问题推迟到运行时。

## 6. 打包 wheel 与发布

```bash
uv build            # 生成 dist/*.whl 与 *.tar.gz
uv publish          # 发布到 PyPI（需凭证）
```

`pyproject.toml`：

```toml
[build-system]
requires = ["uv_build>=0.9"]
build-backend = "uv_build"

[tool.uv.build-backend]
module-name = "shop"
module-root = "src"
```

对照 PHP：

| PHP | Python |
|---|---|
| Composer 包 | wheel / sdist |
| `autoload` | 包内 `__init__.py` |
| 全局命令 | `[project.scripts]` entry point |
| `vendor/bin/phpunit` | `.venv/bin/pytest` |

entry point：

```toml
[project.scripts]
shop = "shop.cli:main"
```

安装后即可 `uv run shop ...`。

## 7. 脚本、模块与入口

```bash
uv run python -m shop.main        # 模块执行，包上下文正确
uv run scripts/hello.py           # PEP 723 单文件
uv run uvicorn shop.main:app      # 通过 ASGI 工厂/实例
```

`if __name__ == "__main__":` 的作用：

```python
def main() -> None:
    ...

if __name__ == "__main__":
    main()
```

- 被 import 时不执行。
- 直接运行/`python -m` 时执行。
- 多进程脚本必须把入口放这里，否则 spawn 子进程会重复执行。

## 8. 循环导入

```python
# a.py
from b import B

# b.py
from a import A
```

运行时 ImportError 或半初始化模块。解决顺序：

1. **重构**：把共享类型抽到第三方模块（`types.py` / `schemas.py`）。
2. **延迟导入**：在函数内部 import（能跑但掩盖设计问题）。
3. **TYPE_CHECKING**：只在类型检查时导入。

```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from shop.order.models import Order

def f(order: "Order") -> None: ...
```

3.11+ 可以用 `from __future__ import annotations` 让注解延迟求值，减少一部分问题。

## 9. 三个工程的布局对比

| 工程 | 类型 | 布局 | 入口 |
|---|---|---|---|
| `lang-basics` | 库 + 可执行笔记 | `src/basics` | pytest / PEP 723 脚本 |
| `shop-api` | ASGI 应用 | `src/shop` | `uvicorn shop.main:app` |
| `django-shop` | Django 应用 | 根目录 `config/` + `catalog/` | `manage.py` |

不要机械统一：**库用 src 布局，Django 用框架惯例**。团队约定写在 README 与模板工程里，比口头约定可靠。

## 10. 依赖升级策略

1. Renovate/Dependabot 每周开 PR。
2. CI 跑 `uv sync --frozen` + 全量测试 + mypy。
3. 小版本自动合并，大版本人工 review。
4. 锁定关键框架的上限（如 `sqlalchemy<3.0`），避免意外破坏。
5. 每季度做一次 `uv lock --upgrade` 的“依赖日”，集中处理。
