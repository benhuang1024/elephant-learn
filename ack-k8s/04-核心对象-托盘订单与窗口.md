# 04 核心对象：托盘、订单与窗口

## 1. 一句话说清

**在港口里下订单，要用几种标准的“单子”：托盘单（Pod）、长期订单（Deployment）、取货窗口（Service）、大门导航牌（Ingress）、说明书（ConfigMap）、上锁的信封（Secret）、片区（Namespace）和彩色贴纸（Label）。**

## 2. 港口故事

> 来港口办事的人很多，所以调度中心规定：所有要求都要用**标准单子**来写。今天我们认识八种单子。
>
> **托盘（Pod）**：港口里最小的搬运单位不是集装箱，而是**托盘**。一个托盘上通常只放一个集装箱；但有些箱子必须形影不离，比如“冰淇淋箱”和“给它供电的冷冻机箱”，它们就放在同一个托盘上，一起搬、一起放。
>
> **长期订单（Deployment）**：你不会每天跑来说“放一个托盘”“再放一个托盘”。你会下一张长期订单：“**永远保持 3 个冰淇淋托盘**。”坏了一个，巡查员就自动补一个。想换新口味的冰淇淋？改一下订单就行，港口会一个一个地换，不会一下子全停掉。
>
> **取货窗口（Service）**：托盘会被换来换去，今天在 2 号场地，明天可能在 5 号场地。顾客要去哪里取冰淇淋呢？港口设了一个**固定的取货窗口**，窗口号永远不变。顾客只要去窗口，窗口会把他带到任意一个还在工作的冰淇淋托盘那里。
>
> **大门导航牌（Ingress）**：港口外面的人进来，先经过港口**大门**。大门口立着导航牌：“买冰淇淋走 1 号窗口，买奶茶走 2 号窗口。”
>
> **说明书（ConfigMap）和上锁的信封（Secret）**：有些信息不写死在箱子里，而是单独写在说明书上，比如“今天的冰淇淋卖 5 元”。说明书换了，箱子不用重新做。如果是密码这样的秘密，就放进**上了锁的信封**里，只有被允许的人才能打开。
>
> **片区（Namespace）**：港口很大，所以划分成几个片区：“冰淇淋公司片区”“奶茶公司片区”。各片区的东西可以重名，互不打扰。
>
> **彩色贴纸（Label）**：每个托盘上都可以贴彩色贴纸，比如“红色 = 冰淇淋”“蓝色 = 奶茶”。取货窗口就是靠看贴纸找托盘的：“我负责所有贴红贴纸的托盘。”

## 3. 低年级简化版

- 箱子放在托盘上搬，托盘是最小的单位。
- 我们可以下一张订单：“永远要 3 个托盘”，少了会自动补。
- 托盘会换位置，所以有一个固定的取货窗口，顾客去窗口就行。

## 4. 大人要懂的真相

### 4.1 对照表

| 对象 | 作用 | 港口类比 | 常见误区 |
|---|---|---|---|
| Pod | 最小调度单位，包含 1 个或多个共享网络和存储卷的容器 | 托盘 | 直接创建裸 Pod：挂了没人补 |
| ReplicaSet | 保证指定数量的 Pod 副本 | 订单里的“保持 N 个”条款 | 一般不直接用，由 Deployment 管 |
| Deployment | 管理 ReplicaSet，提供滚动更新和回滚 | 长期订单 | 有状态的数据库不要用它（用 StatefulSet） |
| StatefulSet | 有稳定名字和独立存储的副本（数据库等） | 每个托盘有固定编号、固定仓库的订单 | — |
| DaemonSet | 每个节点运行一个 Pod（日志采集、监控代理） | 每块场地都派一个保安 | — |
| Job / CronJob | 运行到完成的一次性任务 / 定时任务 | 一次性搬运单 / 每天定点的搬运单 | — |
| Service | 给一组 Pod 一个稳定的虚拟 IP 和 DNS 名 | 固定取货窗口 | 用 Pod IP 直连：Pod 一换 IP 就变 |
| Ingress | 按域名、路径把外部 HTTP(S) 流量转给 Service | 港口大门导航牌 | 忘了装 Ingress Controller，Ingress 不生效 |
| ConfigMap | 非敏感配置 | 说明书 | 把密码放 ConfigMap |
| Secret | 敏感配置 | 上锁的信封 | 以为 Secret 是加密的（默认只是 Base64 编码） |
| Namespace | 资源的逻辑隔离与配额边界 | 片区 | 以为 Namespace 默认就有网络隔离（并没有） |
| Label / Selector | 键值标签 / 按标签选择 | 彩色贴纸 / 按贴纸找 | Service 的 selector 和 Pod 标签对不上，导致没有后端 |

### 4.2 一个 Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello
  labels:
    app: hello            # 贴纸
spec:
  containers:
    - name: web
      image: nginx:1.30-alpine
      ports:
        - containerPort: 80
```

同一个 Pod 里的多个容器共享网络（可以用 `localhost` 互相访问）和存储卷。14 章的 Magento 就是把 nginx 和 php-fpm 放在同一个 Pod 里，nginx 通过 `127.0.0.1:9000` 访问 php-fpm。

### 4.3 Deployment + Service

完整文件见 [manifests/01-hello-nginx/](manifests/01-hello-nginx/)。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-nginx
spec:
  replicas: 3                    # 永远保持 3 个托盘
  selector:
    matchLabels:
      app: hello-nginx           # 这张订单管哪些托盘（按贴纸）
  template:                      # 托盘长什么样
    metadata:
      labels:
        app: hello-nginx         # 托盘上的贴纸，必须和上面的 selector 对得上
    spec:
      containers:
        - name: nginx
          image: nginx:1.30-alpine
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: hello-nginx
spec:
  selector:
    app: hello-nginx             # 窗口负责所有贴这张贴纸的托盘
  ports:
    - port: 80                   # 窗口号
      targetPort: 80             # 托盘里集装箱的门
```

### 4.4 Service 的四种类型

| type | 谁能访问 | 港口类比 | ACK 上的效果 |
|---|---|---|---|
| ClusterIP（默认） | 只有集群内部 | 港口内部的取货窗口 | 分配一个集群内虚拟 IP |
| NodePort | 能访问到节点的地方，通过“节点 IP:端口” | 在每块场地的围墙上开一个小门 | 一般只用于调试 |
| LoadBalancer | 公网或 VPC 内 | 港口外面修一条专用道路直通窗口 | 自动创建一个阿里云负载均衡（CLB 或 NLB），**会产生费用** |
| ExternalName | 集群内部 | 窗口贴一张纸条：“请去隔壁某某港口取货” | 返回一个 CNAME |

集群内部访问 Service 用 DNS 名：`<service>.<namespace>.svc.cluster.local`，同一个 Namespace 里直接写 `<service>` 就行。

### 4.5 ConfigMap 和 Secret

```bash
kubectl create configmap app-config --from-literal=PRICE=5
kubectl create secret generic db-secret --from-literal=DB_PASSWORD='S3cr3t!'
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d   # 证明它只是 Base64
```

在 Pod 里使用：

```yaml
env:
  - name: PRICE
    valueFrom:
      configMapKeyRef: { name: app-config, key: PRICE }
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef: { name: db-secret, key: DB_PASSWORD }
```

Secret 的安全加固（etcd 加密、RBAC 限制、外部 KMS）见 [security/03-infra-cloud/kubernetes-security.md](../security/03-infra-cloud/kubernetes-security.md)。ACK Pro 版支持用阿里云 KMS 对 Secret 做落盘加密。

### 4.6 Label 的妙用

```bash
kubectl get pods -l app=hello-nginx                   # 按贴纸找托盘
kubectl label pod <名字> app=quarantine --overwrite    # 把一个托盘的贴纸撕掉换成别的
```

把一个出问题的 Pod 的标签改掉，它就脱离了 Service 和 ReplicaSet：ReplicaSet 会补一个新的，而旧的 Pod 留下来供你排查。这是线上排障的常用技巧。

## 5. 类比在哪里不成立

- 真实的托盘上可以随时加箱子；**Pod 创建后，里面的容器列表基本不能改**，要改就换一个新 Pod。
- 真实的取货窗口有一个人坐着；Service 不是一个进程，它只是一条转发规则（由 kube-proxy 或网络插件在每个节点上实现）。
- “上了锁的信封”听起来很安全，但 Secret 默认**只是编码，不是加密**。有权限读 Secret 的人都能看到明文。
- 片区之间默认**没有围墙**：不同 Namespace 的 Pod 默认可以互相访问，要用 NetworkPolicy 才能隔开。

## 6. 课堂小活动：贴纸找朋友（10 分钟）

1. 给 8 个同学发托盘（硬纸板），每人背后贴一张彩色贴纸：4 红、2 蓝、2 绿。
2. 请一个同学当“红色取货窗口”，他只能说一句话：“贴红贴纸的请举手！”然后把“顾客”（另一位同学）随机带到其中一个人面前。
3. 老师让一个红贴纸的同学“坐下”（坏掉了），巡查员要马上找一个新同学，贴上红贴纸站起来。
4. 提问：顾客有没有发现变化？（没有，他一直去的是同一个窗口）

## 7. 孩子可能会问

- **问：为什么不直接放集装箱，要多一个托盘？**
  答：因为有些箱子必须在一起，比如冰淇淋箱和冷冻机箱。放在同一个托盘上，就保证它们一定在同一块场地，挨得很近，说话很快。
- **问：取货窗口怎么知道哪个托盘好、哪个托盘坏？**
  答：每个托盘会定时报告“我准备好了”。没准备好的托盘，窗口就不会把顾客带过去（这个叫“就绪探针”，05 章会讲）。
- **问：订单能改吗？**
  答：能。改成“保持 5 个”，港口马上加 2 个；改成新口味，港口会一个一个地换。

## 8. 自测题

1. Deployment、ReplicaSet、Pod 三者是什么关系？
2. Service 是怎么找到它的后端 Pod 的？selector 写错了会出现什么现象？
3. 为什么数据库通常用 StatefulSet 而不是 Deployment？
4. Secret 和 ConfigMap 的区别是什么？Secret 默认安全吗？
5. ClusterIP、NodePort、LoadBalancer 分别适合什么场景？

<details>
<summary>参考答案</summary>

1. Deployment 管理 ReplicaSet（每次更新会生成一个新的 ReplicaSet），ReplicaSet 管理 Pod 的副本数量。
2. 通过标签选择器匹配 Pod 标签，再生成 EndpointSlice。selector 写错时 Service 没有后端，`kubectl get endpointslices` 看不到地址，访问会超时或被拒绝。
3. StatefulSet 给每个副本稳定的名字（mysql-0、mysql-1）和各自独立的持久卷，重建后还挂回原来的卷；Deployment 的 Pod 名字随机，没法保证这一点。
4. ConfigMap 放普通配置，Secret 放敏感数据。Secret 默认只是 Base64 编码，需要开启 etcd 加密、严格限制 RBAC，才算基本安全。
5. ClusterIP 用于集群内部调用；NodePort 用于调试或者自带外部负载均衡的场景；LoadBalancer 用于对外暴露 TCP/UDP 服务，在 ACK 上会自动创建阿里云负载均衡。HTTP 服务通常用 Ingress 统一入口。
</details>
