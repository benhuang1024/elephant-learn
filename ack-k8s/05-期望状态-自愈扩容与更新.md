# 05 期望状态：自愈、扩容与更新

## 1. 一句话说清

**你只要告诉港口“我想要什么样子”，港口就会一直努力保持这个样子：坏了自己换，忙了自己加，换新的时候一个一个换，港口不停工。**

## 2. 港口故事

> **空调的秘密。** 你家的空调设成 26 度，你不用告诉它“先开压缩机，再开风扇，5 分钟后关掉”。你只说了“我想要 26 度”。空调会自己一直测温度：热了就吹冷风，到了 26 度就歇一歇。这就是“说出你想要的样子”。
>
> 港口也是这样工作的。你下的订单写着“保持 3 个冰淇淋托盘”，巡查员就像空调的温度计，一直在数：
>
> - **数到 2 个**：有一个坏了！马上补一个。这叫**自愈**。
> - **天太热，排队买冰淇淋的人太多**：“忙碌检测员”发现每个托盘都忙不过来，就把订单改成“保持 6 个”。天凉了再改回 3 个。这叫**自动扩缩容**。
> - **要换新口味**：港口不会一下子把 3 个旧托盘全收走（那样顾客就买不到了），而是先放 1 个新口味的托盘，确认它能正常卖了，再收走 1 个旧的，就这样一个一个换。这叫**滚动更新**。如果发现新口味有问题，马上换回旧口味，这叫**回滚**。
>
> 港口怎么知道一个托盘是“好的”？每个托盘都要定时回答两个问题：
> - “**你还活着吗？**”答不上来，就说明它卡住了，要重启。
> - “**你准备好接待顾客了吗？**”还没准备好（比如冰淇淋机还在预热），取货窗口就先不把顾客带过来。

## 3. 低年级简化版

- 就像空调设成 26 度，港口会一直保持你想要的样子。
- 箱子坏了，港口自己换一个新的。
- 人多了，港口自己多放几个箱子；人少了，再收回来。

## 4. 大人要懂的真相

### 4.1 声明式 vs 命令式

| | 命令式 | 声明式 |
|---|---|---|
| 你说的是 | 步骤：“启动一个 nginx” | 结果：“要有 3 个 nginx” |
| 执行几次 | 执行一次就结束 | 控制器持续保证 |
| 重复执行 | 可能重复创建 | 幂等，结果一样 |
| K8s 中 | `kubectl run`、`kubectl scale` | `kubectl apply -f`（推荐，配合 Git 管理 YAML） |

### 4.2 三种探针

```yaml
startupProbe:          # 启动探针：慢启动的应用（Java、Magento）先过这一关，过之前不做存活检查
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30
  periodSeconds: 5     # 最多等 150 秒
livenessProbe:         # 存活探针：失败就重启容器
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
readinessProbe:        # 就绪探针：失败就从 Service 后端摘除，不重启
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
```

**最容易犯的错**：把“检查数据库能不能连上”放进 liveness。数据库一抖动，所有 Pod 会一起被重启，故障反而扩大。依赖检查应该放进 readiness，liveness 只检查进程本身有没有卡死。

### 4.3 资源请求与限制

```yaml
resources:
  requests: { cpu: 250m, memory: 512Mi }   # 调度依据：场地上至少要空出这么多
  limits:   { memory: 1Gi }                # 上限：内存超了会被 OOMKill
```

- `requests` 决定 Pod 能被调度到哪个节点，也是 HPA 计算 CPU 利用率的分母。
- CPU 超过 limit 会被限流（变慢），内存超过 limit 会被杀掉（OOMKilled）。
- Java 应用要让 JVM 感知容器内存：`-XX:MaxRAMPercentage=75`（shop-api 的 Dockerfile 里已经设置了）。

### 4.4 滚动更新与回滚

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 更新期间最多多出 1 个
      maxUnavailable: 0    # 更新期间不允许少于期望副本数
```

```bash
kubectl set image deployment/hello-nginx nginx=nginx:1.30.6-alpine   # 换新口味
kubectl rollout status deployment/hello-nginx                         # 看更新进度
kubectl rollout history deployment/hello-nginx                        # 历史版本
kubectl rollout undo deployment/hello-nginx                           # 回滚到上一个版本
```

滚动更新能不能真正做到不中断，取决于三件事：**readiness 探针准确**、**应用支持优雅停机**（Spring Boot 的 `server.shutdown: graceful`）、**有一个短暂的 preStop 等待**（让负载均衡先把流量摘掉）。

### 4.5 HPA：水平自动扩缩容

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello-nginx
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: hello-nginx }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

- HPA 依赖 metrics-server（ACK 集群默认就装好了）。
- **HPA 加的是 Pod**（托盘）。如果场地满了，新 Pod 会一直 Pending，这时就需要**节点自动伸缩**来加场地（见 09 章）。

### 4.6 PodDisruptionBudget
节点升级、缩容时会“驱逐”Pod。PDB 规定“同一时间最多被赶走几个”，防止一次性全被赶走：

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: hello-nginx }
spec:
  minAvailable: 1
  selector: { matchLabels: { app: hello-nginx } }
```

## 5. 类比在哪里不成立

- 空调只控制一个量（温度）；K8s 有很多个控制器，各自管自己的对象，它们是**接力**合作的（Deployment → ReplicaSet → Pod）。
- 真实港口“修好”一个箱子；K8s 的自愈是**重建**：旧容器扔掉，用镜像新建一个。容器里没有持久化的数据会丢。
- HPA 扩容不是瞬间的：要等指标采集周期，加上新 Pod 启动时间。Java 应用可能要几十秒。

## 6. 课堂小活动：空调游戏（5 分钟）

1. 老师说：“我们的港口要保持 **4 个**同学站着。”
2. 请一位“巡查员”，他的任务是不停地数，少了就拍一位坐着的同学站起来，多了就请一位坐下。
3. 老师随机让站着的同学坐下（坏了），或者让坐着的同学站起来（多了）。

## 7. 孩子可能会问

- **问：为什么不一次把旧箱子全换掉？那样不是更快吗？**
  答：那样换的时候就没有箱子卖冰淇淋了，顾客会买不到。一个一个换，虽然慢一点，但一直有人在卖。
- **问：坏掉的箱子去哪了？**
  答：直接扔掉了。电脑里的箱子扔掉不心疼，因为有设计图，随时可以装一个新的。
- **问：港口能无限加箱子吗？**
  答：不能，场地的空位是有限的。场地满了，要再租新的场地。

## 8. 自测题

1. liveness 和 readiness 失败的后果分别是什么？为什么数据库连接检查不能放在 liveness 里？
2. `requests` 和 `limits` 分别影响什么？内存超限和 CPU 超限的后果有什么不同？
3. 要做到滚动更新不中断，需要满足哪三个条件？
4. HPA 把副本数从 3 扩到 10，但新 Pod 一直 Pending，可能是什么原因？怎么解决？

<details>
<summary>参考答案</summary>

1. liveness 失败会重启容器；readiness 失败会把 Pod 从 Service 后端摘掉，但不重启。数据库抖动时，如果检查放在 liveness 里，所有 Pod 会被同时重启，故障被放大。
2. requests 影响调度，也是 HPA 计算利用率的基准；limits 是上限。内存超限会被 OOMKill，CPU 超限只会被限流。
3. 准确的 readiness 探针；应用支持优雅停机；preStop 留出摘流量的时间（再配合 `maxUnavailable: 0`）。
4. 节点资源不够（requests 太大、节点满了）。可以开启节点自动伸缩或节点即时弹性，用虚拟节点（ECI/ACS）弹性扩容，或者调整 requests。用 `kubectl describe pod` 看 Events 确认原因。
</details>
