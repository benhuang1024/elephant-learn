# 03 Kubernetes：港口调度中心

## 1. 一句话说清

**Kubernetes 是一个聪明的港口调度中心：你只要告诉它“我要什么”，它就负责把集装箱放到合适的场地上，坏了换新的，忙了多放几个。**

## 2. 港口故事

> 集装箱发明以后，港口里的箱子越来越多，几千个、几万个。问题又来了：这么多箱子，放在哪块场地？哪块场地满了？哪个箱子坏了？
>
> 于是港口盖了一座**调度中心**。调度中心里有四个重要的角色：
>
> 1. **服务窗口**：所有人都只能到这个窗口来办事。你想放箱子、想查箱子，都要来窗口填单子。窗口会先检查：你是谁？你有没有权限？单子填得对不对？
> 2. **总账本**：窗口收下的每一张单子，都要记进总账本。港口里应该有什么、现在有什么，全都写在账本上。账本特别重要，丢了整个港口就乱了，所以它会抄好几份。
> 3. **调度员**：他一直盯着账本，看到“有箱子还没决定放哪”，就去看看每块场地还剩多少空位，然后决定：“这个箱子放 2 号场地！”再把决定写回账本。
> 4. **巡查员**：他一刻不停地巡逻，拿着账本核对。账本上写“要有 3 个红箱子”，他数了数只有 2 个，马上去补一张单子：“再来 1 个红箱子！”
>
> 港口里还有很多块**场地**，每块场地有一个**场地管理员**。管理员会定时去看账本：“有没有分配给我这块场地的箱子？”有的话，就叫吊车把箱子装好、打开、跑起来，然后一直照看它，向调度中心汇报：“我这里的箱子都好好的。”
>
> 这一整个港口，就叫一个**集群**。这个调度中心系统，名字叫 **Kubernetes**，在希腊语里是“舵手”的意思。因为单词太长，K 和 s 中间有 8 个字母，大家就简写成 **K8s**。

## 3. 低年级简化版

- 箱子太多了，需要一个调度中心来管。
- 调度中心里有一本大账本，记着“应该有什么”。
- 有一个巡查员一直在数箱子，少了就补，多了就收。

## 4. 大人要懂的真相

### 4.1 组件与类比

```
                 ┌──────────────── 控制面 Control Plane ────────────────┐
 kubectl ──────► │ kube-apiserver ◄──► etcd                             │
 (你)            │      ▲   ▲                                           │
                 │      │   └── kube-scheduler（决定 Pod 去哪个节点）       │
                 │      └────── kube-controller-manager（各种控制器）      │
                 │      └────── cloud-controller-manager（对接云：建 SLB 等）│
                 └──────────────────────────────────────────────────────┘
                         ▲ watch / 上报状态
        ┌────────────────┴───────────┐        ┌────────────────────────────┐
        │ Node 1                     │        │ Node 2                     │
        │ kubelet、kube-proxy         │        │ kubelet、kube-proxy         │
        │ containerd（容器运行时）      │        │ containerd                 │
        │ [Pod] [Pod]                │        │ [Pod]                      │
        └────────────────────────────┘        └────────────────────────────┘
```

| 组件 | 职责 | 港口类比 |
|---|---|---|
| kube-apiserver | 集群唯一入口，负责认证、鉴权、准入校验，读写 etcd | 服务窗口 |
| etcd | 分布式键值存储，保存集群全部状态 | 总账本（抄好几份） |
| kube-scheduler | 给还没有节点的 Pod 选节点 | 调度员 |
| kube-controller-manager | 运行各种控制器，让实际状态向期望状态靠拢 | 巡查员（其实是一群，各管一种东西） |
| cloud-controller-manager | 和云厂商对接，比如为 LoadBalancer 类型的 Service 创建负载均衡 | 港口和城市交通部门的联络员 |
| kubelet | 每个节点上的代理，负责拉起和照看本节点的 Pod | 场地管理员 |
| 容器运行时（containerd） | 真正拉镜像、启动容器 | 吊车 |
| kube-proxy | 维护节点上的 Service 转发规则（iptables/IPVS） | 场地里的指路牌 |

### 4.2 下一个订单之后发生了什么（一定要能默写）

以 `kubectl apply -f nginx-deployment.yaml`（要 3 个 nginx 副本）为例：

1. **kubectl → apiserver**：把 YAML 发到服务窗口。apiserver 认证（你是谁）、鉴权（RBAC：你能不能做）、准入（单子格式和策略对不对）。
2. **apiserver → etcd**：把 Deployment 对象写进账本。
3. **Deployment 控制器**发现新的 Deployment，创建一个 ReplicaSet（“保持 3 个”）。
4. **ReplicaSet 控制器**发现应该有 3 个 Pod、实际有 0 个，于是创建 3 个 Pod 对象（这时还没有节点）。
5. **scheduler** 发现 3 个 Pod 还没有分配节点，按资源、亲和性、污点等规则打分，把 `nodeName` 写回去。
6. **kubelet** 发现有分配给自己的 Pod，叫 containerd 拉镜像、启动容器，再把状态（Running/Ready）上报给 apiserver。
7. 之后某个 Pod 挂了：kubelet 上报 → ReplicaSet 控制器发现只有 2 个 → 再建 1 个 → scheduler 选节点 → kubelet 拉起。**这就是自愈。**

要点：**所有组件只和 apiserver 说话，彼此之间不直接通信**；它们都是通过 watch 机制“盯着账本”干活的。

### 4.3 声明式：你写的是“期望”，不是“步骤”
你提交的 YAML 描述的是**期望状态**（我要 3 个 nginx），而不是**操作步骤**（去 A 节点启动一个 nginx）。控制器会一直循环做同一件事：

```
while true:
    期望 = 读账本()
    实际 = 观察世界()
    if 期望 != 实际:
        采取行动让实际靠近期望()
```

这个循环叫**调谐循环（reconcile loop）**，是 Kubernetes 最核心的思想。

### 4.4 第一次用 kubectl

```bash
kubectl get nodes                 # 有哪些场地
kubectl get pods -A               # 所有片区里的托盘
kubectl describe pod <名字>        # 某个托盘的详细情况和最近事件
kubectl get events --sort-by=.lastTimestamp   # 港口最近发生了什么
```

## 5. 类比在哪里不成立

- 真实的港口调度员可能出错、可能偷懒；K8s 的调度器按规则**确定性地**打分，规则可以配置。
- 真实的巡查员是人在走路巡逻；控制器是通过 apiserver 的 **watch** 机制“订阅”变化，账本一变它马上就知道，不是一圈圈地走。
- 真实港口只有一个调度中心；K8s 的控制面通常有**多个副本**（ACK 托管版会跨可用区部署），坏一个不影响。

## 6. 课堂小活动：港口调度中心（10 分钟）

角色：1 个“服务窗口”、1 个“账本员”（拿一个本子）、1 个“调度员”、1 个“巡查员”、3 个“场地管理员”（各站在一块地垫上）。

1. 老师（下订单的人）把一张纸条交给“服务窗口”：“我要 3 个红色纸杯。”
2. 服务窗口检查后交给账本员，账本员在本子上写：“红杯：要 3 个，现有 0 个。”
3. 调度员看账本，决定每个杯子放哪块地垫，写到账本上。
4. 场地管理员看账本，发现有分配给自己的杯子，就去拿一个红纸杯放在自己的地垫上，并报告“好了”。
5. 老师偷偷拿走一个杯子。巡查员核对账本，发现“要 3 个，现有 2 个”，喊“补一个！”，流程再走一遍。

活动后提问：**谁直接和谁说话？**（所有人都只和服务窗口、账本打交道）

## 7. 孩子可能会问

- **问：调度中心自己坏了怎么办？**
  答：调度中心有好几个“分身”，总账本也抄了好几份。坏一个，其他的继续工作。用 ACK 的话，这些分身由阿里云来照看。
- **问：为什么不直接把箱子放到场地上，要绕一圈账本？**
  答：因为港口太大，人太多。如果每个人都随便放箱子，就会乱套。所有事情都先记到账本上，大家看同一本账本，就不会冲突。
- **问：K8s 是谁发明的？**
  答：最早是谷歌的工程师参考他们内部的系统做的，2014 年公开给全世界免费使用，现在由一个叫 CNCF 的组织维护。

## 8. 自测题

1. 为什么说 apiserver 是集群的“唯一入口”？这样设计有什么好处？
2. 写出 `kubectl apply` 一个 Deployment 之后，从 YAML 到容器跑起来的 6 个步骤。
3. 什么是调谐循环？
4. etcd 坏了会怎样？

<details>
<summary>参考答案</summary>

1. 所有读写都经过 apiserver，认证、鉴权、准入、审计都集中在一个地方做，其他组件也不用彼此认识。
2. 见 4.2 节：kubectl→apiserver 校验 → 写 etcd → Deployment 控制器建 ReplicaSet → ReplicaSet 控制器建 Pod → scheduler 绑定节点 → kubelet 拉起容器并上报。
3. 控制器不断比较期望状态和实际状态，发现不一致就采取行动，让实际状态向期望状态靠拢。
4. 集群无法读写任何状态：不能创建、修改、调度新的东西；已经在运行的容器通常还能继续跑，但没人能管它们了。所以 etcd 必须多副本并定期备份。
</details>
